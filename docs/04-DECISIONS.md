# Architecture Decision Log

Every rule in `AGENTS.md` traces back to an entry here. To change a rule, add a new ADR that supersedes the old one, never edit history silently.

Status: **Accepted** = user decided. **Accepted (proposed)** = Claude proposed an industry default on 2026-10-08, the user can veto it. **Open** = waiting for the user.

| ID | Decision | Status |
|---|---|---|
| ADR-001 | Fresh start. Old banijjik code moves to branch `archive/v0`. Good parts are re-imported deliberately, never bulk-copied. | Accepted |
| ADR-002 | banijjik is the clean successor of manoxen (`E:\WEB-DEVELOPMENT\PROJECTS\business-platform\manoxen`, live at manoxen.com). Tested business logic and tests are ported module-by-module. The manoxen frontend shell, 3 scope route groups, scope-sync code, watchdogs/guards and double `auth()`/`queryContext()` mounts are never ported. | Accepted |
| ADR-003 | Multi-industry from day one. Common entities and fields are code-defined and shared by all industries. Industry-specific modules, entities, fields, forms and website components are enabled and configured from the Platform Panel without a code deploy. First go-to-market is F-commerce/Retail. | Accepted |
| ADR-004 | No "scope" concept. Data hierarchy is `Organization → Location` (2 levels). A default Location is auto-created and hidden while an org has only one. In the UI a location is a page filter (`?location=`) or a form field, never a global header switcher. One owner with several businesses = several Organizations, switched from the account menu (a full reload is fine). | Accepted |
| ADR-005 | Org-level definition + location-level override, for catalog (`ProductLocation`), stock, settings and staff assignments (`[{ locationId \| ALL, roleId }]`). | Accepted |
| ADR-006 | MongoDB (Mongoose) on a replica set, so multi-document transactions are available in every environment including local. | Accepted |
| ADR-007 | Tools: Claude Code + Cursor. `AGENTS.md` is the single rule file. `CLAUDE.md` and `.cursor/rules/` only point to it. | Accepted |
| ADR-008 | Stack: TypeScript strict, npm workspaces + Turborepo, Express 5 API, Next.js App Router frontends, Zod, Redis + BullMQ, Vitest. | Accepted (proposed) |
| ADR-009 | Apps: `apps/api`, `apps/admin` (tenant dashboard + POS as a PWA route group), `apps/platform` (platform panel), `apps/storefront` (tenant website, resolved by domain/slug). No mobile app until Phase 8. | Accepted (proposed) |
| ADR-010 | Auth via httpOnly secure cookies (access + refresh). Server-rendered app shell. `ssr:false` on the app shell is forbidden. This removes manoxen's removeChild/watchdog problem class. | Accepted (proposed) |
| ADR-011 | Domain code MAY import pure constants/types from `@banijjik/contracts`. It may not import any runtime library, infrastructure or application code. This drops the old "twin enum" rule, which added code without adding safety. | Accepted (proposed) |
| ADR-012 | Request validation runs once, in a route-level `validate(schema)` middleware, using schemas from `@banijjik/validation`. | Accepted (proposed) |
| ADR-013 | Money is stored as integer minor units (poisha) plus a currency code. Floating-point arithmetic on money is forbidden. | Accepted (proposed) |
| ADR-014 | Stock is an append-only `StockMovement` ledger. `InventoryLevel` is a projection rebuilt from it. Accounting uses double-entry journals. | Accepted (proposed) |
| ADR-015 | Custom field values are stored in an embedded `customFields` map on the entity document. Definitions live in `CustomFieldDefinition` (industry/org scope + entity type). Searchable fields get indexes chosen by the engine. | Accepted (proposed) |
| ADR-016 | Settings are resolved `System → Industry → Organization → Location`. Each key declares in a settings registry whether a location may override it. | Accepted (proposed) |
| ADR-017 | Tenancy: every tenant-owned document has `organizationId`, enforced by a Mongoose plugin that reads it from `AsyncLocalStorage` tenant context. A client-supplied `organizationId` is never trusted. Location access is filtered the same way. Shared database first. Dedicated database only when a paying customer needs it. | Accepted (proposed) |
| ADR-018 | IDs are UUID strings in domain and persistence. The Mongo `_id` is kept internally. | Superseded by ADR-036 |
| ADR-019 | Frontend data fetching: TanStack Query. UI: Tailwind + shadcn/ui. Mobile-first. PWA. | Accepted (proposed) |
| ADR-020 | Performance budgets: API p95 < 200 ms, in-app navigation < 300 ms, LCP < 2.5 s on 4G, INP < 200 ms. Budgets are checked in CI from Phase 6. | Accepted (proposed) |
| ADR-021 | Product brand: **Banijjik** for the Bangladesh launch, with package names "Banijjik Store" (website) and "Banijjik Chat" (chatbot). "OmniFlow" was a name suggested by Gemini and is not used. Condition: the owner confirms domain availability and a trademark search (P2) before public launch. See ADR-038. | Accepted (proposed, pending P2 checks) |
| ADR-022 | One user, many organizations. Global User identity (verified email/phone). Session is per user. The active organization comes from the URL `/[org]` and is validated against the user's memberships on every request. No second login. A separate business = a separate organization. Extra capabilities in the same business = more modules. Details: `06-AUTOMATION-AND-ACCOUNTS.md §2`. | Accepted (proposed) |
| ADR-023 | Tenancy modes. Shared is the default. Dedicated database per organization is designed for but built later (Phase 8). From Phase 0, business code gets models via a kernel accessor `models(ctx)`, never by direct import. Organization has `deployment: SHARED \| DEDICATED`. Platform data lives in a separate platform DB. Amends ADR-017. | Accepted (proposed) |
| ADR-024 | Channel connection is OAuth-based and one-click. The platform owns a single Meta app. Sellers never create apps or webhooks. Facebook/Instagram via Page OAuth plus webhook subscription. WhatsApp via the official Cloud API and Embedded Signup. Unofficial WhatsApp libraries are forbidden. | Accepted (proposed) |
| ADR-025 | The chatbot answers only from banijjik data (catalog, stock, policies). It never depends on a seller's website. We never require code changes on, or access to, a seller's existing website. An optional chat widget and catalog import are the only integrations. | Accepted (proposed) |
| ADR-026 | The banijjik catalog is the single source of truth for products. Entry: quick-add form, import-from-Facebook-post (reviewed draft; new Page posts auto-create drafts for one-tap approval; "import last N posts" on onboarding), bulk CSV/photo import (reviewed draft). Output: publish-to-post. A `ProductSocialLink` maps posts/ads to products. A PDF or price list is only a draft input. | Accepted (proposed) |
| ADR-027 | Ads are human-approved. No autonomous ad spending. Starts as "boost post" using the seller's own ad account (Phase 8). | Accepted (proposed) |
| ADR-028 | Fulfilment: courier providers behind one `CourierProvider` port (Steadfast first, then Pathao and RedX), plus an own-rider flow (rider role, mobile view, COD handover). Courier credentials are per organization and encrypted. | Accepted (proposed) |
| ADR-029 | Website CMS: platform-owned templates and design tokens. Each region is `locked`, `content-only` or `fully-editable`. Tenants edit within the allowed limits. Sites are rendered from JSON and tokens. No tenant code runs on the server. | Accepted (proposed) |
| ADR-030 | Bot cost and safety: retrieve top-k products, never the whole catalog. Structured JSON/tool output, no text flags. "Not found" is not "out of stock". Cost ladder: rules/FAQ/cache → small model → large model on low confidence. Prompt caching. Per-org AI quota by plan; over quota → rules-only mode. Several ideas reviewed from an external Gemini conversation (2026-10-09). | Accepted (proposed) |
| ADR-031 | Own domain ≠ own hosting. Shared hosting with a free subdomain + custom domain via an edge custom-hostname/SSL service. Dedicated = managed by us. Self-hosted Docker for customers is rejected for now (code leakage, version sprawl, breaks the single Meta app). | Accepted (proposed) |
| ADR-032 | Product packaging: Website and Chatbot are separately sold entitlements on one platform, sharing one login, one dashboard and one data core (catalog, orders, customers, courier). Never separate dashboards or apps per product. The dashboard home, menu and onboarding adapt to the purchased packages. | Accepted (proposed) |
| ADR-033 | Capability model: Module (code manifest) / Package (DB) / Industry template (DB) / Org config (DB) are separate concepts. One resolver, `resolveOrgConfig`, feeds the API gate, menu, bot tools, storefront sections and settings. Feature code never reads `industry` (lint-enforced). Every manifest gets generated "module off" contract tests. Replaces manoxen's per-industry capability flags. See `07-CAPABILITY-MODEL.md`. | Accepted (proposed) |
| ADR-034 | Offerings with a closed set of kinds (PRODUCT, SERVICE, PLAN, RENTAL, EVENT) are code primitives. Booking (resources + availability) and Subscription (plans/enrollments) are **core** modules, not industry packs. An industry = template data (kinds, modules, fields, terms, templates, bot defaults). New code only for a genuinely new kind or capability module. | Accepted (proposed) |
| ADR-035 | Universal bot: tool-calling agent over generic tools generated from org config, a structured state machine, a grounding guard and an eval harness of golden conversations per industry template. No per-industry or phrase/regex bot code. Every bot fix starts with a failing golden conversation. See `08-UNIVERSAL-BOT.md`. | Accepted (proposed) |
| ADR-036 | IDs: hybrid UUID v7. Every entity has a domain ID `<entityName>Id` (UUID v7 from `@banijjik/ids` `newId()`), used in domain, DB references, API, frontend and events. Mongo `_id` (ObjectId) stays internal to infrastructure only and never leaves mappers. Branded ID types. Human-facing document numbers come from per-org atomic counters. Slugs only in human URLs. Supersedes ADR-018. Details: `05-CONVENTIONS.md`. | Accepted |
| ADR-037 | Adopted from manoxen rules, adapted rather than copied: canonical field names with forbidden aliases (rule 7), slug vs ID (rule 13), one Contact master per org with phone-first dedupe (rule 11), typed and audited `runAsSystem(reason)` (rule 9), mandatory central error capture (rule 19), AI provider/business-tool separation (rule 22). Not adopted: BU/outlet scope rules (6, 15, 16, 18, 20, 21) and `success: true` envelopes. Reason: no scope model here, and the envelope stays `{ data, meta }` per conventions. | Accepted (proposed) |
| ADR-011a | Amends ADR-011: domain code may import only `@banijjik/contracts` (constants/types) and `@banijjik/ids` (pure `newId()` + branded ID types). No other runtime library. | Accepted (proposed) |
| ADR-038 | The brand is decoupled from code. The code namespace `@banijjik/*` and repo names never change. Every user-visible brand string (product name, package names, emails, SMS sender, storefront footer, legal pages) comes from platform config/i18n. A rebrand costs zero code changes. Lint/CI forbids the literal brand name in UI strings. | Accepted (proposed) |
| ADR-039 | People and companies a business deals with are one **Contact** model (`contactId`), with roles (`CUSTOMER`, `SUPPLIER`, `LEAD`, …) and industry terms for labels (Customer / Student / Patient / Member). This is the industry-standard party model (Xero/QuickBooks "Contacts", Odoo partner, HubSpot contacts). References use a role prefix where needed (`supplierContactId`, `billToContactId`); on orders/bookings the buyer is `contactId`. A separate `customerId`, `supplierId`, `studentId` or `patientId` is forbidden. | Accepted |
| ADR-040 | Ethical revenue principle: no third-party advertising inside the product, and tenant or end-customer data is never sold or shared for marketing. Revenue comes only from subscriptions, add-ons and usage. The tenant-facing "run Facebook ads for your products" feature is allowed: it is the seller advertising their own business, not us monetizing users. | Accepted (proposed) |
| ADR-041 | Readable code is a hard requirement: full-word names, small single-purpose functions, guard clauses, no magic values, no `any`, why-comments, module READMEs, behaviour-named tests. Enforced by Prettier, ESLint limits (function 60 lines, file 300 lines, complexity 10, depth 3, params 3) and REVIEW. See `05-CONVENTIONS.md` "Readable code". | Accepted |
| ADR-042 | Parallel work: phases stay sequential; only independent card pairs from the roadmap's "Parallel lanes" run at the same time, each in its own git worktree and branch. Handoffs are per-card files. Shared hot files are add-only. One PLAN session may plan both cards of a pair. | Accepted |
