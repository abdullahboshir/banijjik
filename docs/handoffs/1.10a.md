## Per decision

1. Code lives in `core/iam`. Use cases, controller, router and `platform-operator.composition.ts`. Mounted at `/operators` in `routes/platform.ts`. Proved by `platform-operators-api.test.ts` (7 tests).
2. `OPERATOR_READ` and `OPERATOR_WRITE`. SUPER_ADMIN has both via `ALL_PLATFORM_PERMISSIONS`. SUPPORT and BILLING have neither. Proved by the contracts role-table test and the 403 cases.
3. `GET /` is paged (`page`, `limit`, `hasNext`), optional `status`, order `createdAt` desc then `platformOperatorId` desc. `findByIds` is one query. Proved by the happy-path list and `mongo-iam.repositories.test.ts` "loads several users in one query".
4. `GET /{id}` returns the same summary. Unknown id is 404.
5. `POST /` grants to an existing ACTIVE user. Unknown identifier is `OPERATOR_USER_NOT_FOUND`. A non-ACTIVE user is `OPERATOR_USER_NOT_ACTIVE`. An existing operator is 409 `errors.operator_exists`, including a duplicate `userId` key. Two simultaneous grants: one 201 and one 409.
6. `PATCH /{id}` changes roles. Same role set is 200 with no write, no audit and no version bump. Stale version is 409.
7. `POST /{id}/disable` and `/enable`. Same no-op rule. Disable sets `DISABLED` and revokes PLATFORM refresh sessions only. Enable restores no session. Proved by the effect test: platform refresh 401, admin refresh 204, platform login 200 after enable.
8. Own PATCH, disable and enable are 422 `OWN_OPERATOR_ACCESS` before any transaction, so a stale version still answers 422.
9. Every real write touches the actor (`referenceVersion` only) and then the target, inside one transaction. A grant has no target row, so it touches only the actor. If the actor is missing or is not an ACTIVE SUPER_ADMIN, the write is 403. Proved by `operator-write-guard.test.ts` and the concurrency test below.
10. One `PlatformAuditLog` per committed write: `OPERATOR_CREATED`, `OPERATOR_ROLES_CHANGED`, `OPERATOR_DISABLED`, `OPERATOR_ENABLED`. Reads and no-ops write none. The happy path asserts exactly four actions.
11. `identifierHint` uses `maskIdentifier`, moved unchanged into `packages/validation`.
12. `reasonSchema` is exported from `platform-schemas.ts` and reused. Not re-exported from the package index.
13. Docs: `09 §4.1` (`status`, `referenceVersion`), `14 §7` (the endpoint list, no delete), ADR-093 (permission list and the sign-in sentence), iam README.

## Deviations

- `buildIamPlatformOperatorRouter` is defined in `platform-operator.composition.ts` and re-exported from `core/iam/index.ts`. Putting the function in `index.ts` crossed the 300-line file limit.
- `routes/platform.ts` mounts packages and operators through `mountPackageAndOperatorRoutes`, so `buildPlatformRouter` stays within 60 lines. The mount order is unchanged: organizations, module overrides, subscription, packages, operators, audit, me.
- A grant touches only the actor. There is no target row yet. The unique `userId` index covers two grants of one user.
- A no-op is detected with a read before the transaction, so the common path does not bump `referenceVersion`. If the row changes inside the transaction, the post-touch comparison returns without an audit.
- Zod unknown keys are reported with path `""` and `validation.unrecognized_keys`, which is the existing error mapper.
- A successful admin refresh is 204. The effect test expects 204.
- `findByIds` projects `passwordHash` so `User.restore` can rebuild the entity. The API response never sends it.
- In-memory `UserRepository` and `PlatformOperatorRepository` implement the new methods so `tsc` still accepts the fakes. The API tests use MongoDB.
- An optional list `status` of `undefined` is omitted before it is passed to the use case (`exactOptionalPropertyTypes`).
- Platform screen catalogs gained four audit-action labels. The platform coverage test builds a key for every `PLATFORM_AUDIT_ACTION`.

## Existing assertions changed

- `mask-identifier.test.ts` moved with the same four expects. `get-tenant.use-case.ts` now imports `maskIdentifier` from `@banijjik/validation`.
- The contracts role-table test expects `OPERATOR_READ` and `OPERATOR_WRITE` to be false for SUPPORT and BILLING. Those roles were not given the keys.
