### Findings (both answer the handoff's open questions, and both are required for a T1 card holding sensitive data)

**R1-1 · MAJOR · a caller who may not read a sensitive value can overwrite it blind.** Only the UI leaves redacted fields out of the request. `AGENTS.md`: "Enforce permissions in the API. Hiding UI is never the protection."

Fix:
- In the profile and member write paths, before merging: if the request contains any key whose field is `isSensitive`, and the caller lacks the read permission for that entity (`organization.profile.update` at ALL for the profile; `organization.member.readSensitive` at ALL for members), answer **`403 FORBIDDEN`** with messageKey `errors.custom_field_sensitive_forbidden` and `details.fieldKeys`.
- Nothing is written.
- This applies to setting a value and to clearing it with `null`.
- Tests:
  - a MANAGER without `readSensitive` → 403 on a member's `medical_notes`, and the stored value is unchanged
  - the same MANAGER can still change a non-sensitive key
  - the OWNER can change both

**R1-2 · MAJOR · sensitive values are copied into `customFieldSearch`.** `toSearchEntries` (2.3, `packages/validation/src/custom-field`) does not skip sensitive fields. A lower-cased copy of a medical note or an NID then sits in a plain, indexed array that any future search endpoint could match against, which bypasses the redaction.

Fix:
- `toSearchEntries` skips every field with `isSensitive`, even when it is `isSearchable`.
- Say so in its doc comment and in ADR-102/ADR-107 in one line: a sensitive field is never searchable by value.
- Tests:
  - the helper unit test
  - an API test that a sensitive + searchable member field leaves no `customFieldSearch` entry

Fix R1-1 and R1-2 with new commits, rerun the full "Done means" list, add a "Review 1 fixes" section, and tell the owner. Do not merge, do not push.
