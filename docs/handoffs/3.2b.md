## Lead requests handled in this card

2. **API gap of 3.2a closed here:** `GET /orgs/{organizationId}/offerings/{offeringId}/locations` (`catalog.offering.read`), paged (`page`, `limit` ≤ 100), optional `?locationId=`; only rows of locations the caller reaches (a named location outside the reach is 403); backed by the existing unique index `(organizationId, offeringId, variantId, locationId)`. Row added to `14-API.md`. Tests: `catalog-offering-locations-api.test.ts` (happy, cross-org 404, unreachable location hidden and refused, paging and the limit).
3. **One image component:** `PublicImage` is the generic plain image (`loading` lazy by default); `LogoImage` (3.12) is now a thin wrapper that uses it with `loading="eager"`.

## Deviations from the plan (and why)
1. **Browser scenarios are PRODUCT only.** The spawned API stack offers only the kind the catalog provides (`PRODUCT`); the SALON service and GYM plan scenarios cannot run. They are covered by unit and jsdom tests (`offering-request.test.ts`, `offering-editor.test.tsx`: service duration, long-hair variant with a longer duration and price, plan billing period, joining fee, month-count override). **SERVICE and PLAN become usable (and get browser scenarios) when booking 3.6 and enrollment 3.7 provide those kinds.** A SALON or GYM business cannot add services or plans until then; this is the capability model working as designed (decided with the lead). No test-only switch was added to production code.
2. **Category image is not in the screens.** The API supports `imageFileId`; the plan lists an image on the category. Left out to keep the tree page small; recorded as a gap.
3. **Synonyms are edited as a word and a comma-separated text,** not as chips (no `ChipInput` was built). The saved data is the same.
4. **Category and add-on forms are inline panels,** not sheets (the page is short and the sheet adds code to the first load).
5. **No drag and drop for photos:** up/down buttons only (touch friendly, 44 px).
6. **RENTAL and EVENT kinds have no details section** yet (no fields are defined for the screens; their cards come later).
7. `ImageInput` shows one preview; the photo list is drawn by the editor with `PublicImage` (the ui component stays single-image).
