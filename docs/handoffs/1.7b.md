- **Not done / known gaps:**
  - Menu entries (decision 12), see open question 1.
  - **Write skew:** a location archive and a concurrent member assignment to that location can both commit (both read, different documents). The worst case is a member assigned to a just-archived location. Closing it needs a document both writers update (for example a counter on the organization); left for the review.
  - **Limit race:** the limit check counts, then inserts, in one transaction but without a lock, so two concurrent creates can overshoot by one.
  - The locations index `{ organizationId, name }` is now a partial unique index on ACTIVE locations. An existing database keeps the old full unique index until the index-sync task (STATUS gap of card 0.4b) drops it.
  - Invitation links are shared by hand until SMS and email sending exists (5.13). The identifier match on accept is the only binding until identifiers are verified (STATUS gap of 1.2).
  - Stock and open-request checks on location archive arrive with the inventory and sales cards.
- **Deviations from plan (and why):**
  1. **Menu entries not added** (decision 12): they would change existing assertions.
  2. **Audit entity type of invitations is `member`** (`entityId` = `invitationId`), not a new `invitation` type: `audit-contracts.test.ts` asserts the exact list `["organization", "location", "member", "role"]`.
  3. **Audit actions are lower-case words**: `organization.member.updated` for any member edit (including assignments), because the same test requires `/^[a-z-]+\.[a-z]+\.[a-z]+ed$/` (no `assignmentsChanged`). The event keeps the plan name `organization.member.assignmentsChanged`.
  4. **Two events beyond the plan:** `organization.member.reactivated` and `organization.invitation.revoked`, so every write has its event.
  5. **Events only where the plan names them:** a profile change without a rename, and a member edit without assignments (display name, job title), publish no event (as a role rename does). The audit entry is always written.
  6. **Error keys in a separate list:** `ORGANIZATION_MESSAGE_KEYS` is asserted to hold `validation.*` only, so the six `errors.*` keys live in `ORGANIZATION_API_MESSAGE_KEYS` with a new i18n test.
  7. **Anti-escalation also guards removal:** the caller must hold the keys of every role they take away, and of every role of a member they suspend, reactivate or remove (ADR-092). The plan text only named granting.
  8. **Reactivation checks the `members` limit** (ACTIVE + pending), since it adds an ACTIVE member.
  9. A SUSPENDED member counts as "already a member" for the duplicate-identifier check on invitations (the plan said ACTIVE or INVITED); a REMOVED one can be invited again.
  10. `jobTitle` added to `Member` (it was in `09 §4.4` but not in code).
  11. `PostalAddress` and `OrganizationProfileFields` fields are `?: T | undefined` (validated bodies carry explicit `undefined` under `exactOptionalPropertyTypes`).
  12. `POST /invitations/{token}/accept` has a per-user rate limit (10 per hour) in addition to the public preview's per-IP limit (30 per minute); not in the plan, cheap guard against token guessing.
  13. The create response is `201`; revoke, archive and the other transitions answer the changed record with `200`.
