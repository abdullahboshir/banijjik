## 2. New findings introduced or left by `0fc798a6`

### 1. Minor (documented) — delivery is a new interim `website.deliveryCharge` setting and is never frozen on the order
`apps/api/src/routes/storefront-price-adapter.ts:152-165`; `apps/api/src/modules/commerce/website/module.manifest.ts:93-99`; `packages/contracts/src/website/checkout-contracts.ts:173-177`

The old 60 BDT literal is gone, but the replacement is a new organization setting (`website.deliveryCharge`, INTEGER, default 0) rather than the documented `sales.deliveryCharges` source (`docs/11-OFFERINGS-AND-REQUESTS.md:63,122`). Lines, tax, discounts and currency are real; the delivery amount is real data but is added only to the quote/`Checkout.acceptedTotals` and never reaches the order command or payment summary (`storefront-order-commands.ts` returns `paymentRequired: placedOrder.totals.grandTotal`). With a non-zero setting the receipt total and the request payable differ by that amount. The handoff and STATUS record this for COD S1 (`docs/handoffs/4.3-a5a.md:57`), and COD S1 owns DeliveryZone freezing (`docs/plans/4.3-COD.md:50`), so this is a known gap rather than a hidden stub. Still: the new setting has no ADR entry and is not listed in `docs/10-MODULE-CATALOG.md`; the owner should accept it explicitly (or default it to 0 and drop it from the quote) before COD S1.

### 2. Minor — no test mounts the production storefront composition end to end
`apps/api/src/routes/storefront-commerce-commands.api.test.ts:149-194`

The test calls `buildStorefrontCommerceCommands(...).publicOrders.place` directly; it does not mount `buildStorefrontSurfaceCheckoutRouter` or `storefront.ts` and does not run `POST /checkout`. Booking and enrollment command wiring is never executed at runtime. Type-checking makes the three command options required, but a regression that passed mock commands from `storefront.ts` would pass every test. A single supertest through the mounted surface would close this.

### 3. Minor — the existence oracle survives on the claim and request-detail paths
`apps/api/src/modules/commerce/website/application/claim-checkout.ts:121-139`; `read-own-requests.ts:188-203`

`getRequestDetail` answers `errors.request_not_found` when the link is missing and `errors.checkout_not_found` when the owner mismatches. Both are HTTP 404, but `messageKey` is part of the public error envelope (`kernel/http/error-handler.ts:86-98`), so a same-org caller can still tell "exists but foreign" from "missing". `ClaimCheckoutUseCase.loadAndVerifyAccess` still returns 403 for a foreign or revoked access, which is a stronger oracle. Neither path is cross-org (tenant scoping holds), and the R2 finding named the detail path only; recommend 404 with one message key on both.

### 4. Minor — `revoke()` writes access then links; atomic only inside a caller transaction
`apps/api/src/modules/commerce/website/infrastructure/mongo-checkout.repository.ts:140-158`

The access update commits before the link update. Both use `getActiveSession()`, so a caller that wraps `revoke()` in `withTransaction` gets atomicity; a caller that does not (today only the test) can leave the access revoked while the links stay live, so the checkout disappears from detail but remains in the list. A5B's erasure participant must call it inside the unit of work; alternatively make `revoke()` run its own transaction.

### 5. Minor — the claim test still does not read the order/booking/enrollment row
`apps/api/src/modules/commerce/website/checkout-tracking-claim.api.test.ts:888-940`

The test now reads the request link before and after and checks id/type/number/status/owner, which backs its name at the tracking level, but it never reads the underlying order and does not assert the link's `paymentRequired` (the R2 remediation mentioned the payment amount). The invariant is structurally enforced today because `ClaimCheckoutUseCase` has no order/booking/enrollment dependency; a future dependency added to the claim would not be caught.

### 6. Minor — the pagination test does not assert `organizationId` in the DB filter
`apps/api/src/modules/commerce/website/checkout-tracking-claim.api.test.ts:497-515`

`filters[0]` is matched on `revokedAt`, `ownerType`, `ownerIdentifier` only; `organizationId` is never asserted, and `skip`/`limit` are checked for two of the four calls. The repository does include `organizationId` and the tenant plugin filters all queries, so there is no leak today; the test just does not guard that part of R2's suggested assertion.

### 7. Minor — the cross-org list assertion is trivially true
`apps/api/src/modules/commerce/website/checkout-tracking-claim.api.test.ts:673-680`

An org-B guest has no links, so an empty list would pass even if the list query lost its organization filter. The claim 404 + unchanged org-A ownership is the real cross-org guard; the list half adds little. R2 asked for the org-A guest cookie on the org-B claim (matching phone); the test uses the org-B guest cookie instead.

### 8. Minor — `StorefrontRequestItem.details` is still untyped
`packages/contracts/src/website/checkout-contracts.ts:242`

The detail fields are now concrete, but the list item's `details?: Readonly<Record<string, unknown>>` still defeats compile-time redaction on `/me/requests`; the current writer puts `{ items: live.items }` there, which is safe at runtime but not enforced. Type it as `{ items: readonly StorefrontOrderItem[] }`.
