# Handoff: card 3.8, part B1 · Payment screens

Implemented by: Antigravity (Sonnet) · Date: 2026-10-23 · Plan: `docs/plans/3.8.md` (Refresh 2) · Branch: `s/3.8-ui-payments`

## What was built
- **Payment Routes & Pages:**
  - `apps/admin/app/[orgSlug]/(app)/payments/page.tsx` & `apps/admin/src/payments/payments-page.tsx`:
    - Server-side page fetching payments query with pagination (`limit <= 100`), location list, and `payment.methods` settings.
    - Mounts `PaymentsManager` with date, method, direction, and location filters.
    - Link to `/payments/dues` at the top of the manager.
  - `apps/admin/app/[orgSlug]/(app)/payments/[paymentId]/page.tsx` & `apps/admin/src/payments/payment-detail-page.tsx`:
    - Server-side detail route fetching individual payment by `paymentId`.
    - Mounts `PaymentDetailView` displaying overview facts, allocations with `revenueState` badge (`Advance` / `Earned revenue`), approval snapshot (if approved), and detail actions.
- **Payment Components (`apps/admin/src/payments/`):**
  - `payment-api.ts`: Typed API client methods (`fetchPayments`, `getPayment`, `receivePayment`, `refundPayment`, `reversePayment`, `listApprovers`, `grantApproval`, `saveMethodsSettings`).
  - `payment-labels.ts` & `payment-labels-builders.ts`: Bengali and English translations loader with sub-functions adhering to strict function line/complexity budgets (<= 60 lines, <= 300 lines/file).
  - `payment-card.tsx`: Mobile card item rendering amount, direction badge, method, date, location name, and reference.
  - `payments-filter-form.tsx`: Responsive filter form with method, direction, location, and date range inputs.
  - `payments-manager.tsx`: Orchestrates mobile card / desktop table switching, pagination controls, filter form, and lazy receive payment sheet.
  - `payment-detail-view.tsx` & `payment-detail-actions.tsx`: Detail overview, allocations table, approval section, and refund/reversal modal triggers.
  - `receive-payment-sheet.tsx`, `receive-payment-sheet-lazy.tsx`, `receive-payment-fields.tsx`, `receive-payment-allocations.tsx`, `use-receive-payment-form.ts`:
    - Lazy-loaded slide-over sheet for receiving payments.
    - Amount, location, allowed methods (from org settings or defaults), bKash/Nagad reference requirement with placeholder and business account instructions.
    - Allocation amounts pre-filled from dues.
    - Overpayment calculation: auto-credit to store credit notice (requires contact selection for non-cash), or cash change return notice.
  - `refund-dialog.tsx`, `refund-dialog-lazy.tsx`, `refund-allocations.tsx`, `use-refund-flow.ts`:
    - Lazy-loaded dialog for full or partial refunds.
    - Allocation refund amount editors.
    - Integrated with `ApprovalPinDialog` via `useApprovalDialogState`: retries with approval token strictly when approval is required (`ERROR_CODE.APPROVAL_REQUIRED`).
  - `reversal-dialog.tsx`, `reversal-dialog-lazy.tsx`, `use-reversal-flow.ts`:
    - Lazy-loaded dialog for full reversal with warning notice and reversal note.
    - Approver lookup and PIN grant via `ApprovalPinDialog`.
    - Handles 409 conflict gracefully by closing the PIN dialog and presenting the reload notice and button.
  - `payment-methods-section.tsx`: Configuration section allowing managers/owners to toggle accepted payment methods and saving via `PATCH /orgs/:organizationId/settings` (`payment.methods`).
- **Booking Integration:**
  - `apps/admin/src/bookings/booking-detail-page.tsx` & `booking-detail-payment-section.tsx`:
    - Adds payment status badge, total price, deposit required notice, and "Receive payment" button triggering `ReceivePaymentSheet` directly on the booking detail page.
    - Fetches dues for the booking and prefills remaining due amount rather than total price.
    - Passes real location name and booking number.
- **Translations (`packages/i18n/src/catalogs/`):**
  - `bn.json` / `en.json`: Permission labels and error message keys for payment domain rules.
  - `screens/bn.json` / `screens/en.json`: All UI keys for payments list, filters, details, receive sheet, refund dialog, reversal dialog, and settings section.

## Review R1 fixes
1. **Float money math in allocation editor:**
   - Replaced float math in `AllocationsEditor` and `RefundAllocationsList` with local text state parsed via `parseMoneyInput(trimmed, 2)`.
   - Used integer math `minorUnitsToDecimal` for display string initialization without float roundoff.
   - Shows field-level error on invalid text instead of silently coercing to 0.
2. **Booking receive payment due prefill:**
   - Updated `booking-detail-page.tsx` and `BookingDetailPaymentSection` to fetch and resolve remaining due (`dueItem.due.amount` or `0` for PAID or full price only if unpaid/no dues).
   - Passes real location name (from locations fetch) and customer-facing `bookingNumber` instead of hardcoded strings or raw UUID slices.
3. **User-facing raw keys and literals:**
   - Localized all raw message keys in `use-receive-payment-form.ts` and `use-approval-dialog-state.ts` through `t(knownMessageKeyOrInternal(...))` with reload CTA for 409 conflict.
   - Replaced all English literal strings in hooks and components with BN/EN i18n keys (`amountInvalid`, `locationRequired`, `failed`, `conflict`, `loadApproversFailed`, `approvalFailed`, `refundFailed`, `reverseFailed`).
   - Sliced UUID and raw enum in `AllocationsEditor` replaced with translated `requestTypeLabel` and booking number.
4. **Approval PIN dialog:**
   - `isApprovalError` in `use-refund-flow.ts` restricted strictly to `error.code === ERROR_CODE.APPROVAL_REQUIRED`. Over-refunds (422) and permission denials (403) show error message directly without prompting for PIN.
   - Similar strict check verified in `use-reversal-flow.ts`.
5. **Literals & delays:**
   - Replaced `"BOOKING"` literals with `PAYMENT_REQUEST_TYPE.BOOKING`.
   - Removed artificial delay `setTimeout(..., 600)`.

## Deviations from the plan
1. `apps/api/src/modules/commerce/payment/module.manifest.ts`:
   - Changed `PAYMENT_REFUND_MANAGER_WITHOUT_APPROVAL_SETTING_KEY` from `isClientVisible: false` to `isClientVisible: true`.
   - Reason: `OrgConfigResolver` filters out settings that are not client-visible when returning `effective.config.settings` to the frontend. Because Card 3.8 Part A left this setting hidden from client, the frontend could not read whether `managerWithoutApproval` was enabled or disabled, causing refund approval gating in UI to always assume manager was permitted. User permission was requested and explicitly granted via `ask_question`. Accepted by lead in Merge Check R1.
