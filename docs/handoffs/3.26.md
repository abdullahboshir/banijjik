## Causes and changes

1. `apps/api/src/kernel/idempotency/idempotency.middleware.test.ts`: the takeover test guessed that each request had entered the held handler after 200 ms. On a slow runner the clock could advance before the first claim, or the release loop could run before the takeover parked. The probe now signals after registering its release callback; the test awaits that signal before checking the active lock and before releasing both requests.
2. `apps/api/src/kernel/rate-limit/mongo-rate-limiter.test.ts`: the shared `MutableClock` starts on 2026-10-11, so its counter expiry dates are already past relative to MongoDB's real clock. The TTL monitor can delete the middleware counter between requests; the injected clock itself does not tick, and the earlier tests use different buckets/keys. The middleware test now clears the counter collection and uses its own limiter, fixed future clock (2099), bucket and explicit subject, removing TTL cleanup and client-address variability from this assertion. This is a test-fixture clock mismatch, not a production limiter bug.

## Proposed conventions note (lead adds at merge)

**Writing time-dependent tests:** Inject a clock and move it explicitly at the behaviour boundary. When persisted documents have TTL indexes, keep their expiry dates ahead of the database's real clock unless expiry is the behaviour under test. Await a signal from the operation being coordinated instead of sleeping for a guessed duration. Give each counter test an isolated bucket and subject, and clean its persisted counters before the scenario.
