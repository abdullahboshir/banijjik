# Card 3.6b Part A3 — event bookings

Date: 2026-10-24. Branch: `s/3.6b-api-event-booking`. Tier: T1.
Plan: `docs/plans/3.6b.md`, section "Refresh 2" (2026-10-23, based on `main 46c5ddb`).

## Built

- **Shared kind-keyed reader** (`infrastructure/booking-catalog-adapter.ts`, decision 1):
  `readOffering` now answers SERVICE, RENTAL and EVENT views; a new `toOfferingBookingView`
  does the three arms, and unreadable `kindDetails` means "not bookable". The A2 narrow
  `EventSessionOfferingReader`, its adapter and its duplicate location helper are deleted;
  `event-session.use-cases.ts` reads through `BookingOfferingReader` and refuses a
  non-EVENT or inactive offering with `OFFERING_NOT_BOOKABLE`. Manifest `providesKinds`
  has `EVENT`.
- **Event create and hold** (`application/event-booking-parts.ts`, decisions 2 and 3):
  validation gained `eventSessionId` on `bookingCreateRequestSchema` (the hold reuses it).
  An EVENT offering requires a session, any other kind forbids one; the session must belong
  to the same offering, seat class and location and still be SCHEDULED
  (`BOOKING_EVENT_SESSION_NOT_OPEN`), and sales close at
  `startsAt − salesCloseMinutesBefore` (`BOOKING_EVENT_SALES_CLOSED`). The booking copies
  the session times, blocks nothing but seats, and stores `eventSessionId` through the
  schema, mapper, entity props and `BookingResponse`. Both the staff create path
  (`create-booking-attempt.ts`, `staff-booking-prepare.ts`) and the hold path
  (`hold-booking-reserve.ts`, `hold-booking-prepare.ts`) branch on the kind and call the
  same helpers; `reserveResourceForSlot` is never reached for an event.
- **Seat counter** (`domain/event-session.entity.ts`,
  `application/ports/event-session-repository.ts`,
  `infrastructure/mongo-event-session.repository.ts`, decision 3): `reserveSeats` is one
  conditional `findOneAndUpdate` with `$expr: seatsSold + seats <= capacity` and status
  SCHEDULED, inside the caller's transaction; a miss re-reads once and answers
  `409 SLOT_UNAVAILABLE` with `BOOKING_EVENT_SOLD_OUT`, or `BOOKING_EVENT_SESSION_NOT_OPEN`
  when the session stopped being schedulable. `releaseSeats` filters `seatsSold >= seats`
  and throws on drift instead of clamping. Neither bumps `version`.
- **One release path** (`releaseBookingCapacity`, decision 4): EVENT gives seats back, every
  other kind gives its slot back. Used by the cancel use case and the expire-holds job. The
  manual no-show and the no-show job use `releaseCapacityForMissedBooking`, which leaves an
  event seat sold.
- **Reschedule** (decision 5): `bookingRescheduleRequestSchema` has optional `startsAt` and
  `eventSessionId` with an exactly-one-of refine. An EVENT booking moves between sessions of
  the same offering, seat class and location in one transaction
  (`moveEventSeats`: reserve the new session, release the old, versioned booking update);
  the same session is `BOOKING_EVENT_SAME_SESSION`; a sold-out target answers 409 and
  changes neither counter. `timeZone` became a required dependency of
  `RescheduleBookingUseCase` and the `"Asia/Dhaka"` fallback is gone (§11 item 20).
- **Session cancel** (decision 6): `EventSessionUseCases.cancel` marks CANCELLED and, in the
  same transaction, publishes `booking.eventSession.cancelled` and audits it (new
  `AUDIT_ACTION.EVENT_SESSION_CANCELLED`, new audit entity type `eventSession`). The new
  field `bookingsSettledAt` is job bookkeeping: `markBookingsSettled` uses `$set` only so it
  never bumps the version admins see. The new scheduled job
  `booking.cancelEventSession` (every minute) reads up to 10 unsettled cancelled sessions and
  up to 100 open bookings each, cancels every booking in its own transaction (release seats,
  `settleBookingTermination` with `mode: CANCEL` and `feeMode: CANCEL_FEE_MODE.NONE`,
  versioned cancel transition, `booking.booking.cancelled` event, audit), logs and skips a
  failing row, and stamps `bookingsSettledAt` only when the session has no open booking left.
- **Session completion and EVENT auto-complete** (decisions 7 and 8):
  `booking.autoComplete` completes up to 100 past SCHEDULED sessions through the versioned
  update, and `listAutoCompleteCandidates` became an `$or` of the rental rule and
  `kind: EVENT, status: CHECKED_IN, endsAt <= now` (no grace).
- **Expire-holds hardening** (decision 9): per-row `try/catch` with the `bookingId` logged,
  so one bad row no longer blocks later runs.
- **Contracts and catalogs** (decision 10): five rule keys, their five `errors.*` keys in
  `BOOKING_MESSAGE_KEYS`, BN and EN strings, the session-cancel note key, the event type and
  `EventSessionEventPayload`. The audit vocabulary gained `AUDIT_ACTION.EVENT_SESSION_CANCELLED`
  and the entity type `eventSession`, which the audit-contracts enumeration test lists in
  insertion order.
- **Lint cleanup** (no behaviour change): six functions had grown past the 60-line rule when
  the EVENT arm was added, so the slot bounds, the hold resource arm, both capacity moves,
  the catalog view switch and the prepared-booking shape are now named helpers
  (`slotBookingBounds`, `holdSlotResource`, `moveEventSeats`, `moveSlotCapacity`,
  `toOfferingBookingView`, `PreparedStaffBooking`, `EventBookingBounds`).
- **Module README:** the booking README had grown past the 30-line module-shape limit, so the
  A2 section, the new A3 section and the job notes are now one bullet list per topic. The
  module-shape and audit-vocabulary tests caught both of these on the first CI run
  (https://github.com/abdullahboshir/banijjik/actions/runs/40043905935, failed); they are
  fixed in `fix(booking): shorten the module readme and list the eventSession audit type`.

## Clarifications and deviations

- **The session-cancel note is on the audit entry, not on `booking.note`.** The job passes
  `BOOKING_EVENT_SESSION_CANCEL_NOTE_KEY` into the cancel transition, but
  `transitionBookingProps` never writes `props.note` (the manual `CancelBookingUseCase` drops
  its reason the same way on main). Adding that write would be an entity change outside this
  card, so test 26 asserts the audit change set carries the key. Part B reads it from audit.
- **The index choice for decision 7 is:** `event_sessions`
  `{organizationId, status, bookingsSettledAt, eventSessionId}` for the cancel job and
  `{organizationId, status, endsAt, eventSessionId}` for completion, each sorted by its own
  time and ended by the id; `bookings` uses `{organizationId, eventSessionId, status}` for
  both the job and the reads.
- **Test fixtures had to move to COACHING.** Only the COACHING seed enables the EVENT kind
  (`enabledKinds: ["PLAN","EVENT"]`), so the A2 session suite and both new A3 suites build a
  COACHING world through `worldFor(harness, RETAIL, COACHING)`, and a new
  `publishBookableEvent` helper in `test-support/booking-api-world.ts` publishes an EVENT
  offering with `salesCloseMinutesBefore` and any number of seat classes. COACHING also makes
  the contact custom fields `class_level` and `guardian` required (ADR-073), so the seat buyer
  in the API suite carries them.
- **The sales-close test advances the shared harness clock in hours, not `vi.useFakeTimers`.**
  Every booking API test signs in once and shares `harness.clock`; a jump of days expires the
  httpOnly cookie and later calls return 401. The session window is therefore the morning
  after the harness start, with two 40-second advances around the closing edge.
- **`releaseSeats` drift and the "loop" test are split across files**: the counter-drift
  refusal is the repository test (test 23), the loop that keeps both sessions exact is an API
  test (test 20), and expiry release once is the job test (test 24). One file cannot hold all
  three: the API suite has no repository-level way to write a drifting row.
- **A session id on a non-EVENT offering answers `VALIDATION_ERROR` with rule key
  `OFFERING_NOT_BOOKABLE`** (decision 2 said "the same validation error"); the rule key names
  the reason so the client can show it. The exactly-one-of refine message is the machine key
  `start_or_session_required`, following the existing `contact_required` in the same file.
- **File spread (decision "keep production files near 15"):** 15 production files carry 20 or
  more added lines; 38 more are add-only edits under 20 lines (ports, mappers, lifecycle
  wiring, contracts, catalogs), 53 in total. The owner chose to finish A3 as one part with
  these counts recorded here rather than split it.
- No `apps/admin` file was touched, and
  `booking/application/ports/resource-exclusive-holds.ts` (card 3.7) is untouched.

## Known gaps and next part

- **An event session does not block its resources' slots** (decision 11). A hall a session
  reserves can still be rented for the same hours. Written here and in the STATUS note; the
  lead plans it separately (the guide board calls it "event sessions occupy resources").
- **No notification when a session is cancelled.** `docs/11 §5.5` asks for one; A3 publishes
  `booking.eventSession.cancelled` on the outbox so the notification card can react to it,
  but sends nothing itself.
- Waitlist stays reserved (`allowWaitlist` unused), as planned.
- Part B (screens) owns the admin side: EVENT kind details, session lists and the seat
  counters on the booking sheet.
