## 2. Checklist Walk (§11 & `RUN-WITHOUT-CLAUDE.md` §7)

### Multi-tenant security & tenant isolation
- **Verdict: Pass.**
  - `organizationId` is resolved exclusively via `getRequestContext().organizationId` (from the route path through the kernel tenancy middleware). It is never accepted from the request body or query.
  - Cross-organization isolation is strictly enforced in `ResolveGuestSessionUseCase.execute`: if `session.organizationId !== organizationId`, it returns outcome `{ kind: "CROSS_ORG" }`, which maps directly to HTTP 403 `FORBIDDEN`.
  - Database collection uses `MODEL_TENANCY.ORGANIZATION` with a compound unique index starting with `organizationId`: `{ organizationId: 1, guestSessionId: 1 }`.
  - Verified by integration test: `"rejects guest session cookie belonging to another organization (cross-org isolation)"`.

### Cookie handling & session lifecycle
- **Verdict: Pass.**
  - Cookie name: `sf_guest` (`SF_GUEST_COOKIE_NAME`).
  - Cookie format: `${guestSessionId}.${rawSecret}` (`formatGuestCookie`). Deserialized securely via `parseGuestCookie` with index bounds checking.
  - Attributes: `httpOnly: true`, `secure: isProduction`, `sameSite: "lax"`, `path: "/"`, `maxAge: 30 * 24 * 60 * 60 * 1000` (30 days).
  - Cookie cleanup: `clearGuestCookie` properly clears stale, expired, or invalid cookies on failed resolution with `maxAge: 0` / empty string and matching attributes (`path: "/"`, `httpOnly: true`, `sameSite: "lax"`, `secure: isProduction`).
  - Verified by integration tests: `"creates guest session with 32-byte opaque secret in httpOnly sf_guest cookie"`, `"sets 30-day absolute expiry on guest session and cookie"`, and `"rejects expired guest session and clears stale cookie"`.

### Rate limiting & abuse protection
- **Verdict: Pass.**
  - Rate limiting is applied to `POST /guest-session` using `rateLimit` middleware with `bucket: "storefront.guest_session.ip"`, `limit: 10`, `windowSeconds: 3600` (10 sessions per hour per IP).
  - Exceeding the rate limit returns HTTP 429 `RATE_LIMITED`.
  - Verified by integration test: `"enforces IP rate limit of 10 guest sessions per hour per IP"`.

### Cryptographic security & hashing
- **Verdict: Pass.**
  - Secret generation: Node `crypto.randomBytes(32).toString("hex")` generates 32 bytes (256 bits) of entropy (64 hex characters).
  - Storage: Only the SHA-256 digest (`secretHash`) is persisted to MongoDB. The plaintext secret is never saved to the database.
  - Constant-time verification: `verifyGuestSecret` computes `hashGuestSecret` and compares digests using `crypto.timingSafeEqual` after a buffer length check, eliminating timing side-channels.
  - Verified by integration tests: `"stores SHA-256 hash and never plaintext secret in database"`, `"rejects forged, tampered, or invalid secret hash"`.

### Database schema, TTL & indexes
- **Verdict: Pass.**
  - `GuestSession` schema defines `guestSessionId: { type: String, required: true, immutable: true }` and `organizationId: { type: String, required: true, immutable: true }`.
  - Unique compound index: `{ organizationId: 1, guestSessionId: 1 }, { unique: true }`.
  - MongoDB TTL index: `{ expiresAt: 1 }, { expireAfterSeconds: 0 }`.
  - Application-level expiry check: `isGuestSessionExpired` and `clock.now()` verify expiration in the application layer regardless of MongoDB background TTL worker frequency.
