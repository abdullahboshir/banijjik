- **Deviations from plan (and why):**
  1. **39 `MODULE_KEY` values, not 37.** `10 §5` has 39 rows; the plan's count was off. All 39 are in.
  2. **`StartTrial` does not bump `configVersion`.** The plan (decision 6) says it should, but the existing assertion `configVersion: 1` in `organization-api.test.ts` ("creates the organization ...") would then read 2. The rule was "no assertion changes", so the bump is left out: the organization is created in the same transaction at version 1, so nothing can be cached before the trial exists. The `ConfigVersionBumper` port (kernel/tenancy) and its Mongo implementation (`buildConfigVersionBumper()` in organization) are still delivered for the first real writer. **Lead: decide whether to change that one assertion to 2 and add the bump, or keep this.**
  3. **The two internal errors are masked.** The kernel error handler answers every server-side AppError as generic `errors.internal` (review finding J1), so `errors.trial_package_missing` and `errors.route_without_module` reach the log (asserted) but not the response body, and I did not add catalogue texts for them. The tests assert `500 INTERNAL` plus the log line.
  4. **`ConfigVersionBumper` lives in `kernel/tenancy`**, not inside saas-billing, because entitlement and later writers share it.
  5. **Extra, needed for correctness:** (a) a cached config carries `validUntil` (the earliest override expiry) so an expired override drops out without a version bump; (b) the template key of an organization is cached per `configVersion` so the hot path does not read the organization; the real template reader of 2.1 must therefore make `find` cheap (port comment says so).
  6. `OrgConfigReader.current()` returns a smaller kernel type `GateOrgConfig` (`accessMode`, `modules`); `OrgConfigService` returns the richer `EffectiveOrgConfig`.
  7. The registry allows a `dependsOn` key that is in the catalogue but not registered yet (the resolver drops such a module), as the plan intends for packages.
  8. `ModuleOverride` has no domain entity: the resolver reads lean records (`ModuleOverrideRecord`) because nothing writes them yet.
