## What was built

Permission keys `report.home.read`, `report.daily.read`. No system reason is added: the rebuild card adds `SYSTEM_REASON.REPORT_REBUILD` when it lands (review R1, item 2).

- **Module** `apps/api/src/modules/commerce/report/`: manifest (CORE, not disableable, no settings, no menu), `DailySummary` (LOCATION tenancy, unique `{organizationId, locationId, businessDate}`, read index `{organizationId, businessDate, locationId}`), marker `ReportEventApplied` (unique `{organizationId, eventId}`, TTL 400 days), UNORDERED handler `report.summarize`, use cases for home and daily, controller, router, README.
- **Counting** (decisions 3 and 4): every event of the plan's inputs, plus `sales.return.reversed` (3.5b A2 is merged). Each fact counts on its organization-local date. A fact in another currency, or a fact missing its date or link, throws and goes to the dead-letter list.

- **Wiring** (add-only): `core-tenant-routers.ts`, `tenant-module-routers.ts`, `module-registry.ts`, `v1.ts`, `start-worker.ts` (`routes/report-event-handlers.ts`), `routes/report-tenant-router.ts`, i18n catalogs (6 keys each), `eslint/restrictions.mjs` (`/report` added to the domain import exception, as `/pos` was).
- **Grants**: `report-role-grants.ts` (owner ALL, manager ALL, the rest NONE). See deviation 1.
- **Home sections** (decision 8): `sections` lists the sections whose source modules are effective (`isModuleEffective`, ADR-033). For RETAIL the list is SALES and MONEY.

## Deviations from the plan (with reasons)
1. **Grants table extracted (lead decision, Q1).** `system-role-grants.ts` is at its 300-line cap. The `sales` and `payment` blocks moved, unchanged, to `sales-role-grants.ts` and `payment-role-grants.ts` in their own commit (`0b6bd34d`, zero behaviour change: `system-role-grants.test.ts`, `grant-map.test.ts` and `role-grant-rules.test.ts` pass unchanged). The `report` row and its import then fit at 284 lines. The cap and the rule are unchanged.
2. **Rebuild dropped (lead decision, Q2).** Decision 6 and test A10 are not implemented, and `report:rebuild` is not written. Live counting is kept. See follow-ups.
3. **No Reports menu entry** (lead confirmed). It comes with part B, like the POS precedent.
4. **Range above 92 days is `VALIDATION_ERROR` (400), not 422.** Plan A9 says 422; decision 7 says `VALIDATION_ERROR`, and the shared error table maps that code to 400. Lead confirmed 400. The plan wording should be fixed (follow-ups).
5. **Marker is an upsert, not an insert.** `ReportEventApplied` is written with `updateOne({upsert: true})` and `upsertedCount` tells new from repeat. A duplicate-key error inside the transaction would abort the counters as well, which is why the kernel's own marker does the same. The code comment in `mongo-report.repositories.ts` says so. Same semantics as plan decision 3 (lead accepted).
6. **ADR number 148, not 147.** The plan reserved 147, but M.9 took 147 on main first.
7. **Home values for every section are present.** `sections` lists only the effective sections, as decision 8 says. The `periods` values are still computed for every section, and a section whose modules are off has zero counters by construction (its events never arrive). The response does not strip those fields.
8. **Plan wording only:** decision 1's "menu entry" is part B (deviation 3).
