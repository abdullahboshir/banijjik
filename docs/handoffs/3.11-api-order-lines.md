## Built
- **Sales (`commerce/sales`):** optional `performedByMemberId` on every order line (draft create, edit, instant, place re-quote). Rule: the member must be ACTIVE and assigned at the order location or at ALL, else `422 SALES_PERFORMER_NOT_AT_LOCATION`. Stored on the line; an order stored before this card reads `null`. The performer can change only while the order is editable (the existing `assertEditable` gate, `409 INVALID_TRANSITION` after COMPLETED or CANCELLED).
- **Performers lookup:** `GET /orgs/:organizationId/sales/performers?locationId=` (permission `SALES_ORDER_CREATE`, caller's locations only), names only, at most 100, sorted by name. Backed by `MemberPerformerReader` in `core/organization` (exported from its index).
- **Commission (`commerce/commission`):** `commission.accrue` also handles `sales.order.completed`. Each performed line gets one ACCRUAL (`sourceType ORDER_LINE`, `sourceId` = order id, `sourceLineId` = line id). Base = line net total minus line tax. `sourceGrossTotal` = the order grand total (ADR-135 note). `reconcilePaymentSources` reconciles ORDER allocations per line and member. Race marker touched with (`ORDER_LINE`, order id).
- **Split:** `accrue-commission.ts` (over 300 lines) became `accrual-shared.ts` (types, shared helpers), `reconcile-sources.ts` (reconcile, payment handling) and `accrue-commission.ts` (accrual). `accrue-commission.ts` re-exports the shared types and `reconcilePaymentSources`.
- **Admin:** a "Done by" select on each order line (new order and edit sheet), loaded lazily and shown only when the commission module is on (server flag `commissionEnabledOf`). Order detail shows the performer name per line. A commission entry of an order line links to its order (`CommissionEntryList` gets `orgSlug`).
- **Contracts / validation / i18n:** `OrderLineSnapshot.performedByMemberId`, `SalesPerformerResponse`, `MAX_ORDER_PERFORMERS`, rule key `SALES_PERFORMER_NOT_AT_LOCATION`, `COMMISSION_SOURCE_TYPE.ORDER_LINE`, `salesPerformersQuerySchema`, `performedByMemberId` on the line schema, en/bn keys for the error, the select and the entry source.

## Deviations from the plan (and why)
1. **Route prefix in the manifest.** The performers route sits under `/orgs/:organizationId/sales`, so the sales manifest `routes.admin` gained that prefix (the module router is gated by its manifest prefixes; without it the path answered 404).
2. **Reader location.** The performer reader lives in `core/organization` (the member collection is there), exported from its `index.ts`, not in `core/iam/index.ts`. `routes/sales-tenant-router.ts` passes it to sales as the `performers` port.
3. **`readOrder` has no `completedAt`.** The business date of an accrual is the organization's local date of the completion event's `occurredAt`, the same as for bookings. No separate completion timestamp is read.
4. **"Absent means none" for the line field.** The admin sends `performedByMemberId` only when a member is chosen; the API schema accepts it absent or `null`. This keeps the existing `order-lines.test.ts` expectation unchanged.
5. **Booking replay path.** `accrueCompletedBooking` now resolves the rule on a replay too and relies on the unique `sequence 1` (`insertIfAbsent`) to write nothing. The outcome is the same as before (existing accrual tests pass unchanged).
6. **Module off.** The performers lookup is a sales read and answers with the module off, as the plan says. The admin hides the select when the module is off.
