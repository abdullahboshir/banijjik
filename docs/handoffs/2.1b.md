## Per decision

### 1. Create, clone, patch, publish, retire

`POST /platform/industry-templates` creates a DRAFT, or copies kinds, modules and configuration from a template of any status. A taken key is `409 errors.industry_template_key_taken`. A key that is not the ADR-097 format is 400. A module that is not CORE or OPTIONAL is 400. `PATCH` replaces the given fields and moves `version` (409 when stale). The key and the status do not change through PATCH. Publish accepts DRAFT or RETIRED. Retire accepts PUBLISHED. The same status is 200 with no write and no audit. Any other transition is `422 INDUSTRY_TEMPLATE_STATUS_INVALID`.

Proved by `industry-template-write-api.test.ts`: PHARMACY 201 DRAFT, RETAIL taken 409, `pharmacy` 400, `iam` 400, SALON clone copies kinds, modules and contact roles, stale version 409, DRAFT retire 422, second publish 200 with the same audit list.

### 2. Additive PATCH

Once a template is PUBLISHED, RETIRED, or used by at least one organization, a PATCH may only add. `details.removed` lists every removed item. An unused DRAFT may remove freely. A DRAFT that an organization uses is locked. Signup cannot create that organization (a draft is not selectable), so the test moves a RETAIL organization onto the draft first.

Proved by the same file: LOCKED_SHOP removal returns `customField:contact::skin_type`, `kind:SERVICE` and `module:booking` together; adding EVENT returns 200; FREE_DRAFT may drop booking; USED_DRAFT returns 422 after one organization is moved onto it.

Removing a SELECT or MULTI_SELECT option on a field that remains is also listed (`option:…`). The plan allows options to be added. Other field edits (label, type, required) are allowed. Unit cases are in `additive-change.test.ts`.

### 3. Reader cache

The template view is cached for 30 seconds per key. After a PATCH that adds booking, `/me/config` still shows the old modules, and shows booking after `clock.advanceSeconds(31)`.

### 4. Publish, retire, and existing organizations

Publishing SIGNUP_SHOP lets signup return 201. Retiring it makes the next signup `422 INDUSTRY_TEMPLATE_NOT_AVAILABLE`. The organization that already exists still reads `/me/config` with 200. Publishing the retired template again returns 200.

### 5. Change an organization's template

Unknown key is 404 (`industryTemplateNotFound`). A RETIRED target is `422 INDUSTRY_TEMPLATE_STATUS_INVALID`. A DRAFT target is allowed. The check compares kinds and modules only. The same key is 200 with no audit and no `configVersion` bump. A real move sets the key, bumps `configVersion`, writes one platform audit entry and emits `organization.organization.industryTemplateChanged` inside the organization context.

`core/organization` does not compare the key. `AssessIndustryTemplateMove` returns `"unchanged"` or `"allowed"`.

Proved by the write API test: RETAIL to SALON returns 200, `configVersion` 2, `/me/config` gains booking, one event and one audit. SALON back to RETAIL is 422 and lists `kind:SERVICE` and `module:booking`. BAKERY is 404. The same key does not add an audit entry.

### 6. Signup versus retire

`reserveForSignup` is `findOneAndUpdate({ industryTemplateKey, status: PUBLISHED }, { $inc: { referenceVersion: 1 } })` in the active session, with `timestamps: false`. It does not move `version`. The cheap read before the transaction stays. The second read inside the transaction is this reserve.

The race test starts the signup request, waits 20ms, then retires. Supertest does not send until `end` is called, so awaiting both promises together let retire finish first on every round (eight 422s) and never reached the guard. With the request actually in flight, a signup can commit while retire runs.

Proof that the guard is required: `reservePublished` was temporarily a `findOne` with no `$inc`. The race test then failed:

### 7. Permissions and audit

SUPPORT and BILLING receive 403 on create, patch, publish, retire and change-template. No session is 401. An admin cookie on a platform route is 401. Each real write has one audit entry. A repeated publish and a same-key move add none. A configuration change is stored as `{ configuration: { to: true } }`, because `AuditValue` cannot hold `{ changed: true }`. Localized name and description are stored as `name.bn`, `name.en`, `description.bn` and `description.en`.

## Open question

Moving an organization does not write the template document, so it does not conflict with a concurrent retire. Signup and retire do, because the reserve increments `referenceVersion` on that document. A move that passes the "not retired" check and a retire that commits before the move can still both commit. The plan's race is signup versus retire only. This card did not add a second guard.

### Findings

**R1-1 · MAJOR · moving an organization is not serialized with the target template's writes.** The handoff's open question is real, and the same gap has a second consequence. The move re-assesses the target inside its transaction but writes nothing on the target document, so under snapshot isolation it conflicts with neither of these:
- **a concurrent retire** of the target: the organization can end up on a template that was retired before the move committed
- **a concurrent PATCH that removes modules or kinds from an unused DRAFT target.** The PATCH counts 0 users and drops, say, `booking`; the move checked the old target and commits. The organization has lost a module it had, which is exactly what the additive rule (ADR-046) forbids.

Fix, the same mechanism as signup (ADR-092):
- Inside the move transaction, **reserve the target atomically**: `findOneAndUpdate({ industryTemplateKey: target, status: { $in: [DRAFT, PUBLISHED] } }, { $inc: { referenceVersion: 1 } })` in the active session, with `timestamps: false`. No match → `422 INDUSTRY_TEMPLATE_STATUS_INVALID` (retired) or 404 (gone). Then compare kinds and modules against the reserved document.
- Retire and PATCH already write that document inside their transactions, so each pair conflicts and the retry decides again: the PATCH now counts one user and refuses the removal, and the move sees the retired status.
- Tests in the style of the signup race, both with a failing-before proof (paste the output, restore):
  - a move and a retire of the target: never "moved onto a template retired before the move committed"
  - a move onto an unused DRAFT and a PATCH that removes `booking` from it: either the PATCH is refused (422 with `details.removed`), or the move is refused because the target no longer contains `booking`; never both commit

**R1-2 · MAJOR · a locked template may change an existing field's type.** The additive diff lists removed fields and options, but a field that stays may change `fieldType` (and `referenceEntity`). `09 §4.6`: "`fieldType` cannot change once values exist." A PUBLISHED or used template is exactly the case where values may exist. Changing `weight_kg` from DECIMAL to TEXT would make every stored value fail 2.3's builder.

Fix:
- On a locked template, a kept field whose `fieldType` or `referenceEntity` differs is listed as `fieldType:<entityType>:<offeringKind>:<fieldKey>` (and `referenceEntity:…`) in `details.removed`, which gives the same 422.
- A link change (`link.relationKey`) is listed the same way.
- Label, options added, `isRequired`, visibility and the other flags stay editable.
- Unit cases in `additive-change.test.ts`, plus one API case.
