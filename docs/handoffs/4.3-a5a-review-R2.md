## 2. Findings

### 1. Blocker — the live storefront checkout creates fabricated requests, not orders/bookings/enrollments
`apps/api/src/routes/storefront-checkout-router.ts:58-83`, wired at `apps/api/src/routes/storefront.ts:241-248`

`buildStorefrontCheckoutRouter` falls back to `buildFallbackLink`, which returns `requestId: newId()` with a made-up status ("PLACED"/"HELD"/"PENDING") when `publicOrders` / `publicBookings` / `publicEnrollments` are absent. `storefront.ts` never passes them, so every real `POST /storefront/orgs/:org/checkout` writes a `Checkout` and `CheckoutRequestLink`s that point at IDs that exist in no order, booking or enrollment collection. The guest receives `201` with a fake `orderId`; `readOrderStatus` then finds nothing and the tracking API echoes the fabricated link status forever. Nothing in the handoff or STATUS records this gap; the plan (`docs/plans/4.3.md:918`) explicitly requires this adapter to wire the sales/booking/enrollment `Public*Commands`.

Failing scenario: a shopper completes a product checkout on a real domain. `POST /checkout` returns 201 with `requests[0].requestId`. `GET /me/requests` shows a `PLACED` order. The sales dashboard, stock ledger and payments have no such order. This is mock data presented as finished (AGENTS.md "No TODO, stub, mock data"; plan A5A table row).

Fix: build the real commands in the composition root — `buildStorefrontOrderCommands(buildSalesDependencies(buildSalesTenantPorts(...)))`, `buildStorefrontBookingCommands(...)`, `buildStorefrontEnrollmentCommands(...)` — pass them into `buildStorefrontCheckoutRouter` from `storefront.ts`, delete `buildFallbackLink` and make the three command options required. Add one integration test that mounts the production composition and asserts a real order row (public number, stock reservation) exists after checkout.

### 2. Blocker — the live quote prices checkout with stubbed money values (hardcoded deposit, delivery, zero tax, literal BDT)
`apps/api/src/routes/storefront-checkout-adapters.ts:73-103`

`buildCatalogQuoteReaderAdapter.priceSelections` computes every line as `subtotal = total = unitPriceMinor * quantity`, with `discount = tax = 0`, `amountRequiredBeforeConfirmation = Math.min(lineTotal, 1000)`, `deliveryCharge = 60` whenever the fulfillment is delivery/courier, `currency` initialised to the literal `"BDT"`, and `configVersion: 1`. This adapter is the production default in `buildStorefrontCheckoutRouter` (`storefront-checkout-router.ts:159`), so the quote shown to customers and the `acceptedTotals` stored on `Checkout` contain invented amounts.

Failing scenario: an organisation with 120 BDT delivery, a 10% promotion and a 25% deposit on a service quotes the customer 60 BDT delivery and a flat 1000 BDT upfront, and `Checkout.acceptedTotals` stores those numbers. It also violates ADR-013 ("no `BDT` literal") and the plan's "prices lines via server pricing".

Fix: price through the real pricing source (the same routine the sales/POS path uses) and take `currency`, `deliveryCharge`, discounts/tax, upfront amount and `configVersion` from it. No literal currency and no magic 1000/60 values. If no such source exists yet, stop and ask for an ADR rather than shipping the stub.

### 3. Must-fix — `/me/requests` is still an N+1 read path
`apps/api/src/modules/commerce/website/application/read-own-requests.ts:180-189`; readers at `apps/api/src/routes/storefront-checkout-adapters.ts:145-151, 180-186, 204-210`

The page is bounded, but each item costs two queries: `findById`/`find` on the request store plus `summaries.findByRequest`. A full page (limit 100) issues up to 200 sequential-ish queries per list request (`Promise.all` only parallelises within the page). AGENTS.md hard rule: every list endpoint has "No N+1 queries". The plan's A5A also claims "without leaking … a bounded database pagination and no N+1 reads" fix.

Failing scenario: a guest with 100 past requests opens `/me/requests`; the API performs ~200 reads and the storefront list latency grows with page size.

Fix: batch per request type with `findByIds`/`$in` on orders/bookings/enrollments and one `findByRequests([...])` payment-summary query, then join in memory by ID. Add a test that asserts one query per collection per page.

### 4. Must-fix — the list path ignores `CheckoutAccess.revokedAt`, and nothing ever writes `CheckoutRequestLink.revokedAt`
`apps/api/src/modules/commerce/website/infrastructure/mongo-checkout.repository.ts:253-278` (filter), `:202-212` (`revoke`), `:280-304` (`transferOwner`)

The denormalisation contract is "link owner mirrors `CheckoutAccess`". Detail and claim check `accessRecord.revokedAt !== null` (`read-own-requests.ts:229`, `claim-checkout.ts:125`), but `listByOwner` filters only the link's `revokedAt`, and neither `revoke()` nor any A5A code writes `revokedAt` on links. Today `revoke()` has no caller; A5B's erasure participant will call it, and from then on an erased/revoked checkout will still appear in `GET /me/requests`.

Failing scenario: A5B erasure revokes a customer's `CheckoutAccess` and scrubs the contact snapshot. `GET /checkouts/:id` correctly returns 403, but `GET /me/requests` still lists the checkout and its order number because the link's `revokedAt` is null.

Fix: in the same transaction as `access.revoke`, `updateMany` the checkout's links with `revokedAt`/`updatedAt`, or have `revoke()` own both writes. Add a test that revokes access and asserts the list is empty (the "revoked access denied" T1 line).

### 5. Must-fix — two planned test names are not backed by what their bodies assert
`apps/api/src/modules/commerce/website/checkout-tracking-claim.api.test.ts:436-492` and `:716-759`

- "projects enrollment payable amount using enrollmentPeriodId as payment requestId" (line 436): the test injects a fake `requestStatusReader` keyed by the enrollment's `requestId`; `enrollmentPeriodId` is only placed inside the returned `plan` object and is never used to look up a payment summary. The actual requirement (the adapter must query payment summaries with `currentEnrollmentPeriodId`, ADR-139) is not exercised. A regression back to `requestId` would still pass.
- "preserves immutable creationPrincipalKey and does not merge contacts or rewrite historical orders on claim" (line 716): it asserts the `Checkout` document only. No order/booking/enrollment row or request link is read before/after the claim, so "does not rewrite historical orders" is not verified.

Fix: unit-test `readEnrollmentStatus` with a payment summary stored under `currentEnrollmentPeriodId` and a decoy summary under `enrollmentId`, asserting the former's due amount. In the claim test, create a real request link/status snapshot and assert requestId, status and payment amount are unchanged after claim.

### 6. Must-fix — the new pagination test does not fail on the pre-fix implementation
`apps/api/src/modules/commerce/website/checkout-tracking-claim.api.test.ts:395-434`

The test creates two checkouts with one link each and asserts page 1/2 and `total`. The pre-fix code (load all access records → load all links → filter → sort → `slice`) returns exactly the same responses for this data. So the test name "applies request type filters in the database query" is not proven and the blocker-2 fix has no regression guard.

Failing scenario: revert `listByOwner` to the in-memory implementation and this test still passes; a regression that reloads every link of every checkout would merge unnoticed.

Fix: add a repository-level test (or a spy on the Mongoose model) asserting the query object passed to `countDocuments`/`find` contains `organizationId`, `ownerType`, `ownerIdentifier`, `revokedAt: null`, the `requestType` filter, and `skip`/`limit`; or seed a checkout with more links than the page size and assert only `limit` items were fetched.

### 7. Must-fix — cross-organisation proof covers detail only
`apps/api/src/modules/commerce/website/checkout-tracking-claim.api.test.ts:536-554`

The only cross-org test is a guest from org B reading an org A checkout detail (404). It would also pass before the fixes, because `findByCheckoutId` was already organisation-scoped. There is no test for `GET /me/requests` (org B cookie against org B path must not list A's links) and no test for `POST /checkouts/:id/claim` in org B. The completion-check's blocker 4 therefore remains partly open.

### 9. Minor — checkout-enabled fallback contradicts the manifest default
`apps/api/src/routes/storefront-checkout-adapters.ts:252`

`Boolean(resolved.config.settings["website.checkoutEnabled"] ?? true)` fails open; the manifest declares `systemDefault: false` (`website/module.manifest.ts:79-82`). The resolver normally supplies the default, so this is currently dead, but any resolver/settings change that omits the key silently enables checkout. Use `?? false` and preferably read the typed resolved setting rather than casting.

### 10. Minor — pre-existing `as unknown as` casts remain in the read path
`apps/api/src/modules/commerce/website/infrastructure/checkout-mappers.ts:18, 37, 56, 70`

`toCheckoutRequestLink` (line 70) is now on the `/me/requests` read path and still uses `doc as unknown as WithAudit`. This is pre-existing A4 code, not introduced by this branch, so it does not reopen blocker 3, but the T1 checklist line ("no `as unknown as` in the new/changed read path") is not literally met. Type the stored documents with `createdAt/updatedAt` (`WithTimestamps`) instead of casting.

### 11. Minor — `transferOwner` cannot report a missed link transfer
`apps/api/src/modules/commerce/website/infrastructure/mongo-checkout.repository.ts:280-304`

`updateMany` returns nothing and the caller ignores `matchedCount`. Today a checkout always has at least one GUEST link when the access check passes, but if a link were ever written with a different owner (data repair, future path) the claim would commit the access transfer while leaving guest-owned links behind — the guest would keep seeing the request in `/me/requests`. Return `matchedCount` and throw `CONFLICT` inside the transaction when it is zero.

### 12. Minor — public response contract uses `unknown`
`packages/contracts/src/website/checkout-contracts.ts:247-254`

`StorefrontRequestDetailResponse` declares `items?: readonly unknown[]`, `schedule?: unknown`, `plan?: unknown`, `fulfillment?: unknown`. This defeats compile-time redaction guarantees: any adapter can put internal fields there and TypeScript will accept it. Use concrete safe DTOs (`StorefrontOrderItem[]`, schedule `{ startsAt, endsAt }`, plan `{ startsOn, endsOn }`, `StorefrontOrderFulfillment`).

### 13. Minor — 403 for a foreign request in the same organisation reveals its existence
`apps/api/src/modules/commerce/website/application/read-own-requests.ts:220-244` via `:200-209`

`getRequestDetail` loads the link first, then authorises. A customer who guesses another same-org request ID gets 403 (exists) instead of 404 (not found). Not cross-org, but it is an existence oracle. Return `NOT_FOUND` for owner mismatch as well, as the storefront tracking surface has no reason to distinguish.

## 3. T1 checklist walk (concrete scenarios)

**Tenant / location isolation**

**Authorisation / claim**
- Claim route requires a valid customer token for the same organization (`storefront.ts:278` mounts `customerAuthOptional`; `authenticate-customer-optional.middleware.ts:28-35` checks `claims.organizationId` and active account) plus a parsed `sf_guest` cookie (`checkout.router.ts:230-233`). Holds.

Comparison is against `checkout.contactSnapshot.phoneE164`. Holds (test line 655).
- Revoked access denied: detail and claim check `revokedAt`; the list does not (finding 4).
- Replay authorisation after claim: `buildAuthorizeReplay` compares the access owner with the caller principal, so a guest replay after claim is 403 (`storefront-principal.middleware.ts:104-127`; test line 643). Holds.
- No phone-only recovery: route rejects a missing/malformed cookie with 401 before any lookup (test line 700). Holds.
- Claim atomicity: `updateOwner` (CAS on `version`) and `transferOwner` and the outbox publish run inside `unitOfWork.run` (`claim-checkout.ts:56-83`), which is a real `withTransaction` (`kernel/db/unit-of-work.ts:7-11`, `with-transaction.ts:106-123`). A failed link transfer or event write aborts the access update; a stale version returns 409. Holds. Residual: no `matchedCount` check (finding 11).

**Caching** — `Cache-Control: private, no-store` set on detail, list, request detail and claim (`checkout.router.ts:151, 177, 197, 224`); the org surface cache guard also forces it. Holds (test asserts detail/list).

**Code hygiene** — no `any`, `console.*`, empty `catch`, TODO/FIXME in the diff; ESLint clean. `read-own-requests.ts` casts are gone. Holds (residual pre-existing mappers casts, finding 10).

**Pagination** — limit capped by schema (`pagination.ts:7-12`) and code (`read-own-requests.ts:170`); deterministic sort `{ createdAt: -1, checkoutRequestLinkId: 1 }`; `total` from the same filter; `requestType` in the DB filter; index starts with `organizationId` (`checkout.schema.ts:85-92`). **Safe projection** — order lines are exactly `{ name, quantity, unitPrice }`, fulfillment is `{ method }`; the unit test compares with `toEqual`, so an extra field fails. Booking/enrollment expose only schedule/plan dates. Holds.
