## 1. R1 blockers — closed

### B1 · outbox delivery

R1: `RecordingQueue` was constructed and never inspected; `website.checkout.created` has `consumes: []`, so `DISPATCHED` proved enqueue-at-all, not delivery.

At this head:

- `OutboxDispatcher.dispatchBatch` drains until **this** org has zero `PENDING` rows (`dispatchUntilOrgQuiet`, `:570-587`). A zero-claim batch while this org still has `PENDING` throws. Catch-up clock (+24h) is the in-process stand-in for the worker waiting on `nextAttemptAt` / `lockedUntil` (comment `:562-567`).
- Jobs are recorded, then filtered by `organizationId` (`dispatchAndDeliverThisOrg`, `:593-604`).
- First handler run is `processOrganizationOutbox` → `runEventHandler` (the worker's exactly-once runner). Replay of **the recorded jobs** must be `ALREADY_PROCESSED`.
- `assertOutboxDelivery` (`:627-654`) keys rows by **this** `checkoutId` / `orderId`, not a global count:
  - `website.checkout.created` for this checkout is `DISPATCHED`, `handlersFor` length 0, **zero jobs** (does not pretend a consumer ran).
  - `sales.order.placed` for this order is `DISPATCHED`, `handlersFor.length > 0`, at least one job with `eventId` / `type` / `handlerKey` / `organizationId`.

That is delivery of an event that has consumers, plus an honest zero-consumer read-back for checkout.created. Not a stub.

**Nit (not a reopen):** the first handler invocation is `processOrganizationOutbox` walking Mongo, not `for (job of queue.jobs) runEventHandler(job)` as the first pass. The recorded jobs are the replay proof. Same runner, same four-field `EventJobData` the worker consumes. Acceptable.

### B2 · unpaid hold through the worker

R1: `buildExpireHoldsJob(...).run(...)` in-process; no second run.

At this head `runExpireHoldsJob` (`:768-774`) is `runScheduledJob(jobRegistry.find("booking.expireHolds"), { clock: harness+1h, effectiveness })`. That is the same function the BullMQ worker calls (`kernel/jobs/job-queue.ts`). The job itself uses the runner's `now` argument (`expire-holds.job.ts:89-90` `listHeldExpired(now)`), not a hidden wall clock.

Second run (`:1046-1057`): status still `EXPIRED`, **version unchanged**, unpaid slot used = 0, paid booking still `CONFIRMED` with its slot used = 1. "Once" is proven.

No Redis/BullMQ process is started. That is how every other API scheduled-job test in this repo works; R1 asked for the production **entry**, not a live queue.
