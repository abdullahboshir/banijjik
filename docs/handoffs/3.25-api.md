# Card 3.25 · Local business dates and held advances (handoff)

Tier: **T1** (API only) · Branch: `s/3.25-posting-dates-advances` · Based on commit: `origin/main 460731c0`

## What was built

1. **Booking business date (`booking-posting-source.ts`):**
   - Completed bookings use `businessDateOf(booking.endsAt, timeZone)`: service revenue is recognized on the date the service ends in the organization's timezone.
   - Cancellation-fee and no-show entries use the status change timestamp (`booking.updatedAt`) in the organization's timezone. `history[]` cannot be used: only reschedules append an entry, so a cancelled booking has none (lead decision, 2026-10-24); every transition writes `updatedAt` and both statuses are terminal, so nothing re-dates it afterwards.
   - The organization timezone is read from the required `timeZone` reader port (no fallback literal).

2. **Held advance reader (`commerce/payment`):**
   - New port `RequestAdvanceReader` in `payment/application/ports/request-advance-reader.ts`:
     ```ts
     export interface RequestAdvanceReader {
       readHeldAdvance(input: {
         readonly organizationId: OrganizationId;
         readonly requestType: PaymentRequestType;
         readonly requestId: string;
       }): Promise<Money>;
     }
     ```
   - Mongo implementation in `payment/infrastructure/request-advance.reader.ts`, exported as `buildRequestAdvanceReader(): RequestAdvanceReader` from `payment/index.ts`.
   - Backed by compound multikey index on `payments`: `{ organizationId: 1, "allocations.requestType": 1, "allocations.requestId": 1 }`, reading with projection `{ direction: 1, allocations: 1, _id: 0 }`.
   - Computes net `BEFORE_REVENUE` money: `IN` allocations minus `REFUND` and `REVERSAL` allocations. Clamped to `Math.max(0, netMinor)`. Allocations marked `AFTER_REVENUE` are excluded.
   - Query works unchanged for `BOOKING`, `ORDER`, and `ENROLLMENT`.

3. **Booking posting snapshot (`booking-posting-source.ts`):**
   - Sets `advancesToSettle` to `readHeldAdvance({ organizationId, requestType: BOOKING, requestId: bookingId })`.
   - Unpaid required deposits settle 0 (no `booking_completed_settle_advances` entry is drafted, matching `draftBookingCompleted`). Overpayments or partial advances before the visit settle the exact advance held.

4. **Credit local business dates (`commerce/credit`):**
   - `credit/application/use-cases/business-date.ts` now accepts `(now: Date, timeZone: string)` with no UTC fallback.
   - Wired via `CreditDependencies.timeZone` through `buildOrganizationTimezoneReader()` from `modules/core/organization/index.js`.
   - Every caller passes the organization timezone: `adjust-credits.use-case.ts`, `verify-credit-purchase.use-case.ts`, `unlock-listing.use-case.ts`, and `expire-credits.use-case.ts`.

5. **Records:**
   - ADR-124 amendment added in `docs/04-DECISIONS.md`.
   - Module `README.md` updated for `booking`, `payment`, and `credit`.
   - `docs/STATUS.md` updated for row 3.25.

## Deviations from plan (and why)
1. **Cancellation-fee and no-show dates come from `booking.updatedAt`, not `history[].at`.** The plan assumed the transition history records every status change; it records reschedules only (`booking-transition-apply.ts` builds an entry solely when `input.reschedule` is set), so a cancelled booking has no history and a rescheduled-then-cancelled one would be dated at the reschedule. `updatedAt` is written with the transition instant on every action and both statuses are terminal. Decided with the lead on 2026-10-24 (the plan's own "if the history has no time, stop and ask").
2. **`RequestAdvanceReader.readHeldAdvance` takes `currency`.** The plan's snippet had no currency; the T1 review fix (§11 item 3) made the caller name the request's currency instead of assuming `BDT`, and the adapter refuses an allocation in another currency with `INTERNAL`. The booking source passes `booking.price.currency`. Test: `refuses an allocation in another currency instead of assuming one`.
3. **The adapter reads with `find` + projection and sums in code**, not an aggregation pipeline: the multikey index `{ organizationId: 1, "allocations.requestType": 1, "allocations.requestId": 1 }` serves the filter, the projection keeps `direction` + `allocations` only, and each returned row is one payment.
4. **`buildBookingPostingSourceAdapter()` keeps its zero-argument signature** so `routes/accounting-event-handlers.ts` and the existing handler tests compile unchanged; the booking module supplies the payment reader and the time zone reader from `booking/index.ts`.
5. **The booking time zone comes from the existing `buildOrganizationTimezoneReader()`**, which is what the plan named; that reader falls back to `Asia/Dhaka` when an organization row has no timezone (pre-existing behaviour used by the whole booking module). The credit path has no such fallback: its port must return a zone or the router answers `404`.
6. **ENROLLMENT and ORDER work unchanged** with the same reader (it is keyed by `requestType`/`requestId` only). This card registers `BOOKING`; ORDER registration is card 3.24.

## Lead review fixes (2026-10-24, T1 review)
The review found four small items; the lead fixed them on the branch (guide §10 leftovers rule):
1. `request-advance.reader.ts` assumed `CURRENCY_CODE.BDT` when a request had no allocation (§11 item 3). The reader now takes the request's `currency` from the caller (the booking price) and fails with `INTERNAL` on an allocation in another currency. Test: "refuses an allocation in another currency instead of assuming one".
2. `ExpireCreditsUseCase.execute()` fell back to a random `newId()` organization when none was passed (its time zone read would fail or read the wrong organization). `organizationId` is now a required input.
3. `AdjustCreditsUseCase` read `String(getRequestContext().organizationId)`, which turns a missing organization into `"undefined"`. New `credit/application/use-cases/active-organization.ts` throws instead.
4. **Bug introduced by the local business date:** the daily unlock limit counted `unlockedAt` inside the **UTC** day of the local date string, so between 00:00 and 06:00 Dhaka time it counted the wrong day and the limit did not hold (two `credit-api.test.ts` cases failed when run at 05:48 Dhaka; CI ran in the afternoon). New `businessDayBounds(businessDate, timeZone)` gives the local midnights; `countByCustomerToday` takes `{ from, to }`. Tests: "bounds a Dhaka business day by its local midnights, not the UTC day", "keeps a DST day at its real length".

Follow-up (not in this card): `ExpireCreditsUseCase` is not registered as a scheduled job anywhere, so credit expiry never runs in production (gap from M.4). Written to the lead state.
