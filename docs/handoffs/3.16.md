# Handoff: card 3.16 dead-letter replay race fix

Branch `s/3.16-dead-letter-replay-race` · Implemented by Sonnet 5.5 · Plan `docs/plans/3.16.md`

## What was built
- `apps/api/src/kernel/events/dead-letter-replayer.ts` only. `requeue` now reads the old job with `job.getState()` and follows the plan table through a small private `decideRequeue(state)`:
  - no job or `unknown`: enqueue, REPLAYED
  - `failed`: remove, enqueue, REPLAYED
  - `completed`: REPLAYED without enqueue
  - `active`, `waiting`, `delayed`, `prioritized`, `waiting-children`: nothing, row stays REPLAY_REQUESTED, debug log `events.dead_letter_replay_deferred` (fields `eventId`, `handlerKey`, `jobState`)
  - any other state: treated as "still in queue", logged at warn
- `requeue` returns a private `RequeueOutcome` (`QUEUED`, `ALREADY_RAN`, `OLD_JOB_STILL_IN_QUEUE`); `tryRequeue` returns true only for `QUEUED`, so `replayPending` counts only jobs it queued. A deferred row is neither reported nor counted. The REPLAYED write moved into `markReplayed` and keeps its `status: REPLAY_REQUESTED` filter.
- No change to the worker, `dead-letter.ts`, admin, schema, contracts, API or screens.

## Deviations
None. Small notes: the info log of the REPLAYED write now says "failed event handler replay done" (it also covers the ALREADY_RAN case); the test helper `requestedReplay` got optional `eventId` and `handlerKey` parameters.

## Tests (`dead-letter-replayer.test.ts`)
Existing four unchanged and passing. New:
- does not mark a replay REPLAYED while the old job is still active (commit 94266f0d)
- queues the replay on the next poll once the old job has failed
- leaves a replay waiting while the old job is waiting / delayed / prioritized / waiting-children (`it.each`)
- marks REPLAYED without adding again when the replayed job already completed
- treats an old job in state unknown as gone and queues the replay
- waits, and never marks REPLAYED, when the old job is in a state it does not know (extra, covers the plan's risk note)
- real Redis (`describeWithRedis`, own prefix): a replay asked for while the last attempt is still running is carried out after the job fails. A bare BullMQ worker blocks inside the job on a promise the test controls; the test writes the FAILED row and asks for the replay while the job is `active` (the gap), checks 0 queued, REPLAY_REQUESTED and one active job, then lets the job fail and checks REPLAYED and that the fresh job with the same ID completes. All waits use `waitFor`.
