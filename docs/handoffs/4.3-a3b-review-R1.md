## 2. Invariant & Architecture Checklist

- [x] **Storefront hold creation:** Booking is created in `HELD` status with `holdExpiresAt` when a deposit is required (`depositRequired.amount > 0`).
- [x] **Zero-deposit bypass:** When deposit is zero, booking directly transitions to `REQUESTED` (if `requireApproval` is true) or `CONFIRMED` (if `requireApproval` is false) with an atomic booking number drawn from `SEQUENCE_KEY.BOOKING`.
- [x] **Payment Fence concurrency:**
  - `beginReceipt` increments `paymentFenceVersion` to fence out concurrent hold expiration.
  - Expiry job skips any hold where `paymentFenceVersion > 0` or version mismatch.
  - Payment is rejected if hold is expired (`now >= holdExpiresAt`) before payment begins.
  - Payment is rejected if booking is in a terminal status (`CANCELLED`, `COMPLETED`, `EXPIRED`).
- [x] **Atomic termination & refund:** Expired holds with partial advance settle via `settleBookingTermination` with fee `NONE` (full customer refund), release capacity, and publish outbox events.
- [x] **Deposit completion transition:** `endReceipt` transitions `HELD` booking to `REQUESTED` or `CONFIRMED` once required deposit is satisfied.
- [x] **Multi-tenancy & Isolation:** Enforces organization-enabled kinds and cross-organization isolation on location.
- [x] **Code Quality:**
  - Zero TODOs, stubs, mocks in production code, or commented-out blocks.
  - All files <= 300 lines (longest production file is `storefront-booking-commands.ts` at 279 lines).
  - All functions <= 60 lines.
  - Nesting depth <= 3, cyclomatic complexity <= 10.
