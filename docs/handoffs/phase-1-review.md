## Verdict: PASS WITH FIXES

Every required command passes, every roadmap "Done" line is met (three of them only through test-only wiring, see the checklist), and both real-browser suites pass.

It is not a clean pass: **2 BLOCKER, 5 MAJOR, 24 MINOR**. Both blockers are access-control defects that I reproduced against the real app on a real replica set:

- the platform admin seed turns an account that somebody else registered first into a `SUPER_ADMIN`, with that person's password (B1);

### Unverified suspicions (not findings)

- **Role archive against a concurrent assignment.** Read: archive writes the role and the organization document; a member PATCH writes the member and the named locations. No document is written by both, so under snapshot isolation both should commit and an ACTIVE member would hold a just-archived role. Not reproduced (timing-dependent). The safe direction (an archived role grants nothing).
- **Referer leak of the invitation token** from the admin page `/invitations/[token]` to any third-party resource. Not checked in a browser.
- **Storefront subdomains (Phase 4).** If `COOKIE_DOMAIN` is a parent domain and tenant storefronts live on sibling subdomains, the httpOnly access cookie (`Path=/`) is sent to tenant-controlled hosts and SameSite no longer separates them; the origin check would be the only CSRF defence. Needs a decision before 4.2.
- **MongoDB 8.0.13.** All runs here and in every handoff used 8.2.5. The `$in` partial index on `platform_subscriptions` is still unproven on the pinned version.
- **BullMQ under a long Redis outage.** Each dispatch retry leaves one more command in the ioredis offline queue (`maxRetriesPerRequest: null`); not measured.
- The first GitHub Actions run and the SIGTERM spawn test have still never happened.

## Security of the access stack (what was attacked, and the result)

| Area | Result |
|---|---|
| Sessions and refresh | Rotation and the successor insert share a transaction; rotation is checked before expiry; reuse after the 10 s grace revokes the family; a refresh token works only for its own audience; refresh re-checks the user (and the operator on the platform). Known and accepted: an access token lives up to 15 min after logout, logout-all or removal of a user; member status is checked on every tenant request. **M5.** |
| Two audiences and cookies | One HS256 secret, separated by `aud` (`admin` / `platform`) and by cookie name. `authenticatePlatform` also reads the operator row on every request. The browser suite confirms that neither session opens the other app. Cookies are httpOnly, SameSite=Lax, Secure in production. |
| CSRF / origin check | `createOriginCheck` is mounted in `app.ts:70` before every route, so it covers `/platform/*` and `/invitations/*/accept`. An unsafe request without an `Origin` header passes by design (non-browser clients). `POST /auth/logout` has no limit and no auth (harmless). |
| Rate limits | Login per IP and per identifier, register, refresh, platform login/refresh in their own buckets, invitation preview per IP, accept per user, organization create per user. **M6, M7, M8, M9.** In production they need J4. |
| Tenant isolation | Every normal read, write, count, aggregate, bulk and document operation is filtered, stamped or refused (57+ tests, re-run).
