## What was built

- Till search and cart show SERVICE rows with a small service badge. A service line uses a whole-number stepper (no weight keypad) and a lazy "Done by" picker from `GET /sales/performers?locationId=` for the device location. `POST /pos/sales` sends `performedByMemberId` when set. The receipt prints the performer's display name under the line.
- Admin offering search includes SERVICE only in instant-sale mode (`form.isInstant` on new order, and the exchange's new-goods step). Draft and placed order editors stay product-only. The existing performer picker is unchanged.
- BN and EN keys: `pos.sale.kindService`, `pos.sale.performedBy`, `pos.sale.performerNone`, `pos.sale.performerLoadFailed`, `pos.sale.performerUnknown`, `orders.line.kindService`.

## Deviations from the plan (and why)

1. No weight keypad exists on the till (card 3.42 leftovers). Service lines use the same whole-number stepper as products; `quantityControlOf` / `usesWeightKeypad` lock services off a future keypad.
2. Local admin browser suite not run: port 4000 is the lead `banijjik` API. CI runs the suite.
3. Exchange new lines also search services, because they go through the instant prepare (decision 13: instant-sale mode, not draft/placed).
