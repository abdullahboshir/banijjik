- **Deviations from plan (and why):**
  1. **Retry is split by label.** `TransientTransactionError` repeats the whole attempt (backoff 50/200/800 ms, `maxAttempts` default 3). `UnknownTransactionCommitResult` repeats only `commitTransaction()` (same backoff and cap), never the work. The plan and manoxen say both labels retry the attempt, but in manoxen the driver's `session.withTransaction` retried the commit internally. Re-running the work after a commit that may have succeeded could write twice (sequence numbers, money). Transactions are driven manually (`startTransaction`, work, `commitTransaction`) so the backoff and attempt count are exact; the commit-retry path is tested with a fake session (`transaction-retry.test.ts`).
  2. **Extra startup step `initializeModels()`** (not in the plan): compiles every registered model and awaits `init()` (collection and indexes) right after connecting. Without it the first transaction could race with the background index build. Tests call it too.
  3. **Extra check:** `DB_TENANT_SHARED_URL` must name a different database than `DB_PLATFORM_URL` (the same name would mix collections).
  4. **The `/ready` 503 body is written by a small `createReadyHandler` (kernel/http)**, not the error handler, because the error handler maps INTERNAL to 500.
  5. **`updateVersioned` takes an optional `session`** and defaults to the active transaction session.
  6. **`isDatabaseReady(timeoutMs, probe)`** has an injectable probe so the timeout and failure paths are tested without breaking the server.
  7. **R26 scope follows the plan's glob** (domain, application, presentation; platform application and tests exempt). See open question 2.
