## 2. False-pass hunt (R2 required)

These were the ways the R1 FAIL could have been "fixed" on paper.

1. **Outbox not actually dispatched.** Not the case. `OutboxDispatcher.dispatchBatch` → `claimNextEvent` → `queue.enqueue` per handler → `markDispatched`. Jobs are filtered to `job.organizationId === shop.organizationId`. `checkout.created` is asserted to have **no** jobs. `order.placed` jobs are keyed by this row's `eventId`. A zero-claim batch while this org still has PENDING **throws**.
2. **Handlers never run; ALREADY_PROCESSED is a no-op on an empty list.** Not the case. `processOrganizationOutbox` runs `runEventHandler` for every handler of this org's events (the same runner the worker uses). The recorded jobs are then replayed and must return `ALREADY_PROCESSED`. An empty `ours` would fail `placedJobs.length > 0`.
3. **RecordingQueue still never consumed.** True, and allowed: R1 asked to assert job shape **or** run the handler chain. This round does both. Jobs are not pulled through BullMQ; that is the same in-process pattern as other API scenario tests. Not a remaining blocker.
4. **expireHolds not through the scheduler.** Not the case. `runScheduledJob` iterates active orgs and passes `now`. Direct `job.run(...)` is gone.
5. **Amounts hardcoded without a quote.** Not the case. `quote()` hits `POST /quotes`; assertions read `quoted.lines` / `quoted.total`. Catalog create uses the same constants, so a mispriced kind fails.
6. **Cross-org not actually another org.** Not the case. `commerceShop` → `worldFor` → `createTwoOrganizations`; `shopOf` is org A; the negative call uses `shop.world.organizationB` and `locationB1`.
