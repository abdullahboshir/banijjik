## What was built

- **Order detail** (`apps/admin/src/sales/order-detail-client.tsx`, `order-action-bar.tsx`, `order-detail-page.tsx`): a "Return items" action for a COMPLETED order that still has goods to return and sits inside the return window, shown to a user with `sales.return.create` at the order's location. It opens the return sheet lazily. The order header shows the return status (no return, partly, fully) and a link to the order's returns.
- **Return sheet** (`return-sheet.tsx`, `return-line-card.tsx`, `use-return-sheet.ts`, lazy `lazy-return-sheet.tsx`): one line per sold line with sold, returned and left counts; a quantity stepper capped at what is left; a goods-state select (back on the shelf, damaged, never received); a delivery-charge switch; reason and note (note required for OTHER); the server preview (value, due reduced, refund); the refund method and the mobile-money reference only when a refund is due; the PIN dialogs; one `Idempotency-Key` per submit (a retry of the same body reuses it). On success it opens the return detail.
- **Returns list** `/[orgSlug]/returns` (server page, `returns-list-page.tsx`, `return-query.ts`): filters by order (from the order's link), from and to dates, one page of cards (limit 50). Menu entry `sales.returns` in the sales manifest (path `returns`, `sales.return.read`).
- **Return detail** `/[orgSlug]/returns/[salesReturnId]` (`return-detail-page.tsx`, `return-actions.tsx`): summary, goods, the reversal when there is one, and "Reverse return" for an ACTIVE non-exchange return when the user holds `sales.return.reverse`. An exchange return shows a note instead.
- **Reverse sheet** (`return-reverse-sheet.tsx`, `return-payback-fields.tsx`, lazy `lazy-return-reverse-sheet.tsx`): reason (required), note (required for OTHER), and the payback switch only when the return refunded money (method, and the reference for bKash and Nagad). One approval PIN (`SALES_RETURN_REVERSAL`, the return value), one key per submit.
- **Shared approval collector** (`return-approval-flow.ts`): asks for each PIN in turn with the same approver list and resolves with the tokens. A return can need two PINs (refund, then not-received). Closing the sheet rejects with `ApprovalCancelledError`, which the caller ignores.
- **Model and API** (`return-model.ts`, `return-api.ts`): the pure rules (quantity caps, body building, approval steps from the preview, window check, refund-method choice) and the five endpoint calls.
- **Shared admin changes (add-only):** `order-approval.tsx` exports `ApprovalDialogView` (the dialog takes the state and the handlers, no retry); `order-approval-dialog.tsx` takes that view.
- **i18n:** 94 `returns.*` and `orders.returnStatus.*` / `orders.returns.link` keys in `packages/i18n/src/catalogs/screens/{bn,en}.json`, plus `menu.sales.returns`. The rule messages `errors.sales_return_*` already existed from A1 and A2.
- **API (one manifest entry and test lists):** `apps/api/src/modules/commerce/sales/module.manifest.ts` adds the menu entry (order 10, so it sits right after orders). `me-config-menu-api.test.ts` (four lists) and `entitlement-api.test.ts` (one list) gained the `sales.returns` key where the role reads returns. No other expectation changed.

## Deviations (and why)

1. **Route `/returns`, not `/sales/returns`.** The admin menu paths are relative to the org (`orders` is `/[orgSlug]/orders`), so `returns` follows the same convention. The API path stays `/sales/returns`.
2. **Menu icon is `receipt`.** The UI icon set has no return glyph. Adding one touches the shared UI package, which this card does not own.
3. **Window hint from the business date.** `OrderResponse` has no `completedAt`, so the button uses `businessDate` plus `sales.returnWindowDays` (read from the settings, client visible). The server is the judge (`completedAt` rule, 422 `SALES_RETURN_WINDOW_CLOSED`). A return on the last day of the window stays open; the day after closes it.
4. **Preview with placeholders.** The server refuses a preview that refunds money without a method, and a preview needs a reason. The sheet previews with CASH and CHANGED_MIND until the staff member chooses. Neither changes an amount; the real choice is sent on submit only.
5. **Two PIN dialogs for one submit** (refund, then not-received), asked one after the other. The PIN text stays in the field between the two dialogs (the dialog is not remounted). Known gap, see below.
6. **Shared `order-approval-dialog` props** narrowed to `ApprovalDialogView` (the order flow's `attempt` is not needed by the dialog). The order screens' behaviour is unchanged.

## Known gaps

- `OrderResponse` carries no `completedAt`: the window hint uses `businessDate` (see deviation 3). A return on the boundary day may be shown the button and then refused by the server, or the reverse.
- The PIN text stays in the field between two PIN dialogs of one return (deviation 5).
- The returns list filters by business date, not by completion date.
- Exchange (B2) is not built; the order and return detail show the exchange note only.
- `.claude/settings.json` in the main folder is not touched by this branch.
