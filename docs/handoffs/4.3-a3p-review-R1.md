## 2. Invariant & Architecture Checklist

- [x] **Transaction Ordering & Atomicity:**
  - `beginReceipt` executes inside `unitOfWork.run` prior to reading summary or checking allocation limits.
  - `endReceipt` executes inside `unitOfWork.run` after `updateSummaries` has persisted the payment allocation.
  - Any error or abort in payment processing automatically aborts the unit of work transaction, rolling back booking status transitions and payment fences.
- [x] **Dynamic acceptsPayments Gating:**
  - Terminal statuses (`CANCELLED`, `COMPLETED`, `EXPIRED`, `NO_SHOW`) report `acceptsPayments: false`.
  - Expired holds (`now >= holdExpiresAt`) report `acceptsPayments: false`.
  - Active holds and confirmed bookings report `acceptsPayments: true`.
- [x] **Pass-Through Request Lifecycles:**
  - Default lifecycles for `ORDER` and `ENROLLMENT` safely pass through without unnecessary side effects or blocking.
- [x] **Concurrency & Fence Isolation:**
  - `paymentFenceVersion` increment is conditionally restricted to `HELD` bookings, preventing optimistic lock conflicts on existing confirmed/requested bookings.
  - Cross-organization isolation is strictly enforced across reader, beginReceipt, and payment reception.
- [x] **Code Quality:**
  - Zero TODOs, stubs, mocks in production code, or commented-out blocks.
  - All files <= 300 lines (longest production file is `apps/api/src/modules/commerce/payment/application/use-cases/receive-payment.use-case.ts` at 311 lines with extensive JSDoc and helper functions).
  - All functions <= 60 lines.
  - Cyclomatic complexity <= 10.
  - Exact optional properties strictly typed.
