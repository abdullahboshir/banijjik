## Deviations from the plan (and why)

1. **Waiting device shows no code expiry.** The plan says "waiting for pairing, code expires …". The list response (`PosDeviceResponse`) has no `pairingExpiresAt`; only the create answer has it. The screen shows "Waiting for pairing" without the time. Adding the field is a contract change in part A's area, so it is left for the lead to decide. Known gap, also in STATUS.
2. **No Idempotency-Key on add.** The API route has none (a stored answer would keep the one-time code), so the screen sends none either. A lost answer followed by a retry can add a second device; the usage line shows it.
3. **List is paged (20 per page), not one long list.** The API is paginated; the screen has previous/next links with `?page=`. The plan did not name a page size.
4. **The browser suite was not run on this PC.** Port 4000 (the browser stack's API) and port 3000 are held by a dev stack from the lead's folder (`banijjik`, node PIDs 964 and 5668). The browser stack then gets `origin_not_allowed` from that API. This card must not stop another folder's stack, so the browser test is left for CI. The browser test file is written and lints and typechecks. CI is the judge (rule 6 of the card).
5. **State sentences are not an enum.** The state is a presentation sentence built from `status`, `pairedAt`, `lastSeenAt` and `isAwaitingPairing`. No new contract enum was added.
6. **Times** ("last seen", "code expires") use the browser's time zone (`Intl.DateTimeFormat` with the user's locale). The business time zone is not used here.
