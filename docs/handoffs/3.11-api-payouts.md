## Deviations from the plan (and why)
1. **Posting drafts live in `accounting/domain/commission-posting-rules.ts`, not at the end of `posting-rules.ts`.** `posting-rules.ts` was at the 300-line `max-lines` limit; the new drafts and snapshots would have made it 320. The new file reuses `journal-lines.ts` and `METHOD_ACCOUNT_CODE`. `accounting/index.ts` re-exports the drafts and snapshot types.
2. **A BKASH or NAGAD payout without a reference answers 400 `VALIDATION_ERROR`, not 422.** The plan says 422; the project's request validation answers 400 (A1's rule tests assert the same). The rule sits in `commissionPayoutCreateRequestSchema`.
3. **The claim, the preview and the sum filter on the organization currency** (`amount.currency`), and `expectedTotal.currency` must equal it (`errors.commission_currency_mismatch`, reused). The plan's claim filter has no currency; this only keeps a mixed-currency sum impossible. `CURRENCY_CODE` is only BDT today, so no behaviour differs yet.
4. **The router builder was split** (`mountPayoutRoutes`) because `buildCommissionTenantRouter` exceeded the 60-line function limit.
5. **`accounting.postCommission` registers only when `commissions` is supplied** (`AccountingHandlerDependencies.commissions?`), the same pattern as payments and bookings and as the plan ("registered only when a `CommissionPostingSource` adapter is supplied"). Guide §11 item 20 dislikes optional dependencies; this one is the plan's own design, and `routes/accounting-event-handlers.ts` always passes it.
6. **Admin bookkeeping label:** `JOURNAL_SOURCE_LABEL` is a `Record<JournalSourceType, …>`, so the new `COMMISSION` journal source needed a label (`apps/admin/src/bookkeeping/labels.ts`, bn/en `bookkeeping.sourceCOMMISSION`). Without it admin typecheck and build fail. No screen was added.
7. **The handler reads the payload with a small type guard** (`readIdField`), not the `as unknown as` cast of the older handlers (plan "Interfaces & types").
