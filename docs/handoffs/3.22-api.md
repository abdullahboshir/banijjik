# Card 3.22 · Ordered handlers follow whole streams

Implemented 2026-10-23 on `s/3.22-ordered-stream-follow`, part API. T1: **awaiting the lead's independent review**. Plan: `docs/plans/3.22.md`. Implementation commit: `df169f52` (rebased on `origin/main` `460731c0`).

## What changed

- `kernel/events/event-handler-registry.ts`: discriminated handler union; ORDERED handlers require a nonempty stream-prefix tuple; UNORDERED handlers forbid it. Registration rejects invalid or overlapping prefixes. `handlesType` and `followsStream` drive deduplicated type-or-stream fan-out.
- `outbox-dispatcher.ts`: passes type and ordering key to the registry, delivering every event of a followed stream.
- `handler-runner.ts`: after NEXT, unhandled types advance the position transactionally without calling the handler or writing a processed marker (`SKIPPED_NOT_HANDLED`). Keyed deliveries outside the handler's declared streams throw INTERNAL / `errors.event_handler_stream_mismatch` and follow normal retry/dead-letter handling. Earlier, ahead, module-off and keyless behavior remains covered.
- The three accounting handlers declare `booking:`, `paymentAccount:` and `expenseAccount:` respectively; their posting logic is unchanged.
- Contracts and BN/EN catalogs include the two stream error message keys. The shared module-contract test helper aliases `HandlerRunResult`, avoiding a second outcome union that would omit the new result.
- ADR-136 is **Accepted (proposed)** and ADR-115 points to its amendment. No new dependencies, endpoints, migrations or module behavior were added.
