# 3.8 Part B1 (payment screens) merge check R1

Reviewer: lead (Opus 5.5), 2026-10-23. Branch `s/3.8-ui-payments` at `6010cebd`, CI 39965073929 green. **Verdict: changes required.** The screens, routes, lazy sheets and budget checks (172.6 / 169.8 KiB) are in place; the items below break the plan's money rule, the i18n rule or give wrong results to a cashier.

## Must fix
1. **Float money math in the allocation editor.** `receive-payment-allocations.tsx:40-42` shows `amountMinor / 100` and parses with `Number(value) * 100`. That is float math on money (ADR-013, plan Refresh 2 item 4), and because the input is controlled by the parsed number the cashier cannot type a decimal ("12." becomes "12"). Keep the typed text in state and parse it with `parseMoneyInput(text, 2)`, as `refund-allocations.tsx` and `use-receive-payment-form.ts` already do. An invalid text must show a field error, not become `0`.
2. **The booking's receive sheet prefills the full price, not the due.** `booking-detail-payment-section.tsx` passes `amount: booking.price.total` and `initialDueMinor = booking.price.total.amount`. On a PARTIAL booking the cashier is offered the whole price again, and the excess silently becomes store credit or change. Prefill the due (`total − paid`). If the booking response has no paid or due amount, read it from `GET /dues?requestType=BOOKING&requestId=` (or stop and ask the lead if no read gives it; do not change the API). Test: a booking with a part payment opens the sheet with the remaining due.
3. **Users see raw message keys and English text.**
   - `formatError` in `use-receive-payment-form.ts` and `use-approval-dialog-state.ts` returns `error.messageKey` itself (the user reads `errors.payment_reference_taken`). Translate it as `use-store-credit-adjustment.ts` does: `t(knownMessageKeyOrInternal(failure.messageKey))`, and a 409 shows the reload label.
   - English literals shown to users: `"Amount must be greater than zero"`, `"Location is required"`, `"Payment failed"` (`use-receive-payment-form.ts`), `"Failed to load approvers"`, `"Approval failed"`, `"Refund failed"` (`use-refund-flow.ts`), `"Reversal failed"`, `"Failed to load approvers"` (`use-reversal-flow.ts`), `name: "Booking location"` (`booking-detail-payment-section.tsx`). Every one becomes a BN/EN key. For the booking location, pass the real location name the booking page already loads.
   - `receive-payment-allocations.tsx` shows `` `${alloc.requestType} (${alloc.requestId.slice(0, 8)}...)` ``: a raw enum and part of a UUID. Show a translated request type and the booking number (customer-facing numbers are never the UUID).
4. **Any 403, 422 or validation error opens the PIN dialog.** `isApprovalError` in `use-refund-flow.ts` treats `error.status === 422`, `=== 403` and `ERROR_CODE.VALIDATION_ERROR` as "approval needed". A refund above the paid amount or a permission denial must show its error, not ask for a PIN. Open the PIN dialog only for `ERROR_CODE.APPROVAL_REQUIRED`. Check the reversal flow for the same pattern. Test: a refund above the paid amount shows the error and no PIN dialog.
5. **Literals:** `requestType: "BOOKING"` → the contracts constant `PAYMENT_REQUEST_TYPE.BOOKING`; `setTimeout(..., 600)` in `use-receive-payment-form.ts` → a named constant with a reason, or drop it (the sheet already closes in `onSuccess`).
