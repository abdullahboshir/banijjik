## Deviations from the plan (and why)
1. **Money shape** is the plan correction above.
2. **A price override at a location needs a `variantId`.** The plan says `{ variantId?, isAvailable, priceOverride? }` and does not say what one price for every size would mean. An offering-wide row therefore only switches the offering on or off (`400` at `priceOverride` otherwise). Recorded in ADR-116.
3. **Variants without options are told apart by name** (case-insensitive). The plan says option values are unique; a salon's "short hair" and "long hair" variants have none, so the rule needed this second key.
4. **A SKU stays taken by an archived variant.** A partial unique index cannot skip array elements by status. To free a SKU, send the archived variant's id again with another SKU.
5. **The offering-limit counter** is a document that every create increments and compares through `LimitGuard.assertBelow` (the guard takes a count). The plan's "conditional `$inc`" would need the limit value inside the repository; this keeps the limit lookup in entitlement. Concurrent creates serialize on the document (tested at the edge).
6. **`depositRule` shape** was undefined in `11 §2`. It is `{ required: NONE|FIXED|PERCENT|FULL, value? }`, the shape of the `booking.deposit.*` settings, stored and not interpreted. Added to `11 §2`.
7. **Publishing re-checks references** (categories, add-ons, images must still be ACTIVE), because a published offering reaches the storefront and the bot.
8. **Sensitive custom fields** of catalog entities need `catalog.offering.update` at every location. The plan names no sensitive permission for the catalog.
9. **Audit action names** `catalog.availability.changed` and `catalog.addon.*` (the audit vocabulary test allows lower-case entity words only); the audit entity types are `offeringLocation` and `modifierGroup`.
10. **New file in `core/organization`** (agreed with the lead): `OrganizationCurrencyReader` port, `mongo-organization-currency.reader.ts`, and in `index.ts` two import lines plus one export block at the end (`buildOrganizationCurrencyReader`). 3.12 owns the rest of that module.
11. **Probe module key**: `test-support/module-contract/probe-modules.ts` used `MODULE_KEY.CATALOG` for a CORE probe; it now uses `MODULE_KEY.SALES` (agreed with the lead). Its comment names `sales` as the module that will replace it.
12. **Test-support additions:** `put` in the API test client (`auth-api-client.ts`), `fileOverrides` already added by 3.0 is used by the catalog tests, and `test-support/catalog-world.ts` (probe modules `booking` and `enrollment` that provide the SERVICE and PLAN kinds, since those modules are not built yet; `worldFor`).
13. **`@banijjik/contracts/catalog` subpath** with the domain lint exception and the new-module test aliases, as the plan and the wave table say.
