# 3.5b part B2 handoff (exchange screen, T2)

Branch `s/3.5b-ui-exchange` from `origin/main` (6e5ac596). Plan `docs/plans/3.5b.md`, "Refresh 3", section "B2 · Exchange screen" and its B2 tests. API from A3 (`POST …/orders/:orderId/exchange` and `/exchange/preview`), screens from B (return sheet, line cards, return approval flow).

## What was built

- **Order detail action.** "Exchange items" beside "Return" for a COMPLETED order with a customer inside the return window, shown only when the user holds both `sales.return.create` and `sales.order.create` at the order's location (`order-detail-page.tsx` `canExchange`, `order-detail-client.tsx`, `order-action-bar.tsx`).
- **Lazy sheet** (`lazy-exchange-sheet.tsx` → `exchange-sheet.tsx`), loaded only when opened. Three steps:
  1. **Return** (`exchange-steps.tsx` `ExchangeReturnStep`): B's `ReturnLineCard` (stepper capped at what is left, goods state), delivery charge, reason, note (required for Other).
  2. **New items** (`ExchangeNewLinesStep`): the instant sale's `OrderLinesEditor` and `OrderDiscountFields`, a live `LazyOrderQuotePanel`, the order note.
  3. **Summary and payment** (`exchange-payment-step.tsx`): the server preview (return value, new total, store credit used, store credit left, still due), payment lines (method, amount, bKash/Nagad reference), at most five.
- **Submit** (`use-exchange-sheet.ts` `useExchangeSubmit`): a fresh quote decides whether the new order's discount PIN is needed; the return's PINs (refund, not received) and the discount PIN are collected in order through B's `useReturnApprovalFlow`; one `Idempotency-Key` per submit, reused on a retry of the same body.
- **Result** (`exchange-result.tsx`): both numbers (new order total, store credit left) and links to the return and the new order. The sheet stays open on the result.
- **Pure rules** (`exchange-model.ts`): caps (`leftToPayMinor`, `clampPaymentMinor`, `clampedAmountText`), body building (`buildExchangeBody`: no refund method on the return part, the granted tokens under the names the server reads), blockers (`exchangeBlockerOf`, split into return, new-items and payment parts), `canOfferExchange`, `exchangeMethodsFor`, `discountApprovalOf`, `exchangeApprovalStepsOf`.
- **Preview** (`use-exchange-preview.ts`): requested once there is a returned line and a valid new line; a stale answer is dropped.
- **Modules split** to stay within the file and function limits: `use-exchange-sheet.ts` (form and submit), `use-exchange-preview.ts`, `exchange-step-rules.ts`, `exchange-api.ts`, `exchange-labels.ts`.
- **i18n**: 32 `returns.exchange.*` keys in `packages/i18n/src/catalogs/screens/{bn,en}.json`, and `returnLabels.exchangeOpen`. Reused existing keys for the return and order screens' texts.

## Deviations (with reasons)

1. **Discount PIN decided from the quote, not by a failed attempt.** The quote's `approvalsRequired` lists DISCOUNT, so the PIN is collected before the request. The instant sale attempts first and asks on `403 APPROVAL_REQUIRED`. Reason: the exchange has several PINs and one request; a failed attempt would otherwise need a second retry with the same key. Consequence: an owner who is exempt on the server may still be asked a PIN the server then ignores.
2. **Reason select written in the exchange sheet.** B's `ReturnReasonFields` is bound to the return form's whole props (preview, refund fields). The exchange renders its own small select (about 25 lines) with the same labels. All other pieces are B's: `ReturnLineCard`, `useReturnForm`, `buildReturnBody`, `approvalTokensOf`, `returnApprovalStepsOf`, `needsRefundReference`, `useReturnApprovalFlow`, `newSubmitKey`.
3. **Exchange labels are built on the server** in `returnLabelsOf` (`returnLabels.exchange`) and passed as props. Screen text is not in the bundled client catalog: a first version read the labels through `useTranslator` in the sheet and showed raw keys in CI (caught by the unit test). The button label is `returnLabels.exchangeOpen`.
4. **Payment methods** are the shop's allowed methods intersected with `SALES_EXCHANGE_PAYMENT_METHODS` (CASH, BKASH, NAGAD, BANK, CARD). No store credit line.
5. **Payment amounts are clamped on typing** to what is left to pay (after the store credit and the other lines), not rejected. Payment lines are disabled until the server preview is ready.
6. **Result inside the sheet**, not a navigation to the return (the staff member can open either link).

## Known gaps

- If the preview request fails (for example a stock short), the payment step shows the generic "amounts could not be calculated" text, not the server's rule message. A rule message needs the failure mapped like the submit's (`failureOf`); not done here.
- The discount PIN is asked from the quote (deviation 1), so an owner exempt on the server is still asked.
- The exchange at the till (`POST /pos/…`) is out of scope (plan A3 out of scope).
- The returns list still filters by business date, not completion date (from B).
