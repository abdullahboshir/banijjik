## Done

- **Period field and helper** (decision 2): `EnrollmentPeriod.revenueRecognizedOn` (local date, set once). `recognizePeriodRevenue` in `enrollment/application/period-revenue.ts` touches the summary through the port, saves the period with its `version`, and publishes `PERIOD_REVENUE_RECOGNIZED` (ordering key `enrollmentPeriod:<id>`), all inside the caller's transaction.
- **Call sites**: activate (`businessDate` = activation date), renew (new current period, `businessDate` = its `periodStartsOn`, only when not PENDING), cancel (decision 6), and **create as ACTIVE** (amendment 2: `businessDate` = creation date, called after `insert` and `initializeSummary`, event after `ENROLLMENT_CREATED`). A PENDING create recognises nothing.
- **Cancel** (decision 6, amendment 1): after the cap, every non-waived period is read at its net paid N. A recognised period publishes `PERIOD_REVENUE_CLOSED` with `recognizedBeforeCancel: true`. A period not recognised with N > 0 is recognised at the cancel date (touch at N, so dues keep the kept amount) and publishes the close with `recognizedBeforeCancel: false`. N = 0 publishes nothing. The touch never clears `closedAt`.
- **Close event contract** (amendment 1): `PERIOD_REVENUE_CLOSED` payload `{ enrollmentId, enrollmentPeriodId, keptAmount, recognizedAmount, recognizedBeforeCancel }`; `PERIOD_REVENUE_RECOGNIZED` payload `{ enrollmentId, enrollmentPeriodId }`. Both in contracts and the payload map (add-only).
- **Reader** (decision 5): `routes/enrollment-request-reader.ts` returns `AFTER_REVENUE` when `revenueRecognizedOn` is set.
- **Summary touch** (decision 4): `EnrollmentPaymentAdapter.touchForRevenue` (`routes/enrollment-payment-adapter.ts`) ensures the summary and sets the total (fee on start, N on cancel).
- **Postings** (decision 7, 8): `accounting/domain/enrollment-posting-rules.ts` (`draftPeriodRevenueRecognized`, `draftPeriodClosed`; the close branch reads only `recognizedBeforeCancel`), handler `accounting.postEnrollments` (ORDERED, `enrollmentPeriod:` stream, handles both events) in `post-enrollments.handler.ts`, registered in `register-handlers.ts`, wired in `routes/accounting-event-handlers.ts` with `buildEnrollmentPeriodPostingSource(buildRequestAdvanceReader())`. Posting source port: `ports/enrollment-posting-source.ts`, adapter `enrollment/infrastructure/enrollment-period-posting-source.ts` (cancel date = the cancelled enrollment's `endsOn`). New keys: `enrollment_period_revenue`, `enrollment_period_advance_settle`, `enrollment_period_revenue_cancel`, `enrollment_period_cancellation_fee`; `JOURNAL_SOURCE_TYPE.ENROLLMENT`.
- **Write-off** (decision 9, Refresh 1): `write-off-posting-rules.ts` `ENROLLMENT: true`. The bad-debt journal stays one per reversal payment (3.34 shape, `sourceType PAYMENT`, Dr `BAD_DEBT_EXPENSE` / Cr `CUSTOMER_ADVANCES`).

## Deviations from the plan (and why)

1. **Create as ACTIVE** (Amendment 2): the plan's decision 2 table had three call sites. The lead added the create row after the implementer asked (`STATUS: QUESTION`, answered "option A").
2. **Stale-version test (A11)** bumps the period version inside `MongoPaymentSummaryRepository.setTotal` (the recognition touch runs before the period save, in the same transaction), not inside the enrollment repository `savePeriod`. The enrollment repository class is not exported from `enrollment/index.ts` (§11 item 23). The bump joins the open transaction (`getActiveSession`), so it does not wait on the transaction's own locks.
3. **A6 (race)** did not conflict or retry. The paused payment read `BEFORE_REVENUE`, the recognition committed in between, and the payment wrote without retry (`revenueState` stays `BEFORE_REVENUE`). The posting then settles its 300 from the held advance (`enrollment_period_advance_settle` Dr `CUSTOMER_ADVANCES` 300) and `CUSTOMER_ADVANCES` nets to zero. The plan's "conflicts and retries" wording does not match what the summary write does, so the test asserts the pair actually observed: (`BEFORE_REVENUE`, settle 300).
4. **A9 "activate after a recognised renew"** is not tested. An ACTIVE enrollment cannot be activated again (the transition refuses it). The replay (posting twice, and the event row count) covers the idempotency.
5. **A12** lives in `enrollment-payment-api.test.ts` (the enrollment file has the payment and reversal helpers), not in the payment suite. It checks the bad-debt journal of the reversal payment.
6. **accounting `index.ts`** exports `buildPostEnrollmentsHandler` (add-only), so the enrollment test can run the real handler.
7. **Module-off test** asserts the ORDERED behaviour: with accounting off the handler returns `SKIPPED_MODULE_OFF`, and the second delivery returns `ALREADY_PROCESSED` (ADR-115: the position advances). No revenue journal is posted for that event. See Known gaps 2.

## Known gaps (also in the STATUS note)

1. **No backfill (decision 10, Amendment 1 item 3).** Periods in service before this card have no `revenueRecognizedOn`. A cancel of such a period with money kept takes the cancellation-fee path. The project has no production data, so this is accepted.
2. **Module-off skip loses the posting.** With accounting off, the ORDERED handler skips the period event and advances its position (ADR-115). When accounting is turned on later, that event is not replayed, so its revenue journal is never posted. The period field and the dues are correct. Fixing the replay for skipped events is a platform change, not this card.
3. **Activate after a recognised renew** has no separate test (Deviation 4).
4. **The payment-reversal race** (A6) observed no retry (Deviation 3). A later card that changes the payment write must rerun A6.
