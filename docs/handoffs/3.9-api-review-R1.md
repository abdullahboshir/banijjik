## Result: accepted, merged after two lead fixes

Checked against the plan's T1 heart and guide §11:
- **One transaction (decision 4):** `CreatePosSaleUseCase` runs `markSale`, `sales.commit` (order, stock, summary) and every `ReceivePaymentUseCase` call in one `unitOfWork.run`; the payment use case's own `MongoUnitOfWork` joins the outer one (ADR-084). Test `a failure in the payment step leaves no order, no stock movement and no payment` proves it.
- **Close and sale race (decision 6):** the sale's first write is `markSale` (conditional on `status: OPEN`) on the session document; the close reads payments in its snapshot and writes the same document, so one of two concurrent transactions gets a write conflict and retries on the new state. Covered by the two-transaction repository test and the API race test.
- **Device security (decision 2):** the cookie holds 32 random bytes and only its SHA-256 is stored; the pairing code is an organization-bound HMAC, cleared on claim, rate limited per member; the device lookup runs after `permission(...)`, so the LOCATION tenancy narrows it; the location of every write comes from the device. Cookie httpOnly, SameSite Lax, Secure by config.
- **Money:** integer minor units; currency compared in the tender, the float, the counted cash and the expected cash; store credit through the existing payment path; idempotent POST routes; GAPLESS `ZREPORT` taken in the close transaction.
- No `as unknown as`, no `console`, no lint disables; the three narrowing casts are the existing `CurrencyCode` kind.
