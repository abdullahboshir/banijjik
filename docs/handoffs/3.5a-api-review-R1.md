# 3.5a Part A (API orders) review R1

Reviewer: lead (Opus 5.5), 2026-10-23. Branch `s/3.5a-api-orders` at `6043913`. **Verdict: changes required.**

The module is in good shape overall: quote-only totals, snapshots, place in one transaction (approval, counter, number, reservation, event, audit), the reservation key `(ORDER, orderId)`, the gapless INVOICE inside the completion transaction, business date and month key in the organization's timezone, and a broad test set (parallel last-unit and limit-edge tests included). The findings below are about money control, the edit path and the jobs. Use the checklist in `docs/plans/parallel-sessions-guide.md` §11 for the whole module, not only these items.

## Blockers
1. **The discount approval does not bind the amount.** `resolveApproval` calls `approvals.consume(token, { action, subjectKey })` without `amount`. ADR-121 binds a token to an amount and `consume` checks it only when `expected.amount` is set (`approval-verifier.ts:49`). So a manager approves a 50-taka discount and the cashier uses that token for a 5,000-taka discount. For the counter sale it is worse: every instant sale shares the subject `order:instant`, so a token requested for one sale works for any other sale in its 2 minutes.
   - Fix: pass `amount` = the total manual discount of the quote (line manual discounts + order manual discount, in minor units, in the order's currency) on place, edit and instant. Read it from the quote result, never from the client.
   - Tests: a token approved for a smaller amount is refused (place, edit, instant); the same token cannot be used twice (plan: "the token is single-use" has no test yet).
2. **The edit consumes the approval token outside its transaction.** `UpdateOrderUseCase.approvalOf` runs `resolveApproval` before `unitOfWork.run`. If the versioned update then fails (409), the token is spent and the edit is not saved. Plan decision 3 and ADR-121 say consume runs in the order's transaction. Move it inside, as place and instant already do. Test: a stale-version edit with a token leaves the token usable.
3. **An edit can empty a PLACED or CONFIRMED order.** `clearedContentOf` zeroes lines and totals for any editable status, and `restock` then releases the reservation. The result is a numbered PLACED order with no lines that can still be confirmed and completed, which takes a gapless INVOICE number for a zero sale. The same PATCH can also set `contactId: null` on a PICKUP order that place only allowed with a contact phone.
   - Fix: after place, an edit must keep at least one line (`orderNeedsLine`) and, for PICKUP, a contact with a phone (the place rule). Clearing everything stays allowed for a DRAFT only.
   - Tests for both refusals.
4. **One failing order stops the job for the organization, every hour.** `autoCancelPlaced` and `expireDrafts` call the use case in a plain `for` loop. The first error ends the pass, and the scan is oldest first, so the same order fails first on every later pass and nothing behind it is ever processed. The common case is not rare: staff confirm an order between the scan and the cancel, and the cancel gets 409.
   - Fix: per row, skip a conflict (409) and an invalid transition (the order already moved on). Log any other error with the `orderId` and continue with the next row.
   - Tests: a raced row is skipped and the next row is still cancelled; a row that throws does not stop the rest.

## Must fix (smaller)
5. **Literals:**
   - `entityType: "order"` in every audit call: use `AUDIT_ENTITY_TYPE.order`.
   - `settings.advanceRequired !== "NONE"` (place and confirm): use `SALES_ADVANCE_REQUIRED.NONE`.
   - `AUTO_CANCEL_REASON` stores an English sentence in the order. Store a reason code from contracts instead (for example `SALES_CANCEL_REASON.AUTO_PLACED_TIMEOUT`), so Part B shows it through i18n. Free-text staff reasons stay as they are.
6. **The edit's stock calls lose the actor.** `restock` passes `actorUserId: null` to release and reserve, although the editing user is known. Pass `input.actorUserId`.
7. **The list reads whole orders.** `MongoOrderRepository.list` loads every line of every order on the page to show seven fields. Add a projection for the list row (AGENTS: `lean()` + projection on reads).
8. **Records:**
   - ADR-131 says the instant subject is `order:<orderId>:instant`; the code uses `order:instant`. Make them agree and describe the amount binding from item 1.
   - The handoff lists the jobs' settings problem: add to STATUS that, until card 3.19 (lead, foundation) lands, both sales jobs fail every hour with `jobs.organization_failed` (they never run in production). No change in this card's code for that.
9. **Tests the plan lists that are missing or need a stronger body:**
   - the token is single-use, and the amount checks from item 1
   - the monthly counter at a month boundary in Dhaka time (for example `2026-10-31T19:00:00Z` counts in `2026-11`) with a fixed clock (§11 items 13–14)
   - the ported manoxen sales tests (transitions, totals recalc invariants, edit after confirm, reservation then commit): list them in the handoff by name, or say which existing tests cover them

## Checked and fine
- Quote-only money: strict schemas refuse client prices; totals, prices, tax class and promotion ids are snapshots; tests prove a later price change does not alter an order.
- Place transaction order: approval consumed, counter `$inc` then limit check (rolled back on refusal), FAST ORDER number, reservation, versioned update, event and audit, all in one unit of work.
- Completion: GAPLESS INVOICE number and `commitSale` inside the transaction; the 3.3 ledger fix (release before the SALE movements) is correct and keeps the pair atomic.
- Edit re-reserve: `release` deletes the reservation, so the following `reserve` under the same key really reserves again.
- Idempotency: `place` and `instant` go through the kernel idempotency middleware; transitions are versioned.
- Business date and month key use the organization's timezone.
- Indexes start with `organizationId`, including the job scan index `{ organizationId, status, createdAt, orderId }`.
- Tenancy and access: cross-organization 404, unassigned location 403, viewer cannot create; module registry and grants are add-only.
