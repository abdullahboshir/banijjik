## Blockers (money, ledger, accounting stream)

1. **Store-credit events block the accounting stream.** Overpayment, refund-to-credit and manual adjustment publish `payment.storeCredit.changed`. `readStoreCreditSnapshot` returns `undefined` for every kind except EXPIRY, and `post-payments.handler.ts` `postStoreCreditChange` then throws `postingSourceMissing`. The handler is ORDERED per organization, so the first overpayment dead-letters and blocks every later accounting event of that organization.
   **Lead decision:** keep publishing the event for every entry. Change `StoreCreditPostingSnapshot.kind` to the full entry kind. `postStoreCreditChange` posts a journal only for EXPIRY and returns without a journal for the other kinds, because overpayment and refund-to-credit are already posted from the payment event, and manual adjustment has no journal yet (plan refresh item 3). A missing entry still throws.
   Test through the real handler: overpayment, then a later payment → both journals are posted and nothing is dead-lettered.
2. **A STORE_CREDIT payment writes no ledger entry.** `handleStoreCreditPayment` lowers the contact balance but creates no − `StoreCreditEntry`, so Σ entries ≠ balance (ADR-014, plan decision 4). Write the DEBIT entry (`paymentId` set) in the same transaction and publish its event.
3. **Credit can be lost or written for a foreign contact.** `handleOverpayment` and `creditStoreCreditOnRefund` ignore `adjustBalance(...).success`. On a version conflict, or for a contact that is not in this organization, the entry is still written (with `balanceAfterMinor: 0`) while the balance is unchanged. Also, `contactId` on any payment is never checked to exist in the organization.
   Fix: throw on `success: false` (a conflict error, so the transaction retries or the caller gets 409). Validate `contactId` through contact's index port; an unknown contact gets 400. Also set `paymentId` on every entry made by a payment.
4. **Over-refund and over-allocation race.** The limits are checked before the transaction. `findByRequest` reads without the session, and `upsert` `$set`s values computed from that read. Two concurrent refunds (or payments) for one booking can both pass, giving refunded > paid, which means money out.
   Fix: inside the transaction, update the summary with one conditional `$inc` whose filter holds the limit (`$expr`: allocated − refunded + amount ≤ total for IN; refunded + amount ≤ allocated for REFUND). Zero matched means 400 (or 409 for a lost race). Keep `$inc`, never a `$set` of computed totals.
   Test: two concurrent refunds of the full paid amount → exactly one succeeds. Same for two payments that together exceed the total.
5. **Double reversal race.** `findReversalOf` runs outside the transaction, and there is no unique index. Add a unique partial index `{ organizationId, reversesPaymentId }` (where `reversesPaymentId` is a string) and map the duplicate-key error to `paymentReversalAlreadyReversedError`.
   Test: two concurrent reversals with two valid tokens → one 201, one 409.
6. **A reversal ignores store credit and refunds.**
   (a) Reversing a STORE_CREDIT payment does not give the credit back.
   (b) Reversing an IN with overpayment leaves the credit on the contact.
   (c) Reversing a payment whose requests were refunded afterwards makes allocated − refunded negative.
   **Lead decision:** (a) and (b) are undone in the same transaction with ledger entries; if the overpayment credit is already spent, refuse with 422. (c): refuse the reversal with 422 when any of its requests has a refund (new error code in contracts).
7. **Accounting reverses only one journal.** `postPaymentReversal` returns after the first posting key it finds, but a payment with overpayment, or with allocations in both revenue states, has several journals. Reverse every journal whose source is that payment. This is 3.8c code, but 3.8 is the first card to use it.
   Plan refresh item 3 tests are missing and are required: IN, refund, reversal (including one with overpayment) and expiry, each through the real handlers, give balanced journals.
8. **Store credit never expires, and would expire twice.** No entry sets `expiresAt` (the setting `payment.storeCreditExpiryDays` is never applied). `listExpiredUnprocessed` has no "processed" marker, so once it is set, every daily run expires the same entry again.
   Fix: set `expiresAt` on CREDIT entries from the setting. Record the source on the EXPIRY entry (`expiresStoreCreditEntryId`) with a unique index `{ organizationId, expiresStoreCreditEntryId }`, and skip sources that are already expired.
   Test: the job run twice gives one EXPIRY entry.
9. **Part of the approval token is stored.** `approvalId: input.approvalToken.slice(0, 16)` persists part of a bearer secret in the payment, the API response and events. Use the approval id that `ApprovalVerifier.consume` returns (if it returns none, stop and ask).

## Must fix (rules and plan)

10. **The refund approval rule uses role keys.** `isManagerOrOwner` hardcodes OWNER and MANAGER role keys, so custom roles break and location scope is ignored. Use the permission `payment.payment.refundWithoutApproval` (already in contracts, granted to OWNER and MANAGER) together with the setting `payment.refund.managerWithoutApproval`.
11. **Deposit (decision 6) is only part done.**
    - The check uses `allocated`; it must use `allocated − refunded`.
    - Auto-confirm on create is not checked.
    - `depositCheck` is optional, so the check is skipped silently when it is not wired; make it required.
    - Cancellation and no-show (`11 §5.4`: refund or credit inside the free window, otherwise retain the fee, plus the event for `CANCELLATION_FEE_INCOME`) is not implemented. Implement it, or stop and ask the lead to split it into a follow-up card. Do not drop it silently.
12. **`revenueState` is read at posting time** (in the worker, later). If the booking completes between the payment and its posting, an advance is posted as after-revenue. Store `revenueState` on each allocation when the payment is made, and let the posting adapter read the stored value.
13. **`businessDate` uses the UTC date.** In Bangladesh, payments made between 00:00 and 06:00 local time land on the previous day. Use the organization's local date (look for the helper that 3.8b or 3.8c use for business dates; if none exists, stop and ask). Do not accept a client `businessDate` unless the plan allows it; it does not, so remove it from the request schemas.
14. **Dues leak across locations.** `PaymentSummary` is registered with ORGANIZATION tenancy, so a location-restricted caller sees every location's dues. Make it ORGANIZATION_AND_LOCATION (bookings always have a location), or filter by the caller's allowed locations in the use case.
    Test: a cross-location caller sees no foreign dues.
15. **The refund route ignores `:paymentId`.** `POST /payments/:paymentId/refund` never reads the param. **Lead decision:** change it to `POST /refunds` (the refund is by request allocations, decision 2). No screens exist yet, so this costs nothing.
16. **Records are missing.** ADR-123 ("Accepted (proposed)", the contents listed in plan decision 9), the notes in `09`, `11 §7` and `14`, and an honest deviations list in `docs/handoffs/3.8-api.md`.
17. **Plan tests are missing.** Add them, with names as behaviour specs:
    - two concurrent store-credit uses → one wins and the balance stays ≥ 0
    - expiry job run twice (item 8)
    - the dues scenario UNPAID → PARTIAL → PAID → REFUNDED
    - deposit cancel inside and outside the free window
    - events carry `paymentAccount:<organizationId>` and no personal data
    - permission denied (VIEWER receive, CASHIER reverse or adjust)
    - cross-location (STAFF at L1 receives at L2 → 403)
    - the ported manoxen finance tests (`15-PORT-MAP.md` payment row)
    - the real-handler journal tests (item 7)
