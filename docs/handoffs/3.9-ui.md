## What was built (in `apps/admin/src/pos/**`, route `apps/admin/app/[orgSlug]/pos/**`)
- Slice 1 (earlier commits): pos manifest menu entry, route `/[orgSlug]/pos` with its own layout (requireOrgAccess, no OrganizationShell), pairing, open register, sale search and cart, API client.
- Slice 2 (earlier commits): payment sheet (quick cash, change, split methods), receipt print view (58 and 80 mm), lazy wrappers.
- Slice 3 (`861f2e25`): close register. Counting form (counted cash, optional note, one Idempotency-Key per attempt), Z-report print view (58/80 mm, every number from `GET /pos/sessions/:id/z-report`), lazy close screen. The sale screen has a "Close register" button, disabled while the cart has lines (a cart would be lost on close). Back from the close screen returns to the same sale view.
- Slice 4 (`b25a6fe8`): customer by phone and store credit at the till. Customer search by phone or name (`GET /contacts?q=`), store credit balance from the newest store-credit entry (`GET /store-credit?contactId=&limit=1`), store credit applied before the tender (capped by balance and bill, the server re-checks), credit sale (no payment, server refuses when `pos.allowCreditSale` is off). The customer block is shown only when the member holds `contact.contact.read` and `payment.storeCredit.read`.
- Slice 5 (`57e4b6e0`): catalog cache in IndexedDB keyed by organization and location (`pos-catalog-cache.ts`), refreshed with `since` on open and every 5 minutes (`pos-catalog-refresh.ts`), merged with removed rows (`pos-catalog-merge.ts`). A scan resolves from the in-memory rows of the cache; the sale is still quoted by the API. IndexedDB failures fall back to a full read (no cache).
- BN and EN keys: `pos.close.*`, `pos.z.*`, `pos.customer.*`, `pos.sale.closeRegister`, `pos.sale.closeBlocked` (both catalogs, 86 + 12 `pos.*` keys in the screens catalog).
- Money through the shared formatter (`formatMoney`); money input through `moneyFromInput`.

## Deviations from the plan (with reasons)
1. Path: the plan named `apps/admin/src/app/[orgSlug]/pos/**`; the code lives in `apps/admin/app/[orgSlug]/pos/**` (the admin app has no `src/app`). Lead decision, recorded.
2. Menu entry in the pos manifest: approved by the lead (slice 1).
3. Customer block gated on two permissions, not a new setting read. A cashier does not hold `contact.contact.read` or `payment.storeCredit.read` (`pos-role-grants.ts`), so a cashier sells anonymously. Owner question: should cashiers find customers and read store credit? (see STATUS).
4. "Sell on credit only when the setting allows": the UI does not read `pos.allowCreditSale`. The till offers the credit-sale choice whenever a customer is attached; the server refuses it when the setting is off and the till shows the refusal. Known gap.
5. Close screen re-reads the open register before counting (the sale bumps the session version), so the close never sends a stale version.
