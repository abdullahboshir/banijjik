# Handoff · 3.5b part A3 · exchange (API, T1)

Branch `s/3.5b-api-exchange`, plan `docs/plans/3.5b.md` "Refresh 3" (A3 only). Status: **implemented, all plan tests exist and pass locally**.

## What was built
- Endpoints (existing sales mount): `POST /orders/:orderId/exchange` (`Idempotency-Key`; needs `sales.return.create` and `sales.order.create`) and `POST /orders/:orderId/exchange/preview` (no writes, no key).
- Body `salesExchangeRequestSchema` (`packages/validation/src/sales/sales-exchange-schemas.ts`): `return` (the A1 return body without refund method and reference), `order` (the instant body without location, contact and fulfillment), `payments` (`method` in `SALES_EXCHANGE_PAYMENT_METHODS`, `amount` as Money, at most `MAX_EXCHANGE_PAYMENTS`).
- Pure money plan `planSalesExchange` (`sales/domain/sales-exchange-plan.ts`): credit used = min(R, G), credit left = R − used, payments above what is left refused, currency compared.
- `CreateSalesExchangeUseCase` / `PreviewSalesExchangeUseCase` (`sales/application/use-cases/sales-exchange.use-cases.ts`). Before the unit of work: order load, contact check, `InstantSaleService.prepare` of the new order. Inside it: `prepareSalesReturn`, `planSalesExchange`, `writeSalesReturn` (with `exchangeOrderId`), `InstantSaleService.commit`, payments, one audit entry `sales.exchange.created`.
- `InstantOrderUseCase.prepare` picks the new order id (`PreparedInstantSale.orderId`); POS and `/orders/instant` keep their behaviour. `writeSalesReturn` takes `exchangeOrderId` (null for a plain return).
- Contracts: `sales-exchange-contracts.ts` (types, constants), rule keys `SALES_EXCHANGE_NEEDS_CONTACT`, `SALES_EXCHANGE_PAYMENTS_ABOVE_TOTAL`, `SALES_EXCHANGE_CURRENCY_MISMATCH` with BN and EN messages, audit action `SALES_EXCHANGE_CREATED`.
- Store-credit balance read joins the caller transaction (see deviations).

## Deviations (with reasons)
1. **Payment adapter session (lead exception, approved).** `MongoContactStoreCreditAdapter.getBalance` passes `sessionOption(getActiveSession())`. Reason: E6 one unit of work; the store-credit payment must see the credit the return writes in the same transaction. Without it the exchange failed with `store_credit_insufficient`. No other payment code changed; payment and store-credit suites pass (`payment-store-credit-and-reversal-api`, `payment-api`).
2. **Cross-location answers 404, not 403** (lead decision, as A1 and A2). Location-owned rows are invisible outside the caller's locations. The test keeps the plan's name `an exchange at another location's order is 403` and asserts 404 with the same comment as A1/A2.
3. **Payment amount is a Money object** (`moneySchema`, as the POS body) rather than a bare integer, so the currency is compared.
4. **`payments` in the response include the store-credit spend** (first), as the POS `payments` list does; `storeCreditUsed` is also returned separately.
5. **Preview takes the full body** (including payments), so `dueAmount` matches the create.
6. The refund method of the return part is forced to `STORE_CREDIT` on the server; the client cannot choose it.

## Tests
Domain (`sales/domain/sales-exchange-plan.test.ts`, run locally, 3 of 3 pass):
- `plans an exchange: the return credit pays the new order first and the rest is paid or left as due`
- `refuses payments above what is left to pay and payments in another currency`
- `an unpaid original order gives no credit, so the new order is paid by the payments or left as due`

API (`sales/presentation/sales-exchange-api.test.ts`, real Mongo 8.2, run locally, 15 of 15 pass):
- money and stock: `an exchange for a cheaper item leaves the difference as store credit`; `an exchange for a dearer item takes the difference in cash`; `an exchange for a dearer item without payment leaves the difference as a due on the new order`; `the same variant can be swapped: the returned unit is restocked before the new sale takes it`; `a failure in the new order writes nothing: no return, no credit, no stock movement`; `a discount on the new order without its approval refuses and writes no return` (fixture discount 1000 on a 1500 item: above the percent threshold; a 100 discount was under it)
- rules and approvals: `refuses an exchange on an order without a contact`; `the return of an exchange points to the new order and cannot be reversed`; `a store credit refund in an exchange needs the REFUND approval unless the caller is exempt`; `the same Idempotency-Key returns the first exchange and writes nothing twice`; `the preview returns the same numbers as the exchange and writes nothing`
- access: `a caller without sales.order.create gets 403`; `a caller without sales.return.create gets 403`; `another organization's order is 404`; `an exchange at another location's order is 403` (asserts 404, deviation 2)

Accounting (`sales/presentation/sales-exchange-accounting-api.test.ts`, run locally, 1 of 1 passes): `the exchange posts the return and the new order once each, also on event replay (trial balance: the contact's store credit liability equals creditLeft)`. It runs the real registered handlers twice through `runEventHandler` (`test-support/outbox-replay.ts`, no Redis needed), checks one `sales_return_value` and one `order_revenue` journal per source, a balanced trial balance, and `STORE_CREDIT_LIABILITY` = `storeCreditLeft`.

Regression, run locally, all pass: `payment-store-credit-and-reversal-api` (6), `payment-api` (13), `order-return-api` (20), `sales-return-reverse-api` (18), `order-instant-api` (3), `pos-sale-api` (11).

Commission (`sales/presentation/sales-exchange-commission-api.test.ts`, run locally, 1 of 1 passes): `the returned line's commission goes down and the new order's lines accrue`. It grants the booking and commission add-ons for the organization (the commission manifest depends on booking), creates a 10% member rule, sells two performed units, exchanges one for a cheaper performed unit, then runs the real accrual handler over the outbox. The original line goes from +200 to +100 (−100 reversal), the new order accrues +60.
