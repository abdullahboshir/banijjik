- **Adaptations to the real kernel and iam names (mechanical):**
  1. Cross-module reads need more than the plan listed. `GET /me/orgs` spans organizations, so iam's read port is `findRoleKeysByIds(organizationIds, roleIds)` (both are filters; the plan said a single `organizationId`). The creator's name and language (for `displayName` and `defaultLocale`) come from a new iam export `buildReadUserProfileUseCase()` returning only `{ name, preferredLocale }`; organization wraps it as an `ActorProfileReader` port. iam's `index.ts` therefore exports `buildProvisionSystemRolesUseCase(clock)`, `buildRoleKeyReader()`, `buildReadUserProfileUseCase()`.
  2. Each module has its own `DomainRuleError` (the domain may not import another module), so organization has a copy in `domain/errors.ts` plus `SlugTakenError` (DUPLICATE, `details.field = "slug"`). `requireCurrentUserId` and `translateDomainErrors` are likewise per-module copies.
  3. `buildOrganizationRouters({ clock, rateLimiter })` follows `buildIamRouters`; `routes/v1.ts` mounts `/me/orgs` before `/me` (lines added only).
  4. `employeeNumber` is stored as a string ("1"), as in `09 §4.4`; formatting is card 2.4.
  5. `createdByUserId` is `UserId | null` in the three entities, because the audit field is null for system writes.
  6. Specific message keys `validation.slug_invalid`, `slug_reserved` and `name_length` are emitted by the domain (`Organization.create` re-checks name and slug with the shared contracts constants). The request schema reports the generic Zod keys (`validation.too_small`, `invalid_format`, `custom`), because the kernel `validate()` maps only the issue code. Both give 400 with the field path.
  7. The test harness `registerIamApiModels()` also registers the sequence model (one line added), because creation takes a MEMBER number.
  8. Added `package-lock.json` sync from the 1.1 dependency changes (validation depends on contracts; api depends on validation `*`).
