- **Deviations from plan (and why):**
  - The kernel probe manifest moved from `MODULE_KEY.SETTINGS` to `MODULE_KEY.FILE` (`core/file`). The real settings module now owns `settings`, and registering both would refuse startup. Expected module lists that named the probe `settings` now say `file`.
  - The location-override probe in the settings API test uses `MODULE_KEY.NOTIFICATION` (`notification.probeFlag`), because `file` is the kernel probe whenever a test builds its own router.
  - Industry defaults are read by mutating the stored RETAIL template in the test database. SALON cannot be selected at signup, and the seed JSON belongs to card 2.3.
  - Location existence uses the registered model name `Location` inside settings. The plan does not add an organization export, and wave 1 leaves that module's index alone apart from its manifest.
  - Organization-level "ALL locations" is checked per item in the use case. `requireAllLocations` on the route would block a one-location manager from writing their own location.
  - `GET` reads the parsed query from `response.locals.validated`. Express 5 makes `request.query` read-only; `validate()` already documents this.
  - A batch that touches the same key at more than one scope resolves each scope and then sorts the keys. The response has one entry per key.
