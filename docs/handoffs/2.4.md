### Findings

**R1-1 · MAJOR · settings reads another module's model.** `infrastructure/mongo-location-existence.ts` reads `models({}).get("Location")`, the `core/organization` model, by its registered name. That reaches into another module's storage behind its back:
- `AGENTS.md`: import another module only through its `index.ts`
- ADR-011a: module boundaries
- ADR-023: business code gets its own models through `models(ctx)`

The lint does not see it, because the name is a string. If `core/organization` renames, moves or reshapes the model, settings breaks silently.

Fix:
- `core/organization` exports a builder from its `index.ts`, like `buildActiveLocationCounter`: `buildLocationLookup(): { isActiveLocation(locationId): Promise<boolean> }`.
- It reads its own `Location` model inside the organization context, so the tenant plugin filters.
- Only ACTIVE locations count: an archived location takes no new settings.
- `routes/core-tenant-routers.ts` adapts it to settings' `LocationExistence` port.
- Delete `mongo-location-existence.ts`.
- Tests: a location of another organization → 404 (existing); an **archived** location → 404 (new).

**R1-2 · MINOR · the raw input is stored instead of the parsed value.** `prepareSettingChange` checks `buildSettingValueSchema(...).safeParse(item.value).success` and then stores `item.value` as sent. A STRUCTURED schema (zones, rules) will strip unknown keys or normalize values, and the stored value must be exactly what the schema returned. Otherwise extra keys a client sends end up in the database.

Fix:
- Keep `parsed.data`, and store and audit that.
- Test with a test-only STRUCTURED schema (the registry already accepts a schema map in tests) that strips an unknown key: the stored and returned value has no extra key.

**R1-3 · MINOR · a no-op still writes an audit entry, an event and a bump.** `value: null` for a row that does not exist returns `{ from: null, to: null }`, and the batch still records it, publishes the event and bumps `configVersion` (deviation "deleting a row that is already absent still writes…").

Fix:
- Items with no change (an absent row deleted, or a value equal to the stored one) are left out of the audit `changes`.
- A batch where every item is a no-op writes **no** audit entry, no event and no bump, and answers `200` with the resolved values.
- Test both.
