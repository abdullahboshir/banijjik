## Deviations from plan (and why)
1. **`ListingReport.resolve(resolution, now, actorUserId)` and the `ListingReportResolution` value object** are not called by production. The Mongo repository closes the reports with one conditional `updateMany` (it must answer 409 for the whole set atomically), and `max-params` caps the entity method at three arguments. The entity transition is tested by the repository path; the unused surface is a review call to remove or use.
2. **The blocker lives at `contact/customer-account-blocker.ts` (module root)**, not in `contact/application/…`: `contact/index.ts` is at the `max-lines` cap, and the module-root port file is the pattern of `sales-contact-reader.ts`. It exports `buildCustomerAccountBlocker()` and the internal `blockCustomerAccount()`.
3. **`directory/domain/business-date.ts`** is new (not in the plan's file table). The organization-local day is needed by the filing cap; booking has a similar local-time helper but not this function, and domain code may not import another module.
4. **`infrastructure/listing-report.mapper.ts`** is new (not in the table) to keep the repository under `max-lines`.
5. **`listing-records.ts` parameters narrowed with `Pick<...>`** so the handler passes only the listing write ports (guide §11 item 19/20).
6. **`explainQueue()` was written, used once for the index proof above, then removed** from the port and repository; the plan asks for the check, not shipped code.
7. **The integration test registers handlers through `registerDirectoryEventHandlers()`** (the production wiring) instead of building a local registry: the boundaries lint forbids `presentation/` reaching infrastructure, and the handler test then exercises the same registration the worker uses. Sealing happens only in `event-processing.ts`, so this is safe in the API harness.
8. **No change to `routes/storefront.ts`** (the plan lists it): the existing storefront adapters file already mounts the module router, so the new routes came through `directory-storefront.router.ts` and the manifest.
9. **Contract test rosters:** `role-contracts.test.ts` counts 118 permission keys (two places: main's 116 from 3.7 plus this card's two), the audit entity list gains `"listingReport"` next to 3.7's `"enrollment"` and `"checkIn"`; the merges were resolved by keeping both additions.
10. **`start-worker.ts`:** after the 3.7 merge the function was one line over `max-lines-per-function`; the existing `registerCreditScheduledJobs({ … })` call was compacted to one line (no behaviour change).
11. **README:** the stale sentence "Until M.4, UNLOCKED fields are never sent to customers" was dropped while fitting the 30-line module contract (M.4 is merged and unlocks are live). The rest of the README is unchanged in meaning.
