# Handoff: card 3.8, part A · Payments, dues and store credit API

Implemented by: Antigravity (Sonnet) · Date: 2026-10-22 · Plan: `docs/plans/3.8.md` · Branch: `s/3.8-api-payments`

## What was built
- **Contracts (`@banijjik/contracts/payment`, `@banijjik/contracts/booking`, `@banijjik/contracts/accounting`):**
  - Payment method enum (`CASH | BKASH | NAGAD | BANK | CARD | STORE_CREDIT | GATEWAY | COD_COURIER | RIDER_CASH`), payment directions (`IN | REFUND | REVERSAL`), store credit entry kinds and directions, payment status (`UNPAID | PARTIAL | PAID | REFUNDED`).
  - Permissions: `payment.payment.{read,receive,refund,refundWithoutApproval}`, `payment.due.read`, `payment.storeCredit.{read,adjust}`.
  - Setting keys: `payment.methods` (structured), `payment.refund.managerWithoutApproval` (boolean), `payment.storeCreditExpiryDays` (number), plus booking cancellation/no-show fee settings (`booking.freeCancelHours`, `booking.lateCancelFee`, `booking.noShowFee`, `booking.feePercent`).
  - Sequence key: `PAYMENT`.
  - Audit actions: `PAYMENT_RECEIVED`, `PAYMENT_REFUNDED`, `PAYMENT_REVERSED`, `STORE_CREDIT_ADJUSTED`.
  - Accounting contracts: added contract-defined reversal posting keys (`reversal_payment_in_advance`, `reversal_payment_in_after_revenue`, `reversal_payment_store_credit`, `reversal_overpayment_to_store_credit`) and helper `reversalPostingKeyFor`.
  - Contracts subpath exports: `@banijjik/contracts/payment`, `@banijjik/contracts/booking`, `@banijjik/contracts/accounting`.
- **Validation (`@banijjik/validation/payment`):**
  - Request and query schemas for `receivePaymentSchema`, `refundPaymentSchema`, `reversePaymentSchema`, `adjustStoreCreditSchema`, `listPaymentsQuerySchema`, `listDuesQuerySchema`, `listStoreCreditEntriesQuerySchema`.
  - Structured setting schema for `payment.methods` registered in `@banijjik/validation/settings`.
  - Validation subpath export: `@banijjik/validation/payment`.
- **Commerce / Payment Module (`apps/api/src/modules/commerce/payment`):**
  - **Domain:**
    - Aggregate root `Payment` (append-only, immutable, storing allocation `revenueState` at payment/refund time).
    - Aggregate root `StoreCreditEntry` (append-only ledger).
    - Entity `PaymentSummary` (per-request balance projection: total, allocated, refunded, paymentStatus, due).
    - Domain rules in `payment-rules.ts`: `computePaymentStatus`, `validatePaymentAllocations`, `validateRefundAllocations`.
    - Errors in `errors.ts`.
  - **Infrastructure:**
    - Mongoose schemas with compound indexes (`PaymentSchema`, `StoreCreditEntrySchema`, `PaymentSummarySchema`). Unique partial indexes on `(organizationId, reversesPaymentId)` and `(organizationId, method, externalReference)`.
    - Repositories: `MongoPaymentRepository`, `MongoStoreCreditRepository`, `MongoPaymentSummaryRepository` (with atomic conditional `$expr` guards on `applyAllocation` and `applyRefund` to prevent race conditions).
    - Adapters: `ContactStoreCreditAdapter` (atomic balance adjustment with optimistic concurrency locking and negative-balance guard), `PaymentPostingSourceAdapter` (for accounting posting engine), `MongoBookingPaymentStatusAdapter`.
    - Scheduled jobs: `expireStoreCredit` registered via `kernel/jobs`.
  - **Application Use Cases:**
    - `ReceivePaymentUseCase` (+ `receive-payment-helpers.ts`): cash change handling, overpayment auto-credited to store credit when contact is provided, mobile money external reference uniqueness, idempotency key support, atomic store credit debit and summary allocation.
    - `RefundPaymentUseCase` (+ `refund-payment-helpers.ts`): manager/approval gating with `ApprovalVerifier` (`PAYMENT_REFUND`, subjectKey sorted requestIds), refund to store credit or source method, atomic summary refund guard.
    - `ReversePaymentUseCase`: one-time reversal with `APPROVAL_ACTION.PAYMENT_REVERSAL`, mirrored allocations, store-credit reversal (credits back `STORE_CREDIT` payments or debits back unspent overpayment credit; rejects with 409 if overpayment credit was spent). Reversals store `externalReference: null`.
    - `AdjustStoreCreditUseCase`: staff manual adjustment with `APPROVAL_ACTION.STORE_CREDIT_ADJUSTMENT`.
    - `GetDuesUseCase`, `GetPaymentUseCase`, `ListStoreCreditEntriesUseCase`, `settleBookingTermination` (`settle-booking-deposit.ts`).
  - **Presentation & Routes:**
    - `PaymentController` (enforcing `ensureLocationAllowed` on writes and location filters), `buildPaymentTenantRouter`.
    - Tenant router mounted in `routes/v1.ts` and registered in `routes/tenant-module-routers.ts`, `routes/module-registry.ts`.
    - Handlers and scheduled jobs registered in `start-worker.ts` and `accounting-event-handlers.ts`.
    - Grants: Cashier has `payment.payment.{read,receive}`, `payment.due.read`, `payment.storeCredit.read`; Manager/Owner has refund/reversal/adjust grants.
- **Booking & Accounting Integration:**
  - `BookingPostingSourceAdapter` and `BookingPaymentStatusAdapter` wired.
  - `PaymentSummary` created/updated when a booking is created (`create-booking.use-case.ts`) and settled on cancel/no-show (`cancel-booking.use-case.ts`, `booking-status-transitions.use-cases.ts`), storing `cancellationFeeRetained` on `Booking`.
  - Deposit check enforced on booking confirmation when `booking.deposit.required !== NONE`.
  - `post-payments.handler.ts` handles `payment.received`, `payment.refunded`, `payment.reversed` (reversing all journals of a multi-journal payment using contract-defined reversal keys), and `payment.storeCredit.changed` (posting expiry journals and ignoring non-expiry entries without throwing).

## Deviations
1. `Payment.approval` internal domain/DB subdocument retains the field name `approverUserId` (storing `consumed.approverMemberId`) and maps it to `approvedByMemberId` in `PaymentResponse` (`payment-view.ts`).
2. `Payment.allocations[].revenueState` (`BEFORE_REVENUE | AFTER_REVENUE`) is persisted on each allocation at receive/refund time so asynchronous accounting handlers post against the revenue state at the moment of payment rather than the mutable booking state at handler execution time.
3. `Booking` persists `cancellationFeeRetained: Money | null` at cancel/no-show time so `BookingPostingSourceAdapter` reads the exact retained fee rather than recomputing from settings later.
4. Added ADR-123 (`docs/04-DECISIONS.md`) documenting `Contact.storeCreditBalanceMinor` updated by the payment module via `ContactStoreCreditPort`.

## Ported manoxen Finance Rules
Source: `15-PORT-MAP.md` row for Payment (`__tests__/finance/*`, `order-receivable-policy.spec`, `order-collect-policy.spec`):
1. **Multi-request split payment allocation:** A single payment can allocate funds across multiple customer requests (e.g., multiple bookings). Tested in `payment-dues-deposit-and-access-api.test.ts` ("ports manoxen finance rules: multi-request split allocation...").
2. **Sequential partial refunds:** Multiple partial refunds against an existing payment or allocation succeed sequentially as long as cumulative refunds do not exceed total allocated.
3. **Over-refund refusal:** When a refund request exceeds the remaining net paid amount on any allocation, the system rejects with 422 `paymentAllocationRefundExceeded`.
4. **Order-specific receivable/collect policies (`order-receivable-policy.spec`, `order-collect-policy.spec`):** Not ported in card 3.8 because Orders and Order Collect/COD workflows belong to cards 3.5a/3.5b (orders) and 3.9 (courier/COD). The payment ledger structure built here exposes the generic `PAYMENT_REQUEST_TYPE` port which orders will plug into.
