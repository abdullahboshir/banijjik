## Done

1. **Vocabulary first** (`packages/contracts/src/sales/`, exported as `@banijjik/contracts/sales`): 5 `sales.order.*` permission keys, `ORDER_STATUS` (with the Phase-5 shipping statuses), `FULFILLMENT_METHOD`, `ORDER_SOURCE`, `SALES_EVENT_TYPE` (7 past-tense events), `SALES_RULE_KEY`, `SEQUENCE_KEY.ORDER` / `.INVOICE`, `LIMIT_KEY.ordersPerMonth`, `MODULE_KEY.SALES`, the 6 sales settings keys and the `sales.orders` menu key. Audit gained entity `order` and 7 actions; `EVENT_TYPE` / `event-payloads` got the sales rows.
2. **Schemas** (`packages/validation/src/sales/`, `@banijjik/validation/sales`): `OrderCreateRequest`, `OrderUpdateRequest`, `InstantOrderRequest`, `OrderTransitionRequest`, `OrderListQuery` — all strict (`.strict()`), so a client-sent price or total is `400 validation.unrecognized_keys`.
3. **Module** `apps/api/src/modules/commerce/sales/` with `module.manifest.ts` (CORE, routes, menu, settings, sequences, limits), domain (`order.entity.ts`, `payment-status.ts`, `business-date.ts`, `errors.ts`), application (create / place / update / transition / instant / delete-draft / read use cases, `sales-quote-lines.ts`, `sales-approval.ts`, `sales-settings-reader.ts`, ports), infrastructure (mongo model + repository + mapper, catalog/org/payment adapters) and presentation (`order.controller.ts`, `order-tenant.router.ts`).
4. **Money is the quoter's.** Lines go through `PriceQuoter` (3.4) in the same request; the order stores unit price, name, tax class and promotion ids as snapshots, so a later catalog change cannot rewrite an order. Totals are quote totals + `deliveryCharge` (0 for INSTANT/PICKUP).
5. **Stock.** Reservation keyed `(sourceType ORDER, sourceId orderId)` through the 3.3 `StockLedger`: place reserves, edit releases and re-reserves the difference, cancel releases, complete writes one SALE movement per component. Every stock write is inside the order's transaction.
6. **Discount approval** reuses the 3.4b PIN token: subject `order:<orderId>` (and `order:<orderId>:instant`), missing token → `403 APPROVAL_REQUIRED` before any number, counter step or reservation; `sales.discountOwnerWithoutApproval` (default on) exempts the OWNER.
7. **Numbers and the counter.** `ORDER` is FAST (gapless would burn numbers on an aborted place), `INVOICE` is GAPLESS and is taken at completion. `LIMIT_KEY.ordersPerMonth` is a conditional `$inc` in the place transaction (3.2a pattern) → `422 LIMIT_REACHED`.
8. **Instant sale** `POST /orders/instant`: create + place + complete in one transaction, `Idempotency-Key` required — the primitive POS (3.9) will call.
9. **Two hourly jobs** in `kernel/jobs`: `sales.expireDrafts` (`sales.draftExpiryHours`, default 48) and `sales.autoCancelPlaced` (`sales.placedAutoCancelHours`, default off) with `ORDER_CANCELLED` audit + event and the stock release. Both are idempotent.
10. **Wiring** added-only: `routes/module-registry.ts`, `routes/core-tenant-routers.ts`, `routes/tenant-module-routers.ts`, `routes/v1.ts` (model registration), new `routes/sales-tenant-router.ts`, `start-worker.ts` (job deps), `system-role-grants.ts`, `eslint/restrictions.mjs` + `scripts/new-module/new-module.test.mjs` (the `@banijjik/contracts/sales` and `/sales` subpath allow-lists).

### Blockers

1. **The token binds the amount.** `prepareOrderLines` now returns `manualDiscountTotal` (the quote's `Σ lineDiscount − promotionDiscount`, in the order currency — the line manual discounts plus the granted order discount) and `resolveApproval` consumes every token with it, on place, edit and instant. The number never comes from the client. The instant sale keeps the shared subject `order:instant` because the token is asked for before the order exists; the amount binding is what keeps one token to one sale at the approved size, and ADR-131's `order:<orderId>:instant` wording is amended to say so.
2. **The edit consumes the token inside its transaction.** `UpdateOrderUseCase.approvalOf` moved inside `unitOfWork.run`, as place and instant already had it.
3. **An edit cannot hollow a placed order.** New `assertContentOfPlacedOrder` (every non-DRAFT status): an edit that clears every line is `422 ORDER_NEEDS_LINE`, and a PICKUP order keeps an ACTIVE contact with a phone or the edit is `422 CONTACT_PHONE_REQUIRED` — the same rules place enforces. Emptying a DRAFT stays allowed.
4. **One failing row no longer stops a pass.** New `application/jobs/run-job-row.ts` wraps each row: a raced write (`AppError CONFLICT`) or a transition the status no longer allows (`DomainRuleError INVALID_TRANSITION`) is skipped; any other error is logged as `sales.job_row_failed` with the `orderId` and the pass continues.
