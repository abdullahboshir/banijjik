- **Deviations from plan (and why):**
  1. **API change beyond the menu (ADR-108, owner chose "add definitions to the API").** `GET` and `PATCH /settings` now also return `definitions` per key (`SettingValueSpec`, `allowsLocationOverride`). Without it the screen cannot draw inputs from the registry, and a hard-coded admin copy would break "manifest-driven". Add-only; a contract test is in `settings-api.test.ts`.
  2. The value mapping (`setting-value.ts`) is an app-local copy of the platform's `setting-input.ts` (the plan allowed this). Move to web-client when a third screen needs it.
  3. Light form state (`field-state.ts`) is split from the schema-heavy builders (`field-form.ts`) so the fields route stays under budget: `field-form-sheet` reached the page's first load through `new-field-button` and the route was 203.7 KiB; now 165.1.
  4. The template field for the browser test is added to every seeded template (`updateMany`) in `test-support/browser-stack.ts`, so test code does not name the industry key (lint rule ADR-033) and no lint scope was widened.
  5. Added `holdsPermissionAt` (`shell/permissions.ts`), `SourceBadge`, `useSheetSubmit` and `SheetFeedback` (`settings/`) as small shared pieces.
  6. Message keys `setting.<key>`, `module.<key>` (copied from the platform catalog keys), `terms.key.<term>` and the screen texts are in the **screen catalogs** (server-only), so the browser bundle is unchanged.

Forms, `/me/config` and value checks use `forEntity`, which never returns a hidden field; the list uses the new `forManagement` (a separate method, so no form can ask for hidden fields by mistake).
