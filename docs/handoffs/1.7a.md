## Rebase and loop guard

- **Rebase:** onto `main 25e31cd` (card 1.6a). Only conflicts: the two i18n catalogs (both key sets kept, add-only). No other file conflicted; `npm install` changed no tracked file. The API change of this card is still only `auth-cookies.ts` (+ test, README). The browser-test API start works unchanged (the API seeds packages at startup).
- **Redirect loop guard (closes the "possible redirect loop" gap above):** after a successful refresh the `/session` page sets `session_renewed=1` (Max-Age 15 s, SameSite=Lax, Path=/, not httpOnly) just before `location.replace(next)`. `requireSession` passes that fact to `sessionGuardTarget`: no marker goes to `/session`, marker goes to `/sign-in?next=...&reason=session`. `proxy.ts` deletes the marker on `/sign-in` (server components cannot delete cookies). The sign-in page shows `auth.session_unavailable` (bn + en) for that reason. No web storage.
- **Tests:** unit decision table (`session-guard-target.test.ts`); browser test strips `access_token` from every document request and asserts one `/session` round, the message, `reason=session`, and no leftover marker; browser test that a cross-origin 429 on sign-in shows the wait message (Retry-After is now exposed by the API CORS config). The 429 test asserts the message shape, not the number of minutes (the limiter reported 1 minute in this run).
