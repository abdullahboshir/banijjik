### Q2 — Is export bounded, org-scoped and limited to the customer's checkouts?

Yes.

- `fetchLimit = maxRows + 1`, `truncated = accesses.length > maxRows`, slice to `maxRows` (`checkout-privacy-participants.ts:86,94-96`). Test passes `maxRows: 1` against two checkouts and asserts `truncated === true` and one item (`checkout-privacy.api.test.ts:349-356`), so dropping the `+1` fails the test.
- Owner filter is `ownerType: "CUSTOMER"` + `identifier` + `revokedAt: null`, org-scoped (`checkout-privacy-participants.ts:87-92`; `mongo-checkout.repository.ts:142-167`). A claimed checkout has a CUSTOMER access and is included; an unclaimed guest checkout cannot match. Test 2 seeds one target, one GUEST-owned and one other-customer checkout and asserts exactly the target (`checkout-privacy.api.test.ts:359-401`).
- Checkouts and links are then fetched in two bounded batch reads by the same org and ids (`checkout-privacy-participants.ts:106-109`; `mongo-checkout.repository.ts:70-84`; `mongo-checkout-request-link.repository.ts:55-69`).

### Q4 — Do the tests assert their names, and would they fail on revert?

Reading the assertions against the fix, each of the five names is backed, and each fix is load-bearing:

- Remove `revokeForOwner` → `accessAfter.revokedAt` and `version === 2` fail (`checkout-privacy.api.test.ts:494-500`), and the list test still passes only because links are separately stamped.
- Remove the link stamping → `linkAfter.revokedAt.toISOString()` is `undefined` (`:543-547`) and `listAfter.total` is 1, not 0 (`:548-556`).
- Remove `redactContactSnapshots` → `checkoutAfter.contactSnapshot` deep-equal fails (`:503-511`).
- Remove `scrubPrincipalQuotes` → the direct quote's address/custom fields fail (`:514-527`); remove `scrubQuotesByIds` → the claimed quote's phone fails (`:529-540`). These are the two halves the author's stated mutation run targeted.
- Remove the export owner/org filter → test 2 returns 3 or 2 checkouts instead of 1 (`:399-400`), and test 5's cross-org export is not empty (`:791-796`).
- Remove truncation → `truncatedResult.truncated` is false (`:355`).

Test 5 also proves erasure isolation: erasing customer B in org A leaves org B access live and the snapshot unredacted, and the correct org B erase then redacts only B (`checkout-privacy.api.test.ts:754-827`). This would fail on any unscoped query. Gaps in test fidelity: M4, M5, M6, M10.

### Q5 — Cross-organisation

No cross-org write or read was found: every access/checkout/link/quote query and update includes `organizationId`, quote matching additionally keys on the globally unique `CUSTOMER:<customerAccountId>` principal. The cross-org test described above is execution evidence, not just inspection. Quote isolation is protected by the same filters but not asserted by the test (M10).

### Q6 — Privacy leaks left in export or retained links

- Export projection contains only the customer's own checkout ids, location, quote id, accepted total, their own contact snapshot, their own request links (type/id/public number/status/payment/hold) and `createdAt` (`checkout-privacy-participants.ts:28-58`; `packages/contracts/src/contact/customer-data-export.ts:85-114`). No `_id`, `organizationId`, `contactId` of others, hashes, versions, audit rows or provider payloads. A second customer's or unclaimed guest's data cannot enter via the owner filter.
- Retained links keep `checkoutRequestLinkId`, `requestId`, `publicNumber`, status, amounts and the internal `ownerIdentifier` (customer account id, not a phone). That is the economic evidence the handoff documents, and the links are `revokedAt`-stamped so the private list no longer serves them.
- Residuals: delivery `postalCode` survives the quote scrub (M1); export does not include the delivery address it scrubs (M3); provisional guest contact name and order recipient snapshots remain outside A5B (M9).
