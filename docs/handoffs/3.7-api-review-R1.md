The lifecycle still has holes that would trap real members, and the jobs are not robust. Fix every item, add the named tests, push, get CI green, update the handoff, and report the new run. Where a lead decision is given, follow it. If anything else is unclear, stop and ask.

## Blockers

1. **A manual renewal can never happen.** `renewEnrollment` refuses unless `today > periodEndsOn`. But the `renew` job expires a non-auto-renewing enrollment on `periodEndsOn + 1`, and EXPIRED cannot be renewed. So for `autoRenew: false` the "renew" endpoint (plan decision 3) has no usable window.
   **Lead decision (advance renewal):**
   - For a non-auto-renewing enrollment, `POST …/renew` is allowed while it is ACTIVE or OVERDUE and `today <= periodEndsOn`. It creates the **next** period right away: it starts on `periodEndsOn + 1`, and its fee is the current quote, or the locked fee with `lockPriceOnRenewal`. It emits `renewed`.
   - `currentEnrollmentPeriodId` does **not** move yet. Check-in, the overdue check and the reminder keep working on the period that is running now.
   - It is refused (`NOT_DUE`, or a new rule key `ALREADY_RENEWED`) when a period with `periodNumber + 1` already exists. It is also refused when the fixed term is reached (`periodNumber >= fixedTermPeriods`).
   - The `renew` job at `periodEndsOn + 1`:
     - if the next period exists, it moves `currentEnrollmentPeriodId` to it (versioned save, audit; no second `renewed` event)
     - else, if `autoRenew`, it creates the next period as today
     - else, it expires the enrollment
   - `freeze` is refused while an advance period exists. The lead decision on freeze allows only the latest period's end to move, and the latest period would not be the current one. Use a rule key and an i18n message.
   - `UNUSED_PERIODS` then refunds a paid advance period, which is what `11 §8.4` means.

   Tests:
   - a non-auto-renewing enrollment renewed 2 days before its end → 200 with two periods, and the current period is unchanged
   - the job on end + 1 moves the current period, and running it twice changes nothing
   - a second advance renew → refused
   - without an advance renew, the job expires the enrollment
   - freeze with an advance period → refused
   - a fixed term at its last period → renew refused

2. **A frozen member can get stuck forever.** `unfreezeEnrollment` refuses once `frozenDaysInYear > maxFreezeDaysPerYear`. Nothing unfreezes automatically, and the jobs skip FROZEN. A member who stays frozen past the limit can then never be unfrozen, renewed or expired. The only way out is cancel.
   **Lead decision:**
   - (a) Unfreeze is never refused because of the limit. `daysFrozen` records the real days. The latest period's end grows by `min(daysFrozen, allowance left before this freeze)`, so the yearly limit caps the credit, not the action. Note it in ADR-126.
   - (b) The daily `renew` job first ends the freeze of a FROZEN enrollment when its open freeze has used up the yearly allowance (only when `maxFreezeDaysPerYear` is set). It does that through the normal `unfreeze` transition, with actor null.

   Tests:
   - frozen 10 days with 7 allowed → unfreeze succeeds and the end moves by 7
   - the job ends a freeze that reached the allowance, and the enrollment then renews or expires normally
   - no limit set → the job leaves the freeze alone

3. **One bad enrollment stops the whole organization's job.** `runEnrollmentJob` throws, so the `for` loop in `buildEnrollmentJobs` stops and every later enrollment of that organization is skipped. That repeats daily. A likely cause: renewal calls `context.plan(enrollment)` and `context.fee(…)` again. Both throw as soon as the plan offering is archived, the variant is deactivated, or the location is closed.
   Fix:
   - (a) Catch the error per enrollment, report it through the central logger (`event: "enrollment.job_item_failed"`, `jobKey`, `enrollmentId`, `err`), and continue. Never use an empty catch.
   - (b) A renewal uses the enrollment's own `plan` snapshot for `billingPeriod`, `sessionLimitPerPeriod` and `fixedTermPeriods`. It does not read the live plan again.
   - (c) **Lead decision:** if the plan's offering or variant is no longer active or sellable at that location when an auto-renewal is due, the job expires the enrollment ("no renewal at period end → EXPIRED", `11 §8.1`). It does not create a period. The same check refuses a manual advance renew (rule key `PLAN`).

   Tests:
   - two enrollments in one organization; the plan of the first is archived; run `renew` → the first is EXPIRED, the second has its next period
   - a fee quoter that throws for one enrollment → that one is unchanged and logged, and the next one still renews

4. **The jobs depend on hitting one exact minute.** `isLocalMidnight` is true only when the clock reads `00:00`, and the runner passes one `now` for all organizations. A late tick, a worker restart or a slow queue around midnight skips the whole day. The reminder uses `today === periodEndsOn - reminderDays`, so a missed day loses it for good.
   **Lead decision:**
   - Remove `isLocalMidnight`. Run the three jobs `everyMinutes: 60` and let state make them idempotent, which it mostly already does.
   - The reminder fires once per **period**: when `periodEndsOn - reminderDays <= today <= periodEndsOn`, and only if no reminder was sent for that period. Store `reminderSentForEnrollmentPeriodId` with a conditional update. Replace `lastReminderOn`, which only dedupes per day.
   - The candidate scan becomes `status: { $in: <non-terminal statuses> }` and gets an index `{ organizationId: 1, status: 1, enrollmentId: 1 }`. Today it scans every enrollment ever created, including terminal ones, through the unique index. Record the index in the README `db:sync-indexes` note.

   Tests:
   - the reminder job run on two days inside the window → one `renewalDueReached` event
   - first run on the second day of the window (the first day missed) → still one event
   - `renew` run at 01:00 and again at 02:00 on end + 1 → one new period

## Must fix (smaller)

5. **A future-start enrollment never becomes ACTIVE by itself.** With `requirePaymentToActivate` false, create sets ACTIVE only when `startsOn <= today`. A later start stays PENDING until staff act. `11 §8.1` says PENDING waits for payment or for the start. Fix: the daily `renew` job activates a PENDING enrollment when `today >= startsOn` and payment is not required (the `activate` transition, actor null, `activated` event). Test: create with a start tomorrow → PENDING; the job tomorrow → ACTIVE; run twice → one event.

6. **The bed release date has to be an exclusive end (lead correction).** My bed decision said "a new enrollment starting on or after the release date gets the bed" and set the release date to "the last period's end". But `periodEndsOn` is the last day the bed is **used** (inclusive), so a new resident could take it on that same day.
   Fix:
   - The hold's `endsOn` is exclusive. On expire and complete, set it to `periodEndsOn + 1`. On cancel, set it to `max(today, hold.startsOn)`, so a hold that never started has zero length.
   - `Enrollment.endsOn` stays the inclusive last day.
   - Correct the ADR-126 text.

   Tests:
   - after an expiry whose last period ends 2026-03-31, a new bed enrollment starting 2026-03-31 → 409, and one starting 2026-04-01 → 201
   - cancelling a future-start enrollment before it starts → a new enrollment on the same start date gets the bed

7. **State the payment gap in STATUS and the handoff.** Until periods can be paid (3.8), no period is ever PAID or WAIVED. So:
   - (a) with the default `requirePaymentToActivate` (true), no enrollment can ever be activated
   - (b) every ACTIVE enrollment turns OVERDUE after `graceDays`, and check-in is then blocked by default

   Write both effects in the STATUS row and under "Known gaps". Also name the follow-up: register `ENROLLMENT` in payment's request readers; allocations to `enrollmentPeriodId`; PAID and PARTIAL; OVERDUE back to ACTIVE; activation on the first full payment of period 1.

   Also: `docs/STATUS.md` is modified in the folder but shows no content change (`git diff` prints no lines, probably only line endings). Make sure the row really says `implemented (awaiting review), part A, CI <run link>`, and commit it with LF endings.

8. **Booking now exports its whole infrastructure repository.** `booking/index.ts` exports `MongoBookingRepository` (and `localDateTimeToUtc`) only so that enrollment can find today's confirmed booking. That lets another module call every booking write. Replace both with one narrow read-only function in booking's `index.ts`, built like `buildContactBillToReader`. For example: `buildConfirmedBookingReader(): { findForCheckIn({ contactId, locationId, businessDate, bookingId? }): Promise<BookingId | undefined> }`. It does the timezone handling inside booking. Remove the repository export.

Return the custom-field validation error that contacts and offerings use, with the field details. Test: an unknown or invalid enrollment custom field → 400 with that code, not the plan message.
