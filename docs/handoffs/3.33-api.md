# Handoff: 3.33 API (event sessions occupy their resources)

## Result

An event session that names resources takes each resource's whole capacity in the shared 5-minute `resource_slot_usages` buckets for its window (conditional upsert on `used: 0`, so a booking, a rental or another session in any bucket refuses it). The units taken are stored on the session as `resourceHolds`. Cancel and move release exactly those units; completion keeps past counters. A time-off overlap, a resource of another location or organization, more than ten or duplicated resource ids, and a span over 31 days are refused.

## What changed, by area

- Contracts and validation: rule keys `EVENT_SESSION_RESOURCE_BUSY`, `EVENT_SESSION_RESOURCE_SPAN_TOO_LONG`, `MAX_EVENT_SESSION_RESOURCES`; `resourceIds` max 10 and unique.
- Domain: `EventSession.resourceHolds`, span rule on create and update, `cancel` clears holds, `complete` keeps them; `eventSessionResourceBusyError`.
- Application: `event-session-resource-holds.ts` (take in sorted order, release by stored units); `EventSessionUseCases` create (one retried transaction), move (one retried transaction), cancel (existing unit of work).
- Infrastructure: `takeWholeResource` / `releaseWholeResource` on the slot repository, `resourceHolds` schema field and `$set`.
- Docs: ADR-141, `11 §5.5` note, booking README.

## Deviations from the plan

- Move writes the session once (one version bump). The earlier code wrote it twice, so a move answered `version + 2`. Now a stale `version` is compared with the stored one before any counter is touched, and the single versioned write at the end still guards a concurrent change (it rolls the transaction back).
- `EventSession.update` checks holds against `resourceIds` only when the caller passes new holds. A session created before this card has empty holds and must stay editable (capacity edit); the plan's strict check would have thrown INTERNAL for it. `create` stays strict.
- Create now passes `eventSessionResourceBusyError` as the retry-exhaustion mapping (plan decision 10); the first draft left the default.
- Test support: new `test-support/booking-hall-world.ts` (shared hall world for the API and concurrency tests). The hall is a STYLIST-type resource linked to a RENTAL and a SERVICE offering; the organization is switched between the COACHING, RESTAURANT and SALON templates to publish the three kinds (each template sells one kind), and ends on SALON.
- A5 inserts the time-off row through `MongoResourceTimeOffRepository` instead of the endpoint (see the finding below).

## Finding outside the card

`POST /orgs/:org/resources/:resourceId/time-off` answers 500 in every case: `CreateResourceTimeOffUseCase` calls `audit.record` outside a transaction, and the recorder throws without one. No existing test covered the endpoint. Fix in a separate card (wrap the insert and audit in the unit of work).

## Tests

- Validation (`packages/validation/src/booking/event-session-schemas.test.ts`): V1 `rejects more than ten resources on an event session`, V2 `rejects a resource named twice on an event session`.
- Domain (`event-session.entity.test.ts`): U1 `a session with resources longer than thirty-one days is refused`, U2 `a session without resources may last longer than thirty-one days`, U3 `cancel clears the resource holds and complete keeps them`, U4 `holds that do not match the resource ids are refused`, plus `a capacity edit of a session created before holds existed keeps its empty holds`.
- API (`event-session-resource-api.test.ts`, real Mongo, real rentals and a real availability call): A1 to A15 under the plan names. A3, A6 to A9, A11 and A12 compare the `resource_slot_usages` buckets before and after.
- Concurrency (`event-session-concurrency.test.ts`): C1 `a session and a rental racing for the same hall never both win` and C2 `two sessions racing for the same hall never both win`. Each runs five rounds on a fresh hall of capacity 2 with two parallel HTTP writes; exactly one 201, the loser is 409 `SLOT_UNAVAILABLE`, and all twelve buckets hold the winner's units (2 for a session, 1 for a rental).
- Job (`booking-scheduled-jobs.test.ts`): J1 `completing an ended session keeps its hall counters` (the earlier draft had renamed an unrelated test; it is restored).
