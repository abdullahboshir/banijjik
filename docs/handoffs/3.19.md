# 3.19 Config inside scheduled jobs and event handlers (handoff)

Lead card (Opus 5.5, 2026-10-23), T1 foundation fix. Found in the 3.5a Part A handoff and confirmed by the lead.

## The defect
`SettingsResolver.resolve` (and every other caller of `OrgConfigReader.current()`) needs the request's `configVersion`. The job runner and the event handler runner enter the organization with `runInOrganizationContext`, which sets the organization but no `configVersion`, so `current()` threw `errors.missing_tenant_context`. In production every scheduled job that reads settings failed each hour with `jobs.organization_failed`: booking `markNoShows` (merged, covered only with a faked reader) and the 3.5a sales jobs. Event handlers that read settings would fail the same way.

## The fix
`apps/api/src/modules/platform/entitlement/application/org-config.service.ts`: `current()` still throws without an organization. Without a `configVersion` it now reads the organization's version, as the existing `forOrganization` does for code outside a request. The cache key is unchanged (`configVersion` is part of it), so a job sees a new config as soon as the organization's version moves. The organization comes from the tenant context, never from input, so this adds no cross-organization path. Request paths are unchanged: `tenantContext` always sets `configVersion`.

## Tests
`entitlement-api.test.ts` › the config inside a scheduled job or an event handler › resolves the organization's modules without a request's configVersion (card 3.19). It runs `current()` in the job runner's kind of context (organization, no member, no `configVersion`) and checks a revoked module is absent.

## Deviations
None. No plan file: a one-method fix the lead found during the 3.5a review.
