## Deviations from the plan (mechanical adaptations to real names; none changes behaviour)

1. `PERMISSION_KEY` is a `const` object (`IAM_ROLE_READ: "iam.role.read"`), not `defineEnum`, because the keys contain dots. `permissionDefinition(key, options?)` in contracts builds a manifest entry (label key `permission.<key>`, surface ADMIN).
2. Validation has one `iam/role-schemas.ts` (create, update, archive, params) plus `pagination.ts`, instead of three schema files. `permissionKeys` repeats are collapsed; unknown keys are rejected by `z.enum`.
3. `Role` gained `name`, `status`, `updatedByUserId`; `nameKey` became nullable (system roles have `nameKey`, custom roles have `name`). Schema indexes added: partial unique `{ organizationId, name }` for ACTIVE named roles (an archived role frees its name) and `{ organizationId, isSystem, name, roleId }` for the list.
4. The new repository methods live in a separate port `RoleManagementRepository`; `RoleRepository` is unchanged. Reason: extending `RoleRepository` would have broken the fake in `provision-system-roles.use-case.test.ts`, and existing tests keep their text. `MongoRoleRepository` implements both.
5. iam cannot import organization (organization already imports iam). So iam defines the ports `MemberAccessReader` and `RolesVersionBumper`, organization implements them (`buildMemberAccessReader`, `buildRolesVersionBumper`) and `routes/v1.ts` wires them. The plan said the gate "reads the member in the org context"; this is how.
6. `buildIamTenantRouter` takes `{ catalog, memberAccess, rolesVersion, permission, clock }`; `buildPermissionGate` takes `{ catalog, memberAccess, clock, cache? }`.
7. `V1Dependencies` got `tenantRouterFactories` (functions that receive `permission`), so probe routes in tests can use the real guard; `startIamApi` passes it through. `tenantRouters` keeps its meaning and is mounted after the iam router.
8. Cases the plan left open, decided mechanically:
   - editing or archiving an ARCHIVED role: `409 INVALID_TRANSITION` with `details.currentStatus`
   - a name taken by another ACTIVE role: `409 DUPLICATE` with `details.field = "name"` (key `errors.role_name_taken`)
   - `?location=` outside the narrowed set: `403 FORBIDDEN` (the caller may be at that location, but without this permission)
   - list order: `isSystem` desc, `name`, `roleId` (system roles in creation order: OWNER, MANAGER, CASHIER, STAFF, RIDER, VIEWER)
   - `memberCount` counts ACTIVE members once, even with the role at several locations
9. The "OWNER gets a key of a later module" test uses a cast to a key that is not in `PERMISSION_KEY`, at the grant-function level (the catalogue itself, correctly, refuses unknown keys). The cast has a reason comment.
10. `ActiveMembership` has two new required fields (`memberVersion`, `rolesVersion`); no existing test built that shape.

## Not done / known gaps

- **No membership cache** (decision 12): `tenantContext` still does its two indexed reads per tenant request. Redis work, card 1.5.
- **Redis adapter** for `PermissionCache`: card 1.5. The port is ready; the cache holds Sets and Maps, so that adapter needs a serialization.
- **Archive race:** the "role in use" check and the archive share a transaction, but a member assignment written at the same moment is not guarded. The member endpoints (1.7) must refuse to assign a non-ACTIVE role and bump `Member.version`. An archived role grants nothing, so the worst case is a member who loses a role's keys, never one who gains keys.
- **Key-less read:** "VIEWER R (profile)" means reading the own organization profile needs no permission key. Written in the iam README; there is no profile endpoint yet.
- Organization, member, location and invitation endpoints that use the `organization.*` keys: card 1.7. Entitlement gate and `/me/config`: 1.6 (it will replace the manifest list passed in `routes/v1.ts`).
- Approval PINs and platform permissions: out of scope as planned.
