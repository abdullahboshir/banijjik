## Checked
- ORDER reader: DRAFT, CANCELLED, missing and foreign orders read as `undefined`; COMPLETED is `AFTER_REVENUE`. Payment posting keeps the stored `revenueState` per allocation, so posting the cancel credit after the order is CANCELLED does not need the reader.
- The settlement generalization (`settle-request-termination.ts`) differs from the old booking code only in the request type parameter and the note label. Booking callers keep `settleBookingTermination`.
- Cancel: the whole net paid amount becomes one `CANCELLATION` store credit for the order's contact, the summary total drops to 0 (leaves dues), all inside the cancel transaction before the versioned order update; a second cancel is stopped by the version.
- Edit: `updateTotal` and `updateContact` read the net paid amount and write the summary in the edit transaction, so a concurrent payment on the same summary is a write conflict and retries.
- `paymentStatus` of a summary is computed on read, so a changed total never leaves a stale status.
- List: one `$in` query per page on the unique `{ organizationId, requestType, requestId }` index; the test spies on `findByRequests`.
- `requiredAdvance`: integer math, PERCENT clamped and rounded up, FIXED capped at the total.

## Fixed by the lead
- `sales-settings-reader.ts`: the integer setting helper was named `hoursOf` but also reads `sales.advance.value`; renamed to `integerOf`.

## Follow-ups (not blockers)
1. Confirm reads the summary but does not write it, so a refund committed at the same moment is not a write conflict (snapshot isolation). Staff can refund after confirm anyway, so the advance is a gate at confirm time only. If the advance must keep holding after confirm, a later card refuses refunds below the required advance on a CONFIRMED order.
2. An order placed before 3.23 has no summary. Its cancel with nothing paid writes nothing to the summary collection, so a first payment committed at the same moment could allocate to the just-cancelled order. Narrow (older orders only); staff refund it.
3. An instant sale creates an UNPAID summary and shows in dues until card 3.9 records the POS payment in the same transaction.
