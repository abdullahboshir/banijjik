## Per decision

### 1. Module `core/custom-field` (SYSTEM)
Permissions `custom-field.definition.{read,create,update,archive}`. Admin route prefix `/orgs/:organizationId/custom-fields`. Event `custom-field.definition.changed`. `customFieldEntities: []`. Grants: OWNER and MANAGER ALL, CASHIER, STAFF and VIEWER READ, RIDER NONE. The three write keys are organization-wide (ADR-095). Read stays location-scoped. Writes call `requireAllLocations()`. No `Idempotency-Key`.

Proved by the staff and one-location manager case in `custom-field-api.test.ts`, and by the viewer config case that now includes `custom-field.definition.read`.

### 2. Entity types and availability
`CUSTOM_FIELD_ENTITY_TYPE` is the eleven names in the plan. Startup checks production manifests only (`MODULE_MANIFESTS`), not test probes. An entity is offered when a module in the resolved config declares it. CORE `contact` is effective when the template allows the contact module. Tests pass a contact probe through `startIamApi({ tenantRouters: [], extraManifests })`.

Proved by `declared-entities.test.ts` and by `entityType=booking` on RETAIL returning 404.

### 3–4. INDUSTRY fields are read, not copied, and seeds are labelled
`ReadIndustryCustomFieldsUseCase` returns the template's `configuration.customFields`. A missing template throws `errors.industry_template_missing`. Every seed field has `label.bn` and `label.en`. Every SELECT and MULTI_SELECT option has `optionLabels`. A missing label falls back to the field key.

Proved by `industry-template-seeds.test.ts` ("gives every custom field a Bangla and English label") and by the salon list in the API test.

### 5–6. ORGANIZATION definitions and preferences
Collection `custom_field_definitions`, tenant, versioned, audit fields. Unique on `(organizationId, entityType, offeringKind ?? null, fieldKey)`, including against INDUSTRY keys (`409`, `errors.custom_field_key_taken`). At most 50 ACTIVE definitions per entity type (`422`, `CUSTOM_FIELD_LIMIT`). Archive never deletes. Preferences live in `custom_field_preferences`. Hiding a required field is `422` `CUSTOM_FIELD_REQUIRED`. Existing option keys cannot be removed (`422` `CUSTOM_FIELD_OPTIONS_LOCKED`). Options on a non-select, `fieldType` or `fieldKey` on PATCH, and `max < min` are 400.

Proved by `custom-field-api.test.ts`: the happy path, the bad-definition case, and the duplicate / 51st / hide-required / type-change case (including a concurrent double create).

### 7–8. Effective list and endpoints
Industry fields (preferences applied, hidden ones omitted) come first, then ACTIVE organization fields, each group sorted by `sortOrder` then key. Industry items have `isEditable: false`. Paging is in memory. `PATCH /custom-fields/preferences` is registered before `PATCH /:customFieldDefinitionId`. Each write records one audit entry, emits `custom-field.definition.changed`, and bumps `configVersion` by 1. A preference batch is one write: one audit, one event (the first row), one bump.

Proved by the happy-path case, which checks the salon contact order, a create, a patch, an archive, a hide, a rename and a reorder, plus audit, outbox and `configVersion`.

### 9–10. Shared value builder and ADR-102
`buildCustomFieldValuesSchema` is browser-safe. DECIMAL is a string. There is no user regex. `redactSensitive` and `toSearchEntries` live beside it. Search storage (`customFieldSearch`) is the Phase 3 attribute pattern, recorded in ADR-102. `docs/14-API.md` and the `custom-field` row of `docs/10-MODULE-CATALOG.md` §10 match the grants.

Proved by `custom-field-values.test.ts` (one valid and two invalid values per type, create/update required rules, unknown and storefront-hidden keys, phone and email normalization, February 30, UTC datetime, sensitive redaction, search entries).

## Deviations from the plan

1. The startup check runs on `MODULE_MANIFESTS` only. `registry.all()` includes test probes whose entities (`contract_*`) are not in the enum.
2. The salon contact list asserts four fields (`skin_type`, `hair_type`, `allergies`, `preferred_stylist`). The plan text says five. The fifth salon field, `special_request`, is a booking field.
3. The industry reader is more than one export line. The use case takes `IndustryTemplateRepository` and a small `OrganizationTemplateLookup`, so it never names `industryTemplateKey` (R16, R18). `buildIndustryCustomFieldReader()` and the type `IndustryCustomFieldReader` are exported from `platform/industry/index.ts`. The template-key lookup adapter lives in that index.
4. `IndustryTemplateCustomField` gained optional `label` and `optionLabels` (`packages/contracts/src/platform/industry-template.ts`). The seed schema output would not assign without it. The plan's file list did not name that file.
5. `industry-template-schemas.ts` also gained an `optionLabelsMatch` refine, so a SELECT option without a label fails seed parse. The plan allowed only the two optional keys.
6. The three write keys were added to `ORGANIZATION_WIDE_PERMISSION_KEYS`. The plan says writes need ALL locations. ADR-095 is how that is enforced.
7. The event-name pattern now allows a hyphen in the module segment (`custom-field.definition.changed`). The permission-key length assertion moved from 16 to 20. Audit entity types and the event expected list include the new names.
8. `CUSTOM_FIELD_OPTIONS_LOCKED` is an extra rule key. The plan says existing option keys are never removed and did not name the code.
9. A preference batch is one HTTP write: one audit entry, one event for the first row, and one `configVersion` bump. Rows are still applied inside the transaction.
10. Organization definitions do not store the ADR-073 link object. The plan table omits it. Link behaviour is card 3.1.
11. The effective list is paged in memory. Industry fields are not rows of the tenant collection, and an organization holds at most 50 of its own.
12. Omitting `version` on the first preference creates the row (the schema rejects version 0). Sending a version when no row exists, or omitting it when a row exists, is 409 `versionConflict`.
13. Seeds are inserted only when missing, so an existing database keeps unlabeled rows until 2.1b or a re-seed.
14. `industry-template-seeds.test.ts` gained the label assertion at the end of its describe. That file is under `platform/industry`, which 2.1b also edits.
15. The API test lives at `apps/api/src/modules/core/custom-field/custom-field-api.test.ts`, not under `presentation/`. A presentation test must not import the repository (boundaries). The 50-field setup uses the repository inside `withOrganizationContext`.
16. `buildEffectiveCustomFieldReader()` is exported from `core/custom-field/index.ts` for Phase 3, beside `buildCustomFieldModule`.
17. `docs/10-MODULE-CATALOG.md` §10 is split into a `settings` row and a `custom-field` row. Section 5 still has the combined "settings / custom-field" row, which stays accurate.

- An already-seeded database was not migrated. New databases get the labels. Old rows stay unlabeled until 2.1b or a re-seed.
