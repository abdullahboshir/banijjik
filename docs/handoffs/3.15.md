## Known gaps: production replay race → 3.16 (T1)

Source references below are one-based lines at code commit `e7e44842` (production files are unchanged).

1. `apps/api/src/kernel/events/event-worker.ts:55` awaits writing the final dead letter. `dead-letter.ts:22` writes the MongoDB row and `dead-letter.ts:65` awaits that write. The worker's `event-worker.ts:115` awaits `recordFailure`, then only at `event-worker.ts:116` rethrows to BullMQ. Consequently the MongoDB FAILED row can become visible while the Redis job is still ACTIVE.
2. An operator can now request replay. The existing worker test observes only MongoDB in `ordered-event-worker.test.ts:290`; it requests replay at line 324 after receiving that row at line 319. MongoDB visibility is not a BullMQ terminal-state barrier.
3. `dead-letter-replayer.ts:88` reads the existing job; line 92 removes it only if `old.isFailed()` is already true. If the old job is still active, it remains in the queue. Lines 93–98 call `jobs.enqueue` with the same event/handler; `event-queue.ts:51` uses the stable ID from `buildEventJobId`.
4. BullMQ deduplicates that add against the old job ID, so successful enqueue does not guarantee a fresh job. Nevertheless `dead-letter-replayer.ts:99–104` changes REPLAY_REQUESTED to REPLAYED and writes `requeuedAt`.
5. The old final attempt then becomes FAILED. No new attempt is queued, the row is already REPLAYED, and the ordered stream remains blocked. The observed replay test timeout is consistent with this interleaving; the historical log alone does not prove the exact scheduling on that run. A deterministic production regression and T1 fix belong to 3.16.

**Owner explicitly confirmed this race and instructed that 3.15 must not expand scope.** Worker production code and its tests remain unchanged. No wait for Redis FAILED was inserted into the existing test to hide the API-visible race, no mock replaces replay, and nothing is skipped. Its 20/20 baseline result is not evidence that the production race has been fixed.
