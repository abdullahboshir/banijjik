# Handoff: card 3.36 · Stable enrollment browser test (T3, lead card)

Date: 2026-10-25 · Branch `s/3.36-stable-enrollment-browser-test` · By: lead (Opus 5.5)

## Why
`enrollment-screens.browser.test.ts` › "enrolls a member, refuses activation until period 1 is paid, then activates and checks in twice" failed at least six times on 2026-10-24/25 (among them CI 40126070188, 40131011005, 40133527668, 40134514743 and twice on the 3.34 branch), always after the payment.

## Cause
Since 3.24 (`7fb5061f`) the admin browser stack starts the worker as well as the API. The worker's payment handler syncs the paid period and activates the PENDING enrollment (3.27 decision 7). The test still assumed no worker ("Activate syncs the paid period itself") and clicked Activate with the version it had loaded. When the worker activated first, the click sent a stale version and the API answered a correct 409 ("someone else changed this, reload"); the page was not reloaded, so the ACTIVE badge never showed. The first fix attempt (reload before the click) only narrowed the window; its explain helper showed the 409 in CI 40134514743.

No application bug: the 409 is the intended answer to a stale version.

## What changed
- After the payment the test reloads the detail page every 500 ms, for up to 30 s, until the ACTIVE badge shows (the worker's activation). It no longer clicks Activate after the payment.
- `reloadUntilBadge` (test-local): a timeout throws with the first 600 characters of `main`, so a future failure names its cause.
- The staff path "Activate right after a payment, before the handler ran" stays covered by the API test `enrollment-payment-api.test.ts` › "activates on a staff action right after the payment, before the handler ran".
- No application code changed.

## Tests
The changed browser test itself; CI run on the branch head.

## Known gaps
- One older failure at the payment dialog (not opening within 30 s) is not addressed; if it returns, give that wait the same explanation on timeout.
- `docs/LEAD-STATE.md` said the browser stack starts no worker; the lead corrects it at the next state save.
