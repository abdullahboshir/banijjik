## Goal

A non-technical owner can select an allowed template, edit the content and design options permitted by the platform, preview on phone/desktop, publish and safely restore a previous version. The public site changes only after publication.

## Decisions

1. Website settings home has Site, Pages, Design, Domain and History cards with one-line help. Domain card links to 4.2. One active location hides the location choice; multiple public locations are a form field, never a global switcher.
2. Owner/manager with website.site.update may edit, website.site.publish may publish, website.site.read may preview/history. All-site changes require all-location authority. Never treat hidden buttons as authorization. Website-module-off behavior comes from manifest and API, not package-name conditionals.
3. Fetch allowed templates through resolver-projected keys plus compatibility. Tenant never sets industry or sees another business's site comparison results. Template adoption targets an immutable published revision, never the mutable latest draft.
4. First adoption uses organization branding plus selected preset. Replacing an existing template creates a draft and preserves previous published version. Provide an explicit diff of changed pages/sections/content and ask confirmation **inside the product** before applying the destructive draft replacement. No silent auto-upgrade; current template revision remains selectable while published and compatible.
5. Upgrade/replacement cannot weaken platform per-site restrictions. Current site policy remains authoritative; if new structure cannot satisfy locked required regions, tenant adoption is refused with an explanation to contact the platform. Only a platform operator can change that policy. For first creation, policy is copied from template.
6. Owner can change only allowed fields/palettes/variants. Lock icon and help explain why a control is disabled. Reorder buttons provide keyboard/mobile access. Server revalidates the complete result; client shares schema but is not trusted.
7. Explicit Save draft and Publish, with clear saved/unsaved/live states; no auto-publish and no implicit saving on tab close. Navigation with unsaved changes uses the app's existing unsaved-change prompt. On 409 preserve local unsaved edits, show server changes and offer reload; do not overwrite another actor automatically.
8. Preview renders the server-validated draft with the same packages/ui website renderer as the storefront; loading/validation/error state is visible. It is within authenticated admin/platform origin, no public draft URL. Embedded action buttons are inert; preview never initiates a real checkout, guest session, email or provider action.
9. Content upload uses file module and existing ownership/purpose rules; public website image selection cannot browse private directory photos. Orphaned draft asset cleanup uses file module policy; this card does not delete live images.
10. Publish shows a concise summary and validates schema, references, modules and current policy again. On success display publishedAt and link to resolved canonical host (4.2). A failed publish leaves live site unchanged. Retry uses same idempotency key until response is known.
11. History lists revision/date/publisher label and change summary, paginated. Restore first copies a previous snapshot into a draft through current policy; show diff and preview, then explicit Publish produces a new revision. A disabled capability or deleted private asset blocks restore until resolved, never revives an obsolete permission.
12. Read-only account/subscription state shows saved site and support/billing link; write APIs refuse. No deleting site history or arbitrary reset-to-defaults shortcut.
13. BN/EN content tabs use LocalizedText and existing fallback rules; UI action text always i18n keys. Show terms-driven offering/contact labels. Public user content is escaped and safe Markdown only; no source-code editor.
14. Small-screen design: page/section list as cards, inspector in sheet, sticky Save/Publish actions, 44 px controls, no nested canvas scrolling. Phone/desktop preview controls are viewport simulation, not promises of performance. Lazy-load heavy editor modules on editor routes only.

## Audit correction: adoption, preview and publication (2026-10-28)

First adoption uses the SAME migration fence/import path as 4.1 C1, preserving all saved static content including unpublished drafts and frozen legacy live content until first publication. It cannot treat a migrated draft as an empty new site. expectedVersion=0 is valid only when no Site exists; a racing platform create/adoption causes conflict and reload, never policy replacement. Existing-site replacement keeps current SiteEditPolicy and compares locked content/structure as well as required region presence. Stable region identities cannot be bypassed by new page/section IDs. The adoption preview includes every static/page/content removal and the selected immutable template revision; adoption rechecks expectedVersion, eligibility and that exact diff/input hash before accepting confirmedReplacement.

Preview is one shared renderer in PREVIEW mode, with links/forms/handlers disabled at the component boundary (not a CSS overlay). Live data comes through explicitly composed, permission-checked readers; no server-side loopback fetch to a public/custom host and no public preview token. Production PUBLIC mode uses the sanitized public projection. Test clicks, keyboard submit and hydration cannot create sessions or requests in preview. Unpublish uses 4.1's single command, explicit product confirmation and same-key retries; it immediately hides the site without exposing legacy fallback. B2 includes this action and history states.

PublisherLabel is an authorized human-facing label, never a raw platform operator email/ID; tenant history can say platform operator via i18n. File selection uses WEBSITE_IMAGE from 4.1 F; upload and published-file access retain current ownership/visibility gates. Adopt/save/publish/restore checks page/SEO/navigation policy along with sections. API and manifest define the canonical editor route; the route above is planned, and existing /website/pages remains a working compatibility entry in the same shell.

Add tests P4-07/P4-08/P4-12/P4-17/P4-23 from [assurance](phase-4-assurance.md), first-adopt versus operator-policy race, archived-template eligibility changing after preview, destructive diff changing before apply, and unpublish followed by a stale cached request. Freeze A1/A2 exact files and exported template/preview ports after dependencies merge; both are T1 review seams.

## Out of scope

## Risks & checks

Do not confuse preview with authorization or restore with permission rollback. Run targeted API policy tests, UI state tests and real admin browser suite; verify preview/published parity using one fixture and shared renderer. Full CI gates and merge check for UI; independent T1 review for policy/adoption seam.
