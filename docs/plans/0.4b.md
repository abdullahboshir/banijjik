# Plan: card 0.4b · DB kernel: connections, models(ctx), transactions, sequences, version, runAsSystem

Tier: **T1** · Planned by: Opus 5.5 · Date: 2026-10-10 · Based on: `main c823fcc` + 0.3 + plan `0.4a`. **Starts after 0.4a is merged.** If 0.4a's code differs from its plan's interfaces, a PLAN session refreshes this plan first.

## Goal
The API connects to MongoDB (replica set) at startup and closes the connection on shutdown. Business code gets Mongoose models only through `models(ctx)`, which picks the right database:
- **platform DB:** identity, access, configuration
- **tenant DB:** business records (ADR-043)

The tenant side works for shared tenants now and has a single switch point for dedicated tenants later (ADR-023).

The kernel also provides:
- **`withTransaction()`:** all-or-nothing writes, retried on transient errors, reused when nested, with post-commit callbacks
- **per-org atomic document numbers**
- **a mapper base** that strips `_id`
- **an optimistic-concurrency update helper** that throws `409 CONFLICT`
- **`runAsSystem(reason, fn)`**, typed and logged
- **`GET /ready`**, which checks the database

## Decisions
1. **One cluster client, two databases.** At startup, `connectDatabases(config)` opens one Mongoose connection with `platformUrl` and derives the tenant DB with `connection.useDb(tenantDbName, { useCache: true })`, where `tenantDbName` is parsed from `tenantSharedUrl`.
   - Rule: both URLs must point to the same hosts. If the host part differs, startup fails with `config.invalid` style issue `DB_TENANT_SHARED_URL: INVALID (must be on the same cluster as DB_PLATFORM_URL until dedicated tenants exist)`.
   - Why: one client means one session can span both databases in a transaction (needed by org creation in 1.2 and by any write that touches config + business records), and it uses one connection pool.
   - Dedicated tenants (Phase 8) will add a second client per tenant behind the same accessor.
2. **Model registry** (`kernel/db/model-registry.ts`). Modules register schemas, never models:
   ```ts
   registerModel({ modelName: "Order", collectionName: "orders", database: "TENANT", schema })
   ```
   Registration happens at startup from each module's infrastructure code (wired by `routes/v1.ts`'s module list in later cards). Duplicate `modelName` throws.
   - `database: "PLATFORM" | "TENANT"` is a contracts enum `DATABASE_KIND`.
3. **`models(ctx)`** (`kernel/db/models.ts`): `models(ctx: ModelContext).get<Document>(modelName): Model<Document>`.
   - `PLATFORM` models resolve on the platform connection.
   - `TENANT` models resolve on the tenant connection of the context's deployment. `ModelContext = { organizationId?: string; deployment?: "SHARED" | "DEDICATED" }`.
   - `DEDICATED` throws `AppError(INTERNAL, messageKey "errors.dedicated_not_supported")` until Phase 8. `organizationId` without `deployment` means `SHARED`.
   - Models are compiled once per connection (cached).
   - **Tenant filtering is not in this card.** The tenant plugin (auto `organizationId` filter, throw without context) is card 1.3. 0.4b only guarantees that every model is obtained through `models(ctx)`, so 1.3 can attach the plugin in one place: the registry applies "global plugins" registered by `addGlobalSchemaPlugin(plugin, { database })` before compiling. Expose that hook now, with no plugins registered.
4. **Common schema parts** (`kernel/db/schema-parts.ts`):
   - `auditFields`: `createdAt`, `updatedAt` via `timestamps: true`; `createdByUserId`, `updatedByUserId`: `String`, default null
   - `versionField` (`version: { type: Number, required: true, default: 1 }`)
   - `domainIdField(name)` (String, required, immutable)
   - Every schema uses `{ versionKey: false, id: false, strict: "throw" }` (Mongoose's `__v` is replaced by our explicit `version`, ADR-036).
   - Embedded sub-schemas use `{ _id: false }`.
5. **Mapper base** (`kernel/db/mapper.ts`): `stripMongoInternals<Record>(document): Omit<Record, "_id" | "__v">` for lean results. Repositories call it before building domain objects. It is a pure function with no class hierarchy (no clever inheritance). Projection helpers are not part of this card.
6. **Optimistic concurrency** (`kernel/db/versioned-update.ts`): `updateVersioned({ model, filter, expectedVersion, update, session? })`.
   - Runs `findOneAndUpdate({ ...filter, version: expectedVersion }, { ...update, $inc: { version: 1 } }, { new: true, session, lean: true })`.
   - When nothing matches: if a document matches `filter`, throw `conflict({ currentVersion })`; otherwise throw `notFound()`.
   - Returns the stripped document.
7. **`withTransaction(work, options?)`** (`kernel/db/with-transaction.ts`), ported rules:
   - **Nested reuse:** if a session is active (AsyncLocalStorage), `work(session)` runs in it.
   - **Outer call:** start a session on the cluster client; run `session.withTransaction` with `readConcern: { level: "snapshot" }` and `writeConcern: { w: "majority", journal: true }`.
   - **Retry:** the whole attempt is retried on errors labelled `TransientTransactionError` or `UnknownTransactionCommitResult`, up to `maxAttempts` (default 3), with backoff `[50, 200, 800]` ms. Other errors abort and rethrow at once.
   - **Post-commit:** `onCommitted(callback)` registers a callback for the current transaction. Callbacks run only after a successful commit, in order. Failures are reported through `reportError` and never thrown. Called outside a transaction, `onCommitted` throws `AppError(INTERNAL)`: unlike manoxen, no silent immediate run, so a missing transaction is a bug, not a fallback.
   - `getActiveSession(): ClientSession | undefined` for repositories (they pass `{ session }` to every query).
   - Side effects (SMS, courier, AI) still go through the outbox (1.5), never through `onCommitted` directly. `onCommitted` is for in-process follow-ups such as cache invalidation. This is written in the JSDoc.
8. **Sequences** (`kernel/sequence/next-sequence-value.ts`): `nextSequenceValue({ organizationId, sequenceKey }): Promise<number>`.
   - Runs `findOneAndUpdate({ organizationId, sequenceKey }, { $inc: { nextValue: 1 } }, { upsert: true, new: true, session: getActiveSession() })` on the TENANT collection `sequences`.
   - Unique index `{ organizationId: 1, sequenceKey: 1 }`. The returned number is the new value (the first call returns 1).
   - `SEQUENCE_KEY` enum in contracts, from `09 §5.8`: `ORDER`, `BOOKING`, `ENROLLMENT`, `PAYMENT`, `INVOICE`, `JOURNAL`, `MEMBER`.
   - Formatting (prefix, padding, yearly reset) is a settings concern (2.4). Not here.
   - The sequence document has the standard fields: `sequenceId` (UUID v7, set on insert via `$setOnInsert`), `organizationId`, timestamps.
9. **`runAsSystem(reason, work)`** (`kernel/context/run-as-system.ts`):
   - `SYSTEM_REASON` enum in contracts, from `05` "System access": `AUTH_LOOKUP`, `PERMISSION_RESOLUTION`, `CONTEXT_SETUP`, `SEED`, `PLATFORM_ADMIN`, `MIGRATION`, `WEBHOOK_ROUTING`, `SCHEDULED_JOB`.
   - It runs `work` in a child request context with `systemReason` set. It logs `{ event: "system_access", reason }` at `info` with the current `requestId` (if any) before running. Outside a request it creates a context with a new `requestId`.
   - The tenant plugin (1.3) is what honours it.
   - Lint: a fixture-tested rule (R26) forbids calling `runAsSystem` inside `**/modules/*/*/{domain,application,presentation}/**`. Exception: `**/modules/platform/**/application/**`, which must also write an audit entry (enforced in their cards). It is implemented as another `banijjik-guard` alias of `no-restricted-syntax` (`CallExpression[callee.name="runAsSystem"]`), consistent with ADR-082.
10. **Startup and shutdown wiring:**
    - `main.ts` (both roles) awaits `connectDatabases(config)` before `listen` / worker start, and logs `{ event: "db.connected" }` (no URL).
    - A shutdown task `{ name: "close-databases" }` closes the client after the HTTP server.
    - A connection failure at startup → log `db.connect_failed` (error class + code only) and exit 1.
    - The Mongoose options are `serverSelectionTimeoutMS: 10_000` and `autoIndex` true outside production. In production, indexes are built by the explicit `syncIndexes` task (a script, not now; note it in the handoff).
11. **`GET /ready`:** runs `db.admin().ping()` on the platform connection with a 2 s timeout. It returns `200 { data: { status: "ready" } }` or `503 { error: { code: "INTERNAL", messageKey: "errors.not_ready", requestId } }`. Redis readiness is added when Redis is used (1.4/1.5).
12. **Tests use a real replica set** via `mongodb-memory-server` (`MongoMemoryReplSet`, 1 member, storage engine `wiredTiger`) in a vitest `globalSetup` for `apps/api`. Pin the MongoDB binary version to match compose (`8.0.x`). The binary download is cached under `node_modules/.cache/mongodb-memory-server`; CI caches it (0.2b adds that cache key; note it in the handoff).
13. **Dependencies:** `mongoose@^8` (check `npm view mongoose version` for the current major; if 9 is stable, use it and check the session API notes); dev `mongodb-memory-server@^10`.

## Interfaces & types
```ts
// contracts
export const SYSTEM_REASON: { AUTH_LOOKUP: "AUTH_LOOKUP"; /* … 8 */ }; export type SystemReason = …;
export const SEQUENCE_KEY: { ORDER: "ORDER"; /* … 7 */ };              export type SequenceKey = …;
export const DATABASE_KIND: { PLATFORM: "PLATFORM"; TENANT: "TENANT" }; export type DatabaseKind = …;

// kernel/db
export interface DatabaseConnections { readonly platform: Connection; readonly tenantShared: Connection; close(): Promise<void> }
export function connectDatabases(config: AppConfig): Promise<DatabaseConnections>;
export function registerModel(definition: { modelName: string; collectionName: string; database: DatabaseKind; schema: Schema }): void;
export function addGlobalSchemaPlugin(plugin: (schema: Schema) => void, options: { database: DatabaseKind }): void;
export interface ModelContext { readonly organizationId?: string; readonly deployment?: "SHARED" | "DEDICATED" }
export function models(context: ModelContext): { get<Document>(modelName: string): Model<Document> };
export function stripMongoInternals<Record extends object>(document: Record & { _id?: unknown; __v?: unknown }): Omit<Record, "_id" | "__v">;
export function updateVersioned<Document>(options: { model: Model<Document>; filter: FilterQuery<Document>; expectedVersion: number; update: UpdateQuery<Document> }): Promise<Omit<Document, "_id" | "__v">>;
export function withTransaction<Result>(work: (session: ClientSession) => Promise<Result>, options?: { maxAttempts?: number }): Promise<Result>;
export function onCommitted(callback: () => Promise<void>): void;
export function getActiveSession(): ClientSession | undefined;

// kernel/sequence
export function nextSequenceValue(options: { organizationId: string; sequenceKey: SequenceKey }): Promise<number>;

// kernel/context
export function runAsSystem<Result>(reason: SystemReason, work: () => Promise<Result>): Promise<Result>;
```

## Tests (must exist and pass)
Transactions (port the manoxen spec cases):
- [ ] **rollback:** two inserts in two different collections (one PLATFORM, one TENANT model), then throw inside `work` → neither document exists afterwards
- [ ] commit: both documents exist; `onCommitted` callbacks run once, after commit, in order
- [ ] callbacks do **not** run when the transaction aborts
- [ ] nested `withTransaction` reuses the outer session (same `session.id`), and an inner throw rolls back the outer
- [ ] a work function that throws an error labelled `TransientTransactionError` twice and then succeeds → result returned, 3 attempts made. A non-labelled error → 1 attempt.
- [ ] `onCommitted` outside a transaction throws

Models / registry:
- [ ] a PLATFORM model writes to the platform DB name and a TENANT model to the tenant DB name (check via `connection.db.databaseName`)
- [ ] duplicate `registerModel` throws; `deployment: "DEDICATED"` throws `errors.dedicated_not_supported`
- [ ] a global plugin added for TENANT is applied to TENANT schemas only
- [ ] `strict: "throw"`: writing an unknown field throws

Versioning / mapper:
- [ ] `updateVersioned` with the right version increments `version`; with a stale version → `409 CONFLICT` with `details.currentVersion`; with an unknown id → `404`
- [ ] `stripMongoInternals` removes `_id` and `__v` and keeps everything else

Sequences:
- [ ] 50 concurrent `nextSequenceValue` calls for one org return 1…50 with no duplicates and no gaps
- [ ] two orgs have independent counters
- [ ] inside an aborted transaction the increment is rolled back

runAsSystem:
- [ ] the context inside has `systemReason`; after it, the outer context is unchanged; one `system_access` log line with the reason
- [ ] lint R26 fail/pass fixtures

Startup / readiness:
- [ ] `connectDatabases` rejects URLs on different hosts with the documented issue
- [ ] `/ready` → 200 with the replica set up; → 503 after `connections.close()`
- [ ] shutdown closes the databases (the client is disconnected after the task)

All with `--force`: lint, format:check, typecheck, test, build.

## Risks & checks
- **Transactions across two databases on one client:** prove it with the rollback test (PLATFORM + TENANT in one transaction). If Mongoose `useDb` connections do not share the session correctly, stop and report (do not fall back to two clients).
- **mongodb-memory-server on Windows:** the first run downloads the binary (~100 MB, needs disk space; the owner's C: drive is tight). Set `MONGOMS_DOWNLOAD_DIR` to `node_modules/.cache/mongodb-memory-server` (on the repo drive E:). If the download fails, report it honestly.
- **Concurrency test flakiness:** run the 50-call sequence test 5 times in a loop locally and paste the result.
