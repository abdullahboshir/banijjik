# Plan: card 3.14 · CI for every card branch (full suite plus browser suites on GitHub)

Tier: **T2** (CI configuration only; no application code) · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor, a Claude Code session or the lead · Date: 2026-10-22 · Based on commit: `main 9016a0f`

Phase 3 chore, from `docs/plans/parallel-sessions-guide.md`. **Start now, before the other new cards**: the guide's finish checklist relies on it. No ADR (it extends the existing CI of card 0.4b; it adds no new infrastructure).

## Goal
Every push of a card branch (`s/**`) runs the whole verification on GitHub, including the admin and platform browser suites that today run only on the owner's machine. Sessions stop running 30-to-40-minute suites locally, and the lead reviews against a CI result.

## Inputs read
- `.github/workflows/ci.yml` (jobs `verify` and `secrets`; triggers `pull_request` and `push` to `main`)
- `apps/admin/vitest.browser.config.ts`, `apps/admin/src/test-support/browser-stack.ts` (fixed ports 4000 and 3101, Redis at `127.0.0.1:6380`, `CHROME_PATH` required, `MongoMemoryReplSet` without a pinned version), the same files in `apps/platform`
- `apps/api/README.md` "Tests" (MongoDB 8.0.13 binary cache)

## Session parts
One part (no screens).

## Decisions
1. **Triggers:** add `"s/**"` to `on.push.branches` (keep `main` and `pull_request`). The existing `concurrency` group per ref already cancels an older run of the same branch.
2. **New job `browser`**, parallel to `verify`, on `ubuntu-24.04`, `timeout-minutes: 30`:
   - Redis service `redis:7` mapped to host port **6380** (`6380:6379`), because the browser stacks connect to `127.0.0.1:6380`.
   - Checkout, Node 22 with the npm cache, `npm ci`, and the same MongoDB binary cache step as `verify`.
   - `MONGOMS_VERSION: "8.0.13"` in the job environment, so the browser stacks use the cached binary instead of the library's default version.
   - `npx turbo run build` with `NEXT_PUBLIC_API_BASE_URL: http://localhost:4000` and `NEXT_PUBLIC_BRAND_NAME: Test Brand` (the values the browser configs expect; placeholders, not secrets).
   - `npm run test:browser -w @banijjik/admin`, then `npm run test:browser -w @banijjik/platform` (two steps, so the log shows which suite failed), each with `CHROME_PATH: /usr/bin/google-chrome` (preinstalled on GitHub's Ubuntu runners; nothing is downloaded).
   - If the platform stack needs other environment values, copy them from its `browser-stack.ts` the same way; stop and ask if a value would be a real secret.
3. **No change to `verify` or `secrets`** apart from the trigger. Keep the pinned action SHAs as they are; reuse them in the new job.
4. **Route sizes:** the `verify` job's `npm run build` already prints and checks the route budgets; nothing to add.
5. **Docs:** none beyond the handoff. How sessions read CI results is already in `docs/plans/parallel-sessions-guide.md` §8 (the repository has no root README).
6. **Platform stack:** it waits up to 10 minutes for its ports and uses ports 4000, 3102 and 3201; nothing else runs in the job, so no change is needed.

## Out of scope
- Branch protection rules on GitHub (the owner sets them later if wanted)
- Splitting the API suite into shards or other speed work (a later card if CI takes more than 20 minutes)
- Any application or test code change. If a browser test fails only on CI, record it in the handoff and stop and ask; do not change the test in this card.

## Risks & checks
- **Different Chrome or MongoDB on CI:** a test may be flaky there. Rerun once; if it fails again, report it with the log.
- **Duration:** if `browser` takes more than 30 minutes, report the time; the lead decides on sharding.

## Done when
