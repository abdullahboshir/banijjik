# Plan: card 3.4b · Manager approvals (PIN and one-time approval token)

Tier: **T1** (it guards refunds, reversals and big discounts) · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor or a Claude Code session · Date: 2026-10-19 · Based on commit: `main 3c0165b`

Phase 3, wave 3. Can run beside 3.4: no shared files except add-only lists. Reserved ADR number: **ADR-121**.

## Goal
Some actions need a manager's yes on the same device (`11 §9`):
- discounts above the threshold
- refunds
- payment reversals
- price overrides at POS
- store-credit adjustments
- enrollment refunds

The manager types a personal **PIN**. The server gives back a short-lived, single-use **approval token** bound to exactly that action. The use case that performs the action consumes the token and records who approved it.

This card builds the mechanism once. Each later card (3.5, 3.8, 3.9) only calls it.

## Decisions
**Permission and PIN**

1. **Permission `iam.approval.grant`** (a new key in the iam module; `11 §9` named it `sales.approval.grant`, but the key must belong to a module that exists now). Grants: OWNER and MANAGER. Record the rename in ADR-121 and `11 §9`.

2. **PIN on the member.** Add `approvalPinHash?` and `approvalPinFailedCount` / `approvalPinLockedUntil?` to Member. The PIN is 4 to 8 digits, hashed with the same algorithm as passwords, and never returned or logged.
   - `PUT /api/v1/orgs/{organizationId}/me/approval-pin { currentPassword, pin }`: only a member who holds `iam.approval.grant` somewhere. Re-authenticating with the account password prevents a stolen open session from setting a PIN.
   - `DELETE …/me/approval-pin` removes it.

**Approval token**

3. **`POST /api/v1/orgs/{organizationId}/approvals`** with `{ action, subjectKey, amount?, approverMemberId, pin }`:
   - `action`: contracts enum `APPROVAL_ACTION` = `DISCOUNT | REFUND | PAYMENT_REVERSAL | PRICE_OVERRIDE | STORE_CREDIT_ADJUSTMENT | ENROLLMENT_REFUND | SESSION_LIMIT_OVERRIDE | RETURN_NOT_RECEIVED`.
   - `subjectKey`: an opaque string the caller builds, for example `order:<orderId>`, or `quote:<hash>` before an order exists.
   - `approverMemberId`: the manager standing next to the cashier, chosen from a list of members who can approve at this location (`GET …/approvers?locationId=`).
   - **On a correct PIN** for a member who holds `iam.approval.grant` at the request's location (or ALL): returns `{ approvalToken, expiresAt }`. The token is 32 random bytes; it is stored hashed in `approval_tokens` with TTL 2 minutes and bound to `{ organizationId, action, subjectKey, amount, approverMemberId, requestedByUserId }`.
   - **Failures:** a wrong PIN counts a failure; 5 failures lock that member's PIN for 15 minutes (`423 errors.approval_pin_locked`); the answer never says whether the member or the PIN was wrong (`400 errors.approval_invalid`). Per-IP and per-organization rate limits.
   - The approver cannot be the requester unless a setting allows self-approval for OWNER (`iam.approval.ownerSelfApproval`, default true; a sole owner often runs the counter).

4. **`ApprovalVerifier.consume(token, expected)`**, exported from iam's index for other modules through their own port.
   - It checks hash, expiry, not used, and the exact action, subject and amount (an amount up to the approved one).
   - It marks the token used **in the caller's transaction**, returns `{ approverMemberId, approvedAt }`, and writes the audit entry `iam.approval.used` in that transaction.
   - A second consume of the same token fails.

**Screens**

5. Two pieces:
   - **"Approval PIN"** section on the admin profile menu ("My account"): set, change, remove.
   - **`ApprovalPinDialog`** in `@banijjik/ui` (no API knowledge): approver select, PIN input with a numeric keypad on phones, error and lock messages. Later cards use it. Demonstrate it in a small admin test harness only, not a fake feature.

## Tests (must exist and pass)
- [ ] **PIN:** set needs the current password; a member without the permission → 403; the PIN is never in responses, logs or audit values.
- [ ] **Approval:**
  - a correct PIN returns a token
  - a wrong PIN → 400 with no hint
  - the 5th failure locks for 15 minutes (423)
  - an approver without the permission at that location → 400 (same message)
  - cross-org member → 400
  - the rate limits
- [ ] **Consume:**
  - the exact action and subject consume once
  - a second consume fails
  - an expired token fails
  - a different action, subject or a higher amount fails
  - a lower amount passes
  - a rollback of the caller's transaction leaves the token unused (so the cashier can retry)
- [ ] **Self-approval:** an OWNER may approve their own request by default; with the setting off it fails; a MANAGER never self-approves.
- [ ] **UI:** dialog unit tests (keypad, lock message); My account PIN section.
- [ ] Every existing suite green; full "Done means" list.

## Out of scope
- Remote approval on the owner's phone (a later card; the token shape already supports it)
- Using approvals in sales, payments or POS (their own cards)

## Done when
- A manager can approve one specific action on the cashier's device with a PIN.
- Any use case can consume that approval exactly once with an audit trail.
- The Opus review passes.
