# Plan: card 1.6b · `new-module` script and generated module contract tests

Tier: T2 · Planned by: Opus 5.5 · Date: 2026-10-10 · Based on commit: `main 25e31cd`

Second half of roadmap card 1.6. Runs in parallel with **1.7b**. It owns `scripts/new-module/**`, `apps/api/src/test-support/module-contract/**`, the new contract-test files and the registry tests. Do not edit `modules/core/organization/**` (1.7b's). Shared: `routes/v1.ts` only if a registry export is missing (add-only).

## Goal
1. `npm run new-module -- <group>/<module-key>` creates a module that starts in the same shape as every other: the four layer folders with real starter files, `index.ts`, `module.manifest.ts` (through `defineModule`), `README.md` and a first test. It passes lint, typecheck and its own test unchanged.
2. The **generated contract suite** of `10 §11` runs for **every** registered manifest with no per-module code. For each non-SYSTEM module, turning it off by each possible path makes its routes `403 MODULE_DISABLED`, removes it from the menu and the config, and leaves its data untouched. Plus the registry-wide rules.

This closes the roadmap line "the generated tests cover every manifest automatically".

## Inputs read
- `03-ROADMAP.md` 1.6 and 0.2 (module template), `10 §2, §3, §11`, `05` "Readable code" (module README, layers), ADR-011, ADR-011a, ADR-082, ADR-086, ADR-087, ADR-091
- Code on `main`: `kernel/modules` (`defineModule`, registry), `platform/entitlement` (resolver, gate, `/me/config`, overrides), the probe modules used by the 1.6a tests, the existing modules as the pattern (`core/audit` is the smallest complete one), lint rules (36)

## Decisions
**Script**
1. `scripts/new-module/new-module.mjs` (plain Node, no new dependency), root script `new-module`.
   - Argument `<group>/<moduleKey>`: the group is one of the folders of `10 §4` (`core, commerce, channel, integration, automation, capability, platform`). The key must be in contracts `MODULE_KEY` and kebab-case.
   - It refuses to overwrite an existing folder.
   - It refuses a key that is not in `MODULE_KEY` with the message "add the module key to @banijjik/contracts first" (single source of truth).
2. It writes, from template files under `scripts/new-module/templates/`:
   - `module.manifest.ts`: `defineModule({...})` with the key, path, `moduleClass` taken from a `--class` flag (default `OPTIONAL`), empty lists, `tenantCanDisable` false
   - `index.ts`: the composition root exporting `<name>Manifest` and a `register<Name>Models()` that registers nothing yet
   - `README.md`: the ≤ 30 line outline of `05` (purpose, entities, public API, events, permissions)
   - `domain/errors.ts`: a `DomainRuleError` factory example (ADR-086)
   - `application/ports/`, `infrastructure/`, `presentation/`: one real starter file each. No empty folders, no placeholder files (AGENTS rule):
     - a `<Name>ModuleInfo` use case returning the manifest key (used by the starter test)
     - its port type
     - a transformer
   - `<module>.manifest.test.ts`: asserts the manifest validates and is accepted by a registry
   - The script prints the next steps: add permission keys to contracts, add the manifest to the list in `routes/v1.ts`, add the grant row.
3. The script is tested in a temp directory copy of the minimal tree it needs (like the existing hook tests): generate a module, then run ESLint and `tsc` on the generated files through their APIs, and assert no finding. Also test the refusals (unknown key, existing folder, bad group).
4. Nothing is generated into the real `apps/api/src/modules` by this card.

**Generated contract suite (`10 §11`)**
5. `apps/api/src/test-support/module-contract/` exports `describeModuleContracts({ registry, harness })`. One test file, `apps/api/src/modules/module-contracts.test.ts`, calls it with the **production** manifest list (the same list `routes/v1.ts` uses; export it from one place if it is not already) plus the probe modules the suite needs.
   - A module added to the list is covered with no further code.
6. For every non-SYSTEM, non-PLATFORM module M, it builds an org where M is effective, then turns M off by each path that applies:
   - **not in package:** a subscription on a package without M (skipped for CORE)
   - **`PLATFORM_REVOKE`**
   - **`TENANT_DISABLE`:** only when `tenantCanDisable`
   - **template excludes it:** a test template reader
   - **required kind missing:** only when `requiresAnyKind` is non-empty
   - **dependency missing:** only when `dependsOn` is non-empty; revoke the dependency

   For each path it asserts, per `10 §11`:
   1. every route in `M.routes.admin` under `/orgs/:organizationId` answers `403 MODULE_DISABLED`. The suite requests each declared prefix with GET and with POST; a prefix that answers anything else fails.
   2. `/me/config` `menu` has no entry of M
   3. `botTools` has no tool of M
   4. `storefrontSections` has no section of M
   5. M's setting keys and custom-field entities are absent from the config
   6. M's event handlers do not run for that org (a probe handler per module is registered by the suite for one of M's consumed types, if any)
   7. M's data is untouched: document counts of M's registered models before = after
7. **Today no production module is CORE or OPTIONAL** (all are SYSTEM or PLATFORM). To prove the suite, it also runs over two probe manifests registered only in the test, moved or adapted from the 1.6a probes: one OPTIONAL with `tenantCanDisable`, a dependency and a required kind, and one CORE.
   - The suite must **fail** when a probe route is deliberately mounted without the gate. Prove it once with a negative test: run the same assertions against an app whose gate is replaced by a pass-through, and expect a failure.
8. **Registry-wide tests** (`10 §11`, second list), over the production list:
   - every manifest key is in `MODULE_KEY`
   - `dependsOn` has no cycles
   - every permission, setting, event and section key is unique and declared in contracts
   - PLATFORM modules declare no tenant routes
   - every seed base package contains all CORE modules that have a manifest and is closed under `dependsOn` over the registered manifests (the "closed" rule skips keys with no manifest yet, and lists them in the test output so the gap is visible)
   - every tenant router mounted in `routes/v1.ts` is owned by a manifest route (walk the Express router stack)
9. The suite also checks each module folder against the template shape: `index.ts`, `module.manifest.ts`, `README.md` exist, and `index.ts` exports the manifest. A module that drifts fails the test.

## Tests (must exist and pass)
- [ ] the script tests of decision 3 (generated module passes ESLint and `tsc`; refusals)
- [ ] the contract suite over the probe modules: every applicable off-path × the seven assertions; the negative test of decision 7 fails as expected
- [ ] the contract suite over the production list runs and reports which modules it covered (today: none need off-path tests; the output says so, it does not silently pass)

## Out of scope
- Any real business module; storefront and webhook route gating (their surfaces arrive in Phases 4–5; the suite's route assertion is written so those lists plug in later)
- Changing the resolver or the gate

## Risks & checks
- **Template code must obey all 36 lint rules** (naming, explicit return types, no inline disables). The script test is the proof.
- **Walking the Express 5 router stack** for decision 8: if the stack is not reliably inspectable, compare against the registry's route list from the mounted routers' declared prefixes, and say which way was used.
- **Disk and services:** system MongoDB binary, `TEST_REDIS_URL=redis://127.0.0.1:6380`, `--concurrency=2`. No downloads.

## Done when
The generator produces a lint-clean, type-clean module; the contract suite covers every manifest in the list automatically and is proved able to fail. Real output in `docs/handoffs/1.6b.md`. The merge check (T2) passes.
