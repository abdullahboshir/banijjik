## Goal
Support reconciliation and closure of failed deliveries where goods were partially or entirely lost in transit (`DELIVERY_LOSS_CLOSED`). Requires dual-control manager approval (`APPROVAL_ACTION.DELIVERY_LOSS_CLOSE`), returns only actually received units (restock or damaged), settles paid advance, records an append-only `DeliveryLossClosure` record and publishes `sales.order.deliveryLossClosed`. Also supports subsequent physical recovery of missing units via `DeliveryLossRecovery` (`APPROVAL_ACTION.DELIVERY_LOSS_RECOVER`), bounded by outstanding lost quantity, restocking units to available/damaged inventory without recreating sales or altering customer dues.

## Decisions
1. **Status Transition & Guard:**
   - `DELIVERY_LOSS_CLOSED` is only reachable from `DELIVERY_FAILED`.
   - Requires at least 1 unit lost across all lines (`lostQuantity > 0`). If 0 units are lost, staff must use ordinary RTS (`ReceiveRtsUseCase`).
   - Line reconciliation must account for every shipped unit: `restockQuantity + damagedQuantity + lostQuantity === line.quantity`.
2. **Approval Enforcement:**
   - Loss closure requires an approval token with action `APPROVAL_ACTION.DELIVERY_LOSS_CLOSE` binding the exact total lost cost and location.
   - Physical recovery requires an approval token with action `APPROVAL_ACTION.DELIVERY_LOSS_RECOVER` binding the exact recovered cost.
   - Consumed via `ApprovalVerifier.consume` inside the Unit of Work.
3. **Stock & Cost Accounting Seams:**
   - Only actually received units (`restockQuantity` and `damagedQuantity`) are restocked at closure; lost units are NOT restocked and no duplicate SALE movement is created.
   - Restocked units use original order line cost snapshot (`unitCostSnapshot`).
   - Advance payments are settled via `payments.settleCancellation` adhering to termination policy.
   - Late physical recovery restocks actual recovered units at original cost (`restockQuantity` -> `RETURN`, `damagedQuantity` -> `RETURN_DAMAGED`) and records a `DeliveryLossRecovery`. Recovery never restores sales revenue or customer dues.
4. **Natural Key & Concurrency:**
   - `DeliveryLossClosure` has a unique index on `{ organizationId: 1, orderId: 1 }`. Only one closure per order.
   - `DeliveryLossRecovery` entries are append-only; cumulative recovered quantity per order line is checked against `lostQuantity - alreadyRecoveredQuantity`.
5. **Identifiers & Model Naming:**
   - `DeliveryLossClosureId`, `DeliveryLossRecoveryId` (UUIDv7 from `@banijjik/ids`).
   - Models registered via kernel `models(ctx)` and tenant plugin.

## Tests (must exist and pass)
- [ ] Happy path: Reconcile loss on `DELIVERY_FAILED` order returns received goods, leaves lost out, transitions to `DELIVERY_LOSS_CLOSED`.
- [ ] Happy path: Subsequent physical recovery restocks recovered units up to remaining lost quantity.
- [ ] Refusal: Reconcile loss with 0 lost units fails (directs to RTS).
- [ ] Refusal: Reconcile loss with mismatched line sum (`restock + damaged + lost != total line quantity`).
- [ ] Refusal: Reconcile loss outside `DELIVERY_FAILED` status returns 409 `INVALID_TRANSITION`.
- [ ] Refusal: Missing or invalid manager approval token rejected.
- [ ] Refusal: Physical recovery exceeding outstanding lost quantity rejected.
- [ ] Refusal: Cross-organization and unauthorized location denied.
- [ ] Idempotency: Replay of reconcile call with same Idempotency-Key returns cached response.
