## Goal
Product businesses know what is on the shelf at each branch. **Inventory items** are what is stocked (ADR-098); variants draw from them through **stock components**:
- loose rice and a 1 kg pack from one rice item
- a gift box from several items
- a facial that uses up 20 ml of cream

Every change is a **stock movement** in an append-only ledger. A per-branch **level** projection gives on-hand, reserved and available quantities and the moving average cost.

The business can:
- receive stock
- adjust it with a reason
- transfer it between branches
- see low stock

Sales and returns use the ledger through a port in card 3.5.

## Decisions
**Items** (`commerce/inventory`, CORE, organization scope)

1. **InventoryItem** as `09 §5.6`, plus `lowStockThreshold?` (in base unit precision; else `inventory.lowStockDefault`).
   - `sku` is unique per organization when present (same rule as catalog SKUs; one SKU never names both a variant and an item of a different product).
   - `baseUnitKey` comes from the unit registry and is immutable once a movement exists.
   - Archived, never deleted, while movements reference it.
   - CRUD: list, read, create, update with version, archive.

2. **Stock components switch on** (finishing ADR-098). Catalog's gate is removed: a variant may list 0 to 10 `{ inventoryItemId, quantity }`.
   - Each item is ACTIVE in this organization, and the quantity is a positive integer in the item's base unit precision. Catalog checks this through an inventory port adapted in routes; catalog must not import inventory's internals.
   - **Default tracking:** when `catalog.defaultStockTracked` is on and a PRODUCT variant is created without components, catalog asks inventory to create one item (named after the offering and variant, base unit = the variant's unit) and links it × 1, in the same transaction.
   - The admin catalog editor (3.2b) gains a "Stock from" row per variant: item picker and quantity in words ("১ কেজি প্যাকেট = ১০০০ গ্রাম চাল").

**Ledger** (location scope)

3. **StockMovement** as `09 §5.6`, append-only. Reasons now: `OPENING`, `PURCHASE`, `ADJUSTMENT`, `DAMAGE_WRITE_OFF`, `TRANSFER_OUT`, `TRANSFER_IN`. `SALE`, `RETURN` and `RETURN_DAMAGED` are declared and used by 3.5 through the port (decision 7). Corrections are reversing movements (`reversesStockMovementId`).

4. **InventoryLevel** projection, unique `(organizationId, locationId, inventoryItemId)`: `onHand`, `reserved`, `damaged`, `available = onHand − reserved`, `averageUnitCost`.
   - It is updated in the same transaction as the movement, with a conditional update.
   - Without `inventory.allowNegativeStock` (default false), a movement that would make available or onHand negative fails → `422 INSUFFICIENT_STOCK` with `details.inventoryItemId`, `available`.
   - **Moving average** (ADR-069): on a PURCHASE or positive OPENING with a unit cost, `newAvg = (onHand × avg + qty × unitCost) / (onHand + qty)` in integer minor units per base unit, rounded half up. Outgoing movements use the current average as their `unitCost`.
   - A **rebuild** job (`inventory.rebuildLevels`, on demand through a platform-free admin endpoint for owners, and in tests) recomputes levels from movements and reports differences. It proves the projection.

**Operations**

5. **Endpoints** (`/api/v1/orgs/{organizationId}`; every money and stock write needs `Idempotency-Key`):

   | Endpoint | Permission | Notes |
   |---|---|---|
   | `POST /stock/receipts` | `inventory.adjustment.create` | lines `{ inventoryItemId, quantity, unitCost }`, a location, a supplier name note; one PURCHASE movement per line, one transaction. The supplier payable comes later; the journal posting INVENTORY / method comes with 3.8c's next rule set |
   | `POST /stock/adjustments` | `inventory.adjustment.create` | lines `{ inventoryItemId, quantityDelta, reason: ADJUSTMENT \| DAMAGE_WRITE_OFF, note }`; a negative adjustment above `inventory.adjustment.approvalAbove` (setting, default 0 = off) needs an approval token (3.4b, action `STOCK_ADJUSTMENT`, a new value) |
   | `POST /stock/transfers` | `inventory.transfer.create` | number from sequence `TRANSFER`; `{ fromLocationId, toLocationId, lines }`. **One step for launch:** TRANSFER_OUT and TRANSFER_IN in one transaction at the average cost of the source. Two-step "in transit" is later; record it. Both locations must be in the caller's reach |
   | `GET /stock/levels?locationId&q&lowOnly&page&limit` | `inventory.stock.read` | rows with item name, unit and status |
   | `GET /stock/movements?inventoryItemId&locationId&from&to&page&limit` | `inventory.movement.read` | paged, index `{ organizationId, locationId, inventoryItemId, occurredAt }` |
   | `GET /offerings/{offeringId}/availability?locationId` | `inventory.stock.read` | per variant, `floor(available / quantity)` over its components (ADR-098) |

6. **Low stock:** when a movement takes available to or below the threshold, emit `inventory.stock.low` once per crossing (not on every sale). The admin list shows a low-stock filter and badge.

7. **Port for sales (3.5): `StockLedger`**, exported from the inventory index:
   - `reserve(lines)` / `release(lines)`: reservations per component, idempotent by `(sourceType, sourceId)`
   - `commitSale(lines)`: SALE movements, one per component of each line, releasing the reservation, in the caller's transaction
   - `returnStock(lines, disposition)`: RETURN or RETURN_DAMAGED

   Lines carry `{ offeringId, variantId, quantity }` and the port expands components. 3.3 implements and tests the port with a test caller; 3.5 is its first real caller.

8. **Events** (ids and quantities only, `orderingKey: stock:<locationId>:<inventoryItemId>`): `inventory.stock.changed`, `inventory.stock.low`, `inventory.transfer.completed`.

## Tests (must exist and pass)
- [ ] **Ledger:**
  - receipts raise onHand and the average (worked example in the test)
  - adjustments with reasons
  - damage write-off moves to damaged
  - reversal mirrors
  - movements are never updated or deleted (repository has no such method; a test asserts the collection only grows)
- [ ] **Negative stock:** refused by default (422 with details); allowed with the setting.
- [ ] **Concurrency:** two parallel adjustments taking the last 5 units → one succeeds, available never below 0.
- [ ] **Transfers:** both movements in one transaction (a failure in the second leaves no first); both locations must be reachable (403); the average cost moves with the stock.
- [ ] **Components:**
  - a 1 kg pack and loose rice share one item
  - availability = `floor(available / quantity)`
  - a kit uses the minimum over its components
  - default tracking creates the item × 1
  - an archived item in a component → 400
- [ ] **StockLedger port:** reserve and release idempotent; commitSale writes one movement per component and releases the reservation; returnStock both dispositions.
- [ ] **Low stock** fires once per crossing.
- [ ] **Rebuild** matches the projection after a long scenario.
- [ ] **Permission denied, cross-org, cross-location;** module-off suite includes `inventory`.
- [ ] **Ported manoxen inventory and supply tests** adapted.
- [ ] **Admin:** unit tests for the sheets; browser: receive rice, sell nothing yet, transfer half to a second branch, see both levels and the value.
- [ ] Every existing suite green; full "Done means" list.
