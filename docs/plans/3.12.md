# Plan: card 3.12 · Business branding (logo, colours, tagline)

Tier: **T2** · Planned by: Opus 5.5 (Claude) · Implemented by: a Claude Code session · Date: 2026-10-17 · Based on commit: `main 9ceb629` (3.0 files and 3.13 settings topics merged)

Phase 3, wave 2. Can start now. Read `docs/plans/phase-3-lanes.md` (wave 2 section) first. Reserved ADR number: **ADR-114**.

## Goal
Each business has its own identity, kept in one place and used everywhere that faces its customers:
- a logo
- a primary and an accent colour
- a short tagline

The owner sets it on a simple page under Settings › Business with a live preview. The admin top bar shows the logo. Receipts and invoices (3.5, 3.9), the booking page (4.6) and the website theme (4.1, 4.5) read the same data later, so every business's customer-facing pages look like that business. The platform's own brand (P2) is separate.

## Decisions
**Data**
1. **`Organization.branding`** (embedded, `_id: false`): `{ logoFileId?, primaryColor?, accentColor?, tagline? }`. It is not a new collection: one per business, read with the organization.
   - Colours are `#RRGGBB` (lower-cased on save).
   - `tagline`: trimmed, 1 to 80 characters.
   - Absent means "not set": consumers fall back to the platform defaults.

2. **Writes** go through `PATCH /orgs/{organizationId}/profile` with a new optional `branding` object.
   - Same permission (`organization.profile.update` at every location), the existing `version`, and one audit entry with `branding.<key>` changes.
   - Per key: a value sets it, `null` clears it, absent leaves it (the existing profile rule).
   - No new endpoint.

3. **Logo rule:** `logoFileId` must be an ACTIVE file of this organization with purpose `LOGO`. 3.0's `buildFileReferenceReader().isUsable(fileId, purpose)` already checks the purpose; adapt it in routes to the organization's port. Anything else is 400 at `branding.logoFileId`.
   - Uploading stays `file.asset.create`; only attaching the file as the logo needs the profile permission. A stray LOGO upload by a staff member is harmless and counts against the quota. This settles the 3.0 handoff question.

4. **Readable colours (WCAG):** one contrast helper (relative luminance) in `@banijjik/validation`, used by the schema and by the screen.
   - `primaryColor` must reach **4.5:1 against white**, because it is the button colour with white text.
   - `accentColor` must reach **3:1 against white**, because it is used for links, badges and borders on white.
   - A failure is 400 at the field with `validation.color_low_contrast`.
   - **Presets:** about eight named pairs in contracts (`BRAND_COLOR_PRESETS`, for example green, teal, blue, indigo, purple, rose, orange, slate), each tested to pass. The screen offers presets first and "Custom" second.

**Reads**
5. Where branding appears:
   - `GET /profile` returns `branding` with `logoUrl` (the public `medium` variant through `publicFileUrl`'s path) when a logo is set.
   - `GET /me/orgs` rows gain `logoUrl?` (the `thumb` variant) for the top bar and the business switcher.
   - Nothing else reads branding in this card. A public read for the booking page and the storefront comes with 4.6 and 4.1; record that in ADR-114.

**Screens** (`apps/admin`)
6. **Settings › Business › Branding** (`/[orgSlug]/settings/branding`). Menu entry `organization.branding` in the organization manifest, settings group, `settingsTopicKey: BUSINESS`, permission `organization.profile.read`. The page is built with `PageLayout` and three `PageSection`s, each with a help line:
   - **Logo:** `ImageInput` with an upload (purpose `LOGO`), a preview, and remove. Help: square or wide images work; PNG, JPG or WebP up to 8 MB.
   - **Colours:** preset swatches (≥ 44 px touch targets, with names for screen readers), "Custom" with a colour input and a hex field, and a live contrast message.
   - **Tagline:** text with a counter.

   A **preview card** shows a sample header with the logo and name, a primary button and an accent link in the chosen colours, so the owner sees the result before saving. A member without the update permission sees a read-only page. Save uses the sticky action bar and handles version conflicts as on the profile page.

7. **Admin top bar:** shows the business logo (`thumb`) beside the business name when set; otherwise the current initials avatar.
   - The admin app keeps the platform's own colours. Business colours are for customer-facing pages, as most commerce admins do (the admin must stay readable and consistent for staff of every business).

8. **Usability check (carried over from 3.13):** if the owner has not run it yet, it runs at the end of this card with the same three tasks plus "change the logo and colour". The result is recorded in both handoffs.

## Tests (must exist and pass)
- [ ] **Validation:**
  - every preset passes
  - `#ffffff` as primary fails (contrast)
  - a light yellow accent fails
  - a bad hex fails
  - a tagline over 80 fails
  - the contrast helper matches known WCAG ratios (black/white 21:1, `#767676` on white ≈ 4.54:1)
- [ ] **API:**
  - set logo, colours and tagline with version; read back with `logoUrl`
  - clear each with `null`
  - one audit entry
  - logo id of another organization, a deleted file or an OFFERING_IMAGE file → 400
  - STAFF without `organization.profile.update` → 403
  - cross-org → 404
  - `/me/orgs` carries `logoUrl`
- [ ] **Admin unit:** presets select, custom colour with live contrast message, preview reflects choices, read-only view without permission, top bar logo and fallback.
- [ ] **Admin browser:** the owner uploads a logo (a small PNG fixture), picks a preset and saves; the top bar shows the logo; the settings home lists Branding under Business; no sideways scroll at 375 px.
- [ ] Route sizes ≤ 170 KiB (the colour input and preview stay light; the upload helper is already in the bundle).
- [ ] Every existing suite green; full "Done means" list.

## Out of scope
- Website themes (4.1)
- Receipts and invoices (3.5, 3.9; they read branding later)
- A public branding endpoint (4.6)
- Custom fonts
- The platform brand (P2)
- Dark-mode colour variants

## Risks & checks
- **Keep the contrast rule in one shared helper:** never two copies (screen and API).
- Do not let business colours leak into admin tokens.

## Done when
- A business sets a logo, readable colours and a tagline, sees a preview, and its logo shows in the admin top bar.
- The data is ready for receipts, the booking page and the website.
- The review passes.
