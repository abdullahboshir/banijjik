## Goal
Close every way the review found to end up with more access than one was given:
- the seed can no longer promote a stranger to platform super admin
- a role can no longer be widened by someone who does not hold what they add
- an invitation dies with its inviter's access
- a reactivated member cannot come back onto an archived location or role
- invitations and sign-out respect organization status, location limits and audiences

## Decisions
1. **B1: the platform admin seed never promotes on an email match alone.** In `EnsurePlatformAdminUseCase`, when a user with `PLATFORM_ADMIN_EMAIL` exists and has no operator record:
   - verify `PLATFORM_ADMIN_PASSWORD` against that user's stored hash
   - **match** → create the operator (the person who set the environment owns the account)
   - **no match** → create nothing. Log `{ event: "seed.platform_admin_refused", reason: "password_mismatch" }` at `error` with no email, return a result the seed entry turns into **exit code 1**, and print one line telling the operator to use another address or the account's real password.
   - A platform audit entry `platform.operator.seeded` is written when an operator is created (actor: system, reason SEED).
   - Tests: the review's P4 sequence (register the admin email first, then seed with another password → refused, platform login impossible); the matching-password path; the unchanged paths (fresh database; second run).
2. **B2: role create and update follow ADR-092.**
   - `POST /roles` and `PATCH /roles/{roleId}`: every permission key in the request that is **added** (all keys on create) and every key **removed** on update must be held by the caller **at ALL locations**. Otherwise → `422 BUSINESS_RULE` `ROLE_NOT_GRANTABLE` with `details.permissionKeys` listing the keys the caller lacks. This is the same answer the member endpoints give.
   - Role writes (`create`, `update`, `archive`) require their `iam.role.*` permission **at ALL**: a role is an organization-level record. Add a kernel helper `requireAllLocations()` (after `permission(key)`, 403 when the narrowed set is not `"ALL"`) and use it on the three routes. Reading roles stays as it is.
   - Tests: the review's P1 sequence (a member with `iam.role.read` + `iam.role.update` at one location cannot widen any role; with them at ALL they still cannot add a key they lack); an owner still can; a table test over caller grants × added/removed keys.
   - Amend ADR-092 with one paragraph: "roles are covered by the same rule".
3. **J1: an invitation depends on its inviter.**
   - When a member is suspended, removed, or has assignments changed, that member's **PENDING invitations are revoked in the same transaction** (status REVOKED, audit `organization.invitation.revoked` with reason `INVITER_ACCESS_CHANGED`, event as today).
   - On **accept**, in the accept transaction: the inviter must be an ACTIVE member and must still hold every key of every invited role at the invited locations (the existing `assertCallerHoldsEveryKey`, evaluated for the inviter). If not → the invitation is marked REVOKED and the answer is the same 404 as an invalid token.
   - Tests: the review's P2 sequence; an inviter demoted (not removed) below the invited role; the unchanged happy path.
4. **J5: reactivation re-validates.** `REACTIVATE` runs `guard.assertAssignable(member.assignments)` inside its transaction (ACTIVE locations, ACTIVE roles, the guard-document touch of ADR-092). A member whose location or role was archived meanwhile → `422 BUSINESS_RULE` `MEMBER_ASSIGNMENTS_INVALID` with a message that says to fix the assignments first.
   - `PATCH /members/{memberId}` assignments is allowed for a SUSPENDED member, so the fix is possible. Add it if the current code refuses it.
   - Tests: the review's P6 sequence.
5. **M1: organization status on the invitation routes.** `GET /invitations/{token}` and `POST …/accept` answer 404 when the organization is not ACTIVE. A suspended business takes no new members.
6. **M2: invitations respect the caller's reach.**
   - `GET /invitations` lists only invitations whose every assignment the caller could have made: each location within the caller's locations for `organization.member.invite`, and "ALL" assignments only for callers holding it at ALL.
   - `POST /invitations/{invitationId}/revoke` runs `assertCallerHoldsEveryKey` on the invitation's assignments (taking away follows the same rule as giving). An invitation outside the caller's reach → 404.
   - Tests: the review's P7.
7. **M5: `logout-all` is per audience.** The admin `POST /auth/logout-all` revokes only `ADMIN` sessions of the user. Add `POST /platform/auth/logout-all` for the platform audience, with the matching row in `14 §7`. Tests both ways.
8. **Not decided here (owner):** M3. Organization-level permissions for profile, audit log, members and invitations granted at a single location still act organization-wide. This card applies the at-ALL rule only to **role writes**, because that is where the privilege escalation is. The rest waits for the owner's answer. Write it in STATUS.
