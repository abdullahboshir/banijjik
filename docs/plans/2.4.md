Tier: **T1** (every later module reads its behaviour from here) · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor · Date: 2026-10-14 · Based on commit: `main 8291363`

**Wave 1 of Phase 2, in parallel with 2.1b and 2.3.** Read `docs/plans/phase-2-lanes.md` and `docs/ops/implement-with-cursor.md` first. Reserved ADR number: **ADR-103**.

## Goal
A setting is a code-registered key whose value resolves **System → Industry → Organization → Location** (ADR-016). After this card:
- Modules declare their settings in their manifests, with a declarative value type.
- An organization reads its resolved settings and changes them through the API, with versions, audit and location overrides only where a key allows them.
- Later modules (booking, sales, POS, enrollment) only declare keys; they never build their own settings storage.

Terms and putting settings into `/me/config` are card 2.2 (wave 2).

## Decisions
**Declaring settings**
1. **The manifest declares settings, not bare keys.** In `module-manifest.ts` (2.4 owns this file in wave 1), replace `settingKeys: readonly string[]` with `settings: readonly SettingDefinition[]`, and update every existing manifest (all have none today, so `settings: []`).

   ```ts
   interface SettingDefinition {
     readonly settingKey: string;           // `<moduleKey>.<camelCaseName>` or `<moduleKey>.<group>.<name>`; must start with the module's key
     readonly value: SettingValueSpec;
     readonly systemDefault: unknown;       // must pass `value`
     readonly allowsLocationOverride: boolean;
     readonly isClientVisible: boolean;     // 2.2 puts these into /me/config
   }
   type SettingValueSpec =
     | { kind: "BOOLEAN" }
     | { kind: "INTEGER"; min: number; max: number }
     | { kind: "MONEY"; min: number; max: number }        // integer minor units (ADR-013)
     | { kind: "DURATION_MINUTES"; min: number; max: number }
     | { kind: "ENUM"; values: readonly string[] }
     | { kind: "TEXT"; maxLength: number }
     | { kind: "STRUCTURED"; schemaKey: string };         // a Zod schema registered in packages/validation
   ```

   - Put the types in contracts and the validator `buildSettingValueSchema(spec)` in `packages/validation`.
   - **STRUCTURED** values (for example delivery-charge zones) use a schema registered by key in `packages/validation/src/settings/structured-setting-schemas.ts`. It starts empty; the owning card adds its schema.

2. **Registry checks at startup** (in the module registry). The API refuses to start when:
   - a key is duplicated
   - a key does not start with its module's key
   - a `systemDefault` fails its spec
   - a STRUCTURED `schemaKey` is unknown

   Each check gets a unit test.

3. **Register the two common settings that exist today** in the `organization` manifest: `organization.digitScript` (ENUM `LATIN | BENGALI`, default `LATIN`) and `organization.numberGrouping` (ENUM `WESTERN | INDIAN`, default `WESTERN`). Both are client-visible, without location override.
   - Number formatting adopts them in 2.2/2.7; say so in the README.
   - **Do not** register `organization.defaultLocale`: it is a profile field today, and two sources of one value are not allowed.
   - Every other key in the template seeds (`sales.*`, `booking.*`, `pos.*`, …) is registered by its own module's card later. Until then resolution ignores it (decision 5).

**Storing and resolving**
4. **`SettingValue`:** collection `setting_values`, tenant DB, tenancy `ORGANIZATION`, versioned, audit fields.
   - Fields: `settingValueId`, `settingKey`, `locationId?` (null = organization level), `value`.
   - Unique `(organizationId, settingKey, locationId ?? null)`.
   - `locationId` is validated in the use case: the key allows location overrides, and the location belongs to the organization and is in the caller's reach. The location plugin needs a location on every row, so this is not an `ORGANIZATION_AND_LOCATION` model.

5. **`SettingsResolver.resolve(organizationId, { locationId?, keys? })`.** For each registered key of the organization's **effective modules** (from `OrgConfigReader`), the first of:

   | Order | Source |
   |---|---|
   | 1 | the location row (only when `allowsLocationOverride` and a `locationId` is given) |
   | 2 | the organization row |
   | 3 | the template's `settingsDefaults[key]`, if it passes the spec |
   | 4 | the `systemDefault` |

   Each answer carries `{ value, source: "LOCATION" | "ORGANIZATION" | "INDUSTRY" | "SYSTEM", version? }`.
   - A template default that fails its spec is skipped. Log a `warn` once per key and template version (data error, ADR-076), never an exception.
   - Keys of modules that are not effective are absent (`07 §3`: "settings are hidden").
   - **Reading the template defaults:** add exactly **one new file** in `platform/industry`, `application/use-cases/read-industry-setting-defaults.use-case.ts`, plus one export line `buildIndustrySettingDefaultsReader()`. Nothing else there (2.1b owns it).
   - **One query:** the organization's rows for the requested keys are read in one query (lean, projection, index `{ organizationId, settingKey, locationId }`). No N+1.
   - Export the resolver builder from `core/settings/index.ts`; later modules import it through the index.

**Endpoints** (`/api/v1/orgs/{organizationId}/settings`, the tenant pipeline; new module `core/settings`, SYSTEM, the key exists)

6. **`GET /settings?keys=&location=`** (`settings.setting.read`): the resolved values with source and version.
   - `keys` is optional, at most 100.
   - The result is bounded by the registry, so it is a keyed read, not a paged list. Write that in `14`.
   - `?location=` goes through the existing `locationAccess` and must be within reach.

7. **`PATCH /settings`** (`settings.setting.update`): a batch of `[{ settingKey, value, locationId?, version? }]`, at most 50 items, **all or nothing in one transaction**.
   - `value: null` deletes that row, so the value falls back to the next source.
   - A key not registered for an effective module → 404 `errors.setting_not_available`.
   - A bad value → 400 at `items.<n>.value`.
   - `locationId` on a key without location override → 422 ruleKey `SETTING_NOT_LOCATION_SCOPED`.
   - **Updating an existing row needs its `version`**; a stale one → 409. Creating a row needs no version; a concurrent create of the same row → 409 through the unique index.
   - **Permissions:** an organization-level item needs the permission at **ALL** locations; a location item needs it at that location (ADR-095 reach).
   - **Per batch:** one tenant audit entry listing every `{ settingKey, locationId, from, to }`; one event `settings.setting.changed` with the keys; one `configVersion` bump.

8. **Permissions and grants** (add-only):
   - keys `settings.setting.read`, `settings.setting.update` (`settings.term.update` belongs to 2.2)
   - role grants: OWNER ALL, MANAGER ALL, CASHIER READ, STAFF READ, VIEWER READ, RIDER NONE. Screens and the POS need to read behaviour settings.
   - the event type `settings.setting.changed` in contracts and the manifest

**Generated module-off tests**
9. `describe-module-contracts.ts` gets the "settings are hidden" assertion for real. A probe module declares one location-overridable setting, then:
   - with the module off, `GET /settings` does not list it and `PATCH` → 404
   - with it on, both work

   Adjust the suite's reading of `settingKeys` to `settings`. This is the only test-support change.

10. **Records:**
    - ADR-103 ("Accepted (proposed)"). It records:
      - declarative value specs
      - STRUCTURED schemas by key
      - the resolution order with template defaults that fail validation skipped
      - unregistered template keys ignored until their module registers
      - organization-level writes need ALL locations
    - `14` rows, the module README, `10` (the `settings` and `organization` rows if a cell changes), the 2.4 STATUS row.

## Tests (must exist and pass)
- [ ] **Value specs (unit):** every kind, valid and invalid; MONEY refuses a float; ENUM refuses an unknown value; STRUCTURED with an unknown `schemaKey` refused at registry check.
- [ ] **Registry startup checks:** duplicate key, wrong prefix, bad default, unknown schema key — each refuses to start.
- [ ] **Resolution order** (API, organization on SALON or a template fixture with `organization.digitScript = BENGALI`):
  - SYSTEM → INDUSTRY (template default) → ORGANIZATION (PATCH) → LOCATION (probe key with override), each with the right `source`
  - `value: null` falls back one level
  - a template default that fails the spec is skipped with one warn
  - an unregistered template key never appears
- [ ] **Happy path:** `GET` all and `GET ?keys=`; `PATCH` a batch of two (one audit entry, one event, `configVersion` + 1).
- [ ] **Validation:** a bad value → 400 at the item path; more than 50 items → 400; an unknown key → 404.
- [ ] **Atomicity:** a batch with one bad item changes nothing.
- [ ] **Concurrency:** a stale `version` → 409; two concurrent creates of the same row → one wins, one gets 409.
- [ ] **Permission denied:**
  - STAFF: `GET` 200, `PATCH` 403
  - a MANAGER of one location: organization-level `PATCH` 403, a location `PATCH` for their own location 200, for another location 403
- [ ] **Location rules:** `locationId` on a non-overridable key → 422; a location of another organization → 404.
- [ ] **Cross-org denied:** another organization's settings are never readable or writable.
- [ ] **Generated module-off:** the probe module's setting is hidden and refused when the module is off.
- [ ] Every existing suite green, assertions unchanged except the `settingKeys` → `settings` rename in test support (list it); full "Done means" list.

## Risks & checks
- **Hot path later:** booking and POS will read settings often. Keep `resolve` to two indexed reads (the organization's rows and a cached template default map). 2.2 will add caching per `configVersion`; do not add a cache here.
- **Coordination:** you are the only card that edits `module-manifest.ts` in this wave. 2.3 keeps `customFieldEntities` as it is. Keep the rename mechanical.
- Stop and ask if a resolution case in the template data does not fit the order above.

## Done when
- Settings are declared in manifests, resolved in the ADR-016 order, read and changed through the API with versions, audit and location rules.
- Module-off hides them.
- The Opus review passes.
