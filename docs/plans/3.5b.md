## Goal
A business can take goods back from a completed order: per line, a quantity and what happened to the goods (back on the shelf, damaged, never received). The server computes the value, lowers what the customer still owes, gives back only what was really paid (cash, mobile money, bank, card or store credit), puts stock back at its original cost, posts the books and lowers the staff commission of the returned lines. A wrong return can be reversed, and an exchange returns goods into store credit and pays a new order with it.

## Decisions

### A1 · Create a return
1. **Aggregate `SalesReturn`** (module `sales`, tenancy LOCATION, append-only, versioned for the status change of A2): `salesReturnId`, `salesReturnNumber` (sequence `RETURN`), `orderId`, `locationId` (the order's), `contactId | null`, `lines[{ orderLineId, quantity, disposition: RESTOCK | DAMAGED | NOT_RECEIVED, value: Money, taxPart: Money }]`, `deliveryChargeReturned: Money`, `roundingReturned: Money`, `value: Money` (Σ line values + delivery + rounding), `refund: { method: PaymentMethod | null, amount: Money, paymentId | null, storeCreditEntryId | null }`, `dueReduced: Money`, `reasonKey`, `note?`, `approvals: { action, approvalId, approverMemberId, approvedAt }[]`, `status: ACTIVE | REVERSED`, `reversedBySalesReturnId | null`, `exchangeOrderId | null`, `businessDate`, audit fields, `version`. `RETURN_DISPOSITION` and `SALES_RETURN_STATUS` in `contracts/sales`.
2. **When a return is allowed:** the order is `COMPLETED` (DELIVERED arrives with Phase 5; the rule names both), and the organization's local date of `completedAt` plus `sales.returnWindowDays` is today or later. New setting `sales.returnWindowDays` (INTEGER ≥ 0 or null = no limit, default 7, location override no). Outside → `422 SALES_RETURN_WINDOW_CLOSED`. Other statuses → `422 SALES_RETURN_ORDER_NOT_RETURNABLE`.
3. **Quantity cap, race-safe:** per line, `returnedQuantity + quantity ≤ quantity sold`, else `422 SALES_RETURN_QUANTITY_ABOVE_SOLD`. The check reads the order inside the transaction and the order projection write (decision 7) is a versioned update of the order, so two returns racing for the last unit: one wins, the other gets 409 and writes nothing.
4. **Value per line (server only; the client sends quantities and dispositions):** cumulative, so remainders never drift:
   - `cumulativeValue(q) = q === sold ? lineNetTotal : floor(lineNetTotal × q / sold)`, the same for `lineTax`.
   - this return's line `value = cumulativeValue(returnedBefore + quantity) − cumulativeValue(returnedBefore)`; `taxPart` the same with `lineTax`.
   - **Delivery charge:** body field `returnDeliveryCharge: boolean` (default false). When true, `deliveryChargeReturned` = the order's delivery charge minus delivery returned by earlier ACTIVE returns.
   - **Rounding:** the return that makes every line fully returned also returns the order's `roundingAdjustment` (signed), so a fully returned order owes exactly the kept delivery charge.
5. **Money: the due first, then what was paid (manoxen guide 15).** In the same transaction, through a new `OrderPaymentPort.settleReturn` implemented in `routes/order-payment-adapter.ts` with payment's `index.ts`:
   - summary total `T`, net paid `N` (allocated − refunded); new total `T' = T − value` (never below 0); `dueReduced = min(value, max(0, T − N))`; refund `R = max(0, N − T')`.
   - write `T'` with `setTotal` (a new adapter method that allows a total below the old one only by a return; the existing `updateTotal` guard stays for edits).
   - `R > 0` needs `refundMethod` in the body (`CASH | BKASH | NAGAD | BANK | CARD | STORE_CREDIT`; `GATEWAY` refused until Phase 5: `422 PAYMENT_METHOD_NOT_AVAILABLE`), else `422 SALES_RETURN_REFUND_METHOD_REQUIRED`. `STORE_CREDIT` needs a contact on the order (`422 ORDER_CANCEL_NEEDS_CONTACT` reused). A cash-type refund writes a `REFUND` payment allocated to the ORDER request (`revenueState AFTER_REVENUE`), store credit writes the refund payment plus a `CREDIT` entry of kind `PAYMENT_REFUND`, exactly as the payment module does today. Reuse the payment module's refund code through its index; **if `RefundPaymentUseCase` cannot run inside the caller's transaction, stop and ask** (do not copy it).
   - `R = 0`: no payment, no approval for the refund.
6. **Approvals (§9):** `R > 0` needs an ADR-121 token for `APPROVAL_ACTION.REFUND` (`subjectKey` = the order id, `amount` = R) with the same exemption rule as `POST /refunds` (`payment.payment.refundWithoutApproval` at the location and `payment.refund.managerWithoutApproval`). Any NOT_RECEIVED line needs a token for `RETURN_NOT_RECEIVED` (`amount` = the value of the NOT_RECEIVED lines), never exempt. Both tokens are consumed inside the transaction; missing → `403 APPROVAL_REQUIRED` with the action.
7. **Stock and the order, same transaction:**
   - RESTOCK → `returnStock` disposition `RETURN`; DAMAGED → `RETURN_DAMAGED`; NOT_RECEIVED → no movement.
   - Movements carry `sourceType: SALES_RETURN` (add to the stock source types if missing), `sourceId: salesReturnId`, so the order's own COGS read (SALE movements by order id) never changes.
   - **Unit cost = the order's SALE movement of the same inventory item** (its stored unit cost), not today's average: add an optional `costFrom: { sourceType, sourceId }` to `returnStock`. The COGS reversal then equals the COGS posted at completion.
   - Order projection: each line's `returnedQuantity` += quantity, new order field `returnStatus` (`NONE | PARTIAL | FULL`, contract enum; old rows read `NONE`), one versioned order update.
8. **Events and audit:** `sales.return.created` `{ salesReturnId, orderId }` with `orderingKey: order:<orderId>` (the order's stream: `accounting.postOrders`'s stream prefix), audit `sales.return.created`. Permissions `sales.return.read` (owner, manager, cashier, staff at their locations) and `sales.return.create` (owner, manager, cashier); LOCATION tenancy and the caller's location check.
9. **Books** (accounting, new ORDERED handler `accounting.postSalesReturns`, `streamPrefixes: ["order:"]`, per 3.22 it handles its types and the runner advances for the rest; idempotent on `(SALES_RETURN, salesReturnId, postingKey)`; new `JOURNAL_SOURCE_TYPE.SALES_RETURN`):
   - `sales_return_value`: Dr `SALES_RETURNS` (Σ line value − Σ taxPart), Dr `TAX_PAYABLE` (Σ taxPart), Dr `DELIVERY_INCOME` (delivery returned), Dr or Cr `ROUNDING` (rounding returned, by sign) / Cr `ACCOUNTS_RECEIVABLE` (value). The refund payment posts its own entry (Dr AR / Cr cash, or store credit liability) as today, so AR nets out.
   - `sales_return_cogs`: Dr `INVENTORY` / Cr `COGS` for Σ the return movements' value (RESTOCK and DAMAGED; damaged goods stay inventory until a stock adjustment writes them off).
   - Snapshot through a sales posting-source port (`buildSalesReturnPostingSourceAdapter`), required dependencies; a missing return or a currency mismatch throws `postingSourceMissing`.
10. **Commission per returned line (changes 3.11 C, ADR-135 amended):** `commission.accrue` also handles `sales.return.created`. For each returned line with ORDER_LINE ledgers, the target net is `accrual − floor(accrual × returnedQuantity / soldQuantity)` (the line's cumulative returned quantity read from the order), reconciled with the existing adjustment entries. **Payment refunds no longer reconcile ORDER_LINE ledgers** (a refund without a return is a price concession: the work was still done). BOOKING ledgers keep the refund reconcile. The race marker `(ORDER_LINE, orderId)` is touched in this path too. **Allowed test changes (this plan is the lead's OK):** the 3.11 C tests `a refund of part of the order lowers each line's commission by the order's refunded share` and `a full refund brings every line's commission to zero and a reversal of that refund restores it` become return-based tests with the same intent (`a partial return lowers that line's commission by its returned share`, `a full return brings the line's commission to zero`); add `a refund without a return leaves the order lines' commission unchanged`. No other existing expectation may change.
11. **Endpoints:** `POST /orgs/:organizationId/sales/orders/:orderId/returns` (`Idempotency-Key` required: it creates money and stock; replay returns the first response), body `{ lines: [{ orderLineId, quantity, disposition }], returnDeliveryCharge?, refundMethod?, reasonKey, note?, approvalTokens? }`; `GET /orgs/:organizationId/sales/returns?orderId=&from=&to=&page&limit` (limit ≤ 100, index `{ organizationId, locationId, businessDate: -1, salesReturnId: -1 }`); `GET …/sales/returns/:salesReturnId`. `reasonKey` from a new contract enum `SALES_RETURN_REASON` (`DEFECTIVE`, `WRONG_ITEM`, `NOT_AS_DESCRIBED`, `CHANGED_MIND`, `NOT_DELIVERED`, `OTHER`; `OTHER` needs a note).

### A2 · Reverse and exchange
12. **Reverse** `POST …/sales/returns/:salesReturnId/reverse` (`sales.return.reverse`, owner and manager; approval `REFUND` always, no exemption; `Idempotency-Key`; body `{ version, reasonKey }`): one transaction writes the opposite stock movements (SALE-like OUT at the same unit cost, refused with `422 SALES_RETURN_STOCK_GONE` if the restocked goods are no longer on hand), restores the order total by `value`, takes the refund back (a cash refund: the customer pays back through a new IN payment allocated to the order, recorded here with the method of the refund; a store-credit refund: a `DEBIT` entry, refused if the balance is short), lowers `returnedQuantity`, sets `REVERSED` and `reversedBySalesReturnId` (a reversal row of the same aggregate with negative lines), publishes `sales.return.reversed`; accounting posts the mirror of decision 9; commission reconciles from the new returned quantities. A reversed return cannot be reversed again (unique `reversesSalesReturnId`).
13. **Exchange** `POST …/sales/orders/:orderId/exchange` (permissions `sales.return.create` and `sales.order.create`): one transaction = a return with `refundMethod: STORE_CREDIT` (contact required) + a new order (`INSTANT` sale at the same location, the 3.5a primitive) paid first with that store credit (Payment IN `STORE_CREDIT` + `PAYMENT_USE` entry), the rest paid or left as due like any instant sale, or left in store credit when the new order is cheaper. Both carry the same `checkoutId`; the return's `exchangeOrderId` points to the new order.

### B · Screens
14. Order detail: a "Return" sheet (lazy) for COMPLETED orders inside the window: per line a quantity stepper capped at what is left and a disposition select, the delivery-charge switch, reason, then a server preview of value, due reduced and refund (a `POST …/returns/preview` with the same body, no writes, added in A1), the refund method when a refund is due, the approval PIN dialogs, `Idempotency-Key` per submit. Returns list (`sales/returns`, menu entry under sales with `sales.return.read`), return detail with reverse (A2) and the exchange flow (A2). ≤ 180 KiB per route; the order detail route is already near the limit, so the sheet loads lazily.

## Tests (A1, must exist and pass)
**Domain (unit)**
- [ ] `values a partial return from the stored line total and gives the last unit the remainder` (sold 3, line 1000: returns of 1, 1, 1 → 333, 333, 334)
- [ ] `splits the tax part the same way`
- [ ] `returns the rounding adjustment only with the return that empties the order`
- [ ] `computes due reduced and refund from total and net paid` (unpaid, partly paid, fully paid, overpaid)

**API (real Mongo)**
- [ ] `a full return of a paid cash order refunds the line value in cash and restocks it`
- [ ] `a return of an unpaid order lowers the due and pays nothing out`
- [ ] `a return of a partly paid order lowers the due first and refunds only the paid excess`
- [ ] `a damaged return goes to damaged stock and a not-received return moves no stock`
- [ ] `restocked goods come back at the cost they were sold at, not today's average cost`
- [ ] `refuses a quantity above what is left on the line` and `two returns racing for the last unit: one wins, the other gets 409 and writes nothing`
- [ ] `refuses a return after the return window and on an order that is not completed`
- [ ] `a refund needs a REFUND approval unless the caller is exempt, and a not-received line always needs its approval`
- [ ] `store credit refund needs a contact and adds a credit entry`
- [ ] `the same Idempotency-Key returns the first return and writes nothing twice`
- [ ] `the return posts sales returns, tax and receivable, and reverses the cost of goods for restocked and damaged lines` (trial balance: AR for the order nets to 0 after the refund)
- [ ] `a second delivery of the return event posts once`
- [ ] commission: the three tests of decision 10
- [ ] `the preview returns the same numbers and writes nothing`
- [ ] permissions: `a staff member without sales.return.create gets 403`; cross-org `another organization's order is 404`; cross-location `a return at another location's order is 403`
- [ ] `old orders read returnStatus NONE`
- [ ] Existing sales, order-payment, inventory, accounting (3.24), payment and commission suites green.
- [ ] T1 §11 table in the handoff (items 1–7, 13, 17–24 apply; 8–12 n/a: no job).

## Out of scope
- Return to sender, delivered status, courier (Phase 5); POS register expected cash (3.9 adds `posSessionId` to the refund payment).
- Writing damaged stock off (existing stock adjustment).
- Returns for bookings and enrollments (they use cancellation refunds, §6 last line).
- Loyalty effects.

## Risks & checks
- Decision 5 is the money heart: the due must drop before any money goes out, and `R` can never exceed the net paid. Test every case of the unit test above through the API too.
- Decision 7's cost source: if `returnStock` cannot find a SALE movement of the item for the order (an order completed before 3.24 has none), stop and ask; do not fall back to the average silently.
- The refund reuse in decision 5: no copy of payment code in sales or routes.
- Decision 10 changes merged behaviour; the ADR-135 note and the handoff must say so.
