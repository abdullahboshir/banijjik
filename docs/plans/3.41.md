## Goal

One API test per SALON, GYM, COACHING and RETAIL world runs a real business day through the HTTP API, then through the real outbox and the same handlers the worker uses (`processOrganizationOutbox`). It then reads the report home, the daily report, the Z-report (where a till ran), the trial balance and the commission summary, and those numbers match the day. The 3.10 B browser gap ("after a seeded sale and a payment") is closed.

## Decisions

1. **Four API files, one world each**, under `apps/api/src/modules/commerce/report/presentation/`:
   - `day-scenario-salon-api.test.ts`
   - `day-scenario-gym-api.test.ts`
   - `day-scenario-coaching-api.test.ts`
   - `day-scenario-retail-api.test.ts`
   Shared setup lives in `apps/api/src/test-support/day-scenario-world.ts` (owns): harness start, handler registration, `processOrganizationOutbox` twice (second call is a replay; counters must not change), and helpers to read home / daily / trial balance / commission summary / Z-report.

2. **Harness.** Copy `order-walk-in-money-api.test.ts`: `startCatalogApi()`, then register:
   - `registerAccountingAndExpenseHandlers()`
   - `registerReportEventHandlers(systemClock)`
   - `registerCommissionHandlers(systemClock, orgConfig)` (same `buildOrgConfigService` wiring as that file)
   Worlds: `worldFor(harness, { industryTemplateKey: "SALON" | "GYM" | "COACHING" | "RETAIL" })`. Template keys stay in the test files (lint R16).

3. **No `industry` in production code.** Template keys and nouns ("Haircut") exist only in these tests and existing test helpers.

4. **Amounts are named constants in each file.** Expected report figures are computed in the test from those constants (do not invent a second set of magic totals). Money is integer minor units. Currency is the organization currency from the home response, never a `"BDT"` literal in an assertion against books.

5. **SALON day** (owner + one performer member assigned at the location):
   - Publish a SLOT service (use `publishBookableService`) and a WALK_IN_ONLY service (same shape as `order-walk-in-money-api.test.ts` `serviceOf`).
   - Publish a PRODUCT and receive stock (POS helpers).
   - Commission: one SERVICE rule, 10% (`RATE_BASIS_POINTS = 1000`) targeting the performer, same create-rule body as the walk-in money test.
   - Book the SLOT service with that performer, confirm, complete, take payment in full (CASH).
   - Pair a till, open the register (float `5000`), sell the walk-in service with `performedByMemberId` **and a line or order discount plus tax** (3.40 review R1 note: reports and posting must see a discounted, taxed walk-in), sell the product, both CASH.
   - Close the register (counted cash = expected).
   - After outbox: home `today` has `bookingsCompleted === 1`, `bookingsCompletedValue` = the booking total, `ordersCompleted === 2` (walk-in + product), `netSales` = walk-in total + product total, `paidInByMethod.CASH` = booking payment + both till payments (no double-count of the same payment). Daily row for today matches home today. Z-report `grandTotal` = walk-in + product (till orders only). Trial balance `balances === true`. Commission summary `open` for the performer = 10% of the completed booking value plus 10% of the walk-in line (integer floor as the commission module already does). Replay does not change any of those numbers.

6. **GYM day:**
   - Publish a PLAN, enroll a contact, take the first period's fee in full (the payment path that activates, same as 3.27/3.7 tests).
   - Two check-ins at the enrollment's location.
   - Renew for the next period and take that fee in full.
   - After outbox: `enrollmentsCreated === 1`, `enrollmentsActivated === 1`, `enrollmentsRenewed === 1`, `checkIns === 2`, `paidInByMethod` sums the two fees. Home and daily match. Trial balance balances. Commission summary is `[]` unless a rule was created (do not create one). No Z-report (no till).

7. **COACHING day:**
   - Create a student contact with a RELATED guardian (3.1c path; the template requires the guardian).
   - Enroll the student, pay **half** the first period fee (PARTIAL). Leave the rest a due.
   - After outbox: `enrollmentsCreated === 1`. `paidInByMethod` = the half fee. Home money `moneyInNet` = that amount. Daily matches. Trial balance balances. The enrollment's payment request still shows the remaining due (read the existing payment-summary / dues endpoint the 3.27 tests use; do not invent a new one).

8. **RETAIL day:**
   - Stock receipt of one item that sells both loose and packed (the existing `order-stock-api.test.ts` "sells loose rice and a packed bag from the one item" setup; reuse that helper if it is exported, otherwise copy the minimum into the day-scenario helper).
   - Pair a till, open, sell loose + packed in one POS sale, CASH.
   - Place and complete one admin order of the packed unit, pay it.
   - Return one packed unit of the POS sale through `POST /pos/returns` (cash refund).
   - Close the register.
   - After outbox: `ordersCompleted === 2`, `returnsCount === 1`, `netSalesAfterReturns` = POS grand total + admin grand total − return value. Z-report sales = the POS sale only; expected cash = float + POS cash − cash refund. Trial balance balances. Home and daily match. Replay does not change counts.

9. **Clock.** Use the harness clock as-is (real "now") so the business date is today in `Asia/Dhaka`. Do not freeze the clock across outbox processing (handlers and TTL). One assertion may record `home.businessDate` and reuse it for the daily `from`/`to`.

10. **Browser (add-only on the existing file).** In `apps/admin/src/report/report-screens.browser.test.ts` add one case: seed a completed paid instant sale (the browser stack's API helper, same pattern as `pos-screens.browser.test.ts` seeding a product), wait for the worker by reloading the home until today's net sales is the sale total (deadline 20 s, never a single click race). Then open `/reports` for today and assert that day's net sales after returns equals the same total. Keep the existing empty-business case.

11. **Permissions / cross-org.** Each API file includes: a cashier `403` on `GET /reports/home` (already true in 3.10; one assertion is enough in the RETAIL file). Cross-org: Bob's home does not include Alice's day's net sales (RETAIL file).

12. **No production code** except what decision 10 needs (none if the home already shows seeded numbers). If the home is empty after a real sale, that is a bug in 3.10: stop and ask, do not write a workaround.
