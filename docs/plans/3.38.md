# Plan: card 3.38 · Resource time-off saves without a server error

Tier: T2 · Planned by: Opus 5.5 (lead) · Date: 2026-10-26 · Based on commit: `main 90d2de60`

## Session parts
One part, branch `s/3.38-api-time-off-transaction`.

## Goal
`POST /orgs/{organizationId}/resources/{resourceId}/time-off` answers `201` with the new time-off row instead of `500`. Today the use case writes the row and then calls `audit.record` outside a transaction; the audit recorder requires `withTransaction` and throws, so the request fails after the row is already stored. The admin resource form (`apps/admin/src/resources/resource-form-time-off-fields.tsx`) calls this endpoint, so owners hit the error. No API test covered the endpoint, because the booking tests insert time-off rows directly (`test-support/booking-hall-world.ts` `insertTimeOff`).

## Inputs read
- `apps/api/src/modules/commerce/booking/application/use-cases/resource-timeoff.use-cases.ts` (`CreateResourceTimeOffUseCase`; `ArchiveResourceUseCase` in the same file is the pattern: `unitOfWork.run` around the write and the audit)
- `apps/api/src/modules/commerce/booking/build-booking-controller.ts` (wiring of `createResourceTimeOff`, no `unitOfWork` passed)
- `apps/api/src/modules/commerce/booking/infrastructure/mongo-resource-timeoff.repository.ts` (`insert` calls `create([record])` without the active session)
- `apps/api/src/kernel/audit/audit-recorder.ts` ("`record` must run inside `withTransaction` … without a transaction it throws")
- `apps/api/src/modules/commerce/booking/presentation/booking-tenant-resource.routes.ts` (route, permission `booking.resource.update`)
- `apps/api/src/test-support/booking-hall-world.ts`, `test-support/two-organizations.ts`, `presentation/event-session-resource-api.test.ts` (test harness and helpers)

## Decisions
1. `CreateResourceTimeOffUseCase` takes `unitOfWork: BookingUnitOfWork` (required, like `ArchiveResourceUseCase`). The insert and `audit.record` run inside `unitOfWork.run(...)`. The resource read and the location check stay before the transaction, as in the archive use case.
2. `MongoResourceTimeOffRepository.insert` passes `sessionOption(getActiveSession())` to `create`, like the other booking repositories, so the row is written in the same transaction as its audit entry.
3. `build-booking-controller.ts` passes `repos.unitOfWork` to `CreateResourceTimeOffUseCase`.
4. The audit entry stays as it is (`RESOURCE_UPDATED`, entity `resource`, `changes.timeOff.to = "<startsAt>/<endsAt>"`; the free-text `reason` is not audited).
5. No behaviour change beyond that: no new validation, no overlap rule, no event.

## Tests (must exist and pass)
New file `resource-time-off-api.test.ts`, real API through the harness (`startCatalogApi`, a hall from `booking-hall-world.ts` or a resource created through `POST /resources`):
- [ ] `the owner adds time-off to a resource and gets it back in the list` (201, then `GET …/time-off` returns it)
- [ ] `adding time-off writes one audit entry with the time window` (`audit_logs`: one `resource.updated` row for the resource, `changes.timeOff.to` = the window)
- [ ] `time-off that ends before it starts is refused with 400`
- [ ] `a member without booking.resource.update gets 403` (for example a cashier)
- [ ] `another organization cannot add time-off to the resource` (404, and no row written)
- [ ] `a member assigned only at another location cannot add time-off` (the existing location check: 403 or 404, whatever `assertLocationAllowed` answers today; assert that answer and that no row is written)
- [ ] `a booking cannot take a slot inside time-off added through the API` (create time-off through the endpoint, then a booking or availability call for that window is refused or shows no slot: reuse the existing time-off assertion of `event-session-resource-api.test.ts` "a session cannot take a hall in time-off")

## Out of scope
- Refusing or warning about time-off over existing bookings or sessions (STATUS 3.33 note). That is a product decision for later.
- Deleting time-off, editing time-off, any admin screen change.
- Changing `insertTimeOff` in test support (other tests use it).

## Risks & checks
- The repository change must not break the callers that run outside a transaction (`insertTimeOff` in tests): `sessionOption(undefined)` gives no session, as in the other repositories.
- Run the booking API test files: `npx vitest run --config src/test-support/vitest.config.ts --maxWorkers=1 src/modules/commerce/booking` inside `apps/api`.
