# Plan: card 1.3 · Tenant and location enforcement

Tier: **T1** · Planned by: Opus 5.5 · Date: 2026-10-10 · Based on commit: `main 37779a8`

## Goal
No code path can read or write another organization's data by accident:
- every org-owned model is filtered by the request's organization automatically
- writes are stamped and checked
- a missing context throws
- the only ways around it are explicit, logged and visible in one composition file

Tenant routes `/api/v1/orgs/{organizationId}/…` resolve the organization from the path, check the caller's membership, and set `organizationId`, `memberId` and `allowedLocationIds` in the request context. Location-scoped models are filtered to the caller's locations, and writes outside them are refused.

An isolation suite proves it (roadmap 1.3 "Done").

## Decisions
**Which models are tenant-scoped**
1. `registerModel` gets a **required** field `tenancy: "NONE" | "ORGANIZATION" | "ORGANIZATION_AND_LOCATION"` (contracts `MODEL_TENANCY`). There is no default, so a new model cannot forget it.
   - Checks at registration (throw `errors.invalid_model_definition` with details):
     - a TENANT-database model may not be `NONE`
     - an `ORGANIZATION*` model must have an `organizationId` path that is a required, immutable String
     - an `ORGANIZATION*` model must have at least one index whose first key is `organizationId`
     - an `ORGANIZATION_AND_LOCATION` model must have a required `locationId` path (option `locationField`, default `"locationId"`)
2. Classification of the existing models:
   - **NONE:** `users`, `refresh_sessions`, `platform_operators`, `rate_limit_counters`, `organizations` (the org *is* the tenant)
   - **ORGANIZATION:** `locations`, `members`, `roles`, `sequences`
   - **ORGANIZATION_AND_LOCATION:** none yet. The tests register one test-only model.
3. The plugins attach through the existing global hook. `buildSchemaForCompile` applies the tenant plugin to `ORGANIZATION*` definitions and the location plugin to `ORGANIZATION_AND_LOCATION` ones, keyed on `tenancy` instead of the database kind (`addGlobalSchemaPlugin` gains a `tenancy` filter; the database filter stays).

**Tenant plugin** (`kernel/tenancy/tenant-plugin.ts`)
4. **Organization source:** the request context's `organizationId`.
   - If `getSystemReason()` is set: no injection, no check (the bypass), and the operation runs as written.
   - Otherwise, a missing `organizationId` → throw `AppError(INTERNAL, "errors.missing_tenant_context")`.
5. **Covered operations:**
   - **Queries** (`find`, `findOne`, `findOneAndUpdate`, `findOneAndReplace`, `findOneAndDelete`, `updateOne`, `updateMany`, `replaceOne`, `deleteOne`, `deleteMany`, `countDocuments`, `distinct`): add `organizationId` to the filter.
     - The same value already in the filter is fine. A **different** value → throw `AppError(INTERNAL, "errors.cross_organization_access")`, reported. The filter is never silently overwritten; a mismatch is a bug signal.
     - Updates that set or unset `organizationId` → the same throw.
   - **`estimatedDocumentCount`** on a tenant model → throw (it cannot be filtered).
   - **Writes** (`save` of a new or existing document, `insertMany`): stamp `organizationId` when missing; a different value → throw.
   - **`bulkWrite`:** use Mongoose's model-level `bulkWrite` middleware to apply the same rules to every operation. If the installed Mongoose cannot do this reliably, **stop and report** (do not leave a hole).
   - **`aggregate`:** prepend `{ $match: { organizationId } }`. A pipeline that contains `$lookup`, `$graphLookup` or `$unionWith` → throw `errors.unsafe_tenant_aggregate` outside a system reason, until a card needs joins and designs them.
6. **Raw driver access is a lint matter.** New rule **R35**: in `**/modules/**`, ban member access `.collection` on anything and calls to `.db.collection(`, because both bypass Mongoose middleware. Kernel and tests are exempt. Fixtures: fail in module infrastructure, pass in `kernel/db`.

**Location plugin** (`kernel/tenancy/location-plugin.ts`)
7. For `ORGANIZATION_AND_LOCATION` models, using the context's `allowedLocationIds`:
   - **`"ALL"`:** nothing is added.
   - **A list — queries:** filter with `{ [locationField]: { $in: allowed } }`. A filter on one location outside the list → no rows (the `$in` intersection), not an error, so lists stay simple.
   - **A list — writes (save/insertMany/bulk inserts) and updates that set the location field:** a value outside the list → throw `AppError(LOCATION_FORBIDDEN)` (403).
   - **Missing `allowedLocationIds` inside an org context** → throw `errors.missing_location_context`.
   - System reason → bypass.

**Tenant context on tenant routes**
8. **Kernel port** `MembershipDirectory` (`kernel/tenancy/membership-directory.ts`):
   ```ts
   findActiveMembership(userId: string, organizationId: string): Promise<ActiveMembership | undefined>
   interface ActiveMembership {
     memberId: string;
     organizationStatus: OrganizationStatus;
     deployment: OrganizationDeployment;
     assignments: readonly { locationId: string | "ALL"; roleId: string }[];
   }
   ```
   The organization module implements it (infrastructure; exported from `index.ts` as `buildMembershipDirectory()`).
9. **`tenantContext()` middleware** (`kernel/tenancy/tenant-context.middleware.ts`), mounted in `routes/v1.ts` at `/orgs/:organizationId` after `authenticate`:
   - The path param must parse with `uuidV7Schema`, else `404 NOT_FOUND`.
   - The lookup runs through the directory wrapped with `asSystemPort(AUTH_LOOKUP, …)` (decision 11).
   - No membership, or a membership that is not ACTIVE, or the org is CLOSED → `404 NOT_FOUND` (never reveal existence, ADR-080).
   - A SUSPENDED org → `403 ORG_SUSPENDED`. Suspending is card 1.8, but the field exists now.
   - On success it continues in `runWithRequestContext({ ...current, organizationId, memberId, allowedLocationIds })`. `allowedLocationIds` is `"ALL"` if any assignment is ALL, else the assigned location ids.
   - `RequestContext` gains `memberId`. The logger child already adds `organizationId`; add `memberId` too.
   - **No cache yet.** It is one indexed lookup (`{ organizationId, userId }` unique) plus one org read by id. Card 1.4 adds the membership/permission cache with version invalidation, which needs Redis. Record this in STATUS.
10. **`locationAccess()` middleware** (`kernel/tenancy/location-access.middleware.ts`), mounted right after `tenantContext`: when the query has `location=<id>`, the id must be in `allowedLocationIds` (or the list is ALL), else `403 LOCATION_FORBIDDEN`. A malformed id → `400 VALIDATION_ERROR`. Module use cases still validate that a location exists and is ACTIVE.

**Explicit capabilities, decided in one file**
11. Two kernel helpers, both callable only outside `modules/**` (lint R27 extended: importing them in modules fails; fixtures):
    - `asSystemPort<Port extends object>(reason: SystemReason, implementation: Port): Port` (`kernel/context/system-port.ts`) returns an object whose methods run inside `runAsSystem(reason, …)`. It is used in `routes/v1.ts` only:
      - `asSystemPort(AUTH_LOOKUP, membershipDirectory)` for `tenantContext`
      - `asSystemPort(AUTH_LOOKUP, myOrganizationsReader)` for `GET /me/orgs`
    - `runInOrganizationContext(organizationId, work)` (`kernel/tenancy/run-in-organization-context.ts`) runs `work` with `organizationId` and `allowedLocationIds: "ALL"` in the context, and logs `{ event: "tenancy.context_established", organizationId }` at `info`. It is used for org creation: the creator becomes the owner (ALL) of the org being created.

    Why: modules never hold a bypass. The composition root (`routes/v1.ts`, outside modules) decides which plain module ports run as system, and every such decision sits in one reviewable file. Record this in **ADR-087**.
12. **Changes in `core/organization`** (behaviour unchanged, tests must still pass):
    - `CreateOrganizationUseCase` gets a port `OrganizationContextRunner { run<Result>(organizationId, work: () => Promise<Result>): Promise<Result> }`. After `Organization.create`, the MEMBER sequence call and `storeAll` run inside `runner.run(organization.organizationId, …)`.
    - `routes/v1.ts` passes `runInOrganizationContext` through `buildOrganizationRouters`.
    - `ListMyOrganizationsUseCase` becomes the module's exported `MyOrganizationsReader` (plain). The router receives the system-wrapped instance from `routes/v1.ts`.
    - iam's `findRoleKeysByIds` across orgs runs inside that same system scope.
13. **`routes/v1.ts`** mounts the tenant pipeline once: `v1.use("/orgs/:organizationId", requireAdminUser, tenantContext(…), locationAccess(), tenantRouter)`.
    - `tenantRouter` is a `Router({ mergeParams: true })`. Module tenant routers are added to it from 1.4 on.
    - `buildV1Router` takes `tenantRouters: readonly Router[]` (production passes `[]` until 1.4). The tests pass a probe router through the same parameter; there is no test-only branch in production code.
    - Entitlement and permission middleware slot in between in 1.4/1.6.

**Isolation suite**
14. `apps/api/src/test-support/two-organizations.ts` builds, through the real API and use cases:
    - **org A:** owner Alice, a second location `A-L2`, and staff Sam assigned only to the default location `A-L1` (through `MongoMemberRepository` inside `runWithRequestContext` for A, since invitations come later)
    - **org B:** owner Bob
    - It returns ids and authenticated agents (supertest agents with cookies).
15. **Registry meta-test:** for every registered model, `tenancy` is declared. Every `ORGANIZATION*` model's compiled schema carries the tenant plugin (a marker the plugin sets, e.g. `schema.get("banijjikTenantPlugin") === true`), and a location-scoped one carries both. So a model added by any later card is covered by the plugin automatically and checked by this test.

## Tests (must exist and pass)
Plugin (real replica set, a test-only `ORGANIZATION` model and an `ORGANIZATION_AND_LOCATION` model registered in the test file):
- [ ] in A's context, rows of A and B exist: `find`, `findOne`, `countDocuments`, `distinct`, `aggregate` see only A
- [ ] `updateOne/updateMany/deleteOne/deleteMany/findOneAndUpdate/replaceOne` on a B row match 0 documents
- [ ] inserting with `organizationId: B` throws `errors.cross_organization_access`; inserting without it stamps A; `insertMany` the same; `bulkWrite` mixed operations obey the same rules
- [ ] a filter naming B explicitly throws; `$set: { organizationId }` throws; `estimatedDocumentCount` throws; `$lookup` in an aggregate throws
- [ ] no context → `errors.missing_tenant_context`; inside `runAsSystem(MIGRATION)` both orgs are visible and one `system_access` log line is written
- [ ] location plugin with `["L1"]`: lists only L1 rows; inserting L2 → `403 LOCATION_FORBIDDEN`; updating a row's location to L2 → 403; `"ALL"` sees both
- [ ] registry: an `ORGANIZATION` definition without `organizationId`, or without an index leading with it, or a TENANT-db model with `NONE` → throws at registration; the meta-test of decision 15

HTTP (two-organizations helper + a probe tenant router passed through `tenantRouters`):
- [ ] Alice `GET /orgs/{A}/probe` → 200 and the probe sees `organizationId = A`, `allowedLocationIds = "ALL"`, her `memberId`
- [ ] **cross-org denied:** Alice → `/orgs/{B}/probe` → `404 NOT_FOUND`, identical to a random UUID and to a non-UUID segment
- [ ] a REMOVED or SUSPENDED member of A → 404; org A set to SUSPENDED → `403 ORG_SUSPENDED`; CLOSED → 404; unauthenticated → 401
- [ ] **cross-location denied:** Sam (A-L1 only): `?location={A-L2}` → `403 LOCATION_FORBIDDEN`; a probe write of a location-scoped row in A-L2 → 403; a probe list returns only A-L1 rows
- [ ] **data isolation end to end:** Alice and Bob each create rows through the probe router; neither can read, update or delete the other's rows
- [ ] existing suites unchanged: `POST /me/orgs` and `GET /me/orgs` (now under the plugin) pass as before, including atomicity and the 3-query count

Lint:
- [ ] R27 extension (`asSystemPort`, `runInOrganizationContext` imported in a module → fail; in `routes/` → pass) and R35 fixtures; all existing fixtures pass

All with `--force`: lint, format:check, typecheck, test, build; `npm run test:tools`.

## Risks & checks
- **Mongoose middleware coverage** varies by operation and version (Mongoose 9). Each operation in decision 5 has its own test; any operation the plugin cannot cover must fail loudly (throw), never pass silently. If `bulkWrite` cannot be covered, stop and report.
- **Behaviour of 1.1/1.2 code under the plugin:** every existing test must pass unchanged. A test that needs edits means the plan missed something: report it.
- **Performance:** the plugin adds one filter key and no extra query. `tenantContext` adds two indexed reads per tenant request until the 1.4 cache.
- **Disk:** use the installed MongoDB binary (`MONGOMS_SYSTEM_BINARY`, `MONGOMS_VERSION_CHECK=false`, `--env-mode=loose`). No downloads.
