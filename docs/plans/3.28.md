# Plan: card 3.28 · Credit expiry runs as a scheduled job

Tier: **T2** (follows the existing scheduled-job pattern; credit ledger logic is unchanged) · Planned by: Opus 5.5 (lead) · Date: 2026-10-24 · Based on commit: `main 3cd1970`

## Session parts
One part, API only. Branch `s/3.28-credit-expiry-job`. Merge check by the lead.

## Goal
Purchased credits with an expiry date really expire. Today `ExpireCreditsUseCase` exists (card M.4) but nothing calls it: `registerCreditScheduledJobs` registers only `credit.cancelExpiredPurchases`. After this card an hourly job `credit.expireCredits` runs per organization where the credit module is effective, processes expiring purchases one batch at a time, and one bad row never stops the run.

- `apps/api/src/modules/commerce/credit/index.ts` (`registerCreditScheduledJobs`), `application/jobs/cancel-expired-purchases.job.ts` (the job shape to copy)

- Guide §11 items 8, 9, 10, 12, 13

## Decisions
1. **Job** `buildExpireCreditsJob` in `application/jobs/expire-credits.job.ts`: `jobKey: "credit.expireCredits"`, `everyMinutes: 60`, `moduleKey: MODULE_KEY.CREDIT`, `run: (organizationId) => expireCredits.execute({ organizationId: asId<OrganizationId>(organizationId) })`. Registered in `registerCreditScheduledJobs` next to the existing job. The job key literal follows the existing credit job (job keys are not in contracts today).
2. **Dependencies:** `registerCreditScheduledJobs` builds the `CreditDependencies` the use case needs with the same builders the tenant router uses (repository, unit of work, events, clock, time zone reader). If building them needs a request-only port, stop and ask. Narrow the use case's dependency type with `Pick<CreditDependencies, ...>` if that avoids a cast; no `as unknown as`.
3. **Batches, not one array (§11 item 9):** replace `listExpiringPurchases(today)` with a keyset page read `listExpiringPurchasesPage({ today, after, limit })` returning at most `limit` (100) rows sorted by the existing `occurredAt, creditEntryId` keyset of `readPurchasePages`. The use case loops page by page and passes the last row as `after`. Keep `readPurchasePages` for its other callers if any.
4. **Per-row catch (§11 item 8):** in the loop, a row that throws anything other than `CreditEntryAlreadyExistsError` is logged with `getLogger().error(...)` including `organizationId` and `creditEntryId` (no customer data), and the loop continues. The result gains `failedEntries: number`.
5. **Catch-up and idempotency (§11 item 10):** unchanged: the query is "expiresOn before today" and the EXPIRE partial unique index stops a second entry. Do not change the date semantics.
6. README of the credit module: one line for the new job. STATUS row 3.28. Handoff `docs/handoffs/3.28.md`.
