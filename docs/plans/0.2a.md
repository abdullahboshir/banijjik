## Goal
Every rule in AGENTS.md that can be checked by a machine is checked by ESLint, Prettier, or a git hook, and **each rule has a test that proves it fires**. After this card a violation such as `if (org.industryTemplateKey === "GYM")`, a deep cross-module import, `console.log`, a 70-line function or a staged `.env` file fails locally.

## Decisions
1. **ESLint 10 flat config** (`eslint.config.mjs`). If ESLint 10 breaks any required plugin, fall back to ESLint 9 and write the reason in the handoff. Do not drop a rule to make it work.
2. **Type-aware linting** through `typescript-eslint` `projectService` (needed for `no-floating-promises`). Lint targets are `packages/*/src/**` and `apps/*/src/**`.
3. **One root lint run** (`npm run lint` = `eslint .`), not per package. It must run in < 60 s on this repo size. Cache with `--cache` into `node_modules/.cache`.
4. **Module layout assumed by the boundary rules** (from `01 §2`): `**/modules/<group>/<module>/{domain,application,infrastructure,presentation}/**` and `**/modules/<group>/<module>/index.ts` as the module's public entry. Patterns are written with a leading `**/` so they match both real code (`apps/api/src/modules/...`) and the fixtures used by tests.
5. **Rules are tested with fixtures.** A vitest suite lints small fixture files with the real config and asserts the exact rule ids reported. A rule without a failing fixture and a passing fixture is not done.
6. **Architecture rules as ESLint config, not a custom plugin.** Use built-in rules (`no-restricted-imports`, `no-restricted-syntax`, `no-restricted-properties`, `id-denylist`) plus `eslint-plugin-boundaries`. Write a custom rule only if a required check cannot be expressed; then stop and ask.
7. **Allow-list for reading the industry key (ADR-033).** Only these paths may mention `industryTemplateKey` or compare a value named `industry*`: `**/modules/platform/industry/**`, `**/modules/platform/entitlement/**`, `**/modules/core/organization/infrastructure/**`, `packages/contracts/**`, `packages/validation/**`, and `**/*.test.ts`. (ADR-082)
8. **Vitest upgrade.** Move vitest to the latest stable major (5.x at planning time) to clear the dev-only `npm audit` findings from 0.1. If the 18 existing tests need more than trivial config changes, keep `^3` and record why.
9. **Root `package.json` fixes** (add-only otherwise): `packageManager` → the npm version actually in use (`npm@11.9.0`), `engines.node` → `>=22.12`, `typescript` → `~5.9.3` (typescript-eslint requires `<6.1`).
10. **Line endings:** `.gitattributes` with `* text=auto eol=lf` and binary patterns, then `git add --renormalize .` in a **separate commit** (`chore: normalize line endings`). Prettier `endOfLine: "lf"`.
11. **Hooks via husky 9.** `pre-commit` = lint-staged + `.env` commit block. `commit-msg` = commitlint (Conventional Commits). Hooks must work in the git worktrees we use (husky 9 handles this, verify). **Never** document `--no-verify`.
12. **Module template script (`scripts/new-module`) moves to card 1.6**, because `defineModule()` does not exist yet and a template that cannot typecheck is a placeholder. Update roadmap 0.2 text accordingly.
13. **Prettier settings:** `printWidth 100`, `singleQuote false`, `trailingComma "all"`, `semi true` (matches existing code).

## Fixtures and test harness
- `tools/lint-tests/fixtures/<rule>/{fail,pass}.ts` (or in the real nested path, e.g. `fixtures/apps/api/src/modules/core/demo/domain/entity.ts`) so path-scoped rules and boundaries see the right directory shape.
- `rules.test.ts` uses the `ESLint` class with the repo config, lints each fixture, and asserts: every `fail` fixture reports **exactly the expected rule id(s)** (listed in an expectations table in the test), every `pass` fixture reports **no** errors.
- Fixtures are excluded from the normal `eslint .` run (ignore `tools/lint-tests/fixtures/**` in the main config) but included by the test via an override that re-enables them.
- Boundaries fixtures need real files for import resolution: create the small file tree under `fixtures/` for these.

## Hook behaviour (tests in `block-env-commit.test.mjs`)
- Staged `apps/api/.env` → exit 1 with a clear message naming the file.
- Staged `apps/api/.env.example` → exit 0. Staged `docs/env-notes.md` → exit 0.
- Run against a temp git repo created in the test (never the real repo).

## Risks & checks
- **Rules that never fire** are the main risk: the fixture suite is the proof. Review focuses on it.
- **False positives on existing code:** `npm run lint` must be clean on the 4 packages (fix the code, not the rule; if a rule truly conflicts with correct code, stop and ask).
- **ESLint 10 compatibility:** if a plugin errors on startup, record the exact error before falling back to 9.
- **Windows:** the husky hooks must run under Git Bash. The owner's `core.autocrlf=true` plus the new `.gitattributes` must not leave every file "modified": run `git status` after renormalizing and paste the output.
- **Commands to run and paste in the handoff:** `npm install`, `npm run lint`, `npm run format:check`, `npm run typecheck`, `npm test`, `npm run build`, one deliberate violation commit attempt per hook (commit message `bad message` → rejected, staged `.env` → rejected), `git status --short`.

## Done when
- All rules R1–R22 have passing/failing fixtures in the suite and the suite is part of `npm test`.
- `npm run lint`, `format:check`, `typecheck`, `test`, `build` pass from a clean install.
- Both hooks reject bad input and accept good input (shown in the handoff).
- Roadmap/ADR/STATUS updated; handoff written.
