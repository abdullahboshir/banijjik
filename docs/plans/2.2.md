## Goal
`resolveOrgConfig` becomes complete for Phase 2: one result carries the organization's **terms**, its **client-visible settings** and its **effective custom fields**, next to the modules and kinds it already has (ADR-033).
- Tenants can override the template's terms within the allowed keys.
- Tenants can switch off OPTIONAL modules that allow it (`07 §3`: "− tenant-disabled optional modules").
- The admin menu shows the organization's terms in the user's language.

## Decisions
**Terms** (`core/settings` owns `TermOverride`, `09 §4.6`)

1. **`TermOverride`:** collection `term_overrides`, tenant DB, tenancy `ORGANIZATION`, versioned, audit fields.
   - Fields: `termOverrideId`, `termKey`, `locale` (`bn | en`), `text` (trimmed, 1 to 40 characters).
   - Unique `(organizationId, termKey, locale)`.
   - **Allowed keys** are the keys of the organization's template `configuration.terms`. A tenant renames what the template names; it cannot invent keys.
   - Read the template terms through **one new file** in `platform/industry`, `application/use-cases/read-industry-terms.use-case.ts`, plus one export line `buildIndustryTermsReader()` (the 2.3/2.4 pattern).

2. **Resolved terms:** `Record<termKey, LocalizedText>`. Each language is the override if one exists, otherwise the template's text. **Both languages are always present**, so the client picks its own and never falls back to a key.

3. **Endpoints** (`/api/v1/orgs/{organizationId}/terms`, the tenant pipeline):
   - **`GET /terms`**, permission `settings.setting.read`: every allowed key with `{ termKey, bn: { text, source: "INDUSTRY" | "ORGANIZATION", version? }, en: { … } }`, ordered by key. Bounded by the template, so a keyed read; say so in `14`.
   - **`PATCH /terms`**, new permission **`settings.term.update`** (organization-wide: add it to `ORGANIZATION_WIDE_PERMISSION_KEYS` and require ALL locations): a batch of `[{ termKey, locale, text | null, version? }]`, at most 50, all or nothing.
     - `null` deletes the override, so the text falls back to the template.
     - A key that is not allowed → 404 `errors.term_not_available`.
     - Versions behave as in 2.4: an existing override needs its version; a stale one → 409.
     - **No-op items** (deleting a missing override, or the same text as stored) are skipped, as 2.4's review fix does. A batch that changes something writes one tenant audit entry, one event `settings.term.changed` (new, add-only) and one `configVersion` bump. An all-no-op batch writes nothing.
   - Role grants for `settings.term.update` (add-only): OWNER and MANAGER only.

**Resolver integration** (`platform/entitlement`)

4. **`ResolvedOrgConfig`** gets real values instead of the empty placeholders:
   - `terms: Record<string, LocalizedText>` (decision 2). The domain type and the contract `ResolvedOrgConfigResponse.terms` change from `Record<string, string>` to this.
   - `settings: Record<settingKey, unknown>`: the **organization-level** resolved values (no location) of the settings with `isClientVisible: true` of the effective modules. Location-level values stay on `GET /settings?location=`.
   - `fields: Record<CustomFieldEntityType, EffectiveCustomField[]>`: the effective field list per entity type that the effective modules declare. Today no production module declares an entity, so it is `{}` in production and filled in tests with a probe entity.

5. **No cycle.** The settings resolver and the custom-field availability ask `OrgConfigReader` for the effective modules, and the resolver is what computes them. So the resolver must **pass the effective module set in**, never call back through `OrgConfigReader`. Three ports in `platform/entitlement` (`application/ports/`), adapted in `routes/organization-config-ports.ts` from the modules' public builders:
   - `OrgTermsSource { forOrganization(organizationId, templateKey): Promise<Record<string, LocalizedText>> }`
   - `OrgClientSettingsSource { resolve(organizationId, effectiveModules): Promise<Record<string, unknown>> }`
   - `OrgFieldsSource { forModules(organizationId, effectiveModules): Promise<Record<string, EffectiveCustomField[]>> }`

   Add the module-set-taking entry points to `core/settings` and `core/custom-field` (2.2 owns both in wave 2). Keep the existing `OrgConfigReader`-based paths for their own APIs. Each adapter runs inside the organization context the resolver already runs in.

6. **Caching stays correct without new rules.** The resolved config is cached per `(organizationId, configVersion, templateVersion, registryHash)`:
   - every term, setting and custom-field write bumps `configVersion` (2.3, 2.4, this card)
   - every template edit bumps `templateVersion` (2.1b)

   Write a test that proves each of the three changes shows on the next `/me/config`.
   - **Cost:** a cache miss now runs four more reads (term overrides, setting rows, definitions, preferences), each indexed, with no N+1. Measure one cold `/me/config` in a test log line, without asserting the time.

7. **`GET /me/config`** returns `terms`, `settings` (client-visible, organization level) and `fields` from the resolved config. Update `ResolvedOrgConfigResponse` and its transformer.

**Tenant module switches**

8. **`GET /orgs/{organizationId}/modules`**, permission `settings.setting.read`. For every CORE/OPTIONAL module the organization's package and template offer, it returns `{ moduleKey, moduleClass, isEffective, tenantCanDisable, isDisabledByTenant, requiredBy: ModuleKey[] }`. Paged, limit ≤ 100; bounded by the catalogue anyway.

9. **`POST /orgs/{organizationId}/modules/{moduleKey}/disable`** and **`…/enable`**, new permission **`settings.module.update`** (organization-wide: ALL locations; OWNER and MANAGER), body `{ reason }`.
   - Only a module whose manifest says `tenantCanDisable: true` (OPTIONAL by `10 §1`) may be disabled; anything else → 422 ruleKey `MODULE_NOT_TENANT_DISABLABLE`.
   - **Disabling a module that another effective module depends on** → 422 `MODULE_REQUIRED_BY` with `details.requiredBy`. A paid dependency is never dropped silently (`07 §3`).
   - Already in that state → 200, no write.
   - The write is a `TENANT_DISABLE` `ModuleOverride` (create on disable, delete on enable) through a new public builder of `platform/entitlement`, `buildTenantModuleSwitch()`, called from the `core/settings` route.
   - In one transaction: one tenant audit entry, `configVersion` bump, event `settings.module.toggled` (new).
   - **Why the route lives in `core/settings`:** the permission belongs to `settings` (the tenant's settings area), and `platform/entitlement` stays platform-facing.
   - Today no production module is OPTIONAL with `tenantCanDisable`, so tests use a probe manifest. Also extend the generated module-off suite with one case: a tenant-disabled probe is off everywhere (routes, menu).

**Admin**

10. **The menu uses the new terms shape.** `menu-groups.ts` and `organization-shell.tsx` read `terms[labelTermKey]?.[locale]`, falling back to the existing message key when absent. Update the unit tests to the new shape (list each changed assertion). No other admin change; the settings and terms screens are 2.7.

11. **Records:**

    - `09 §4.6` TermOverride fields, `14` rows (`/terms`, `/modules`, `/me/config` shape), the READMEs of the three modules, the 2.2 STATUS row.

## Tests (must exist and pass)
- [ ] **Terms happy path:**
  - an organization on SALON (DB fixture, or moved with 2.1b's change-template): `GET /terms` shows the template's texts
  - PATCH `contact.bn` → `/me/config` shows the override in `bn` and the template text in `en`
  - delete → back to the template
  - one audit entry, one event, one bump; an all-no-op batch writes nothing
- [ ] **Terms rules:** an unknown key → 404; text of 41 characters or empty → 400; a stale version → 409; a STAFF member → 403; a one-location MANAGER → 403 (organization-wide).
- [ ] **Resolver content:**
  - `/me/config.settings` has `organization.digitScript` (client-visible) and not a non-visible probe setting, and changes after a settings PATCH
  - `/me/config.fields.contact` lists a probe entity's effective fields and changes after a custom-field PATCH
  - after a template PATCH that adds a term, `/me/config.terms` shows it after the 30-second reader window
- [ ] **No cycle:** a unit test of the resolver with fakes proves the three sources receive the module set and that `OrgConfigReader` is never called during resolution.
- [ ] **Module switches:**
  - disable a probe OPTIONAL module → it disappears from `/me/config.modules` and its route answers 404 (the gate)
  - enable → back
  - disabling a non-disablable module → 422
  - disabling a module another effective module depends on → 422 with `requiredBy`
  - STAFF → 403; a one-location MANAGER → 403
  - the generated module-off case passes
- [ ] **Cross-org:** another organization's terms or modules are never read or changed.
- [ ] **Admin:** `menu-groups` unit tests with the `{ bn, en }` shape and a missing term (fallback); the admin browser suite stays green.
- [ ] Every existing suite green; list each changed assertion (the terms shape, `/me/config` expectations gaining `settings`/`fields` content). Full "Done means" list, both browser suites.

## Out of scope
- Settings, terms or field screens (2.7), the dynamic form (2.5), template builders (2.6).
- Plural forms of terms (Bangla mostly needs none; English plurals come with a later UX card).
- Location-level settings in `/me/config`.

## Risks & checks
- **The cycle (decision 5)** is the main trap. If any source needs `OrgConfigReader` during resolution, stop and ask.
- **Payload size of `/me/config`:** fields per entity are bounded (template fields + at most 50 per entity). Log the response size once in a test; stop and report if it passes 50 KB.
- **The lint scope:** only `platform/industry` and the resolver name `industryTemplateKey`. The terms adapter takes the key positionally.

## Done when
- `/me/config` carries real terms, client-visible settings and fields from one resolution, cached correctly.
- Tenants can override terms and switch off allowed OPTIONAL modules, audited and permission-checked.
- The admin menu shows terms in the user's language.
- The Opus review passes.
