# Plan: card 3.1c · Contact roles for custom fields (a related person, fields per role)

Tier: **T1** (changes the template schema and the shared value builder) · Planned by: Opus 5.5 (Claude) · Implemented by: a Claude Code session · Date: 2026-10-17 · Based on commit: `main 9ceb629` (3.0, 3.1a, 3.13 merged)

Start now; 3.1b starts after this card is merged. Read `docs/plans/phase-3-lanes.md` first. Reserved ADR number: **ADR-113**. Owner decision 2026-10-17: "industrial standard" (the CRM "record type" pattern: which fields a record shows and requires depends on its type).

## Goal
Today every template contact field applies to every contact. On COACHING, `class_level` and `guardian` are required, so:
- a guardian or a supplier added by hand must also have a class level and a guardian
- a guardian created through the contact link has those fields empty

After this card a field names the contact roles it belongs to. A guardian, an emergency contact or a relative becomes a contact of the new generic role **RELATED**, labelled by the business's term ("অভিভাবক", "জরুরি যোগাযোগ").

## Decisions
**Roles**
1. **`CONTACT_ROLE` gains `RELATED`**: a person known through another contact (guardian, parent, emergency contact, relative). It is industry-neutral, and its label comes from terms (decision 5).

**Fields per role**
2. **`appliesToContactRoles?: ContactRole[]`** (non-empty when present) on:
   - a template custom field
   - an organization custom field definition (2.3 request schemas, model, response)
   - `EffectiveCustomField`

   It is allowed only when `entityType === "contact"`; otherwise the write is 422 (template) or 400 (definition). **Absent means every role**, so existing fields keep working.

3. **The value builder** gains the option `contactRoles?: readonly ContactRole[]`:
   - A field with `appliesToContactRoles` takes part only when it shares at least one role with `contactRoles`.
   - A field that does not apply is treated like a field hidden from that audience: it is not required, and a value sent for it is refused at `customFields.<key>` (`validation.not_applicable`, a new message key).
   - Without the option, the builder behaves as today. Only the contact use cases pass it.

**Contact rules (`commerce/contact`)**
4. The contact rules:
   - **Create** validates custom fields with the roles of the request.
   - **Update** validates with the roles after the change. A required field that becomes applicable because a role was added is not forced on update, the same rule as a template change today. Values stored for a field that no longer applies stay stored and are not returned, the same as a hidden field.
   - **A contact's roles must be among the template's `contactRoleKeys`** (400 at `contactRoles`). Today any role is accepted; the template already names the allowed ones.
   - **The contact link** (`contact-links.ts`) creates the linked contact with role `RELATED`, not `CUSTOMER`. A template whose fields include a link must list `RELATED` in `contactRoleKeys` (template validation, 422 otherwise).
   - `GET /contacts?role=RELATED` lists guardians and similar contacts; no new endpoint.

5. **Labels of roles from terms:** a role is labelled by the term `contact.<ROLE>` when the template has one (the term key pattern `contact.RELATED` is already valid), else by the catalog message `contactRole.<ROLE>` (new keys for all four roles, bn and en). The admin screens of 3.1b and the field editors use this.

**Templates and seeds** (additive, ADR-101)
6. Template rules:
   - Adding `RELATED` to `contactRoleKeys` and adding `appliesToContactRoles` to a field are additive.
   - **Changing** `appliesToContactRoles` on a used or published template is allowed, like a label: no stored data is removed; values of fields that stop applying are kept and hidden.
   - Seeds:

     | Template | `contactRoleKeys` gains | Fields get `appliesToContactRoles` | Terms gain |
     |---|---|---|---|
     | COACHING | `RELATED`, `SUPPLIER` | `class_level`, `study_group`, `school_name`, `guardian` → `["CUSTOMER", "LEAD"]` | `contact.RELATED`: "অভিভাবক" / "Guardian" |
     | GYM | `RELATED`, `SUPPLIER` | every contact field → `["CUSTOMER", "LEAD"]` | `contact.RELATED`: "জরুরি যোগাযোগ" / "Emergency contact" |
     | CLINIC | `RELATED`, `SUPPLIER` | every contact field → `["CUSTOMER"]` | `contact.RELATED`: "আত্মীয়" / "Relative" |
     | SALON | `RELATED` | every contact field → `["CUSTOMER"]` | none |
     | RETAIL | none | `customer_type` → `["CUSTOMER"]` | none |
     | others | none | none | none |

     Seeds are data; `seed-industry-templates` applies them to the published rows through the existing additive path.

**Screens**
7. Screens touched in this card:
   - **Platform template field editor** (2.6): a role multi-select for contact fields, offering the template's `contactRoleKeys`.
   - **Admin organization field sheet** (2.7b): the same for contact fields.
   - Each shows "All roles" when nothing is chosen.
   - The contact form itself is 3.1b. `/me/config` `fields.contact` carries `appliesToContactRoles`, so 3.1b can show the fields of the selected roles.

**Records**
8. **ADR-113** ("Accepted (proposed)"):
   - the RELATED role
   - `appliesToContactRoles` and its builder option
   - roles limited to the template's list
   - linked contacts as RELATED
   - role labels from `contact.<ROLE>` terms

   Also `09 §5.1`, `12-INDUSTRY-TEMPLATES` (field and role rows), `14` (definition fields, `validation.not_applicable`), and the 3.1c STATUS row.

## Tests (must exist and pass)
- [ ] **Builder:**
  - a field limited to CUSTOMER is required for a CUSTOMER contact
  - it is not required for a RELATED contact, and a value sent for it there is refused with `validation.not_applicable`
  - a field without the property applies to every role
  - without the option, the builder is unchanged (existing tests stay green)
- [ ] **Contacts API** (COACHING):
  - a RELATED contact is created by hand without class level or guardian
  - a SUPPLIER likewise
  - a CUSTOMER still needs both
  - the link creates the guardian with role RELATED, and `?role=RELATED` lists it
  - a role outside the template's list → 400
  - update: adding CUSTOMER to a RELATED contact does not force the fields; values of a field that no longer applies are kept and not returned
- [ ] **Templates:**
  - `appliesToContactRoles` on a non-contact field → 422
  - a link field without RELATED in `contactRoleKeys` → 422
  - adding RELATED and the property to a published template is additive (200)
  - the seeds load and pass the schema
- [ ] **Definitions:** an organization contact field with `appliesToContactRoles` round-trips; on another entity it is 400.
- [ ] **`/me/config`:** `fields.contact` carries the property.
- [ ] **Screens:** the platform and admin field editors show and save the role choice (unit tests); the existing browser suites stay green.
- [ ] Permission, cross-org and module-off checks of the touched endpoints stay green.
- [ ] Every existing suite green; full "Done means" list.

- Stop and ask if a seed change conflicts with the additive rule as coded.
