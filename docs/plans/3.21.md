# Plan: card 3.21 · Organization currency in accounting and bookkeeping

Tier: T2 (money display and approval amounts) · Planned by: Opus 5.5 (lead) · Date: 2026-10-23 · Based on commit: `main b1cf16c`

## Session parts
One part, API only (no screen change), branch `s/3.21-accounting-currency`. Merge check by the lead.

## Goal
Accounting and bookkeeping answer in the organization's currency instead of a hardcoded `"BDT"`. The manual-journal approval amount carries the organization's currency.

Today an organization whose currency is not BDT can never post an approved manual journal: `consume` refuses the token on a currency mismatch (ADR-121).

## Inputs read
- `apps/api/src/modules/commerce/accounting/application/use-cases/`:
  - `get-trial-balance.use-case.ts`: falls back to `"BDT"` when there are no entries.
  - `balance-sheet.use-case.ts`, `profit-and-loss.use-case.ts`, `list-bookkeeping-accounts.use-case.ts`: `currency: "BDT"` on every money field.
  - `post-manual-entry.use-case.ts`: the approval `amount: { amount, currency: "BDT" }`.
- `apps/api/src/modules/commerce/bookkeeping/index.ts`: `BookkeepingTenantDependencies.currencies` already exists, wired in `apps/api/src/routes/bookkeeping-tenant-router.ts`.
- `apps/api/src/modules/commerce/accounting/index.ts`: `AccountingTenantDependencies` has no currency port yet; `routes/accounting-tenant-router.ts` builds it.
- `apps/api/src/modules/core/organization/index.ts`: `buildOrganizationCurrencyReader()`.

## Decisions
1. Each use case listed above gets a **required** port `currency: { read(organizationId: OrganizationId): Promise<CurrencyCode | undefined> }` and the `organizationId` from its caller.
   - Bookkeeping passes its existing `currencies`.
   - Accounting adds `currencies` to `AccountingTenantDependencies`, with the same shape. `routes/accounting-tenant-router.ts` wires `buildOrganizationCurrencyReader()`, the reader bookkeeping already uses.
   - The controllers pass the active organization id the same way the bookkeeping handlers already do for manual entries.
2. An organization without a currency is a data error: throw `AppError({ code: ERROR_CODE.INTERNAL })`. Never fall back to a literal.
3. The trial balance always uses the organization's currency, not the currency of the first entry. Every entry is already in the organization's currency, because ADR-128 validates journals against it.
4. The manual-journal approval amount uses the organization's currency, read in the same request: `amount: { amount, currency }`.
5. No `"BDT"` literal stays in `modules/commerce/accounting` or `modules/commerce/bookkeeping` outside tests.

## Amendment 1 (lead, 2026-10-23, after the implementer stopped on two conflicts)
The implementer was right to stop. The plan missed two facts:
- `CURRENCY_CODE` in `packages/contracts` is `["BDT"]` ("Taka only at launch").
- `POST /approvals` validates the amount against that enum.

A USD approval token therefore cannot exist through the API, and today no organization can hold a non-BDT currency. This card removes the hidden `"BDT"` assumptions so that adding a currency later is a contracts change only. It does **not** add a currency.

**A1. Approval amount test moves to the use-case level.**
- Do **not** change `CURRENCY_CODE`, `moneySchema` or the organization schema. Adding a currency is a product decision with its own ADR, outside this card.
- Delete the uncommitted HTTP "USD approval token" test.
- Add a unit test of the exported `consumeJournalApproval` in `accounting/application/use-cases/post-manual-entry.use-case.ts`, with fakes for `approvals.consume`, `currencies.read` and `policy.ownerMaySkip` (returns false):
  - `consumes the approval with the amount in the organization's currency`: the fake reader returns a non-BDT code and `consume` receives `amount: { amount, currency }` with that code. The value needs a cast, because the type allows only BDT. Put one line above it: `// CURRENCY_CODE is BDT-only at launch; a second code proves the amount is not a literal.`
  - `refuses with INTERNAL when the organization has no currency`: the reader returns `undefined`, the call throws `ERROR_CODE.INTERNAL`, and `consume` is never called.
- The HTTP tests on the raw USD organization (trial balance, profit and loss, balance sheet, account list) stay as written. Those GET endpoints do not validate the currency.

**A2. Two more files are in scope (they hold the last `"BDT"` literals, decision 5):**
- `accounting/domain/journal-entry.entity.ts`: delete `debitTotal()` and `creditTotal()`. Nothing calls them (`git grep` in `apps`), and their `?? "BDT"` fallback is exactly what decision 2 forbids.
- `accounting/infrastructure/mongo-journal.repository.ts`: change both `as "BDT"` casts to `as Money["currency"]`, with `Money` imported as a type from `@banijjik/contracts/accounting`. Add one line above: `// Stored as a plain string; journals are validated against the organization currency on write (ADR-128).`

**A3. The small deviations reported so far are accepted:**
- the shared `accounting/application/organization-currency.ts` helper
- the dependencies object for `ListBookkeepingAccountsUseCase` (lint: at most 3 constructor parameters)
- the new `GetTrialBalanceUseCase` signature in `posting-engine.test.ts`
- the `approvalFor` helper with a `"BDT"` default

List them under "Deviations" in the handoff, with "approved by the lead, Amendment 1".
