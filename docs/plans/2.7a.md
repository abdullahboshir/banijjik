# Plan: card 2.7a · Custom field values on the business profile and on staff

Tier: **T1** (the first entities that store custom field values; sensitive data) · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor · Date: 2026-10-15 · Based on commit: `main 52bf49e`

**Wave 3 of Phase 2, session 2, in parallel with 2.6. Card 2.7b follows in the same session after this card merges.** Read `docs/plans/phase-2-lanes.md` (the wave-3 section) and `docs/ops/implement-with-cursor.md` first. Reserved ADR number: **ADR-107**.

## Goal
The design already gives the business profile and staff members custom fields:
- `09 §4.2`: `Organization.customFields`, entity type `organization`
- `09 §4.4`: `Member.customFields`, the staff profile (NID, blood group, emergency contact), ADR-046
- `10 §5`: the organization manifest declares `organization` and `member`

No entity stores values yet. After this card:
- an owner fills the business's and each staff member's extra details in the admin app, with the template's and their own fields
- values are validated by the server with 2.3's builder
- sensitive values reach only those allowed to see them

This makes the Phase 2 done-criterion true: "its tenants see the right … forms with server-side validation".

## Decisions
**Declaring and storing**
1. The `organization` manifest sets `customFieldEntities: ["organization", "member"]` (`10 §5`). The custom-field engine then offers both entity types to every organization, because `organization` is a SYSTEM module.

2. **Storage:**
   - `Organization` and `Member` get `customFields` (a map, default `{}`) and `customFieldSearch` (`[{ fieldKey, value }]`, the attribute pattern of ADR-102).
   - Add index `{ organizationId: 1, "customFieldSearch.fieldKey": 1, "customFieldSearch.value": 1 }` on `members`. Organizations are one row per tenant and need none.
   - No migration: existing rows read as `{}`.

**Writing**
3. **`PATCH /orgs/{organizationId}/profile`** accepts an optional `customFields` object.
   - The use case loads the effective fields for `organization` (`EffectiveCustomFieldReader`, through an organization port adapted in routes) and validates with `buildCustomFieldValuesSchema(fields, { audience: "ADMIN", mode: "UPDATE" })`.
   - **Merge:** an absent key leaves the stored value; `null` removes it; required fields cannot be nulled (2.3's rules).
   - `customFieldSearch` is recomputed with `toSearchEntries`.
   - The request schema in `packages/validation` accepts `customFields` as an object of unknown values. The real check is the use case's, against the organization's fields, so a 400 points at `customFields.<key>`.

4. **`PATCH /orgs/{organizationId}/members/{memberId}`** accepts `customFields` the same way, for entity type `member`.
   - The existing reach rules (ADR-095) and anti-escalation (ADR-092) are unchanged.
   - Editing only custom fields needs `organization.member.update`, as any member edit does.

5. **Audit:**
   - Every changed key is one audit change, `customFields.<key>: { from, to }`.
   - **A sensitive field's values are never written to the audit log:** use the constant `REDACTED_AUDIT_VALUE = "[redacted]"` (contracts) for both sides. The fact of the change stays visible.

**Reading**
6. Who sees values:

   | Endpoint | Custom field values |
   |---|---|
   | `GET /profile` | all values; sensitive ones only for callers holding `organization.profile.update` at ALL locations, redacted (`redactSensitive`) for everyone else |
   | `GET /members/{memberId}` | all values; sensitive ones only for callers holding `organization.member.readSensitive` (the existing key), redacted otherwise |
   | the member **list** | none (lean rows) |
   | `GET /me/orgs` (my businesses) | none |

   Archived definitions' values stay stored but are not returned (the effective list decides what is shown).

**Admin app**
7. **The business profile page** gets an "Additional details" section. It renders the 2.5 block with `/me/config.fields.organization`, through `toFieldDescriptors`, `validateCustomFieldValues` and `toRequestValues`, inside the existing profile form sheet and save flow. Pending types (FILE, IMAGE, REFERENCE) show 2.5's "not editable here" line.

8. **The member detail page:**
   - shows the member's extra details (read-only list)
   - an "Edit details" sheet with the same block for `fields.member`
   - redacted sensitive values show "Hidden"; the user cannot overwrite a value they cannot see: the sheet leaves redacted fields out of the request
   - the button appears only with `organization.member.update` for that member's reach

9. **Sizes:** the profile and member-detail routes stay **≤ 170 KiB**, so load the block in the lazy sheets. Report the before and after sizes.

10. **Records:**
    - ADR-107 ("Accepted (proposed)"). It records:
      - organization and member store custom fields
      - sensitive redaction by `organization.profile.update` at ALL locations and by `organization.member.readSensitive`
      - redacted audit values
      - the members search index
    - `14 §5.1` (profile and member bodies), `09` if a field note changes, the module README, the 2.7a STATUS row.

## Tests (must exist and pass)
- [ ] **API, profile:**
  - an organization on GYM-like fields (set up with a template fixture; GYM is DRAFT, so move a RETAIL organization onto it with 2.1b's change-template, or edit the RETAIL fixture template) saves an organization field
  - `null` clears an optional field and is refused for a required one (400 at `customFields.<key>`)
  - an unknown key → 400
  - a SELECT outside its options → 400
  - the audit change shows the value, and `[redacted]` for a sensitive field
- [ ] **API, member:**
  - an OWNER saves `emergency_contact` (PHONE, normalized to E.164) and `medical_notes` (sensitive) on a member
  - a MANAGER without `readSensitive` reads the member with `medical_notes` redacted
  - a one-location MANAGER cannot edit a member outside their reach (404, as today)
  - another organization's member → 404
- [ ] **API, list:** the member list returns no `customFields`.
- [ ] **Admin unit tests:** the profile section and the member edit sheet send only changed, visible and non-redacted fields; a validation error shows at the field.
- [ ] **Admin browser:** an owner opens the profile, fills an organization field, saves, reloads and sees it; opens a staff member, fills a member field, saves, sees it. Use the existing `industry-fixture.json` or extend it with one organization field and one member field.
- [ ] Route sizes ≤ 170 KiB for profile and member detail, before and after reported.
- [ ] Every existing suite green; list changed assertions (profile and member response shapes). Full "Done means" list.

## Out of scope
- Location custom fields (not declared in `10`), contacts and every Phase 3 entity, search by custom field in the member list, FILE and IMAGE upload, the settings, terms, fields and modules screens (2.7b).

## Risks & checks
- **Sensitive data:** test every read path. A value must never leak through the list, `/me/orgs`, the audit log, or an error message.
- **Do not let a redacted placeholder be saved back as the value.**
- Stop and ask if the profile form's current save flow cannot carry `customFields` without a new endpoint.

## Done when
- Business and staff extra details are stored, validated by the server, edited in the admin app, and sensitive values are protected on every read and in the audit log.
- The Opus review passes.
