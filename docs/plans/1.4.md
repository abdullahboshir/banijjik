# Plan: card 1.4 · RBAC and permission cache

Tier: **T1** · Planned by: Opus 5.5 · Date: 2026-10-10 · Based on commit: `main 20be8c1`

## Goal
Every tenant action is checked against the caller's permissions in the API:
- Permission keys live in contracts and in the module manifests.
- The six system roles get their grants from a code template (`10 §10`).
- Organizations can create custom roles.
- Each route declares its `permission(key)`.

The check is **location-aware**: a member may hold a permission at some locations only. The middleware therefore narrows the request's `allowedLocationIds` to exactly the locations where that permission is granted, and the location plugin (1.3) then enforces it on data. Resolved permissions are cached, keyed by versions, so a cache hit is fast (p95 < 5 ms) and never stale.

## Decisions
**Permission catalogue**
1. Contracts `PERMISSION_KEY` holds the keys of the modules that exist (`10 §7`):
   - `iam.role.{read,create,update,archive}`
   - `organization.profile.update`
   - `organization.location.{read,create,update,archive}`
   - `organization.member.{read,invite,update,remove}`
   - `organization.member.readSensitive`
   - `organization.ownership.transfer`

   Each later module card adds its own keys, add-only. Also add contracts type `PermissionDefinition { permissionKey, labelKey, isSensitive?, surface }`, `SURFACE` enum (`10 §2`), and `PERMISSION_KEY_PATTERN` (`<moduleKey>.<entity>.<action>`, ADR-054).
2. The iam and organization manifests fill `permissions` with those keys. `labelKey` = `permission.<key>`, both catalogs get the labels, and `isSensitive` is set for the `*` keys of `10 §7`.
3. **`PermissionCatalog`** (iam application) is built at startup from the manifests that `routes/v1.ts` passes in (`[iamManifest, organizationManifest]`; 1.6 replaces the list with the registry).
   - It checks that every key is in `PERMISSION_KEY`, matches the pattern, starts with its manifest's module key, and is unique. Anything else throws at startup.
   - It exposes `all()`, `has(key)`, `ofModule(moduleKey)` and a `catalogHash` (sha-256 of the sorted keys plus the grant table of decision 4).

**System role grants (code template, ADR-054)**
4. `iam/domain/system-role-grants.ts`: one row per module, exactly `10 §10` for the modules that exist. Later module cards add their row (add-only hot file).
   - Grant spec: `"ALL" | "READ" | "NONE" | { only: PermissionKey[] } | { allExcept: PermissionKey[] }`. `"READ"` means the module's keys whose action is `read`.
   - Rows:
     - **organization:** OWNER ALL · MANAGER `allExcept [ownership.transfer, member.readSensitive]` · CASHIER/STAFF/RIDER NONE · VIEWER `only [organization.location.read]`
     - **iam:** OWNER ALL · MANAGER READ · others NONE
   - **"VIEWER R (profile)":** reading the org profile needs no permission. Every active member may read their own organization's profile. This is the only key-less read; write it in the iam README.
   - **OWNER** always has every key of the catalogue, including modules added later (computed, never stored).
   - System roles keep `permissionKeys: []` in the DB (1.2). Their effective keys always come from this template, so a release that changes the template applies to every org without a migration.

**Custom roles**
5. The Role entity gains `status: ACTIVE | ARCHIVED` (contracts `ROLE_STATUS`) and `version` (already there).
   - Custom role: `roleKey` = `custom.<roleId>` (stable, unique, never shown), `name` (2–60 chars, unique among ACTIVE roles of the org), `permissionKeys` (each must exist in the catalogue; platform keys are impossible because the catalogue has none).
   - System roles cannot be changed or archived → `422 BUSINESS_RULE` `details.ruleKey = "SYSTEM_ROLE_IMMUTABLE"`.
   - Archiving is refused while any ACTIVE member has an assignment with the role → `422 BUSINESS_RULE` `ROLE_IN_USE`.
   - Deviation note: `09 §4.5` says "custom: org-chosen" key. The org chooses the **name**; the key is generated so a rename never breaks references. Record this in the handoff and update `09 §4.5` in one line.
6. **Endpoints** (tenant router, mounted through `tenantRouters`; `14 §5.1`):
   | Method & path | Permission | Behaviour |
   |---|---|---|
   | `GET /orgs/{organizationId}/roles` | `iam.role.read` | `?page&limit` (≤ 100), `RoleSummary { roleId, roleKey, name \| nameKey, isSystem, status, permissionKeys (effective), memberCount }`, sorted system first then name. `memberCount` comes from one aggregate on members (no N+1). |
   | `POST /orgs/{organizationId}/roles` | `iam.role.create` | `RoleCreateRequest { name, permissionKeys }` → `201 RoleResponse` |
   | `PATCH /orgs/{organizationId}/roles/{roleId}` | `iam.role.update` | `{ name?, permissionKeys?, version }` → `RoleResponse`; stale → 409 |
   | `POST /orgs/{organizationId}/roles/{roleId}/archive` | `iam.role.archive` | `{ version }` → `RoleResponse` |

   An unknown `roleId` or one of another org → 404 (the tenant plugin makes it invisible).

**Resolution and the location-aware check**
7. The rule (`09 §4.4`): permissions at location L = union of the roles assigned at L and at ALL.
   - `PermissionResolver.resolve(member)` returns a **grant map** `{ allLocations: Set<PermissionKey>, byLocation: Map<LocationId, Set<PermissionKey>> }`.
   - `locationsWith(key)` returns `"ALL"` when the key is in `allLocations`, otherwise the list of locations whose set contains it (possibly empty).
   - Archived roles grant nothing.
8. **Kernel port and middleware** (`kernel/access/`):
   - Port `PermissionGate { locationsWith(permissionKey: string): Promise<readonly string[] | "ALL"> }` reads the context (`organizationId`, `memberId`, `accessVersion`).
   - Factory `createPermissionMiddleware(gate): (permissionKey: PermissionKey) => RequestHandler`, built **once** in `routes/v1.ts` and passed to module router builders as `permission`.
   - The handler:
     - empty result → `403 FORBIDDEN` (`errors.forbidden`)
     - otherwise it continues in a context whose `allowedLocationIds` is the **intersection** of the current `allowedLocationIds` and the permission's locations
     - an intersection that ends up empty → 403
   - When the request names `?location=` (validated by `locationAccess`) and that location is not in the narrowed set → 403.
   - Why: a member who is CASHIER at L1 and VIEWER at L2 may create sales at L1 only. Narrowing the context means the location plugin refuses an L2 write without any per-route code. Record this in **ADR-088**.
9. iam implements `PermissionGate` (`application/permission-gate.ts`) over the resolver and the cache. `index.ts` exports `buildPermissionGate({ catalog })`.
   - On a cache miss it reads the member (in the org context, so the tenant plugin applies) and the roles of its assignments (one `$in` query), then resolves.

**Cache (owner decision: port now, Redis adapter in 1.5)**
10. Port `PermissionCache { get(key): Promise<GrantMap | undefined>; set(key, value): Promise<void> }`. Adapter `InMemoryPermissionCache`: a bounded LRU (10 000 entries) with a 10-minute TTL, no new dependency (a `Map` with insertion-order eviction).
11. **Key** = `perm:{organizationId}:{memberId}:{accessVersion}:{catalogHash}`. `accessVersion` = `{memberVersion}.{rolesVersion}`. Both are read **fresh** on every request by `tenantContext`, which already loads the member and the org (1.3): extend `ActiveMembership` with `memberVersion` and `rolesVersion`, and put `accessVersion` into the request context.
    - `Organization` gains `rolesVersion` (integer, default 1). Every custom role create/update/archive increments it in the same transaction.
    - Any member change already increments `member.version` (assignment edits arrive with the member endpoints).

    Because the key holds versions read from the DB on every request, a per-instance in-memory cache is **never stale**, on one instance or many. Redis (1.5) only adds sharing between instances. A release that changes grants changes `catalogHash`.
12. **No membership cache.** `tenantContext` still does its two indexed reads; caching them needs invalidation on suspend/remove and is left to the Redis work (note in STATUS).

**Wiring**
13. `routes/v1.ts`: build the catalog from the manifests, then the gate and `permission`, then `tenantRouters: [buildIamTenantRouter({ permission })]`. Pipeline order stays `authenticate → tenantContext → locationAccess → (entitlement, 1.6) → route-level permission → validate → controller` (`01 §3`).
14. **Message keys:** `errors.forbidden` (already in `KERNEL_ERROR_MESSAGE_KEYS` through `ERROR_CODE.FORBIDDEN`), the role rule keys, and `permission.*` labels and `role.*` names (both catalogs; i18n key test extended).

## Tests (must exist and pass)
Unit:
- [ ] catalogue validation (unknown key, wrong module prefix, duplicate, bad pattern → throw)
- [ ] the grant template evaluates to exactly `10 §10` for organization and iam, per role (table-driven); OWNER gets a key of a fake extra manifest automatically
- [ ] grant map: union of L and ALL; archived role grants nothing; `locationsWith` returns ALL, a list, or empty
- [ ] LRU eviction and TTL (fake clock)

API (two-organizations helper extended):
- [ ] **happy path:** the owner lists roles (6 system, effective keys shown), creates a custom role, updates it, archives it
- [ ] **permission denied:** a STAFF member → `403 FORBIDDEN` on `GET/POST /roles`; a MANAGER can read but not create (`iam` row: MANAGER READ)
- [ ] **validation error:** unknown permission key, empty name → 400
- [ ] system role update or archive → `422 SYSTEM_ROLE_IMMUTABLE`; archiving a role in use → `422 ROLE_IN_USE`; stale version → 409
- [ ] **cross-org denied:** org B's `roleId` in org A's path → 404
- [ ] **location-aware:** a member with a custom role holding `iam.role.read` only at A-L1 and nothing at ALL: a probe route guarded by `permission("iam.role.read")` sees `allowedLocationIds = [A-L1]`; with `?location={A-L2}` → 403; a location-scoped probe write at A-L2 after the permission check → `403 LOCATION_FORBIDDEN`
- [ ] **invalidation:** after removing a key from a custom role, the very next request of a member holding it is denied (rolesVersion bump); after changing a member's assignments (through the repository in the test) the next request reflects it (member version)
- [ ] **cache:** the second identical check does no role query (repository spy). Benchmark: 1 000 cache-hit checks, report p50/p95, p95 < 5 ms.
- [ ] existing suites stay green (1.1–1.3), including the isolation suite

All with `--force`: lint, format:check, typecheck, test, build; `npm run test:tools`.

## Risks & checks
- **Context narrowing must not widen:** always intersect, never replace. A test checks that narrowing on top of an `["L1"]` context can never produce L2.
- **Benchmark noise on Windows:** run the benchmark 3 times and report all three.
- **Disk:** the system MongoDB binary as before (`MONGOMS_SYSTEM_BINARY`, `MONGOMS_VERSION_CHECK=false`, `--env-mode=loose`).
