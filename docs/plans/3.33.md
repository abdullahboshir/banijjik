## Goal
An event session that names resources (a hall, a room) occupies them for its whole time window. After this card a rental or service booking can no longer take a resource that a scheduled session uses, a session cannot be created or moved onto a resource that is already booked, in time-off, or used by another session, and cancelling or moving a session frees its old window. Availability screens show the session's window as taken without any change to availability code, because the session writes the same `resource_slot_usages` counters that bookings read.

## Decisions
1. **Same counters as bookings.** A session occupies a resource by writing the existing 5-minute `resource_slot_usages` buckets over `startsAt..endsAt`. Not time-off (a read, so it races) and not `ResourceExclusiveHold` (date-based, enrollment-owned). One store means one atomic check for every kind of use, and availability and `reserveResourceForSlot` already read it.
2. **A session takes the whole resource.** For each resource the session writes `used = resource.capacity` into every bucket, and only into buckets where `used` is 0 (conditional upsert). Any existing booking, rental or other session in any bucket refuses the session. A hall used for an event is not shared.
3. **The units taken are stored on the session.** New field `resourceHolds: { resourceId, units }[]` (embedded, `_id: false`), with `units` = the resource's capacity at take time. Release subtracts exactly the stored units, so a later change of the resource's capacity cannot leave a counter stuck or free too much. `resourceIds` keeps its meaning (the resources the session uses); `resourceHolds` records what is held now.
4. **Legacy sessions hold nothing.** Sessions created before this card have `resourceHolds: []` (schema default). They release nothing on cancel, so a rental's counter is never decremented by mistake. No backfill: the project has no production data yet. A time change of a legacy session takes holds for its `resourceIds` like a new session (decision 6).
5. **Create** runs in one transaction through `runWithTxnRetry(unitOfWork, …)`: check resources (exist, at the session's location, as today), check time-off, take the holds in sorted `resourceId` order, insert the session with its `resourceHolds`. Any failure rolls everything back: no session row, no counter.
6. **Time change** (allowed only while `seatsSold` is 0, as today) runs in one transaction: versioned session update first (stale version → 409 before any counter is touched), then release the stored holds, then take holds for the new window (time-off checked again, current resource capacity), and write the new `resourceHolds` in the same update. A busy new window refuses the change and rolls back; the old holds stay. A capacity-only update touches no counter and does not need the retry wrapper.
7. **Cancel** releases the stored holds and sets `resourceHolds: []` in the same transaction as the versioned status write (the existing unit of work).
8. **Complete** (the auto-complete job, after `endsAt`) releases nothing. The buckets are in the past, nobody can book them, and keeping them avoids extra writes in a job. `resourceHolds` stays as the record of what was used.
9. **Time-off is a refusal.** A session whose window overlaps a time-off row of one of its resources is refused, the same way `reserveResourceForSlot` refuses a booking. The weekly schedule is not checked (staff plan events outside opening hours on purpose, the same as rentals).
10. **Errors.** A busy resource (counter taken or time-off) answers `409 SLOT_UNAVAILABLE` with `details.ruleKey = EVENT_SESSION_RESOURCE_BUSY` and `details.resourceId`. Retry exhaustion on a transient conflict maps to the same error (third argument of `runWithTxnRetry`; `resourceId` omitted there).
11. **Bounds.** `resourceIds` in the create body: at most 10, no duplicates (validation, 400). A session that names at least one resource may last at most 31 days (`MAX_EVENT_SESSION_RESOURCE_DAYS = MAX_RENTAL_DAYS`, so one session writes at most the same number of buckets as the longest rental); longer → `422 EVENT_SESSION_RESOURCE_SPAN_TOO_LONG`, checked in the entity on create and on time change. A session without resources keeps no length limit.
12. **Release is lenient, as for bookings.** The release filter is `used >= units` with `$inc: -units`; a bucket that does not match is skipped, the same as `releaseCapacity`. A throw there would leave a session that can never be cancelled (§11 item 11).
13. **Out of the card:** an enrollment bed hold (`ResourceExclusiveHold`) is still not seen by bookings or sessions, and a time-off created later does not check existing sessions or bookings. Both go into the STATUS note as follow-ups; this card does not change them.
14. **Records:** ADR-141 "Accepted (proposed)" (decisions 1–4, 8, 11); `docs/11 §5.5` "Implemented" note: replace the "Known gap" sentence; booking `README.md`; STATUS row 3.33; handoff with the §11 table.

`takeWholeResource` per bucket (`bucketStartsCovering(startsAt, blockedEndsAt)`, the session's `endsAt` is its `blockedEndsAt`):
```ts
findOneAndUpdate(
  { organizationId, resourceId, bucketStart, used: 0 },
  { $inc: { used: units }, $setOnInsert: { resourceSlotUsageId: newId() } },
  { upsert: true, returnDocument: "after", ...sessionOption(getActiveSession()) },

// null result, or duplicate key 11000 (bucket exists with used > 0) → eventSessionResourceBusyError(resourceId)
```
`releaseWholeResource` per bucket: `updateOne({ organizationId, resourceId, bucketStart, used: { $gte: units } }, { $inc: { used: -units } }, session)`. Both methods require an active transaction: call the existing `transactionOptions()` pattern (throw `INTERNAL` without one), as `mongo-resource-exclusive-holds.ts` does.

## Risks & checks
- A long session writes many buckets in one transaction (≤ 8,928 per resource, the same bound as a rental). Keep the per-bucket loop; do not batch with `bulkWrite` (each bucket's condition must refuse on its own).
- Releasing without a stored hold would free a rental's capacity: release only from `resourceHolds` (A12).
- Moving: the versioned update must run first inside the transaction so a stale request never touches counters (A9).
- Verify: `npx vitest run --config src/test-support/vitest.config.ts src/modules/commerce/booking` in `apps/api`, then the full `card:check`.
