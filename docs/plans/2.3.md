# Plan: card 2.3 · Custom field engine (API)

Tier: **T1** (every later entity validates through it) · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor · Date: 2026-10-14 · Based on commit: `main 8291363`

**Wave 1 of Phase 2, in parallel with 2.1b and 2.4.** Read `docs/plans/phase-2-lanes.md` and `docs/ops/implement-with-cursor.md` first. Reserved ADR number: **ADR-102**.

## Goal
Custom fields become one generic engine that every later module uses: contacts, offerings, orders, bookings, enrollments, members. After this card:
- An organization sees the **effective field list** for an entity: its template's INDUSTRY fields plus its own ORGANIZATION fields, with its hide, label and order preferences.
- It can define its own fields.
- **One shared Zod builder** in `@banijjik/validation` validates `customFields` values on the server and, later (2.5), in the browser.

No entity stores values yet. The first consumers are cards 3.1 onward; this card proves the engine with tests and a probe entity.

## Decisions
**Module and entities**
1. **New module `core/custom-field`** (SYSTEM; the key exists).
   - Manifest:
     - permissions `custom-field.definition.{read,create,update,archive}` (add the four to `PERMISSION_KEY`, add-only)
     - admin routes `/orgs/:organizationId/custom-fields`
     - emits `custom-field.definition.changed` (new event type, add-only)
     - `customFieldEntities: []`
   - **Role grants** (add-only row in `system-role-grants.ts`): OWNER ALL, MANAGER ALL, CASHIER READ, STAFF READ, VIEWER READ, RIDER NONE. Staff screens must render forms, so they need to read definitions.

2. **Entity types are a contracts enum**, `CUSTOM_FIELD_ENTITY_TYPE`: `organization`, `location`, `member`, `contact`, `offering`, `category`, `order`, `booking`, `enrollment`, `resource`, `expense`.
   - A manifest still lists its entities as strings. **Do not edit `module-manifest.ts`**: 2.4 owns it in this wave.
   - At startup the engine checks that every manifest entity is in the enum, and refuses to start otherwise.
   - An entity is **available** to an organization when a module in its resolved `modules` declares it. Read the modules through the existing kernel `OrgConfigReader`.
   - Today no production module declares an entity, so tests use a probe manifest that declares `contact`. Phase 3 cards add their entities to their own manifests.

**Definitions**
3. **INDUSTRY definitions are not copied.** They are read from the organization's template configuration (ADR-076: templates are materialized, one source of truth).
   - Add exactly **one new file** in `platform/industry`: `application/use-cases/read-industry-custom-fields.use-case.ts`. It returns a template's `configuration.customFields` by key.
   - Add one export line in `platform/industry/index.ts`: `buildIndustryCustomFieldReader()`.
   - Nothing else in `platform/industry` changes (2.1b owns it).

4. **Labels for INDUSTRY fields.** The seed entries have no labels today.
   - Add optional `label: LocalizedText` and optional `optionLabels: Record<optionKey, LocalizedText>` to the seed `customFieldSchema` in `industry-template-schemas.ts`. This is the only change allowed to that file.
   - Fill both for **every field of the eight seed JSON files**, Bangla first and natural, with English. Only add keys; change nothing else in the seeds.
   - The engine falls back to the field key when a label is missing, for templates made later without one.
   - Seeds are inserted only when missing (2.1a), so existing databases keep the old rows until 2.1b's PATCH or a re-seed. Write that in the handoff.

5. **ORGANIZATION definitions:** collection `custom_field_definitions`, tenant DB, tenancy `ORGANIZATION`, versioned, audit fields.

   | Field | Notes |
   |---|---|
   | `customFieldDefinitionId` | UUID v7 |
   | `entityType` | |
   | `offeringKind?` | only for `offering` |
   | `fieldKey` | immutable |
   | `label: LocalizedText` | |
   | `fieldType` | immutable |
   | `isRequired` | |
   | `options[]`, `optionLabels?` | options can be added; existing keys are never removed |
   | `validation? { min?, max?, maxLength? }` | **no regex patterns**: a user-made regex is a ReDoS risk |
   | `referenceEntity?` | |
   | `visibility { admin, storefront, bot }` | |
   | `botAsk`, `isSearchable`, `isSensitive` | |
   | `sortOrder` | |
   | `status` | `ACTIVE \| ARCHIVED` |

   Rules:
   - **Unique key:** `(organizationId, entityType, offeringKind ?? null, fieldKey)` must be unique among the organization's definitions. It must also not equal an INDUSTRY field of the organization's template → `409 CONFLICT` `errors.custom_field_key_taken`. Check in the use case, and back it with a unique index.
   - **Limit:** at most **50 ACTIVE ORGANIZATION definitions per entity type** (named constant) → 422 ruleKey `CUSTOM_FIELD_LIMIT`.
   - **Archive, never delete.** An archived field disappears from forms; its values stay on the documents.
   - **Contact-link fields (ADR-073):** only the metadata is validated here. The create-or-link behaviour belongs to card 3.1.

6. **Preferences on INDUSTRY fields:** collection `custom_field_preferences`, tenant DB, tenancy `ORGANIZATION`. One row per `(organizationId, entityType, offeringKind ?? null, fieldKey)`: `isHidden`, `label?`, `sortOrder?`, `version`.
   - `isHidden` is allowed only for a field that is **not required**. Hiding a required field → 422 ruleKey `CUSTOM_FIELD_REQUIRED`.
   - Tenants never edit an INDUSTRY definition itself (`09 §4.6`).

7. **Effective list:** `EffectiveCustomFieldReader.forEntity(organizationId, entityType, offeringKind?)` returns the INDUSTRY fields with preferences applied, then the ACTIVE ORGANIZATION fields, sorted by `sortOrder` and then key.
   - Each item has `scope`, `isEditable` (false for INDUSTRY), and the effective label and visibility.
   - Export the builder from `core/custom-field/index.ts`. Phase 3 modules import it through the index.

**Endpoints** (`/api/v1/orgs/{organizationId}/custom-fields`, the tenant pipeline)

8. The endpoints:

   | Endpoint | Permission | Notes |
   |---|---|---|
   | `GET /custom-fields?entityType=&offeringKind=&page=&limit=` | `custom-field.definition.read` | paged (limit ≤ 100); an unavailable entity type → 404 (the module gate's answer for something not offered) |
   | `POST /custom-fields` | `custom-field.definition.create` | |
   | `PATCH /custom-fields/{customFieldDefinitionId}` | `custom-field.definition.update` | with `version`: label, required, options (add), option labels, validation, visibility, `botAsk`, searchable, sensitive, sort order |
   | `POST /custom-fields/{customFieldDefinitionId}/archive` | `custom-field.definition.archive` | with `version` |
   | `PATCH /custom-fields/preferences` | `custom-field.definition.update` | batch of `{ entityType, offeringKind?, fieldKey, isHidden?, label?, sortOrder?, version? }`, at most 100 |

   - **Writes need the permission at ALL locations** (`requireAllLocations()`): fields are organization-wide.
   - **Every write** writes one tenant audit entry, emits `custom-field.definition.changed`, and bumps the organization's `configVersion`, so 2.2's resolved `fields` refresh. Use the existing `buildConfigVersionBumper()` of `core/organization` via `routes/v1.ts`.
   - Writes do not need `Idempotency-Key`: they create no money or stock.

**The shared value builder**
9. **`packages/validation/src/custom-field/`**: `buildCustomFieldValuesSchema(fields: CustomFieldRule[], options: { audience: "ADMIN" | "STOREFRONT" | "BOT"; mode: "CREATE" | "UPDATE" })`. `CustomFieldRule` is the minimal shape both scopes map to.
   - **Strict object** over the fields visible to the audience. An unknown key, or a key not visible to that audience, is a 400 at `customFields.<key>`.
   - **Required:** enforced on CREATE. On UPDATE, an absent key leaves the value unchanged. `null` clears an optional field and is refused for a required one (as 1.9c did for profile fields).
   - **Values per type** (each limit a named constant):

     | Type | Rule |
     |---|---|
     | `TEXT` | trimmed, ≤ 200 characters, or `maxLength` |
     | `LONG_TEXT` | ≤ 2000 characters |
     | `NUMBER` | safe integer, with `min`/`max` |
     | `DECIMAL` | a **string** in canonical form, `^-?\d{1,12}(\.\d{1,4})?$`; never a float |
     | `CURRENCY` | integer minor units of the organization currency, with `min`/`max` |
     | `BOOLEAN` | |
     | `DATE` | a real calendar day `YYYY-MM-DD` |
     | `DATETIME` | ISO-8601 with an offset, normalized to UTC |
     | `SELECT` | one of the options |
     | `MULTI_SELECT` | unique options, at most 20 |
     | `PHONE` | normalized to E.164 with the existing phone helper |
     | `EMAIL` | lower-cased |
     | `URL` | `http` or `https`, ≤ 2048 characters |
     | `FILE`, `IMAGE`, `REFERENCE` | a UUID v7 (existence is checked by the owning module later) |

   - **Helpers in the same folder:**
     - `redactSensitive(values, fields, canReadSensitive)`: drops sensitive values for callers without the owning module's `readSensitive` permission
     - `toSearchEntries(values, fields)`: returns `[{ fieldKey, value }]` with lower-cased strings, for searchable fields

     The attribute pattern: entities store `customFieldSearch` and index `{ organizationId, "customFieldSearch.fieldKey", "customFieldSearch.value" }` (ADR-015's "indexes chosen by the engine"). Entities adopt it in Phase 3.

10. **Records:**
    - ADR-102 ("Accepted (proposed)"). It records:
      - INDUSTRY fields read from the template
      - preferences
      - DECIMAL as a string
      - no regex validation
      - the attribute pattern for search
      - the 50-field limit
    - `14` rows, the module README, `10` if a cell changes, the 2.3 STATUS row.

## Tests (must exist and pass)
- [ ] **Builder (unit), per type:**
  - one valid and two invalid values
  - required on CREATE and UPDATE, `null` on optional and required
  - an unknown key, and a key invisible to STOREFRONT
  - MULTI_SELECT duplicates
  - a DECIMAL float input refused
  - a DATE on February 30th refused
  - a PHONE normalized
- [ ] **Helpers:** `redactSensitive` drops sensitive values without the permission and keeps them with it; `toSearchEntries` lower-cases and skips non-searchable fields.
- [ ] **Seeds:** all 8 still parse; every seed field has `label.bn` and `label.en`; every SELECT and MULTI_SELECT option has an option label.
- [ ] **API happy path:**
  - an organization on SALON (DB fixture) with a probe `contact` entity: the effective list shows the template's five fields first
  - create an ORGANIZATION field
  - PATCH (version moves)
  - archive (it leaves the list)
  - hide an optional INDUSTRY field (gone), rename it, reorder
  - each write: one audit entry, the event, `configVersion` + 1
- [ ] **Validation:** a bad key, a bad type, options on a non-select field, `validation.max < min`, a regex-like field refused → 400.
- [ ] **Business rules:**
  - a key that duplicates an INDUSTRY field → 409
  - a second identical ORGANIZATION key → 409, also under a concurrent double create (the unique index)
  - the 51st field → 422 `CUSTOM_FIELD_LIMIT`
  - hiding a required field → 422 `CUSTOM_FIELD_REQUIRED`
  - PATCH `fieldType` or `fieldKey` → 400 (not in the schema)
- [ ] **Permission denied:** a STAFF member gets 403 on writes and 200 on read; a MANAGER limited to one location gets 403 on writes (ALL required).
- [ ] **Cross-org denied:** reading or patching another organization's definition by id → 404; the list never shows another organization's fields.
- [ ] **Unavailable entity:** `entityType=booking` on a RETAIL organization (booking not effective) → 404.
- [ ] **Startup:** a manifest entity outside the enum refuses to start (unit test of the check).
- [ ] Every existing suite green; full "Done means" list.

## Out of scope
- Storing values on any real entity (Phase 3), the contact-link create behaviour (3.1), the form renderer (2.5), any UI (2.6, 2.7).
- Putting `fields` into the resolved config and `/me/config` (2.2).
- INDUSTRY field CRUD through the platform (they change with the template's configuration, 2.1b).

## Risks & checks
- **The builder runs on both server and client later:** keep it free of Node-only APIs.
- **Do not widen the lint scope:** the engine never reads `industryTemplateKey` itself; the reader port takes it from the organization config.
- **Bangla labels:** natural wording, not word-for-word (`13 §7`). The reviewer reads them.
- Stop and ask if a seed field cannot be labelled without guessing its meaning.

## Done when
- The effective field list, ORGANIZATION definitions, preferences and the shared value builder work and are tested.
- Seed fields have labels.
- The Opus review passes.
