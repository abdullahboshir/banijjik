Tier: **T1** (ledgers: revenue, cost of goods, inventory value) · Planned by: Opus 5.5 (Claude) · Date: 2026-10-23 · Based on commit: `main c11f0c7`

Owner decision 2026-10-23: a stock receipt says how it was paid (cash, bKash, Nagad, bank) or that it was bought on credit (a new payable account); opening stock goes to the opening balance.

## Goal
`11 §10` says "order, stock, return and COD rows come with their cards" (ADR-124), but 3.3 and 3.5a shipped without them: today no order revenue, no cost of goods sold and no inventory value is ever posted, so profit and loss and the balance sheet are wrong for every product seller. After this card:
- a completed order posts its revenue, tax, discounts and rounding, settles the advances it held, and posts its cost of goods;
- a stock receipt posts its inventory value against the payment method, a new payable, or the opening balance;
- stock adjustments and damage write-offs post their gain or loss.

## Decisions
1. **Order revenue entry** (posting key `order_revenue`, source type `ORDER`, source id `orderId`), on `sales.order.completed`:
   - Dr `ACCOUNTS_RECEIVABLE` `grandTotal`; Dr `SALES_DISCOUNTS` `discountTotal`; Cr `REVENUE_PRODUCT` the tax-exclusive goods amount; Cr `TAX_PAYABLE` `taxTotal`; Cr `DELIVERY_INCOME` `deliveryCharge`; `ROUNDING` for `roundingAdjustment` (debit or credit by sign). Zero lines are left out.
   - The tax-exclusive goods amount comes from the order's own totals. Read the pricing quoter to see whether `subtotal` includes tax for tax-inclusive prices, and derive it so the entry balances by construction; a test covers a tax-exclusive and a tax-inclusive order. If the totals cannot express it, stop and ask.
   - Business date = the order's `businessDate` (already the organization's local date). Location = the order's location.
2. **Advances settle** (posting key `order_advance_settle`): Dr `CUSTOMER_ADVANCES` / Cr `ACCOUNTS_RECEIVABLE` for the advance the order actually holds (decision 3), only when it is above zero.
3. **Advance held** comes from payment's `RequestAdvanceReader` (card 3.25 builds it for bookings; this card registers the ORDER request type with it). Never the required advance.
4. **Cost of goods** (posting key `order_cost`): Dr `COGS` / Cr `INVENTORY` for the value of the order's SALE movements (`sourceId` = `orderId`), so COGS and the inventory value use the same numbers. Read them through a function exported by `inventory/index.ts`. Movement value = quantity × `unitCostMicros`, rounded half-up to minor units, by **one** helper in the inventory domain (use the existing one if the moving-average code has it). A SALE movement without a cost → the cost line is left out and the handoff says so (items received without a cost).
5. **Handler** `accounting.postOrders`: ORDERED, `streamPrefixes: ["order:"]` (3.22), handles `sales.order.completed` only for now (3.5b adds returns, Phase 5 adds shipped/RTS). Idempotent through the journal's unique `(organizationId, sourceType, sourceId, postingKey)`.
6. **Stock receipt funding** (owner decision): the receive request gets a required `paidVia`: `CASH | BKASH | NAGAD | BANK | ON_CREDIT` (contracts enum `STOCK_RECEIPT_PAID_VIA`, validation schema). It is stored on each PURCHASE movement of the receipt.
   - Posting key `stock_receipt`, source type `STOCK_RECEIPT`, source id = the receipt's `sourceId`: Dr `INVENTORY` Σ movement values; Cr the method account (`METHOD_ACCOUNT_CODE`), or the new system account `ACCOUNTS_PAYABLE` (LIABILITY) for `ON_CREDIT`.
   - `ACCOUNTS_PAYABLE` is added to `SYSTEM_ACCOUNT_CODE` and the seeds; organizations created before this card get it on first use through an `ensure` writer like `ensure-expense-account.ts`.
   - Paying the supplier later (a supplier payment that clears the payable) is a later card.
7. **Other stock rows** (posting from the movement's `sourceId`):
   - `OPENING` movements: Dr `INVENTORY` / Cr `OPENING_BALANCE` (key `stock_opening`).
   - `ADJUSTMENT`: an increase Dr `INVENTORY` / Cr `OTHER_INCOME`; a decrease Dr `DAMAGE_LOSS` / Cr `INVENTORY` (key `stock_adjustment`).
   - `DAMAGE_WRITE_OFF`: Dr `DAMAGE_LOSS` / Cr `INVENTORY_DAMAGED` when the movement's `stockState` is DAMAGED, else Cr `INVENTORY` (key `stock_write_off`).
   - `TRANSFER_IN/OUT`: no journal (accounts are per organization). `SALE` posts through the order (decision 4). `RETURN`/`RETURN_DAMAGED`: card 3.5b.
8. **Stock events for posting:** inventory publishes `inventory.stockSource.recorded` (`{ sourceType, sourceId }`, ids only, contracts `INVENTORY_EVENT_TYPE`) once per receipt, opening and adjustment, in the same transaction as the movements. Handler `accounting.postStock` is UNORDERED (each source posts once; nothing reverses it yet).
9. **Records:** ADR-138 ("Accepted (proposed)"): the order entries, advance settle from the held advance, COGS from SALE movements, receipt funding with `ACCOUNTS_PAYABLE`, opening/adjustment/write-off rows, the two handlers. `docs/11 §10` notes. Accounting, sales and inventory READMEs. Handoff `docs/handoffs/3.24-api.md` with the §11 table. STATUS row 3.24.
10. **Part B:** the admin receive-stock form gets a required "Paid via" select (the five values, BN/EN keys). Browser test: receive with `ON_CREDIT`, then the trial balance shows `ACCOUNTS_PAYABLE`.

## Out of scope

## Risks & checks
- Wrong sign or wrong account silently skews P&L: every row has a test that reads the trial balance, not only the draft.
- `unitCostMicros` precision: one rounding helper, used in both places.
- The ORDERED order handler depends on 3.22; do not start before it merges.

## Done when
- A product seller's day (receive, sell, adjust) gives a balanced trial balance with correct INVENTORY, COGS, revenue and tax; the Opus review passes; CI green; `npm run card:check` all PASS.
