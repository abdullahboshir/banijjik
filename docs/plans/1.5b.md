## Goal
A use case publishes a domain event in the same transaction as its change. The event lands in an **outbox**. A dispatcher in the **worker process** (`ROLE=worker`) turns each pending event into one BullMQ job per registered handler. Jobs retry with backoff; after the last attempt they are dead-lettered and reported. Handlers run in the event's organization context. Roadmap 1.5 Done (second half): "an outbox job retries after failure".

The events already declared by 1.1 and 1.2 are now really emitted. The Redis adapter for the permission cache (ADR-088, owner decision) lands here too.

## Decisions
**Contracts**
1. `EventEnvelope<Payload>` = `{ eventId, type, version, occurredAt, organizationId: string | null, actorUserId: string | null, payload }`. `organizationId` is null only for user-level events (`iam.user.registered`); update the `05` envelope line to say so.
   - Contracts `EVENT_TYPE` joins the existing `IAM_EVENT_TYPE` and `ORGANIZATION_EVENT_TYPE` and adds `iam.role.created`, `iam.role.permissionsChanged`, `iam.role.archived` (`09 §4.5`; "deleted" there becomes "archived", matching 1.4). Update `09` in one line.
   - Each event type has a payload interface in contracts (ids only, no personal data: e.g. `{ organizationId, organizationSlug }` for org created, `{ userId }` for user registered).

**Publishing (`kernel/events`)**
2. `publishEvent(type, payload, options?: { version?: number })` writes an **OutboxEvent** with the active session.
   - **No active transaction → throw** `errors.event_needs_transaction`: an event must never exist without its change, or the change without its event.
   - `eventId` = `newId()`. `occurredAt`, `organizationId`, `actorUserId` and `requestId` come from the request context.
3. **OutboxEvent** (PLATFORM DB, `outbox_events`, tenancy NONE, kernel-only: the dispatcher spans all orgs):
   - Fields: `eventId`, `type`, `version`, `occurredAt`, `organizationId`, `actorUserId`, `requestId`, `payload`, `status` (`PENDING | DISPATCHED | DEAD`), `dispatchAttempts`, `nextAttemptAt`, `lockedUntil?`, `dispatchedAt?`, `lastError?` (error class + code only).
   - Indexes: `{ eventId }` unique, `{ status, nextAttemptAt }`, TTL 30 days on `dispatchedAt`.
   - Why the platform DB: user-level events have no org, and one client means one transaction spans the tenant DB change and this insert (ADR-084).
4. **Handlers** register at startup through a kernel registry: `registerEventHandler({ handlerKey, eventType, handle(envelope): Promise<void> })`.
   - `handlerKey` is unique (`<module>.<purpose>`). No production handler exists yet; the tests register their own.
   - Duplicates throw. The registry seals with the model registry pattern (adding after start throws).
   - Module manifests list `events.consumes`. 1.6 checks they match and gates handlers on module effectiveness.

**Dispatch and execution (worker process only)**
5. **Dispatcher** loop in `ROLE=worker`, every 500 ms (configurable `OUTBOX_POLL_INTERVAL_MS`, default 500):
   - Claim up to 50 `PENDING` events with `nextAttemptAt ≤ now` one by one: atomic `findOneAndUpdate` setting `lockedUntil = now + 30 s`, so concurrent workers never double-claim.
   - For each, add **one BullMQ job per handler** of its type to the queue `events`, with `jobId = "<eventId>:<handlerKey>"` (BullMQ dedupes by job id), then mark the event `DISPATCHED`.
   - An event with no handlers is marked `DISPATCHED` directly.
   - When adding a job fails (Redis down): increment `dispatchAttempts`, set `nextAttemptAt` by backoff 5 s, 30 s, 2 min, 10 min, 1 h (ported from manoxen), and keep it `PENDING`.
6. **Worker** (BullMQ `Worker` on `events`, concurrency 5):
   - Each job loads the envelope and runs its handler inside `runInOrganizationContext(organizationId)`, or `runAsSystem(SCHEDULED_JOB)` when `organizationId` is null, with a fresh `requestId` (`event:<eventId>`).
   - Job options: `attempts: 5`, exponential backoff starting at 1 s, `removeOnComplete: 1000`, `removeOnFail: false`.
   - **Exactly once per handler:** the handler record `processed_events` (PLATFORM, NONE, unique `{ eventId, handlerKey }`) is inserted in the **same transaction** as the handler's own writes. The wrapper opens `withTransaction`, inserts the marker, runs the handler; a duplicate marker means "already done", so the job completes without running again.
7. **Dead letter:** when a job's final attempt fails, the shared wrapper calls `reportError` (with `eventId`, `handlerKey`, `type`, attempt count) and writes an `event_dead_letters` row (PLATFORM, NONE: `eventId`, `handlerKey`, `type`, `lastError`, `failedAt`). The event's other handlers are unaffected.
   - A replay tool is out of scope; note it in STATUS.
8. **`main.ts` worker role:** connect Mongo, connect Redis (`ioredis`, `maxRetriesPerRequest: null` as BullMQ requires), start the dispatcher and worker, log `worker.started`.
   - Shutdown tasks, in order: stop the dispatcher loop, `worker.close()`, `queue.close()`, `redis.quit()`, close databases. The API role never touches Redis for events: it only writes the outbox. The API connects to Redis only for the permission cache (decision 10).

**Emit the declared events** (add-only lines inside transactions)
9. Events to emit:
   - `iam.user.registered`: `RegisterUserUseCase` now runs its writes inside its `UnitOfWork`, if not already
   - `organization.organization.created`, `organization.location.created`, `organization.member.joined`: create-organization transaction
   - `iam.role.created`, `iam.role.permissionsChanged` (only when keys changed), `iam.role.archived`: role use cases

   The use cases depend on a port `EventPublisher` (each module's `application/ports`), implemented by the kernel's `publishEvent` and wired in the module `index.ts`.

**Redis permission cache (owner decision 1.4)**
10. `RedisPermissionCache` implements the 1.4 `PermissionCache` port: JSON with Sets and Maps serialized to arrays, TTL 10 min, key as in 1.4.
    - Composition: a two-tier cache (the in-memory LRU in front of Redis). A Redis error on get/set is logged at `warn` and treated as a miss, so a Redis outage slows permission checks but never fails or changes them.
    - Correctness does not depend on Redis (ADR-088). Redis adds sharing between instances.
    - `/ready` adds a Redis ping (2 s) for the API role.

**Infra and CI**
11. **Redis host port default 6380** (`infra/docker-compose.yml` `${BANIJJIK_REDIS_PORT:-6380}`, `apps/api/.env.example` `REDIS_URL=redis://127.0.0.1:6380`, READMEs). Same reason as the owner's Mongo 27018 decision: another project's Redis holds 6379 on the owner's machine. Record it in the handoff for the owner.
    - Correction, 2026-10-11: 6380 was the planner's proposal; the owner decided it on 2026-10-11 ("keep 6380"). It is an owner decision of 2026-10-11, not an earlier one.
12. **Tests that need Redis** read `TEST_REDIS_URL`.
    - In CI (`CI=true`) a missing `TEST_REDIS_URL` **fails** the suite (no silent skip).
    - Locally without it, those tests are skipped with one clear warning line, and the handoff must show a run **with** it (the compose Redis on 6380).
    - `ci.yml` `verify` job gets a `redis:7` service container on 6379 and `TEST_REDIS_URL=redis://localhost:6379`.
    - Each test uses its own queue name prefix and flushes only its own keys.
13. **Dependencies:** `bullmq@^6`, `ioredis@^6` (check `npm view`; record the versions). BullMQ requires ioredis as its client.
14. **ADR-090** ("Accepted (proposed)"): outbox in the platform DB in the same transaction; dispatcher in the worker; one job per handler; handler exactly-once through a marker in the handler's transaction; dead letters; no inline fallback.

## Tests (must exist and pass)
Unit/kernel (real replica set; Redis via `TEST_REDIS_URL`):
- [ ] `publishEvent` outside a transaction throws; inside, the outbox row exists only if the transaction commits (abort → no row)
- [ ] **retry after failure (roadmap):** a test handler that throws twice then succeeds is called 3 times and the event's marker exists once; a handler that always fails ends in `event_dead_letters` after 5 attempts with one `reportError` call; another handler of the same event still succeeds
- [ ] exactly once: the same job delivered twice (re-add with a new job id after success) does not run the handler again; the handler's own write and the marker roll back together when the handler throws
- [ ] the handler runs with `organizationId` of the event in the context (the tenant plugin applies); a null-org event runs under `runAsSystem(SCHEDULED_JOB)` with one `system_access` log line
- [ ] dispatcher: two dispatchers in parallel never enqueue an event twice (job ids); Redis unavailable → the event stays `PENDING` with `dispatchAttempts` 1 and `nextAttemptAt` +5 s
- [ ] handler registry: duplicate key throws; registration after start throws

Emission (API level):
- [ ] register → one `iam.user.registered` outbox row; create org → the three organization events in one transaction (atomicity test: an injected failure leaves no outbox rows); role create/update/archive → their events; updating only the name emits no `permissionsChanged`

Cache:
- [ ] `RedisPermissionCache` round-trips a grant map; a Redis error makes `get` a miss and logs a warning; the two-tier cache answers from memory without touching Redis on a hit

Process:
- [ ] `main.test.ts`: `ROLE=worker` with Mongo + Redis logs `worker.started` and dispatches a pending event end to end (spawned process, inline env). Shutdown runs the tasks in order (direct test of the task list; the Windows SIGTERM limitation stands).
