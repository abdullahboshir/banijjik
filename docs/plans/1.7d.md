# Plan: card 1.7d · Admin: business profile, locations and roles screens

Tier: T2 · Planned by: Opus 5.5 · Date: 2026-10-11 · Based on commit: `main b2c5e1b`

Last part of roadmap 1.7. Runs in parallel with **1.8b** (platform web app). 1.8b moves the generic API-client and session code of `apps/admin/src/lib/api` and `src/auth` into a shared package and leaves thin re-exports behind. This card therefore only **imports** from those admin paths and does not edit them. Shared, add-only: the i18n screen catalogs and `packages/ui/src/index.ts`.

## Goal
The three settings entries of the menu lead somewhere real:
- **Business profile:** view and edit the business details, with a "Locations" section that is the way to add a second location.
- **Locations:** list, add, edit, archive. The menu entry appears only with ≥ 2 active locations (ADR-004).
- **Roles:** the six system roles (read-only) and custom roles (create, edit, archive), with permissions grouped by module and sensitive ones marked.

All of it is on the existing API (1.4, 1.7b), permission-aware, in Bangla, on a phone.

## Decisions
1. **Same page pattern as 1.7c**, no new pattern:
   - a server page loads data with `serverApiFetch` and renders the list or detail
   - forms, sheets and dialogs are client parts loaded on first tap
   - every string comes from the server-only screen catalogs (bn + en, identical key sets) and is passed as props
   - actions are hidden without the permission (from `/me/config`) and in READ_ONLY mode; the API still enforces everything
2. **Business profile** (`/{orgSlug}/settings/profile`):
   - Everyone who is a member can open the page (`GET /profile` needs no key). The menu entry stays tied to `organization.profile.update` (1.7c), and the page shows the form read-only without that permission.
   - Fields: name, default language, and the `profile` object (legal name, legal type, phone, email, address fields of `PostalAddress`, trade licence number).
   - It uses the same Zod schema as the API and sends `version`. A 409 shows the "changed by someone else, reload" message.
   - Phone input accepts `01…` and shows `01712-345678` (`13 §7`), through the existing formatter.
   - Slug, currency, timezone and industry are shown read-only with a one-line explanation. They have no edit API.
3. **Locations section on the profile page:** it shows the active locations (one line when there is one). With `organization.location.create` at ALL it has an "Add a location" action. This is how a one-location business reaches the form, since the menu entry is hidden until there are two. After the second location exists, the next page load shows the Locations menu entry (the config version bump of 1.7c).
4. **Locations** (`/{orgSlug}/settings/locations`, `organization.location.read`):
   - **List:** `DataList`: name, type (STORE / WAREHOUSE), phone, status badge; chips ACTIVE / ARCHIVED.
   - **Add / edit form** in a sheet: name, type, address, phone, timezone (a select of IANA zones limited to a short list with `Asia/Dhaka` first, plus "same as business").
   - **Create** sends an `Idempotency-Key` (reused for retries of the same submit, as in 1.7c).
   - **Archive** uses `ConfirmDialog`. The API refusals are shown as their own messages: `LOCATION_IS_DEFAULT`, `LOCATION_IN_USE` (says how to fix it: move the staff first), `LIMIT_REACHED` (explains the package limit; no upgrade link until billing exists).
   - A member limited to some locations sees only those and no create or archive action (the API rule of 1.7b).
5. **Roles** (`/{orgSlug}/settings/roles`, `iam.role.read`; reached from a tab or link on the Staff page, since `10 §6` has one entry "Staff & roles"):
   - **List:** system roles first with their translated names and a "system" badge, then custom roles, with member counts.
   - **Detail:** permissions **grouped by module** (the module key is the first segment), each with its label (`permission.<key>` keys exist since 1.4) and a mark on sensitive ones (`isSensitive`). Only permissions of effective modules are listed (from `/me/config` modules).
   - **Create / edit a custom role:** name + checkboxes per group, with "select all in group". Sensitive permissions sit in a separate "sensitive" block per group (`10 §7`).
   - The form only offers permissions the caller holds themselves. Granting others would be refused by the API anyway, and offering them would only produce errors. A hint says so.
   - System roles are read-only with the reason. Archive is refused with `ROLE_IN_USE` shown as "N members still have this role".
   - The source of the permission list: contracts `PERMISSION_KEY` + the manifest definitions' `isSensitive`. If the client cannot get `isSensitive` without a new endpoint, add `permissionDefinitions` (key, labelKey, isSensitive, moduleKey) to `/me/config`, add-only, with a test. Do not hard-code the sensitive list in the admin app.
6. **Status tones:** add `INVITATION` (PENDING info, ACCEPTED success, REVOKED neutral, EXPIRED neutral), `LOCATION` (ACTIVE success, ARCHIVED neutral) and `ROLE` (ACTIVE success, ARCHIVED neutral) to `statusTone`, with rows in `11 §12`. Switch the invitation badge of 1.7c to it.
7. **Budget:** every new route ≤ 170 KiB initial JS (same measurement as 1.7c). If one exceeds, stop and report the breakdown.
8. **Screenshots:** retake the 1.7c set (it predates the trim) and add this card's, at 375 px and 1280 px in bn, under `docs/handoffs/assets/1.7d/`.
