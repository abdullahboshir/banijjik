## Decisions
**J2: `{ middleware: false }`**
1. **Runtime, fail closed.** Mongoose skips `pre` hooks when a query or aggregate carries `middleware: false`, so a hook cannot catch it. Guard at the only door instead: the model handed out by `models(ctx).get()`.
   - For every model whose tenancy is not `NONE`, or which is `appendOnly`, wrap the compiled model **once** (cached per connection, as today) so that each of these throws `AppError(INTERNAL, "errors.middleware_bypass_forbidden")` unless `getSystemReason()` is `MIGRATION`:
     - a query created from it, when `setOptions`/`options` receives `middleware: false` (override the model's own `Query` subclass `setOptions`, which every options path goes through, and check again in `exec`)
     - an aggregate, when `option({ middleware: false })` is set (check in the aggregate's `exec`)
     - the document and model calls that accept `{ middleware: false }` in Mongoose 9 (`save`, `insertMany`, `bulkWrite`, `deleteOne`/`updateOne` on documents). Verify the list against the installed version's source and list it in the handoff.
   - If any path cannot be guarded reliably in Mongoose 9.11, **stop and report** which one. Do not ship a partial guard described as complete.
2. **Lint:** new rule **R36** in `**/modules/**` (non-test): a property key `middleware` or `skipMiddlewareFunction` in an object literal, and a member call `.setOptions(` whose argument names `middleware`, are errors. Fixtures: fail in a module repository; pass in `kernel/db`.
3. **Tests:** the review's P5, on the real `Location` model and on the append-only audit model: each bypass spelling throws in an organization context; without the option everything behaves as before; `runAsSystem(MIGRATION)` may use it. Add them to the isolation suite, so the registry meta-test covers future models.

**J3: `runAsSystem` in module code**
4. R26 and R27 change from "the four layer folders" to **all of `**/modules/**`**, including `index.ts`, `*.composition.ts` and any other root file.
   - The exemption changes from the glob `**/modules/platform/**/application/**` to an **explicit file list** in `eslint/scopes.mjs` (`SYSTEM_ACCESS_FILES`): exactly the platform use-case files that call `runAsSystem` today. Find them with grep and list them in the handoff.
   - A new platform use case that needs system access must be added to that list in the same commit, which makes the bypass visible in review.
   - Fixtures: `modules/core/organization/index.ts` and a `*.composition.ts` importing `runAsSystem` fail; a listed platform use-case file passes; a new unlisted platform application file fails.
   - If moving to all of `modules/**` reports existing code, that code is a finding: fix it only by moving the call to the composition root (`routes/**`) through a port, as ADR-087 describes. If that is not mechanical, stop and report.

**J4: indexes in production**
5. **Index sync tool:** `apps/api/src/seeds/sync-indexes.ts` + script `db:sync-indexes` (outside modules, like the other seed entries).
   - It connects, registers every module's models, and for each registered model runs `createIndexes` inside `runAsSystem(MIGRATION)`.
   - It then prints a per-collection summary (created / already there / **conflicting**).
   - It **does not drop** anything. An index that exists with the same keys but different options (the old full unique index on `locations.name` is the known case) is reported as conflicting with the exact `dropIndex` command to run by hand, and the exit code is 1.
6. **Startup guard:** when `NODE_ENV=production`, after connecting, `main.ts` checks that every **unique** and every **TTL** index declared by the registered schemas exists on its collection (`listIndexes`; compare keys, `unique`, `expireAfterSeconds`, `partialFilterExpression`).
   - Any missing → log `{ event: "db.indexes_missing", collections: [...] }` at fatal (names only) and exit 1, with the hint to run `db:sync-indexes`.
   - Outside production nothing changes (`autoIndex` stays on).
7. **Docs:** `apps/api/README.md` and `docs/ops/` get a short "first deploy and every deploy: run `db:sync-indexes`" section. STATUS records it as part of the release procedure and removes the "understated" wording the review flagged.
   - **ADR-094** ("Accepted (proposed)"): indexes are created by an explicit task, never dropped automatically; production refuses to start without its unique and TTL indexes.
