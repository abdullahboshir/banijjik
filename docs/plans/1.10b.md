## Goal
A SUPER_ADMIN manages platform operators in the platform panel, on a phone as well as a desktop. The panel shows:
- a list with a status filter
- "Add operator"
- "Change roles"
- "Disable" and "Enable"

Other operators never see the menu entry. The API stays the protection; the screens only follow it.

## Decisions
**Page and menu**
1. **Route `/operators`** in `app/(panel)/operators/page.tsx`, rendering `OperatorsPage` from `src/operators/operators-page.tsx`. It copies the shape of `TenantsPage`.
   - Without `platform.operator.read`, the page shows `state.permissionDenied`, as the other pages do.
   - `PageHeader` with the title and status filter chips: All, Active, Disabled. They map to `?status=` and use `FilterChips`, with a `parseOperatorQuery` / `operatorListHref` / `operatorsApiPath` trio like `tenant-query.ts`.
   - The list below, then `ListPager`.
   - No detail page: everything an operator needs fits the list row and its actions.

2. **Menu entry** in `navigation-entries.ts`:
   - `menuKey: "operators"`, `labelKey: "platform.nav.operators"`, `href: "/operators"`
   - `iconKey: "user"`: already registered, so no change in `@banijjik/ui`
   - permission `OPERATOR_READ`, placed last, after Audit log
   
   SUPPORT and BILLING never see it.

**The list**
3. **`OperatorList`**, built like `TenantList`: cards below `md`, a table from `md` up, no horizontal scroll at 375 px.
   - Columns: name, `identifierHint`, roles, status (`StatusPill`), actions.
   - The roles show as their translated labels, joined with ", ".
   - The row of the signed-in operator carries a "You" badge and **no actions**. Compare `platformOperatorId` with the `/platform/me` operator. The API refuses own changes (`OWN_OPERATOR_ACCESS`); the screen does not offer them.
   - An empty list shows `platform.operators.empty`.

**Actions** (only with `platform.operator.write`; the API checks again)
4. **"Add operator"**, a primary button in the page header. It opens `OperatorFormSheet` in create mode, lazy-loaded on the first tap like `TenantActions`.
   - Fields: identifier (email or phone), roles (three checkboxes), reason (`ReasonField`).
   - Validate with `platformOperatorCreateRequestSchema` before sending. Show field errors at the field, as `status-sheet.tsx` does.
   - The description says the person must already have an account: they sign up in the business app first.

5. **Row actions** for a row that is not the caller's own:
   - "Change roles": `OperatorFormSheet` in roles mode, with the current roles checked, plus the reason. It sends `{ platformRoles, version, reason }`.
   - "Disable" for an ACTIVE row: a danger sheet. Its description says that person's platform sessions end at once and their business sessions are not affected.
   - "Enable" for a DISABLED row.
   - Disable and enable share one `OperatorStatusSheet` (reason only; it sends `{ version, reason }`).
   - Which actions a row gets comes from a pure function `operatorActionsFor(row, viewer)`. Keep it in its own file with a unit test, like `tenant-action-labels.ts`.

6. **After a write:** use the existing `useFinishAction`. It closes the sheet, announces the success message and refreshes the server data. The new version and status come back from the server on that refresh; no client cache.

7. **Errors** go through the existing `api-failure` mapping, so these messages show in the sheet:
   - `OPERATOR_USER_NOT_FOUND`, `OPERATOR_USER_NOT_ACTIVE`, `OWN_OPERATOR_ACCESS` (`422 BUSINESS_RULE`)
   - `errors.operator_exists` (409)
   - the stale-version 409: the existing conflict message, so the operator reloads
   
   The 1.10a message keys already exist in both catalogs. Check that each one renders, and add a mapping only if `api-failure.ts` needs one.

**API client and text**
8. **`src/api/platform-api.ts`** gets:
   - `grantOperator(request)`
   - `changeOperatorRoles(platformOperatorId, request)`
   - `changeOperatorStatus(platformOperatorId, "disable" | "enable", request)`
   
   They are typed with the 1.10a contracts and validation types. Reads go through `fetchPlatformResource`, as the other pages do.

9. **Text:** every new string is a key in both `platform/bn.json` and `platform/en.json`, and the existing catalog tests must pass:
   - `platform.nav.operators`, `platform.operators.title`
   - the column labels, `platform.operators.empty`, `platform.operators.you`
   - `platform.role.SUPER_ADMIN|SUPPORT|BILLING`
   - `platform.status.operator.ACTIVE|DISABLED`
   - the action labels; the sheet titles, descriptions and success messages
   - the identifier and roles field labels and hints
   
   Bangla first: the Bangla text must read naturally, not as a word-for-word translation. Lint R37 already forbids text in JSX.

**Budget and phone**
10. `/operators` must stay **≤ 170 KiB** initial JS. The sheets load lazily, so the route should land near `/tenants` (about 155 KiB). Add it to the budget test in `panel.browser.test.ts` and to the 375 px no-sideways-scroll test, and add a screenshot entry.

## Out of scope
- Any API change. If the screens seem to need one, stop and ask.
- An operator detail page, search by name, bulk actions, invitations by email or SMS, creating accounts for others.
- New icons or `@banijjik/ui` components. Use what exists; if something is truly missing, stop and ask.

## Risks & checks
- **Own row:** decide it from `/platform/me`, never from a client guess. Check that the browser flow's super admin sees no actions on their own row.
- **Stale data:** after a write, the version in the next request must be the new one; the refresh after `useFinishAction` provides it. The 409 test covers a stale tab.
- **Budget:** check the route-size output before and after; lazy sheets keep forms out of the first load.
- **Memory, disk, services:** as in the guide. Browser suites with `VITEST_MAX_WORKERS=1`.
