# Plan: card 2.5 · Dynamic form renderer (custom fields)

Tier: **T2** · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor · Date: 2026-10-15 · Based on commit: `main 1b4f85d`

**Wave 2 of Phase 2, in parallel with 2.2.** Read `docs/plans/phase-2-lanes.md` (the wave-2 section) and `docs/ops/implement-with-cursor.md` first. Reserved ADR number: **ADR-105** (only if an architectural choice comes up; this plan needs none).

## Goal
One mobile-first form block that renders an entity's effective custom fields and validates them in the browser **with the same rules as the server** (2.3's `buildCustomFieldValuesSchema`). Cards 2.7 (organization fields), 3.1 (contacts) and every later entity form reuse it instead of building their own field inputs.

## Inputs read
- ADR-015, ADR-102, `13-UX.md` §3 (forms), §5 (states), §12 (phone), `01 §5` (16 field types)
- Code:
  - `packages/ui/src/components/form.tsx` (`FormField`, `TextInput`, `Textarea`, `Select`, `Checkbox`, `formFieldMessageId`)
  - `packages/ui/src/format/*` (`formatMoney`, `formatNumber`)
  - `packages/ui/package.json`: **ui does not depend on contracts or validation**, and stays that way (pure presentation)
  - `packages/web-client` (depends on contracts, i18n, ui)
  - `packages/validation/src/custom-field/*` (the builder, `CustomFieldRule`, limits)
  - `packages/contracts` `EffectiveCustomField`, `CUSTOM_FIELD_TYPE`

## Decisions
**Split between packages**
1. **`@banijjik/ui` gets the presentation**, `components/custom-field-inputs.tsx` (split per type if the size rules ask for it). Props:

   ```ts
   interface CustomFieldDescriptor {
     fieldKey: string;
     inputKind: "TEXT" | "LONG_TEXT" | "INTEGER" | "DECIMAL" | "MONEY" | "BOOLEAN" | "DATE" | "DATETIME"
              | "SELECT" | "MULTI_SELECT" | "PHONE" | "EMAIL" | "URL";
     label: string;                 // already in the user's language
     hint?: string;
     isRequired: boolean;
     options?: { value: string; label: string }[];
     maxLength?: number;
   }
   interface CustomFieldInputsProps {
     fields: readonly CustomFieldDescriptor[];
     values: Readonly<Record<string, unknown>>;
     errors: Readonly<Record<string, string | undefined>>;   // translated messages
     onChange: (fieldKey: string, value: unknown) => void;
     idPrefix: string;              // unique per form, for label/input ids
     disabled?: boolean;
     currencySymbol: string;        // shown before MONEY inputs
   }
   ```

   - No i18n keys inside ui; every text comes in through props, like the existing form components.
   - No contracts import.

2. **`@banijjik/web-client` gets the glue**, new file `custom-field-form.ts` (exported from `./client`):
   - `toFieldDescriptors(fields: EffectiveCustomField[], locale, t)`: maps types, picks `label[locale]` and option labels, and drops fields invisible to the admin audience.
   - `validateCustomFieldValues(fields, values, { audience: "ADMIN", mode })`: runs 2.3's `buildCustomFieldValuesSchema` and returns `Record<fieldKey, messageKey>`, using the same `validation.<code>` keys the API uses.
   - `toRequestValues(values, fields)`: produces the request map (decision 4).
   - Add `@banijjik/validation` to web-client's dependencies. It is browser-safe (2.3 kept it so).

**Input behaviour per type**
3. Each type, and the value it produces:

   | Type | Input | Value produced |
   |---|---|---|
   | TEXT, PHONE, EMAIL, URL | `TextInput` with `type` and `inputMode` (`tel`, `email`, `url`) and `autoComplete="off"` | a string; PHONE is normalized by the shared schema on submit |
   | LONG_TEXT | `Textarea` | a string |
   | NUMBER | numeric text input (`inputMode="numeric"`) | an integer; never a float |
   | DECIMAL | `inputMode="decimal"` | **a string** in canonical form (2.3) |
   | CURRENCY | `inputMode="decimal"` with `currencySymbol` | the major-unit text the user typed is converted to **integer minor units by string arithmetic**, no float (ADR-013). Add `parseMoneyInput(text, fractionDigits)` beside `formatMoney` in ui, with tests (`"12.50"` → 1250, `"12.505"` → error, `"১২.৫০"` with Bangla digits → 1250) |
   | BOOLEAN | `Checkbox` | a boolean |
   | DATE | `type="date"` | `YYYY-MM-DD` |
   | DATETIME | `type="datetime-local"` | an ISO string with the browser's offset |
   | SELECT | `Select` with an empty "choose" option when not required | the option value |
   | MULTI_SELECT | a group of `Checkbox`es (one per option, ≥ 44 px rows) | an array, in option order |

   - **FILE, IMAGE, REFERENCE are not rendered by this card.** They need upload and picker components that belong to the file module and the entity cards. `toFieldDescriptors` returns them separately as `pendingFieldKeys`, and the block shows one line per field (`form.field.notEditableHere`, passed in as a prop text). Record this gap in STATUS.

4. **Empty and clearing:**
   - An emptied optional field becomes `null` on UPDATE (clears it) and is left out on CREATE (2.3's rule).
   - A required field left empty shows the required message and blocks submit. `toRequestValues` produces the map.

**Layout and accessibility**
5. Mobile first:
   - one column, full width
   - labels above inputs
   - touch targets ≥ 44 px
   - errors linked with `aria-describedby` through `formFieldMessageId`, plus the required marker as the existing `FormField` shows it
   - no horizontal scroll at 375 px

   Sensitive fields need no special rendering here; the API already redacts them for callers without permission.

6. **Bundle.** The block is client-only code and is imported only by forms that use it. Check that the admin and platform route sizes do not change: no existing page imports it in this card.

## Tests (must exist and pass)
- [ ] **ui, per input kind:**
  - renders with its label (found by accessible name)
  - typing or choosing calls `onChange` with the documented value type
  - an error message renders and is linked with `aria-describedby`
  - required marker
  - `disabled` disables
- [ ] **`parseMoneyInput`:** the three cases above plus negative, empty and spaces.
- [ ] **web-client:**
  - `toFieldDescriptors` maps all 16 types (3 to `pendingFieldKeys`), picks the Bangla and English labels, hides storefront-only fields
  - `validateCustomFieldValues` agrees with the API on: required on CREATE, `null` on UPDATE, unknown key, a DECIMAL float, an invalid date
  - `toRequestValues` produces `null` for a cleared optional on UPDATE and omits it on CREATE
- [ ] **One integration test in web-client** renders the block with SALON's contact fields (labels from the seed shape), fills them, and the produced map passes `buildCustomFieldValuesSchema` unchanged.
- [ ] Every existing suite green; full "Done means" list (the browser suites must stay green and the route sizes unchanged).

## Out of scope
- Any page using the block (2.7, 3.1), file upload, reference pickers, the contact-link behaviour (3.1), storefront and bot rendering.

## Risks & checks
- **Same rules on both sides:** never copy a validation rule into ui or web-client; always call the shared builder.
- **No float on money:** string arithmetic only, and a test proves `0.1 + 0.2`-style inputs are exact.

## Done when
- The block renders and validates all thirteen renderable types with server-identical rules, mobile first, and is ready for 2.7 and 3.1.
- The Opus review passes.
