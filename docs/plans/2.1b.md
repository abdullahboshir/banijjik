# Plan: card 2.1b · Industry templates: platform writes

Tier: **T1** · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor · Date: 2026-10-14 · Based on commit: `main 8291363` (2.1a merged)

**Wave 1 of Phase 2, in parallel with 2.3 and 2.4.** Read `docs/plans/phase-2-lanes.md` (conflict rules) and `docs/ops/implement-with-cursor.md` first. Reserved ADR number: **ADR-101**.

## Goal
A SUPER_ADMIN manages industry templates from the API: create, edit, publish, retire, and move an organization to another template. This is how SALON, GYM and COACHING get published for the launch (ADR-099), and how a new industry is created without a deploy (ADR-034, ADR-097).

Every write is audited and versioned. Changes reach tenants additively (ADR-046, ADR-076), and signup can never pick a template that is being retired at the same moment.

## Decisions
**Endpoints** (all under `/api/v1/platform`, permission `platform.industry.write`, so SUPER_ADMIN only; every write takes a mandatory `reason`)

1. **`POST /industry-templates`**: creates a **DRAFT** template.
   - Body:

     | Field | Rule |
     |---|---|
     | `industryTemplateKey` | format of ADR-097; must be new, otherwise `409 CONFLICT` `errors.industry_template_key_taken` |
     | `name`, `description`, `iconKey` | |
     | `enabledKinds`, `allowedModuleKeys` | |
     | `configuration` | |
     | `reason` | mandatory |

   - **Or** `cloneFromIndustryTemplateId` instead of `enabledKinds`, `allowedModuleKeys` and `configuration`. That copies them from an existing template of any status. This is the fast way to start a new industry from a near one.
   - Validated with the existing `industryTemplateConfigurationSchema` and the field rules of 2.1a's entity factory.
   - `allowedModuleKeys` must name CORE or OPTIONAL modules of `MODULE_KEY`, as in 2.1a.
   - Answers `201` with the detail.

2. **`PATCH /industry-templates/{industryTemplateId}`**: replaces `name`, `description`, `iconKey`, `enabledKinds`, `allowedModuleKeys` and `configuration` (each optional) and takes `version`.
   - A stale version answers 409.
   - A save moves `version` by one. The template reader's 30-second cache and the config cache key (`templateVersion`) carry the change to tenants.
   - The key and the status never change through PATCH.

3. **Additive rule** (ADR-046, ADR-076). Once a template is PUBLISHED, RETIRED, or used by at least one organization, a PATCH may only **add**. It may not remove:
   - a kind
   - an allowed module
   - a custom field (by `entityType` + `offeringKind` + `fieldKey`)
   - a term key, a contact role, a relation key, a resource type key

   It may change: labels, descriptions, options added to a SELECT, setting default values, knowledge and bot text.

   A removal answers `422 BUSINESS_RULE`, ruleKey `INDUSTRY_TEMPLATE_CHANGE_NOT_ADDITIVE`, with `details.removed` listing what would be removed. A DRAFT template used by no organization may change freely.

   - "Used by" is a count through a port to `core/organization`, adapted in `routes/platform.ts`: `OrganizationTemplateUsage { countByTemplateKey(key): Promise<number> }`.
   - Add the index `{ industryTemplateKey: 1 }` on `organizations` for it.

4. **`POST /industry-templates/{id}/publish`** (DRAFT or RETIRED → PUBLISHED) and **`POST …/retire`** (PUBLISHED → RETIRED).
   - Body `{ version, reason }`.
   - Already in the target status → `200` unchanged, with no write.
   - Any other transition → `422 BUSINESS_RULE`, ruleKey `INDUSTRY_TEMPLATE_STATUS_INVALID`.
   - Retiring keeps every organization on it working (the reader answers for any status). It only stops new signups.

5. **`POST /organizations/{organizationId}/change-industry-template`**: body `{ industryTemplateKey, reason }`. It moves an organization to another template, **additively**:
   - The target must exist and not be RETIRED. A DRAFT target is allowed, because a platform operator assigns DRAFT templates to pilot organizations (ADR-075).
   - The target's `enabledKinds` and `allowedModuleKeys` must each contain all of the current template's, otherwise `INDUSTRY_TEMPLATE_CHANGE_NOT_ADDITIVE`. Nothing an organization had can disappear.
   - The same key as now → `200` unchanged.
   - On change, in one transaction:
     - `Organization.industryTemplateKey` is set
     - `configVersion` is bumped (ADR-091)
     - one platform audit entry is written
     - the event `organization.organization.industryTemplateChanged` is emitted inside the organization context, like suspend
   - **Where the code lives:**
     - The use case belongs to `core/organization`, which owns the field (it may name `industryTemplateKey`; the lint allows it).
     - The route is mounted from `platform/industry`'s platform router at `/organizations/:organizationId/change-industry-template` in `routes/platform.ts`, like the module-override router. `platform/industry` is a reader file, so it may name the key.
     - The additive check calls `platform/industry` through a port that `routes/platform.ts` adapts.
     - Add the event type to contracts and the organization manifest's `emits` list.

**Signup against retire (2.1a review note)**

6. Replace the second availability read inside the signup transaction with an **atomic reserve**. `IndustryTemplateAvailability` gains `reserveForSignup(templateKey): Promise<boolean>`:

   ```
   findOneAndUpdate({ industryTemplateKey, status: PUBLISHED }, { $inc: { referenceVersion: 1 } }) in the active session
   ```

   It returns `false` when no document matched.
   - Retire writes the same template document inside its own transaction, so a signup and a retire that overlap conflict, and the retry sees the new status (ADR-092).
   - `referenceVersion` is a guard counter: `timestamps: false`, and it never moves `version`.
   - Keep the cheap read before the transaction, so a bad key fails fast.
   - Add a concurrency test (decision 9).

**Audit and records**

7. **New platform audit actions** (add-only):
   - `INDUSTRY_TEMPLATE_CREATED`
   - `INDUSTRY_TEMPLATE_UPDATED`
   - `INDUSTRY_TEMPLATE_PUBLISHED`
   - `INDUSTRY_TEMPLATE_RETIRED`
   - `ORGANIZATION_INDUSTRY_TEMPLATE_CHANGED`
   
   Use targetType `industry_template` (new) or `organization`. `changes` lists the changed top-level fields; a configuration change is recorded as `{ configuration: { changed: true } }`, without copying the whole document. BN/EN labels for the platform audit screen.

8. **Records:**

## Tests (must exist and pass)
- [ ] **Create:**
  - a new key `PHARMACY` → 201 DRAFT
  - a taken key → 409
  - a bad key format → 400
  - a clone copies kinds, modules and configuration
  - a non-CORE/OPTIONAL module key → 400
- [ ] **PATCH:**
  - version moves
  - a stale version → 409
  - the reader shows the new modules after its cache window (fake clock)
- [ ] **Additive:**
  - on a PUBLISHED template, removing a kind, a module or a custom field → 422 with `details.removed`
  - adding works
  - on an unused DRAFT, a removal works
  - on a DRAFT used by one organization, a removal → 422
- [ ] **Publish/retire:**
  - DRAFT → PUBLISHED: signup with it now works (201)
  - PUBLISHED → RETIRED: signup → 422, while an existing organization on it keeps `/me/config`
  - RETIRED → PUBLISHED
  - an invalid transition → 422
  - the same status → 200, no audit
- [ ] **Change template:**
  - RETAIL → SALON (superset) → 200; `configVersion` bumped; `/me/config` gains `booking`; event and audit present
  - SALON → RETAIL (removes `booking`) → 422
  - a RETIRED target → 422
  - an unknown key → 404 or 422 (pick one and document it)
- [ ] **Concurrency:**
  - a signup and a retire of the same template at the same time: either the signup succeeds and the template is retired after it, or the signup gets 422. Never "signed up on a template retired before the signup committed".
  - Prove once that the test fails without the `$inc` (paste the output, restore).
- [ ] **Permissions:**
  - SUPPORT and BILLING get 403 on every write (they keep the reads)
  - no session → 401
  - admin cookie → 401
- [ ] **Audit:** one entry per write, none for no-ops.
- [ ] Every existing suite green, assertions unchanged except where listed; full "Done means" list.

## Out of scope
- Any UI (2.6).
- Registry validation of setting defaults or custom fields against 2.3 and 2.4 (wave 2).
- Per-field CRUD sub-endpoints (`…/custom-fields`): a field changes through PATCH of `configuration` in this card.
- Deleting templates: they are retired, never deleted.

## Risks & checks
- **The additive diff is the security of tenant data.** Unit-test it per category, and make the 422 list every removed item, not only the first.
- **A guard touch in a transaction must use the active session.** Check with the concurrency test.
- **Lint:** only `platform/industry` and `core/organization` name `industryTemplateKey`. Never widen the scope.

## Done when
- SUPER_ADMIN can create, clone, edit, publish and retire templates and move an organization to a superset template, with audit, versions and the additive rule.
- Signup and retire are serialized.
- The Opus review passes.
