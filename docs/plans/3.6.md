# Plan: card 3.6 · Booking core (resources, availability, service bookings, scheduled jobs)

Tier: **T1** (concurrency: two customers must never get the last slot) · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor or a Claude Code session · Date: 2026-10-19 · Based on commit: `main 3c0165b`

Phase 3, wave 3. **Start after 3.4 is merged** (the price snapshot comes from its quoter). Read `docs/plans/phase-3-lanes.md` (wave 3). Reserved ADR number: **ADR-122**.

## Goal
Salons, clinics, tutors and gyms take appointments:
- staff and rooms are **resources** with weekly hours and time off
- a service has a duration
- the business sees free **slots**
- a booking moves through `11 §5`

The booking module also **provides the SERVICE kind**, so SALON, CLINIC and the other service templates can finally add services in the catalog (3.2b's gap). It also starts the platform's **scheduled jobs**, which booking needs to expire holds and mark no-shows.

## Decisions
**Scope:** SERVICE bookings only. The manifest provides the kind `SERVICE`. RENTAL (nights) and EVENT (sessions) need their own rules and come in card 3.6b; record that in ADR-122 and STATUS. Walk-in services stay order lines (`11 §5.3`, card 3.5).

**Resources** (`commerce/booking`, location scope)

1. Fields: `Resource` as `09 §5.4`, plus `ResourceTimeOff`.
   - `resourceTypeKey` must be one of the template's `resourceTypes`.
   - `memberId` must be a member assigned to that location or ALL.
   - `weeklySchedule` uses local times in the organization's timezone, with no overlapping ranges per weekday.
   - `offeringIds` are ACTIVE SERVICE offerings.
   - CRUD and archive, location-scoped writes (2.4 pattern), custom fields (entity `resource`). Term `resource` labels ("চেয়ার", "ডাক্তার").

**Availability**

2. `GET /orgs/{organizationId}/availability?offeringId&variantId&locationId&date&resourceId?` (`booking.booking.read`) returns free slots for that business date.
   - Each slot is `{ startsAt, endsAt, resourceIds[] }`, in UTC with the local time shown by the screen.
   - The duration is the variant's `durationMinutes` override or the offering's, plus `bufferAfterMinutes`, which blocks the resource but is not shown to the customer.
   - Steps of `booking.slotStepMinutes` (default 15).
   - Inside the resource's schedule, outside its time-off, not before `minNoticeMinutes`, not after `maxAdvanceDays`, and with free capacity (decision 3).
   - At most one day per call, so the response stays small and no list paging is needed.

**No double booking**

3. **Capacity in 5-minute buckets** (the mechanism the card had to pick, `11 §5.1`). A collection `resource_slot_usages { organizationId, resourceId, bucketStart (UTC, 5-minute aligned), used }` has a unique index on `(organizationId, resourceId, bucketStart)`.
   - Taking a slot runs one conditional upsert per bucket (`$inc used` where `used < capacity`) inside the booking transaction. If any bucket is full, the whole transaction fails → `409 errors.slot_taken`.
   - Releasing (cancel, reschedule, no-show, hold expiry) decrements the same buckets in that state change's transaction.
   - The buckets are fixed at 5 minutes, so changing `slotStepMinutes` never invalidates stored usage. A service longer than 1440 minutes is refused by the catalog already.
   - Capacity counts HELD, REQUESTED, CONFIRMED and CHECKED_IN, as `11 §5.1` says.
   - ADR-122 records why: a per-bucket counter is checkable by an index, deterministic, and fails safely under concurrency. No locks, no "read then write".

**Bookings** (location scope, versioned, number from sequence `BOOKING`)

4. **Create** `POST /bookings` (`booking.booking.create`, `Idempotency-Key` accepted).
   - Body: `{ offeringId, variantId, locationId, contactId | contact create (3.1a shape), startsAt, resourceId?, note? }`.
   - Without a `resourceId`, the first resource that can serve the offering and is free is chosen in a stable order.
   - The price snapshot comes from the 3.4 quoter (one line, quantity 1). `depositRequired` comes from the deposit settings and the offering's `depositRule` and is stored.
   - Status:
     - with `booking.requireApproval` → `REQUESTED` (numbered)
     - otherwise → `CONFIRMED` (numbered)
     - staff-created bookings never use HELD
   - `providerMemberId` is the resource's member.

5. **Hold** `POST /bookings/holds` (same permission; for the storefront and bot later): `HELD`, no number, expires after `booking.holdMinutes` (default 10). `POST /bookings/{bookingId}/request` turns a valid hold into REQUESTED or CONFIRMED.

6. **Transitions** exactly as `11 §5.2`. Each needs `version`, is audited, and emits an event with `orderingKey: booking:<bookingId>`.

   | Endpoint | Permission | Notes |
   |---|---|---|
   | `…/confirm` | update | REQUESTED → CONFIRMED |
   | `…/reschedule` | `booking.booking.reschedule` | new slot; old buckets released and new taken in one transaction; history entry kept on the booking |
   | `…/check-in` | update | |
   | `…/complete` | update | |
   | `…/cancel` | `booking.booking.cancel` | with a reason |
   | `…/no-show` | update | |

   **Deposits:** the amount is computed and shown. Enforcement before confirm ("deposit satisfied") needs payments and arrives with card 3.8, which adds the check behind `booking.deposit.required`. Until then a deposit is informational; say so in STATUS.

7. **Lists:** `GET /bookings?locationId&date&from&to&status&resourceId&contactId&page&limit` (paged ≤ 100, index starting with `organizationId, locationId, startsAt`) and `GET /bookings/{bookingId}` with names batched.

**Scheduled jobs** (new kernel piece, first users here)

8. **`kernel/jobs`:** a registry like the event handler registry, sealed at worker start. Each job is `{ jobKey, everyMinutes, run(organizationId, now) }`.
   - The worker adds one repeatable BullMQ job per `jobKey`. A run lists the ACTIVE organizations whose job module is effective (`runAsSystem(SCHEDULED_JOB)`, inside `kernel/jobs` only; add it to the allowed files), then runs the job once per organization in its organization context, catching and reporting each organization's failure separately.
   - Jobs must be idempotent; the tests run each twice.
   - First jobs:

     | Job | Interval | Does |
     |---|---|---|
     | `booking.expireHolds` | every minute | HELD past `holdMinutes` → expired, buckets released |
     | `booking.markNoShows` | every 5 minutes | CONFIRMED past start + `noShowAfterMinutes` without check-in → NO_SHOW |

   - Reminders (`reminderLeadMinutes`) are emitted as an event only; sending SMS comes with the notification card. Record that.

**Screens** (`apps/admin`, group `bookings`)

9. Screens:
   - **Calendar** (`/[orgSlug]/bookings`): day view with columns per resource (from `md`) and a list per resource on phones; `?location=` and a date picker; tap a free slot to book; tap a booking to open it.
   - **New booking sheet:**
     1. pick the service (only bookable SERVICE offerings)
     2. pick the variant
     3. pick a free slot from the availability endpoint
     4. pick or create the contact with 3.1b's link input pattern
     5. note, then confirm
   - **Booking detail:** status, actions by permission, history.
   - **Resources** page (term `resource`): list, editor with the weekly schedule (per weekday, ranges), time off, offerings served.
   - Words from terms: `booking`, `resource`. Budget ≤ 170 KiB per route; the calendar grid and sheets are lazy.
   - **Catalog:** add the SALON service browser scenario that 3.2b deferred (the kind is now provided).

**Records**

10. ADR-122 ("Accepted (proposed)"):

## Tests (must exist and pass)
- [ ] **Availability:** schedule edges, time off, buffer, min notice, max advance, timezone (a Dhaka business date across UTC midnight), duration override per variant, a resource that cannot serve the offering is excluded.
- [ ] **Concurrency:**
  - 10 parallel creates for one last slot → exactly one 201, nine 409
  - overlapping but not identical times on a capacity-2 room → never above 2
  - reschedule into a taken slot → 409 and the old slot stays taken
- [ ] **States:** every transition of `11 §5.2` and every refused one (for example check-in on REQUESTED); releases free the buckets (assert counts).
- [ ] **Jobs:** hold expiry and no-show, each run twice (idempotent); a failing organization does not stop the others; module off → skipped.
- [ ] **Validation, permission denied, cross-org (404), cross-location (403);** module-off suite includes `booking`.
- [ ] **Price snapshot** comes from the quoter; a later price change does not change the booking.
- [ ] **Admin:** unit tests for the calendar, the sheet steps and the schedule editor. Browser: on SALON, add a stylist resource with hours and a service, book the last free slot, see it on the calendar, cancel, and the slot is free again; the catalog SALON scenario.
- [ ] Every existing suite green; full "Done means" list.
