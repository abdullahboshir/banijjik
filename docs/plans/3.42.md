## Decisions

1. **No API change.** Use `POST/GET/DELETE /pos/held-carts`, `POST /pos/sales` `unitPriceOverride` + `approvalTokens.priceOverride`, `POST /pos/returns`. Add the missing functions to `pos-api.ts`.

2. **Held carts (lazy).**
   - "Hold" on the sale screen (disabled when the cart is empty). A small sheet asks for `label` (1–40 chars, `POS_HELD_CART_LABEL_MAX_LENGTH`). `POST` the cart as `PosHeldCartPayload` (lines, contactId, note; **no prices, payments or tokens**). On 201, clear the cart. `422 POS_HELD_CART_LIMIT` shows the existing refusal pattern.
   - A "Held" list (lazy) loads `GET /pos/held-carts`. Tapping one replaces the current cart with its lines and contact, then `DELETE` with `version`. Confirm if the current cart is not empty.
   - Touch targets ≥ 56 px. Load the list and the hold sheet lazily so `/pos` stays ≤ 180 KiB.

3. **Price override.**
   - Cart line gains optional `unitPriceOverride: Money | null` (null = list price). A line action "Price" opens a sheet: amount in major units through the shared money input, then quotes (existing `quoteCart`) to show list vs override.
   - Below list: `pos.price.override` plus `ApprovalPinDialog` for `PRICE_OVERRIDE`, `amount` = Σ `(list − override) × qty` across overridden-below-list lines (same as A2-2), `subjectKey` = the instant-order approval subject already used by POS sales. Put the token on `approvalTokens.priceOverride` of the sale body. Above list: no token.
   - Without the permission, hide "Price". A 403 from the sale shows the existing failure text.
   - `buildSaleBody` sends `unitPriceOverride` only when set.

4. **Till return (lazy).**
   - "Return" on the sale screen opens a lazy sheet. The cashier pastes or searches the order number (`GET /orders?q=` if that query exists; otherwise `GET /orders` page 1 at this location, filter COMPLETED client-side to those with `posSessionId` matching the current session **or** any completed order at the location — prefer the current session's orders first).
   - Line picker: quantity to return per line (integer, ≤ sold). Disposition as the sales return sheet already sends (the API ignores it for SERVICE; keep the same field). Confirm → `POST /pos/returns` with one `Idempotency-Key` per attempt (`attemptFor`).
   - Success: show the refunded amount, then back to the sale screen. The Z-report at close already includes till returns.

5. **Credit-sale refusal browser test only.** Do **not** start reading `pos.allowCreditSale` on the till (3.9 B deviation, lead accepted). Add a browser case: owner sets `pos.allowCreditSale` to false (settings API, same as `pos-sale-api.test.ts` `setSetting`), pair, open, attach a customer, choose credit sale, assert the refusal message from the API is visible.

6. **BN and EN keys** for hold, held list, override, return, limit refusal. Mobile first. Route budget test in `pos-screens.browser.test.ts` stays green.

## Amendment 1 (2026-10-27) — price-override permission and token path

The implementer stopped: decision 3 named the PIN and `approvalTokens.priceOverride` but the Files table did not name how `pos.price.override` reaches the till or how the token reaches `POST /pos/sales`. No product change. Copy the two patterns already on the till.

**Permission (same as `canFindCustomer`).** In `pos-page.tsx`, `canOverridePrice = holdsPermission(access.config.permissions, PERMISSION_KEY.POS_PRICE_OVERRIDE)`. Pass it `PosPage` → `PosTerminal` → `PosSaleScreen` → `PosCartPanel`. Hide the "Price" action when it is false. Do not read permissions from a client hook. A 403 from the sale still uses the existing failure text.

**Token (sale-screen state, not a new global).** `CartLine.unitPriceOverride` stays on the cart. `PosSaleScreen` holds `priceOverrideToken: string | null`. The override sheet (lazy, like the payment sheet) quotes the drafted override through `quoteCart`. Below list: `ApprovalPinDialog`; `grantApproval` with `action: APPROVAL_ACTION.PRICE_OVERRIDE`, `subjectKey: INSTANT_ORDER_APPROVAL_SUBJECT`, `amount` = Σ `(list − override) × qty` across overridden-below-list lines, `locationId` = the open session's location. Import `listApprovers` and `grantApproval` from `../payments/payment-api` — do **not** edit that file, `order-approval.tsx`, or anything outside `apps/admin/src/pos/**` plus i18n catalogs. Copy PIN load/grant/error wiring from `apps/admin/src/payments/use-refund-flow.ts`. Above list: no PIN; clear the token when no below-list line remains. Pass `priceOverrideToken` into `PosPaymentSheet` next to `canFindCustomer`. `useSheetCheckout` hands it to `buildSaleBody`, which sets `approvalTokens.priceOverride` only when the token is non-null. If a below-list override or that line's quantity changes after the grant, drop the token (the cashier opens Price again). `quoteRequestOf` in `pos-sheet-quote.ts` sends `unitPriceOverride` when the line has one, so the tender total matches the sale.
