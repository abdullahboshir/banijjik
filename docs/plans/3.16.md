# Plan: card 3.16 · Dead-letter replay race fix

Tier: **T1** (kernel events, foundation code) · Planned by: Opus 5.5 (lead) · Date: 2026-10-22 · Based on commit: `main 072fb8f`

One part, one branch `s/3.16-dead-letter-replay-race`, no screens. No file overlap with 3.15 (which owns `ordered-event-worker.test.ts`), 3.7, 3.8, M.5 or 3.5a. It needs its own folder: run it after 3.15 in `banijjik-m2`, or as a cloud agent.

## Goal
A replay that an operator asks for is never marked REPLAYED unless a job that will really run (or already ran) exists in the queue. Today the replayer can mark it REPLAYED while BullMQ silently ignores the new job, and the event's handler then never runs again.

## The defect (found by the 3.15 session, confirmed by the lead)
1. On the last failed attempt `processJob` in `apps/api/src/kernel/events/event-worker.ts` calls `recordFailure` → `deadLetter`, which writes the row as FAILED, and only then rethrows. BullMQ moves the job to `failed` after the rethrow. Between the two, the job is still `active`.
2. In that gap an operator can ask for a replay (`replayDeadLetter`: FAILED → REPLAY_REQUESTED).
3. `DeadLetterReplayer.requeue` (`dead-letter-replayer.ts`) gets the old job, sees `isFailed()` is false, does not remove it, and calls `enqueue` with the same `jobId`. BullMQ ignores an `add` whose `jobId` already exists.
4. The replayer still writes REPLAYED. A moment later the old job becomes `failed`. Result: the row says REPLAYED, nothing is queued, and the operator cannot ask again (`replayDeadLetter` accepts only FAILED rows).

The window is a few milliseconds, but the result is a lost event with a record that says the opposite, so it is fixed before more ORDERED handlers arrive (3.8 adds the first one).

## Decisions
1. **Fix it in the replayer, not in the worker.** Moving the dead-letter write after BullMQ's `failed` transition (for example into the worker's `failed` event) would lose the row when the process dies in between, which is worse. The replayer instead decides from the old job's state.
2. **The replayer reads the old job's state once with `job.getState()`** and acts as follows:

   | Old job | Action | Row |
   |---|---|---|
   | none, or state `unknown` (removed) | `enqueue` | REPLAYED |
   | `failed` | `remove()`, then `enqueue` | REPLAYED |
   | `completed` | nothing (a replayed job already ran; this happens only when an earlier tick added it and stopped before writing REPLAYED) | REPLAYED |
   | `active`, `waiting`, `delayed`, `prioritized`, `waiting-children` | nothing | stays REPLAY_REQUESTED; the next poll looks again |

   The REPLAYED write keeps its existing filter `status: REPLAY_REQUESTED`, so it can never overwrite a newer FAILED row.
3. **"Not yet" is not an error.** A deferred row is neither reported through `reportError` nor counted by `replayPending`. Log it at `debug` with the event name `events.dead_letter_replay_deferred` (fields `eventId`, `handlerKey`, `jobState`).
4. **Shape of the code.** `requeue` returns a local union `type RequeueOutcome = "QUEUED" | "ALREADY_RAN" | "OLD_JOB_STILL_IN_QUEUE"`, and `tryRequeue` returns `true` only for `QUEUED`. The state table lives in one small private function (for example `decideRequeue(state)`), so `requeue` stays under the ADR-041 limits. The union is private to the kernel; nothing goes into `packages/contracts` (no new public enum, status or event).
5. **Failing test first.** Commit the new unit test for the "old job active" case before the fix (it must fail on the current code), then the fix. Name both commits in the handoff.
6. **The `DeadLetterReplayerOptions.queue` type stays `Queue<EventJobData>`.** The unit tests use a fake queue whose `getJob` returns a stub with `getState()` and `remove()`, in the style of the existing `NO_OLD_JOB`.
7. **No change** to `dead-letter.ts`, `event-worker.ts`, `dead-letter-admin.ts`, the dead-letter schema, contracts, the API or the screens.

## Risks & checks
- A state the table does not list (a new BullMQ version): treat it like "still in queue" (wait), log it at `warn` once per row per tick, never REPLAYED.
- Two worker processes running replayers at once: both may see `failed`; the second `remove` or `add` must not throw out of the loop (it is caught per row today) and REPLAYED is written once thanks to the status filter. The review checks this path.
- Review (strict T1): the lead reads `dead-letter-replayer.ts` line by line against the table in decision 2 and confirms the first test fails on `main`.

## Done when
