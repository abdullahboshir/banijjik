# Plan: card 3.34 · A payment reversed after the request was closed

Tier: **T1** (dues, receivables and the books) · Planned by: Opus 5.5 (lead) · Date: 2026-10-24 · Based on commit: `main c3976ab` · **Starts after 3.24 merges** (both change the accounting payment posting and the order payment adapter)

Reserved ADR number: **ADR-140**. Owner decision (2026-10-24): "follow the industry standard, and keep an option".

## Session parts
One part, API only. Branch `s/3.34-api-reversal-after-close`. T1 review by the lead. The setting appears in the existing generic settings screen; no new screen.

## Goal
A payment can be reversed (a bounced cheque, a payment recorded by mistake) after its request was closed: a booking cancelled with its fee retained, a cancelled enrollment. Today the reversal silently brings the closed amount back into dues, and nobody chose that. After this card:
- **Default, the industry standard:** a reversed payment never happened, so what the closure kept is owed again. It shows in dues. The books already agree: the retained cancellation fee stays as income, and `CUSTOMER_ADVANCES` holds a debit balance for that request (a receivable) until the customer pays again. This is how Xero, QuickBooks and Odoo treat a bounced payment on a settled invoice.
- **Option `WRITE_OFF`:** the organization forgives it. The reversal lowers the closed request's total to the new net paid, so it leaves dues. Where the closure had recognised income (a booking's retained fee), the write-off posts bad-debt expense against `CUSTOMER_ADVANCES`, so the books match the dues.

## Where the case really occurs (checked in the code)
| Closure | What it leaves | Reversal possible? |
|---|---|---|
| Booking cancel or no-show, part refunded to store credit | summary `refunded > 0` | No: reversal is refused (`paymentReversalHasRefundError`) |
| Booking cancel or no-show, the whole net paid kept as the fee | total = fee, refunded = 0 | **Yes** |
| Order cancel (3.23) | the whole net paid goes to store credit | No (refunded > 0); an unpaid order has nothing to reverse |
| Enrollment cancel (3.27) | total capped at net paid, refunded = 0 | **Yes** |

## Decisions
1. **The summary knows that its request is closed.** `PaymentSummary` gets `closedAt: Date | null` (schema default `null`, so existing rows need no migration). A new repository method `closeAtTotal({ organizationId, requestType, requestId, total, now })` sets the total and `closedAt` in one update. The three closure paths call it instead of `setTotal`:
   - `settle-request-termination.ts` (booking cancel and no-show)
   - `order-payment-adapter.ts` `settleCancellation`
   - `enrollment-payment-adapter.ts` `capTotalAtNetPaid`

   `setTotal` stays for edits of an open request. No module outside payment learns about `closedAt`.
2. **Setting** `payment.reversal.closedRequest` in the payment manifest: `{ kind: "ENUM", values: ["REOPEN_DUE", "WRITE_OFF"] }`, `systemDefault: "REOPEN_DUE"`, no location override, client-visible. The constant and the enum go in `@banijjik/contracts/payment`. The reversal reads the setting inside its transaction.
3. **`REOPEN_DUE` is today's behaviour**, now chosen on purpose and tested. Nothing in the data changes. The README and ADR-140 say why it is the standard.
4. **`WRITE_OFF`:** for each allocation of the reversed payment whose summary has `closedAt`, in the reversal transaction, after `restoreAllocation`:
   - `written = total − (allocated − refunded)` after the restore; if `written > 0`, lower the total to the new net paid (`closeAtTotal`, so `closedAt` stays);
   - record it on the reversal payment: `writeOffs: readonly { requestType, requestId, amount: Money }[]`, an empty array when nothing was written off. The payment document is the record; no new collection.
   - Audit `PAYMENT_DUE_WRITTEN_OFF` (new in contracts) per written-off request, with the amount.
   - An open request (no `closedAt`) is never written off: its due reopens, as with any reversal.
5. **Books for a write-off** (accounting, in the existing handler that posts `payment.payment.reversed`): for each `writeOffs` row, a posting rule per request type decides whether the closure had recognised income:
   - `BOOKING`: yes, the retained fee (`draftCancellationFee`). Post Dr `BAD_DEBT_EXPENSE`, Cr `CUSTOMER_ADVANCES` for the written amount. The posting key is `bad_debt_written_off`, in the same journal as the reversal or right after it with its own idempotency key `(paymentId, requestId)`.
   - `ENROLLMENT`: no. Until card 3.31 an enrollment payment stays in `CUSTOMER_ADVANCES` and no income is recognised at cancel, so the reversal already brings advances back to zero. No write-off journal. 3.31 must revisit this rule (write it in ADR-140 and in the 3.31 row of STATUS).
   - `ORDER`: not reachable (table above). The rule posts nothing; a test proves the reversal is refused.
6. **New system account** `BAD_DEBT_EXPENSE` (type EXPENSE) in `SYSTEM_ACCOUNT_CODE` and the seeds. Existing organizations get it through the same catch-up as 3.11 A2's commission accounts. Count tests in contracts change.
7. **Industry independence:** nothing reads an industry or a request kind outside the posting rule table of decision 5, which keys on `PAYMENT_REQUEST_TYPE` (a generic contract enum, like the existing revenue-state rules).
8. **Records:** ADR-140 ("Accepted (proposed)"): closed summaries, the two policies and the standard default, the write-off journal, the 3.31 note. Payment and accounting READMEs. `docs/11 §7` note. Handoff `docs/handoffs/3.34-api.md` with the §11 table. STATUS row 3.34.

## Tests (must exist and pass)
- [ ] **Default REOPEN_DUE, booking:** cancel inside the fee window with the deposit kept as the fee, reverse the deposit payment → the booking shows in dues with the fee amount; the trial balance shows `CANCELLATION_FEE_INCOME` unchanged and `CUSTOMER_ADVANCES` with a debit balance of the fee; a new payment clears both.
- [ ] **Default REOPEN_DUE, enrollment:** cancel with period 1 partly paid, reverse that payment → the period shows in dues with the kept amount.
- [ ] **WRITE_OFF, booking:** same flow → the booking leaves dues, `writeOffs` on the reversal has the fee, the journal has Dr `BAD_DEBT_EXPENSE` / Cr `CUSTOMER_ADVANCES`, and the advances balance for the case is back to zero.
- [ ] **WRITE_OFF, enrollment:** the period leaves dues, `writeOffs` has the amount, and no bad-debt journal is posted.
- [ ] **Open request:** with WRITE_OFF, reversing a payment of an open (not cancelled) booking reopens its due and writes nothing off.
- [ ] **Order:** reversing a payment of a cancelled paid order is refused as today.
- [ ] Rows from before this card (`closedAt` missing) read as open; a booking cancelled before this card behaves as REOPEN_DUE (write it in the handoff).
- [ ] A second delivery of the reversal event posts the bad-debt journal once (idempotency key).
- [ ] An organization seeded before this card gets `BAD_DEBT_EXPENSE` on catch-up.
- [ ] Setting validation (unknown value → 400), permission denied for changing the setting, cross-org reversal 404, cross-location 403 (existing reversal rules unchanged).
- [ ] Existing payment, booking, order-payment and enrollment-payment suites green.
- [ ] T1 §11 items 1, 2, 3, 5, 6, 7, 11, 19, 20, 21, 22, 24, each with a named test or file.

## Out of scope
- Refunds on enrollment cancel (3.32) and enrollment revenue (3.31). A screen for written-off amounts (a later report in 3.10). Collecting a reopened due automatically. Changing when a reversal is allowed.

## Risks & checks
- `closeAtTotal` must replace `setTotal` in all three closure paths; a missed path silently behaves as an open request. The tests above cover each path.
- The write-off and the restore run in the same transaction as the reversal payment.
- Never write off more than the closure kept: `written` is computed after the restore, from the stored summary, never from the request.
