Tier: **T1** (kernel; every ledger posting will depend on it) · Planned by: Opus 5.5 (Claude) · Implemented by: a Claude Code session · Date: 2026-10-17 · Based on commit: `main 9ceb629`

Phase 3, wave 2. Can start now. It touches only `apps/api/src/kernel/events/**`, contracts and one platform screen. Read `docs/plans/phase-3-lanes.md` (wave 2) first. Reserved ADR number: **ADR-115**.

## Goal
Phase 1 review M12 and Phase 2 review: the event worker runs jobs five at a time with independent retries, so the events of one record can be handled out of order. For example, an order's `cancelled` could be posted before its `created`. Accounting (3.8), commission accruals (3.11) and summaries (3.10) need the events of one record in the order they happened.

This card adds the industry-standard guarantee: **ordered per stream, parallel across streams** (the Kafka partition-key model on top of our transactional outbox). It also adds a way to replay a dead-lettered event, because an ordered stream waits behind it.

## Decisions
**Streams**
1. **Ordering key on publish.** `publishEvent(type, payload, { orderingKey? })`:
   - `orderingKey` names the record whose events must stay in order, for example `order:<orderId>`, `booking:<bookingId>` or `contact:<contactId>`. It is the entity name plus the domain id; never a user value.
   - With a key, `publishEvent` takes the next **stream sequence** from a counter keyed by `(organizationId, orderingKey)` in the same transaction: a new platform-DB collection `event_streams { eventStreamId, organizationId, orderingKey, lastSequence }`, unique on `(organizationId, orderingKey)`, updated with `$inc` in the session.
   - It stores `orderingKey` and `streamSequence` on the outbox event.
   - Without a key, nothing changes: existing events stay unordered.
   - Publishers adopt keys in their own cards. 3.1a's contact events get `contact:<contactId>` here as the first user, as a small change in `commerce/contact`.

2. **Ordered handlers.** `EventHandler` gains `ordering: "ORDERED" | "UNORDERED"` (required, so every handler states it; existing handlers say `UNORDERED`).
   - For an ORDERED handler and an event with a key, the runner reads the handler's position `event_stream_positions { handlerKey, organizationId, orderingKey, lastSequence }` (platform DB, unique on the three keys).
   - **`streamSequence === lastSequence + 1`:** run the handler, then set the position to `streamSequence` in the same transaction as the processed marker. Effect, marker and position commit together.
   - **`streamSequence <= lastSequence`:** an earlier delivery already handled it, so treat it as ALREADY_PROCESSED.
   - **`streamSequence > lastSequence + 1`:** an earlier event of the stream has not been handled yet. Re-queue the job with a short delay (start 1 s, doubling, at most 60 s) **without spending one of its attempts**, using BullMQ's delayed retry (`moveToDelayed` + `DelayedError`). After a configurable maximum wait (default 24 h), log `events.stream_waiting` at warn level every hour, so a stuck stream is visible.
   - An event of an ORDERED handler whose module is off for the organization (`SKIPPED_MODULE_OFF`) still **advances the position**, so turning a module off never blocks a stream.
   - Unordered handlers and events without a key behave exactly as today.

3. **Dispatch order.** The dispatcher already claims by `nextAttemptAt`. Add a tiebreak on `streamSequence` and an index `{ status, nextAttemptAt, streamSequence }`. Correctness does not depend on dispatch order (decision 2 waits), but dispatching in order avoids needless waits.

**Dead letters**
4. **Stuck streams and replay.**
   - A dead-lettered event of an ORDERED handler blocks its stream for that handler. That is intended: skipping it would post the next entry on a wrong base.
   - **Replay:** `POST /api/v1/platform/event-dead-letters/{eventDeadLetterId}/replay` (new platform permission `platform.events.replay`, SUPER_ADMIN) re-adds the job with fresh attempts and marks the dead letter `REPLAYED` (`replayedAt`, `replayedByPlatformUserId`; audited).
   - `GET /api/v1/platform/event-dead-letters?status=` lists them, paged.
   - **Skip:** a SUPER_ADMIN may also mark a dead letter `SKIPPED` with a required reason, which advances the handler's position past it. It is audited, and the screen explains that a skip means the handler's effect never happened and must be fixed by hand (for example a reversing journal entry).
   - **Platform screen:** "Failed events" under the platform menu. It shows the list (event type, organization, handler, error summary, attempts, time) with Replay and Skip actions (confirm sheet; reason required for Skip). Mobile card layout, like the other platform lists.

5. **`OUTBOX_STATUS.DEAD`.** Check that the dispatcher sets DEAD after `MAX_DISPATCH_ATTEMPTS` (M12 asked to set or remove it; the code names it) and add the test if it is missing. A DEAD outbox event is listed on the same screen as "not dispatched", with Replay (resets it to PENDING).

## Tests (must exist and pass)
- [ ] **Publish:**
  - three events with one key get sequences 1, 2, 3
  - two keys count separately
  - a rolled-back transaction leaves no gap that blocks the stream (the counter rolls back with it; assert the next publish gets the same number)
  - no key: no sequence
- [ ] **Ordered handler, out of order:** deliver sequence 2 before 1 (enqueue directly). Event 2 waits without losing attempts; after 1 is handled, 2 is handled. The final order of effects is 1, 2 (assert with a recording handler).
- [ ] **Exactly once:** a repeated delivery of a handled sequence is ALREADY_PROCESSED. A handler that throws rolls back the effect, the marker and the position together.
- [ ] **Parallel streams:** events of two keys are handled concurrently (one stream waiting does not block the other).
- [ ] **Module off:** the position advances on a skipped event, and the next event runs.
- [ ] **Dead letter:**
  - after the last attempt, the stream waits
  - replay runs it and the stream continues
  - skip with a reason advances and audits
  - both refused without `platform.events.replay` (403)
  - the list is paged
- [ ] **DEAD outbox event:** set after the maximum dispatch attempts; replay resets it to PENDING.
- [ ] **Unordered handlers** and keyless events: existing worker tests unchanged and green.
- [ ] **Platform screen:** unit tests for the list, Replay and Skip (the reason is required); the platform browser suite stays green.
- [ ] Every existing suite green; full "Done means" list.

## Risks & checks
- **The delayed re-queue must not count as an attempt:** verify against the installed BullMQ version (`DelayedError`). If the API differs, stop and ask before inventing a counter.
- **Hot stream counters:** one document per record, written only by that record's own transaction, which already serializes on the record's `version`.
- Stop and ask if the existing worker tests would need a weakened assertion.

## Done when

- A failed event can be replayed or skipped from the platform screen.
