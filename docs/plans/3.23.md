## Session parts

## Goal
Today an order cannot be paid: payment's request-reader registry has no `ORDER` reader (`POST /payments` with `requestType: ORDER` answers 422), the sales `PaymentSummaryReader` is a stub in `routes/sales-tenant-router.ts` that always returns zero (every order shows `UNPAID`), and confirm refuses every order once `sales.advance.required` is not `NONE`. After this card:
- staff record payments and refunds against an order;
- the order shows its real payment status in the detail and in the list (without N+1);
- the advance rule (`11 §4.4`) is enforced on confirm;
- cancelling an order turns what was paid into store credit, once.

## Decisions
1. **One request-reader factory.** New `routes/payment-request-readers.ts` exports `buildPaymentRequestReaders(): RequestReaderRegistry` that registers BOOKING (existing reader) and ORDER (new). `payment-tenant-router.ts` and `accounting-event-handlers.ts` both use it instead of building their own registry. Any other `new RequestReaderRegistry()` in `routes/` uses it too.
2. **ORDER reader** (`routes/order-request-reader.ts`), built only from a function exported by `sales/index.ts` (for example `buildOrderSnapshotReader()`; no Mongo class in the index):
   - returns `undefined` for a missing order, another organization's order, a `DRAFT` (no number, no summary) and a `CANCELLED` order, so payment answers its existing "request not found/unpayable" error;
   - `total` = `totals.grandTotal`; `contactId` (may be null for an instant sale); `locationId`;
   - `revenueState`: `AFTER_REVENUE` when the status is `COMPLETED` (later also `SHIPPED`/`DELIVERED`, Phase 5), else `BEFORE_REVENUE`.
3. **Order payment port** replaces `PaymentSummaryReader` in sales (`application/ports/sales-ports.ts`), required everywhere (no optional dependency):
   ```ts
   export interface OrderPaymentPort {
     /** Inside the place / instant transaction. Idempotent (payment's ensureSummary). */
     initializeSummary(input: { organizationId; orderId; contactId: ContactId | null; locationId; total: Money; now: Date }): Promise<void>;
     /** Inside the edit transaction. Refuses a total below the net paid amount. */
     updateTotal(input: { organizationId; orderId; total: Money; now: Date }): Promise<void>;
     readTotals(orderId: OrderId): Promise<PaymentTotals>;
     /** One query for a page of orders (list endpoint). Missing ids read as zero. */
     readTotalsMany(orderIds: readonly OrderId[]): Promise<ReadonlyMap<OrderId, PaymentTotals>>;
     /** Net paid (allocated − refunded) in minor units, read with the active session. */
     readNetPaid(input: { organizationId; orderId }): Promise<Money>;
     /** Moves the net paid amount to store credit (cancel). Idempotent per order. */
     settleCancellation(input: { organizationId; orderId; contactId: ContactId | null; locationId; actorUserId: UserId | null; now: Date }): Promise<void>;
   }
   ```
   Adapter `routes/order-payment-adapter.ts`, built like `booking-deposit-adapter.ts`. `PaymentTotals.paidMinor` = `allocated`, `refundedMinor` = `refunded` of the summary.
4. **Summary lifecycle:**
   - Place (`place-order`) and instant sale (`instant-order`) call `initializeSummary` in their transaction with `grandTotal`.
   - Edit of a PLACED or CONFIRMED order calls `updateTotal` in the edit transaction. A new `grandTotal` below the net paid → `422` rule key `ORDER_TOTAL_BELOW_PAID` (contracts `sales-rule-key.ts` + message key in both catalogs). Nothing is refunded automatically.
   - No backfill: no organization is live yet (pre-launch), so an order placed before this card has no summary and stays unpayable. Write this in the handoff.
5. **Advance rule** (`11 §4.4`; the contracts enum `NONE | FIXED | PERCENT | FULL` stays; `DELIVERY_CHARGE` from doc 11 is dropped until delivery charges exist in Phase 5, and doc 11 is corrected):
   - New setting `sales.advance.value` (integer ≥ 0, default 0) in the sales manifest settings and contracts: FIXED = minor units in the organization currency; PERCENT = 0–100.
   - Pure domain function `requiredAdvance(grandTotal: Money, rule, value): Money` in `sales/domain/`: NONE → 0; FIXED → `min(value, grandTotal)`; PERCENT → clamp value to 0–100, `Math.ceil(grandTotal × value / 100)`; FULL → `grandTotal`. Integer math only.
   - Confirm reads `readNetPaid` **inside its unit of work** and refuses with the existing `422 ADVANCE_NEEDS_PAYMENTS` when net paid < required. A required advance of 0 confirms.
   - Auto-confirm at place keeps today's rule (only when the rule is NONE). Auto-confirm after a payment arrives is **out of scope** (follow-up for the storefront/bot phase).
6. **Cancel settles what was paid** (`11 §4.1`: "any advance is refunded or converted to store credit"):
   - Generalize `settle-booking-deposit.ts` so the request type is a parameter (rename to a request-neutral name, keep a thin booking wrapper so booking callers do not change), then call it for ORDER with `mode: CANCEL`, `feeMode: CANCEL_FEE_MODE.NONE`: the whole net paid amount becomes a `CANCELLATION` store credit entry for the order's contact.
   - It runs in the cancel transaction, after the stock release and before the versioned order update, for both `CancelOrderUseCase` and the auto-cancel job (the job already calls the use case).
   - An order with net paid > 0 and **no contact** cannot be cancelled: `422 ORDER_CANCEL_NEEDS_CONTACT` (rule key + message keys). Staff refunds first (`POST /refunds`) or attaches a contact. A PLACED order always has a contact, so this only guards odd data.
   - "Once": the versioned order update in the same transaction stops a second cancel; the settlement helper's own idempotency (the booking tests) still holds for ORDER.
7. **Reads:** every `payments.read` call in sales uses `readTotals`; the list (`read-order.use-cases.ts`) calls `readTotalsMany` once per page. The payment summary repository gets `findByRequests(organizationId, requestType, requestIds)` (one `$in` query on the existing summary index; check the index starts with `organizationId, requestType, requestId` and say so in the handoff).
8. **Remove the stub** `paymentReaderOf` in `routes/sales-tenant-router.ts` and every "card 3.8 replaces …" comment in sales and contracts (`PAYMENT_STATUS` doc comment, `SALES_ADVANCE_REQUIRED` comment, the README line).
9. **Records:** ADR-137 ("Accepted (proposed)"): ORDER as a payment request, revenue state rule, summary lifecycle, `ORDER_TOTAL_BELOW_PAID`, the advance formula and `sales.advance.value`, cancel to store credit, no backfill. `docs/11 §4.4` corrected (enum, value setting). Sales and payment READMEs. Handoff `docs/handoffs/3.23-api.md` with the §11 table. STATUS row 3.23.
