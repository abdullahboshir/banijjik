# Plan: card 3.39 · POS device limit and the devices screen

Tier: Part A T2 (limit check with a lock, a location-scope fix) · Part B T2 (screen) · Planned by: Opus 5.5 (lead) · Date: 2026-10-26 · Based on commit: `main 90d2de60`

## Owner decision (2026-10-26)
The owner asked for the industry standard (Lightspeed, Vend/Lightspeed X, Loyverse and Square for Retail work this way):
- **The number of tills is part of the plan the business pays for.** The platform sets it in the package editor of the platform panel (card 1.8, already built). A business cannot raise its own limit in its settings.
- **A business manages its tills in its own settings:** it sees "2 of 3 devices used", adds a device (gets a one-time pairing code), and revokes one. A revoked device frees its slot.
- **More tills are bought:** an add-on pack adds one more each time.
- **Downgrade:** devices that already exist keep working. Only adding a new one is refused while the business is at or over the limit. This is the same rule as locations and members (`10-MODULE-CATALOG.md` §9 "Limit semantics").
- **Numbers (seed proposals, editable in the platform panel):** STORE 0, CHAT 0 (no POS module), SHOP 1, BUNDLE 2 (unchanged). `ADDON_POS` adds the POS module **and one device** (today it adds none, so a business that buys it cannot add a till). The new pack `PACK_POS_DEVICE` adds one device.

## Decisions — Part A
1. **Limit check on create.** `CreatePosDeviceUseCase` gets a required port `deviceLimit: PosDeviceLimit`. Inside the existing `unitOfWork.run`, before `devices.insert`, it calls `deviceLimit.assertCanAdd(organizationId, () => devices.countActive())`. The adapter in `routes/pos-adapters.ts`:
   - takes the organization limit lock (`buildOrganizationLimitLock()`, newly exported from `core/organization/index.ts`, add-only);
   - counts the ACTIVE devices of the whole organization, all locations;
   - calls `buildLimitGuard(orgConfig).assertBelow(LIMIT_KEY.POS_DEVICES, count)`.

   At the limit the answer is `422 LIMIT_REACHED` (the existing error). The lock makes two concurrent creates at the last free slot run one after the other, as for locations.
2. **What counts:** every device with status `ACTIVE`, paired or still waiting for its code. `REVOKED` devices do not count. A device whose code expired unused still counts until it is revoked. The screen shows it as "code expired" with a Revoke button.
3. **Repository:** `countActive(): Promise<number>` (`countDocuments({ status: ACTIVE })`, active session passed). New index `{ organizationId: 1, status: 1 }` on `pos_devices`.
4. **Usage read:** `GET /pos/devices/usage` (`pos.device.manage`) → `PosDeviceUsageResponse { activeDeviceCount: number }`, counted over the whole organization. The limit itself comes from `/me/config` `limits.posDevices` (`null` = unlimited), so no limit logic is copied to the client.
5. **Location scope (defect found while planning):**
   - `GET /pos/devices` today lists the devices of every location in the organization. `POST /pos/devices/:posDeviceId/revoke` revokes a device at any location. Both ignore the caller's location assignments (AGENTS.md "Location-scoped writes validate `locationId`"). The use case doc comment even says "at the locations the caller manages".
   - Fix: the controller passes `allowedLocationIds` from `readTenantCaller()`, the same as create does.
   - List filters `locationId ∈ allowed` (no filter for `"ALL"`). A `?location=` outside the allowed set → `locationForbidden()` (403).
   - Revoke reads the device first (`findById`; not found → 404), then a location outside the allowed set → `locationForbidden()` (403), then revokes.
   - The usage count stays organization-wide (decision 4): it is a number only, and it is what the limit counts.
6. **Packages (seed data):**
   - `ADDON_POS` gets `limitIncrements: { posDevices: 1 }`: a module add-on with increments, through a small helper next to `moduleAddOn`.
   - New `PACKAGE_KEY.PACK_POS_DEVICE`: a limit pack `{ posDevices: 1 }`.
   - i18n `package.PACK_POS_DEVICE.name`: EN "Extra POS device", BN "অতিরিক্ত পিওএস ডিভাইস".
   - Existing databases keep their stored `ADDON_POS` row, because the seed never overwrites. Before launch that is test data only; the handoff tells the platform admin to edit `ADDON_POS` in the package editor once. No migration.
7. **Docs:** `10-MODULE-CATALOG.md` §9 add-on table (`ADDON_POS` "+ `posDevices +1`", new row `PACK_POS_DEVICE`), module README of `pos` (limit rule, location scope).

## Decisions — Part B
8. **Settings page `settings/pos-devices`.**
   - Menu entry in the `pos` manifest: `menuKey: "pos.devices"`, surface ADMIN, `groupKey: "settings"`, `labelTermKey: "menu.pos.devices"`, `path: "settings/pos-devices"`, permission `pos.device.manage`, `settingsTopicKey: SETTINGS_TOPIC.SALES`.
   - Hidden when the module is off: manifest-driven, and the generated "module off" test covers it.
9. **Page content (mobile first, card list on small screens, touch targets ≥ 44 px):**
   - a usage line "2 of 3 devices used" (`activeDeviceCount` and `limits.posDevices`; "unlimited" for `null`);
   - a location filter (`?location=`, page filter only);
   - one card per device: name, location, state ("paired, last seen …" / "waiting for pairing, code expires …" / "code expired" / "revoked") and Revoke (confirm dialog, sends `version`, 409 → reload message);
   - "Add device": a sheet with name and location (only the caller's locations). The answer shows the 8-digit pairing code once, large, with its expiry time and the instruction "open POS on the till and enter this code". The sheet says the code is shown only once.
   - At or over the limit, "Add device" is disabled with the `LimitNotice` ("Your package allows N devices. Buy an extra POS device or upgrade your package."). A 422 `LIMIT_REACHED` from the API shows the same notice (race).
10. BN and EN keys for every label and state; the page stays within the admin route budget.

## Out of scope
- Prices of the add-on and pack (P2).
- A per-organization limit override in the platform panel. Today only module overrides exist; a business gets more devices by buying `PACK_POS_DEVICE`.
- Issuing a fresh pairing code for an existing device: revoke and add a new one.
- Held carts, till returns, price-override UI (3.9 B gaps, a later card).

## Risks & checks
- The lock must be taken **inside** the same transaction as the count and the insert. Otherwise the concurrent test is flaky; it must pass ten runs in a row locally.
- The location fix changes the list for location-scoped managers. The existing POS browser test runs as the owner (`ALL`), so it should be unaffected; run it on CI.
- Count tests in `packages/contracts` (package keys, menu entries in B) move with other branches: run them after each rebase.
