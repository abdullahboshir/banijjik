## Goal
Businesses book things other than a timed service:
- **Rentals** (a room, a car, a hall) for a number of hours, days or nights.
- **Events** (a class, a tour, a show) with dated sessions and limited seats.

Both use the existing booking lifecycle, deposits, holds and calendar.

## Decisions
1. **Kinds provided:** the booking manifest adds `RENTAL` and `EVENT` to `providesKinds`. Offering readers accept the three kinds and return a view keyed by `kind`; the SERVICE fields stay unchanged.
2. **Rental time model:** a rental booking has `startsAt`, `endsAt` and `quantity` = number of rate units.
   - HOUR: `endsAt = startsAt + quantity hours`.
   - DAY: `quantity` calendar days later in the organization's timezone (use the `timezone.ts` helpers; a DST day is not 24 h).
   - NIGHT: `startsAt` is the check-in day at `checkInTime`; `endsAt` is `quantity` days later at `checkOutTime`.
   - `quantity` must be within `minUnits..maxUnits`, else `422 BOOKING_RENTAL_UNITS_OUT_OF_RANGE`.
3. **Rental capacity:** reuse the 5-minute `resource_slot_usages` counters and the conditional `$inc` inside the booking transaction, over the whole `startsAt..endsAt`. **A rental is capped at 31 days** so one booking cannot write thousands of buckets; longer stays are PLAN (card 3.7), as `11 §2` says. Resources come from `resourceTypeKeys`.
4. **Rental price and deposit:** the price is the pricing quoter's line for `quantity` units. The deposit is the kind details' `depositAmount` when set, else the existing org/offering rule in `domain/deposit.ts`. Enforcing the deposit is card 3.8; this card only computes and stores `depositRequired`.
5. **EventSession** (location scope, versioned): `eventSessionId`, `offeringId`, `variantId`, `locationId`, `startsAt`, `endsAt`, `capacity`, `seatsSold`, `resourceIds[]`, `status` (`SCHEDULED | CANCELLED | COMPLETED`), audit fields.
   - Endpoints: `GET/POST /event-sessions`, `GET /event-sessions/:eventSessionId`, `PATCH` (capacity may grow, never below `seatsSold`; the time may change only while `seatsSold = 0`), `POST …/cancel`.
   - Permissions `booking.eventSession.{read,create,update,cancel}` added to contracts and grants (OWNER, MANAGER all; STAFF and VIEWER read).
6. **Event booking:** `POST /bookings` for an EVENT offering requires `eventSessionId` and `quantity` (seats).
   - Seats use a conditional increment on the session in the booking transaction: `seatsSold + quantity ≤ capacity`, else `409 BOOKING_EVENT_SOLD_OUT`.
   - Sales close `salesCloseMinutesBefore` before start: `422 BOOKING_EVENT_SALES_CLOSED`.
   - Cancelling or expiring a booking releases its seats in the same transaction as the status change, never below 0 and never twice.
   - The booking copies `startsAt/endsAt` from the session. No waitlist (`allowWaitlist` stays reserved).
7. **Event holds:** HELD event bookings count in `seatsSold` too and release on expiry. Extend the existing `booking.expireHolds` job to release seats.
8. **Cancelling a session** cancels its non-terminal bookings in batches of 100 (one transaction per batch, idempotent job `booking.cancelEventSession`). The full deposit is marked refundable (the refund or credit itself is card 3.8). Event `booking.eventSession.cancelled` carries ids only.
9. **Auto-complete:** the existing 5-minute jobs gain two rules (`11 §10`): EVENT bookings complete after the session end; RENTAL bookings complete after `endsAt` plus the new setting `booking.completeGraceMinutes` (default 60; add to the booking settings schema). No-show applies to RENTAL and EVENT like SERVICE.
10. **Screens (Part B):**
    - the catalog kind-details form for RENTAL and EVENT;
    - an "Event sessions" list and sheet (create, edit, cancel with confirmation, seats sold of capacity);
    - the new-booking sheet gets a rental mode (units, resource, computed end and price) and an event mode (pick a session, seats);
    - the calendar shows rentals as multi-day bars and events as session blocks.
    - Mobile layout checked; admin script budget 180 KiB (lazy-load the new sheets).
11. **Records:** ADR-133 ("Accepted (proposed)": rental time model and the 31-day cap, session seat counter, release rules, session cancel job); `09` and `11 §5.5` notes; booking README; STATUS row 3.6b.

## Interfaces & types
```ts
export type OfferingBookingView =
  | ServiceOfferingView
  | RentalOfferingView // kind "RENTAL": rateUnit, minUnits, maxUnits?, resourceTypeKeys, checkInTime?, checkOutTime?, depositAmount?
  | EventOfferingView; // kind "EVENT": salesCloseMinutesBefore, allowWaitlist

export interface EventSessionRepository {
  /** Conditional $inc; false when the session is sold out. */
  reserveSeats(input: { eventSessionId: EventSessionId; seats: number }): Promise<boolean>;
  /** Never goes below 0. */
  releaseSeats(input: { eventSessionId: EventSessionId; seats: number }): Promise<void>;
}
```
`eventSessionId` is a UUID v7 from `newId()`; add `EventSessionId` to `@banijjik/ids` if missing.

## Tests (must exist and pass)
- [ ] **Rental:** HOUR, DAY and NIGHT end-time rules including a DST change day; units below min or above max → 422; over 31 days → 422; two parallel bookings for the last unit → one wins.
- [ ] **Event:** book seats; sold out → 409; parallel last seats → one wins; sales closed → 422; cancel and hold expiry release seats exactly once (run twice); seats never below 0.
- [ ] **Session:** create; edit rules (capacity vs `seatsSold`, time change with seats sold refused); cancel → bookings cancelled in batches; job run twice.
- [ ] **Auto-complete** of events and rentals (with grace), idempotent.
- [ ] **Deposit** computed for rental (`depositAmount`) and event; no payment enforcement here.
- [ ] **Permission denied, validation error, cross-org, cross-location** for sessions and for rental/event bookings; the module-off suite stays green.
- [ ] Existing booking suites stay green (SERVICE unchanged).
- [ ] **Admin (Part B):** unit tests for rental mode and event mode of the new-booking sheet; browser: create a session, book 2 seats, see seats sold, cancel the session.

## Out of scope
- Payments and deposit enforcement (3.8). Accounting already handles the kinds (3.8c).
- Waitlist, recurring sessions, online booking forms (Phase 4), bot tools (Phase 5).
- Long stays and hostel beds (card 3.7).

## Risks & checks
- Bucket writes of multi-day rentals: a test with a 31-day rental checks the transaction still succeeds.
- Seat counter drift: a test that books, cancels, expires and reschedules in a loop ends with the exact `seatsSold`.
- Time zones: all arithmetic in the organization's timezone through the existing helpers; no `new Date(y, m, d)` in server code.
- Merge order with 3.8 and 3.7 in booking files: rebase, keep both sides.

## Done when
- A business sells rentals by hour, day or night and events with limited seats; capacity and seats never oversell; cancellations release them.
- The Opus review passes (Part A); CI green.
