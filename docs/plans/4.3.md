## Decisions

1. Browse is public. Writes require customer session or valid guest session **and** website.checkoutEnabled=true, WEBSITE effective, organization FULL access mode, allowed kind/capability and active public location. READ_ONLY/suspended/unpublished storefront cannot transact. Public catalog never exposes hidden custom fields, costs, margin, supplier data or staff-only notes.
2. Keep OTP accounts as-is. website.guestCheckout is a registered BOOLEAN, default true under the owner's requested launch scope; tenant may turn it off. No guest implicitly becomes an account. A guest submitting an existing phone must not receive the corresponding contactId, membership price, credit, history or personal fields.
3. Guest session: POST /guest-session creates 32 random bytes as an opaque secret in host-only sf_guest cookie, httpOnly/Secure/SameSite=Lax, path /api/v1/storefront, absolute expiry 30 days. Store hash only, scoped organization + guestSessionId (UUID v7). Reject session of another org. This random secret is authentication material, not an entity ID. No token in URL/localStorage/events/idempotency body.
4. Inspected contact.schema.ts: ACTIVE contacts have a unique organizationId/phoneE164 index. Preserve it. Guest Contact creation occurs transactionally on first checkout: create a provisional contact with name/source STOREFRONT and **no canonical phoneE164 or email**; retain the submitted E.164 phone only in a private CheckoutContactSnapshot owned by this checkout/session. Do not phone-dedupe into an existing contact or create CustomerAccount. Reuse only this session's provisional contact. The trusted public-order adapter passes a validated recipient snapshot for this order, satisfying pickup/delivery contactability without claiming a verified contact phone. Staff creates retain the existing contact-phone requirement. Booking/enrollment use the provisional contact ID and the owned checkout snapshot for contactability; never publish it. This explicit ADR-P4-C amendment avoids weakening the phone uniqueness rule or letting an attacker reserve another person's login phone.
5. CheckoutAccess is the sole access authority for tracking, claim, export and replay authorization. A valid session must match its current owner; the request's immutable contact snapshot is not an additional ownership requirement. No phone+orderNumber lookup. Claim requires the original guest session plus a valid OTP-authenticated account whose verified phone matches the checkout snapshot. CAS transfers access to that account and revokes guest access to this checkout, without merging contacts or changing economic request history. Immutable creationPrincipalKey remains unchanged. Re-authentication on a new domain does not auto-claim another guest session.
6. If a guest loses the cookie, show contact-business help without leaking existence or reissuing access by supplied phone. Session renewal cannot extend absolute expiry. Rate-limit guest creation and checkout per IP/session/org (contracts constants: 10 sessions/IP/hour; 10 checkout attempts/session/10 minutes; existing public surface bucket remains). Configurable future tuning, no silent unlimited fallback.
7. One checkout belongs to one organization/location/currency; cart may contain PRODUCT, SERVICE, RENTAL, EVENT and PLAN request groups. Product lines become one Order; each booking group becomes its own Booking; each plan group its own Enrollment; all are linked by checkoutId. Different locations require separate checkouts with clear UI feedback; no cross-location implicit split. Bound a checkout to 20 selections, total serialized input 64 KiB and the existing per-kind quantity/range limits; reject before transactions. Booking deposits are part-payment of total, not added twice. PLAN quote explicitly separates recurring fee, admission fee and refundable security deposit using the existing enrollment rules; the public breakdown must show the entire upfront obligation.
8. Preserve existing kinds: walk-in SERVICE is not silently converted into an online product sale. Online service uses scheduled booking unless its offering is WALK_IN_ONLY; then display visit-in-person and reject reservation. RENTAL uses exclusive/range capacity; EVENT references eventSessionId and seat quantity; PLAN follows billing-period/start-date/resource rules. No industry branches.
9. Quote input contains offering/variant/quantity/modifier choices, selected schedule/location, destination and custom fields; never prices, discounts, total, tax, source, actor, contactId, status or permission fields. Strict schemas reject extra fields. Use existing server quoter and integer minor units/currency, the same promotion/quantity/variant rules as admin. Guest has no account-only pricing.
10. Quote is a persisted, five-minute, principal-bound snapshot (quoteId UUID v7) with input hash, currency, calculated price breakdown, delivery rule versions and catalog/config versions. No stock/capacity hold on quote. Checkout compares FINAL owner-produced totals/lines/fees with the accepted quote before committing, using one session and operation clock. Mismatch aborts all checkout writes and returns PRICE_CHANGED; the client explicitly requests and accepts a fresh quote outside the aborted transaction. Never promise a newly persisted quote in a response that promises no writes. Reuse owner pricing; no website reimplementation or second uncoordinated price read.
11. Checkout transaction creates/loads owned contact, checkout identity, draft/place product order, booking holds/request transitions, pending enrollments, summaries, audit/outbox and request links together. Nested existing UnitOfWork joins it. Refuse any group that fails; no partial successful checkout. Generate checkoutId before commands and pass through all events/links. No parallel writes on a shared Mongo session; process bounded groups sequentially.
12. Business command adapters are explicit public APIs. Staff routes keep their permissions unchanged. Customer adapters receive actorUserId:null, the derived contact, one verified location and internal source STOREFRONT; **never** fabricate staff roles, ALL locations or owner exemption. Refactor only the named source/command seam; reuse existing money/capacity/sequence logic.
13. Product orders are PLACED (auto-confirm only according to existing settings and advance guard), reserve stock, not completed. Pick-up pay-at-store and COD courier/rider methods come from real enabled capabilities and configured zones. Full COD is provided by 4.3-COD. Payment at order submit is not recorded; COD collects at delivery.
14. Booking uses HoldBooking then RequestFromHold; deposit checks remain authoritative. Initialize its payment summary in the hold transaction. An unpaid/part-paid required deposit remains HELD with expiry; without a deposit request/confirm follows booking.requireApproval. A real receipt that satisfies the deposit transitions the hold in the SAME payment transaction. Receipt and expiry share a booking write fence and payment summary; an already expired/terminal hold refuses payment even before the expiry job runs. Expiry settles actual partial advances using settleBookingTermination with fee NONE, releases capacity and emits outbox atomically. GET tracking never mutates status. Replay never recreates expired capacity.
15. PLAN customer request is PENDING even when staff create would activate today. Add trusted creationMode CUSTOMER_REQUEST to enrollment command (not public body). Existing staff behavior unchanged; admission fee, first-period fee and security deposit are calculated by current module rules. Staff activation/payment pathways remain authoritative. Do not bypass a guardian/payer required field.
16. Custom-field definitions come from resolver with storefront visibility. Only writable storefront fields accepted; hidden required fields must have an approved server default or the offering is not online-requestable, with a public explanation key. REFERENCE inputs expose only eligible public choices or an owned inline related-contact intake; never a tenant-wide contact search. Customer cannot set billToContactId or arbitrary guardian ID.
17. Inspected kernel middleware uses organization-only namespaces on tenant requests. A0 MUST add a trusted storefront namespace including organization and customerAccountId/guestSessionId, plus current authorization before replay. Reuse the kernel store; never let the client select a namespace. Durable checkout.unique(organizationId,creationPrincipalKey,idempotencyKeyHash) and input hash commit with the business effects, retaining original result IDs after HTTP replay expiry. Ownership is mutable only in CheckoutAccess. A claim/revocation must invalidate guest replay authorization as well as tracking. A new key cannot consume an already submitted quote again: unique organizationId/quoteId binds one checkout; a conflicting key returns conflict and the authorized existing checkout reference.
18. Browser creates one key at submit and keeps it for network retries; changed cart requires a new quote/key. Do not recreate keys automatically on timeout. No raw cookie secret in stored response; guest session is established **before** checkout. Domain IDs/quotes use newId(); authentication entropy uses approved crypto only.
19. /me/requests projects order/booking/enrollment states and own payable amounts; enrollment dues use enrollmentPeriodId as payment requestId (ADR-139), not enrollmentId. Return minimal status/history/public reference and terms; exclude internal audit, other contacts, accounting account IDs, raw provider payloads.
20. Private tracking is no-store/noindex. Availability and quote are no-store. Public browse may use 4.2 public projection cache but checkout never trusts it. Runtime pricing/capacity checks are independent of design snapshots.
21. All public mutations must pass same-origin guard at storefront proxy and authenticated/guest namespace checks at API. Audit actorUserId remains null with explicit customerAccountId/guestSessionId metadata in the sanctioned audit context; never invent a User ID.
22. Implement all five kinds with real APIs and real errors. No placeholder product pages or fake booking dates. No online gateway claims: /checkout/:checkoutId/pay remains unavailable until 5.17.

## Interfaces & types

```ts
type PublicSelection =
  | { kind: "PRODUCT"; offeringId: string; variantId: string;
      quantity: number; modifierOptionIds: readonly string[] }
  | { kind: "SERVICE"; offeringId: string; variantId: string;
      startsAt: string; resourceIds: readonly string[] }
  | { kind: "RENTAL"; offeringId: string; variantId: string;
      startsAt: string; endsAt: string; resourceIds: readonly string[] }
  | { kind: "EVENT"; offeringId: string; variantId: string;
      eventSessionId: string; quantity: number }
  | { kind: "PLAN"; offeringId: string; variantId: string; startsOn: string;
      resourceIds: readonly string[] };
interface CheckoutSelection {
  selectionId: string; selection: PublicSelection;
  customFields: Readonly<Record<string, unknown>>;
}
interface PublicQuoteRequest {
  locationId: string; selections: readonly CheckoutSelection[];
  fulfillment: { method: "PICKUP" }
    | { method: "COURIER" | "OWN_RIDER"; address: DeliveryAddress };
}
interface CheckoutRequest {
  quoteId: string;
  contact: { name: string; phone: string; customFields: Readonly<Record<string, unknown>> };
}
type CheckoutPrincipal =
  | { type: "CUSTOMER"; customerAccountId: string; contactId: string }
  | { type: "GUEST"; guestSessionId: string };
interface CheckoutRequestLink {
  selectionIds: readonly string[];
  requestType: "ORDER" | "BOOKING" | "ENROLLMENT";
  requestId: string; publicNumber: string | null;
  status: string; paymentRequired: Money; holdExpiresAt: string | null;
}
interface CheckoutResponse {
  checkoutId: string; locationId: string; total: Money;
  requests: readonly CheckoutRequestLink[];
}
interface PublicQuoteResponse {
  quoteId: string; expiresAt: string; total: Money;
  lines: readonly { selectionId: string; subtotal: Money; discount: Money;
    tax: Money; total: Money; amountRequiredBeforeConfirmation: Money }[];
  deliveryCharge: Money;
}
interface StorefrontCommandContext {
  organizationId: string; locationId: string; contactId: string;
  checkoutId: string; actorUserId: null;
}
interface PublicOrderCommands {
  place(context: StorefrontCommandContext, input: {
    selections: readonly CheckoutSelection[];
    recipient: { name: string; phoneE164: string };
    fulfillment: PublicQuoteRequest["fulfillment"] }): Promise<CheckoutRequestLink>;
}
interface PublicBookingCommands {
  request(context: StorefrontCommandContext,
    input: CheckoutSelection): Promise<CheckoutRequestLink>;
}
interface PublicEnrollmentCommands {
  request(context: StorefrontCommandContext,
    input: CheckoutSelection): Promise<CheckoutRequestLink>;
}
interface CheckoutCommands {
  quote(principal: CheckoutPrincipal, body: PublicQuoteRequest): Promise<PublicQuoteResponse>;
  checkout(input: { principal: CheckoutPrincipal; idempotencyKey: string;
    body: CheckoutRequest }): Promise<CheckoutResponse>;
}
```

Custom fields remain unknown only at transport boundary and are validated into the owner's typed values before domain use.

All under existing storefront organization prefix. Keep old /my directory routes unchanged.

New events website.checkout.created/claimed are IDs only. Error constants CHECKOUT_QUOTE_EXPIRED, CHECKOUT_PRICE_CHANGED, CHECKOUT_LOCATION_MISMATCH, CHECKOUT_NOT_AVAILABLE, CHECKOUT_CAPACITY_UNAVAILABLE; reuse owners' validation/conflict codes where possible. ## Audit correction: receipt, replay and privacy seams (2026-10-28)

A0 extends existing IdempotencyOptions with a trusted resolveNamespace callback and an authorizeReplay callback. The storefront registration requires both; callbacks run after session/tenant/capability resolution. The namespace is a technical key (new contract STOREFRONT discriminator), never a business scope/context. Authorization rechecks current CheckoutAccess for a stored checkoutId before returning any cached body. Existing staff behavior is regression-tested unchanged. Replay responses contain no contact snapshot; durable receipts store IDs/hash only where possible.

A3B exposes booking payment lifecycle commands through booking/index.ts. A3P introduces the required internal RequestPaymentLifecycle port, composed by request type:

```ts
interface RequestPaymentLifecycle {
  beginReceipt(input: { organizationId: string; requestType: PaymentRequestType;
    requestId: string; now: Date }): Promise<void>;
  endReceipt(input: { organizationId: string; requestType: PaymentRequestType;
    requestId: string; now: Date }): Promise<void>;
}
```

ReceivePayment calls beginReceipt before reading the request/summary and endReceipt after allocation, within its active transaction. Booking beginReceipt conditionally increments paymentFenceVersion on the booking, checks HELD expiry and rejects terminal states; endReceipt reads updated summary and runs the existing request transition when deposit is satisfied. Other request types have explicit composed implementations preserving their existing guards, never an optional unregistered fallback. Booking expiry and cancellation touch the same fence before settlement. The booking request reader reports acceptsPayments from this shared eligibility policy, not unconditional true. Return a payment acknowledgement only after the booking transition commits.

Verified A3B anchors: application/hold-booking-persist.ts, application/jobs/expire-holds.job.ts, application/ports/payment-ports.ts and application/use-cases/booking-status-transitions.use-cases.ts in booking. Add application/booking-payment-lifecycle.ts and index export. Existing summary initialization becomes idempotent; RequestFromHold cannot reset paid amounts. Existing settleBookingTermination performs refunds/credit, never a second website settlement implementation. Any nested retry helper must join the outer transaction without retrying an aborted inner group; propagate transient failure for the entire outer callback to retry.

A5B implements existing CustomerDataExportParticipant and CustomerErasureParticipant through public module ports. Export includes authorized checkout/access/recipient data within existing bounds. Erasure revokes access and redacts non-retained PII through the shared privacy policy, preserving required economic evidence and immutable amounts. A private redaction overlay can hide historical PII without rewriting ledger history. Guest access/export follows the same authorization and absolute expiry; session TTL deletion alone is not checkout PII deletion. Phase 6.3 retention policy remains a launch gate; no new retention duration is invented here.

Required tests: P4-01 through P4-06 and P4-17 in [assurance](phase-4-assurance.md); paid/part-paid hold expiry, payment just after clock expiry before worker, claim then replay as guest/account, account blocked after successful checkout, duplicate quote with a new key, commit-before-response crash after HTTP TTL, and final owner totals changing after quote. Test real composed payment/booking commands, not only mocked lifecycle ports.
