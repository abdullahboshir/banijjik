## Decisions — Part A

1. **Till cash reversal (T1).**
   - `buildReversalPayment` sets `posSessionId: original.posSessionId ?? null` (same field `ReceivePaymentUseCase` already writes).
   - `expectedCash` subtracts cash `REVERSAL` the same way it subtracts cash `REFUND` (float + cash IN − cash REFUND − cash REVERSAL). Update the unit test name and add a REVERSAL row.
   - Z-report `received` stays the `IN` totals (out of scope to add a reversed line on the Z-report). Expected cash on close is what must change.
   - No new permission, event or index. The existing `{ organizationId, posSessionId, method, direction }` index already groups reversals once `posSessionId` is set.

2. **Cashier contacts.** In `SYSTEM_ROLE_GRANTS.contact`, `CASHIER` becomes `{ only: [CONTACT_CONTACT_READ, CONTACT_CUSTOMER_ACCOUNT_READ] }` — find a customer at the till, do not create or update. `STAFF` keeps `CONTACT_DAILY_KEYS`. Add an API test: a cashier `POST /contacts` → 403; `PATCH` → 403; `GET` still 200.

3. **`approverMemberId`.** Rename `PaymentApprovalSnapshot.approverUserId` → `approverMemberId` in contracts, the payment schema, the mongo mapper, `reverse-payment` / `refund-payment-helpers` / `sales-return-approvals` snapshots, the admin payment-detail view, and tests. No dual-read, no migration: there are no production payments yet. Existing test databases are thrown away per run.

4. **Typed payloads and queries (no `as unknown as` in the listed production files).**
   - **Accounting handlers** (`post-orders`, `post-payments`, `post-sales-returns`, `post-stock`, `post-bookings`, `post-enrollments` / refunds / commission / expenses — every production `as unknown as EventEnvelope` in `application/handlers/`): `handle` takes `EventEnvelope`. `switch (envelope.type)` narrows through `EventPayloadMap`. Handlers with `alsoHandles` switch on each type; they do not cast the whole envelope. Followers that step over other types already return without reading payload.
   - **Controllers:** `order.controller.ts` `deleteDraft` and `list`, and `booking.controller.ts` availability / list / resource list, read `response.locals["validated"].query as OrderDeleteQuery` (etc.), the same pattern as `report.controller.ts` and `pos.controller.ts`. Never `request.query as unknown as`.
   - **Inventory repositories:** `lean<StockMovementRecord>()` (and the matching record type per file) instead of `as unknown as`. Inserts that today use `document as unknown as StockReservationDocument` become a small mapper to the schema type, field by field, no double cast.
   - Tests may keep `as unknown as` on fakes (out of scope).

## Decisions — Part B

5. **`placeOrder` idempotency.** In `apps/admin/src/sales/order-api.ts`, stop calling `newId()` per invocation. Use the `attemptFor` helper (move it to a shared admin module `apps/admin/src/lib/attempt-key.ts` and make `pos/attempt-key.ts` re-export it, **or** duplicate the 15-line helper next to `order-api.ts` if moving it touches POS while 3.42 is open — prefer the re-export only when POS is not being edited in parallel). Key the attempt on the JSON body text (`orderId` is in the URL; body is `{ version, approvalToken? }`). Same body → same key → replay. Changed version or token → new key. Unit-test `placeOrder` with a mocked `apiFetch` that the second call with the same version reuses the first key.
