## Goal
- Routes marked **I** in `14` refuse a missing or malformed `Idempotency-Key`. Replaying the same key with the same body returns the original response. The same key with a different body → `422 IDEMPOTENCY_MISMATCH`. The roadmap's 1.5 Done: "replaying the same idempotent request returns the original response".
- Every business change in the modules that exist writes an append-only **AuditLog** entry in the same transaction as the change. Owners and managers can read them through `GET /orgs/{organizationId}/audit-logs`.

## Decisions
**Idempotency (`kernel/idempotency`)**
1. **Middleware** `idempotency()` is applied per route by the module router (`14` marks routes with **I**). `routes/v1.ts` builds it once and passes it to router builders, like `permission`.
   - The header `Idempotency-Key` must be a UUID (any version, `14 §2`). Missing → `400 VALIDATION_ERROR` field `Idempotency-Key`, `validation.idempotency_key_required`. Malformed → `validation.idempotency_key_invalid`.
2. **Scope:** on tenant routes the scope is `{ scopeKind: "ORGANIZATION", scopeId: organizationId }`; on user routes it is `{ "USER", userId }`. A key never collides across orgs or users.
3. **Record** `IdempotencyRecord` (PLATFORM DB, `idempotency_records`, tenancy **NONE**: kernel-owned technical data spanning user and tenant scopes, accessed only by kernel code with explicit scope filters):
   - Fields: `idempotencyRecordId`, `scopeKind`, `scopeId`, `idempotencyKey`, `requestHash`, `status` (`IN_PROGRESS | COMPLETED`), `lockedUntil`, `responseStatus?`, `responseBody?`, `expiresAt` (24 h), timestamps.
   - Indexes: unique `{ scopeKind, scopeId, idempotencyKey }`; TTL on `expiresAt`.
   - Field names follow `09 §5.8` plus the scope fields; update `09 §5.8` in one line.
4. **Request hash:** sha-256 of `method + " " + route pattern (request.baseUrl + request.route.path) + "\n" + canonical JSON of the validated body` (keys sorted recursively). Mount the middleware **after** `validate()` so the hash covers the parsed body.
5. **Flow:**
   1. **Claim:** insert `IN_PROGRESS` with `lockedUntil = now + 60 s` (an atomic insert; the unique index decides races).
   2. **On a duplicate key**, load the existing record:
      - different `requestHash` → `422 IDEMPOTENCY_MISMATCH`
      - `COMPLETED` → replay the stored status and body with the header `Idempotency-Replayed: true`, and do not run the handler
      - `IN_PROGRESS` with `lockedUntil` in the future → `409 CONFLICT` `errors.idempotency_in_progress` with `Retry-After: 1`
      - `IN_PROGRESS` with an expired lock → reclaim it (atomic conditional update on `lockedUntil`) and run
   3. **Store:** when the handler answers 2xx, capture the JSON body (wrap `response.json` before calling the handler) and mark `COMPLETED`.
   4. **Release:** when the handler answers non-2xx or throws, delete the record, so the client may retry with the same key.
   - Only successes are replayed. `Set-Cookie` and other headers are never replayed.
6. **Limit, written in ADR-089:** the record is not inside the business transaction, so protection is "at least once, replay after success". A crash between commit and `COMPLETED` leaves `IN_PROGRESS` until the 60 s lock expires; the retry then runs the handler again. Business invariants (unique slug, sequence numbers, ledger idempotency per source) remain the final guard. Money and stock cards must keep their own source-level uniqueness (as `11 §10` already requires for journals).
7. **Apply now** to `POST /me/orgs` (`14 §4`, I). Later cards apply it to their I routes. Messages: `errors.idempotency_in_progress`, `validation.idempotency_key_required`, `validation.idempotency_key_invalid` in contracts `KERNEL_ERROR_MESSAGE_KEYS` / validation keys and both catalogs.

**Append-only guard (kernel, reusable for ledgers, ADR-014)**
8. `registerModel` gains an optional `appendOnly: true`. A kernel plugin then throws `AppError(INTERNAL, "errors.append_only_model")` on:
   - every update, replace and delete query
   - `bulkWrite` operations other than `insertOne`
   - `save()` of an existing document

   Inserts are allowed. Applies even under `runAsSystem`, except `runAsSystem(MIGRATION)`, so retention or migrations can be written deliberately later. The registry meta-test of 1.3 is extended: append-only models carry the marker.

**Audit (`core/audit`, SYSTEM module)**
9. **AuditLog** (TENANT DB, `audit_logs`, tenancy ORGANIZATION, `appendOnly`), fields per `09 §5.8`: `auditLogId`, `organizationId`, `actorUserId?`, `actorMemberId?`, `action`, `entityType`, `entityId`, `changes`, `requestId`, `systemReason?`, `occurredAt`. `actorPlatformOperatorId` arrives with platform audit in 1.8 (platform DB copy).
   - Indexes: `{ organizationId, occurredAt: -1, auditLogId: -1 }`, `{ organizationId, entityType, entityId, occurredAt: -1 }`, `{ organizationId, actorUserId, occurredAt: -1 }`.
10. **Kernel port** `AuditRecorder { record(entry: { action: AuditAction; entityType: AuditEntityType; entityId: string; changes?: AuditChanges }): Promise<void> }` (`kernel/audit/`).
    - The audit module implements it. Organization, actor, member, request id and system reason come from the request context, never from the caller.
    - It must run inside `withTransaction` (it joins the active session); without one it throws `errors.audit_needs_transaction`, so an audit entry can never be written without its change, or the change without it.
    - `routes/v1.ts` passes the recorder into module builders.
11. **Vocabulary in contracts:** `AUDIT_ACTION`, using the event-name style `<module>.<entity>.<pastTenseVerb>` (`organization.organization.created`, `iam.role.created`, `iam.role.updated`, `iam.role.archived`), and `AUDIT_ENTITY_TYPE` (`organization`, `location`, `member`, `role`).
    - `AuditChanges = Readonly<Record<string, { from?: AuditValue; to?: AuditValue }>>` with `AuditValue = string | number | boolean | null | readonly string[]`.
    - Modules pass only safe fields: never password hashes, tokens or secrets. Write that rule in the audit README.
12. **Wire the existing actions** (add-only lines inside their existing transactions):
    - `CreateOrganizationUseCase` records `organization.organization.created` (to: name, slug)
    - the three role use cases record `iam.role.created` (to: name, permissionKeys), `iam.role.updated` (from/to of the changed fields), `iam.role.archived`
13. **Endpoint** `GET /orgs/{organizationId}/audit-logs`, permission `audit.log.read`:
    - filters `entityType`, `entityId`, `actorUserId`, `from`, `to` (ISO dates)
    - `?page&limit` (≤ 100), sorted newest first
    - response `AuditLogSummary { auditLogId, action, entityType, entityId, actorUserId?, actorMemberId?, changes, requestId, systemReason?, occurredAt }`
    - The read is narrowed by nothing else: audit is org-level, not location-level.
14. **Permissions and grants:** contracts `PERMISSION_KEY` gains `audit.log.read` (sensitive). The audit manifest declares it. The grant table row is `audit`: OWNER ALL, MANAGER READ, others NONE (`10 §10`). The `audit.retentionDays` setting arrives with settings (2.x).

## Tests (must exist and pass)
Idempotency (real replica set; a probe route, and `POST /me/orgs`):
- [ ] **replay:** the same key and body twice → the same status and body, the second with `Idempotency-Replayed: true`, and the handler ran once (one org created)
- [ ] the same key with a different body → `422 IDEMPOTENCY_MISMATCH`; a missing key → 400; a non-UUID key → 400
- [ ] two concurrent requests with the same key → one runs; the other gets `409` (in progress) or the replay. Never two runs.
- [ ] a handler that fails with 4xx or 5xx releases the key: a retry with the same key runs again
- [ ] an expired `IN_PROGRESS` lock (fake clock) is reclaimed
- [ ] keys are scoped: the same key from two users, or in two orgs, never collides
- [ ] the hash ignores key order in the body and changes with the route

Append-only:
- [ ] `updateOne`, `deleteMany`, `findOneAndUpdate`, `replaceOne`, a `bulkWrite` update and `save()` of a loaded document all throw on an append-only probe model; `insertMany` works; `runAsSystem(MIGRATION)` may delete

Audit:
- [ ] creating an org writes one `organization.organization.created` entry with actor, member, requestId; role create/update/archive write their entries with `changes`
- [ ] **atomicity:** a failure injected after the audit write rolls back both the change and the entry; `record()` outside a transaction throws
- [ ] `GET /audit-logs`: owner 200 with filters and paging; MANAGER 200 (READ); **permission denied:** STAFF 403; **cross-org denied:** org B's entries never appear in org A's list, and B's path is 404 for A's owner; **validation error:** a bad date → 400
- [ ] no audit `changes` contain a password hash or token (grep the stored entries in the API tests)

All with `--force`: lint, format:check, typecheck, test, build; `npm run test:tools`.

## Risks & checks
- **Response capture:** wrap `response.json` only. If a handler uses `send`/`end` directly, the middleware refuses with `INTERNAL` (`errors.idempotency_unsupported_response`), so nothing is silently not stored. Test it.
- **Express 5 route pattern:** confirm `request.baseUrl + request.route.path` is available where the middleware runs (it is mounted on the route, after `validate`).
- **Disk:** the system MongoDB binary as before (`MONGOMS_SYSTEM_BINARY`, `MONGOMS_VERSION_CHECK=false`, `--env-mode=loose`). No downloads.
