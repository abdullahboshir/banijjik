## Goal
Today cancelling an enrollment only tells staff a `refundableAmount` (policy `NONE`, `UNUSED_PERIODS` or `PRORATED`). The money cannot be returned: the payment reader refuses every period of a cancelled enrollment, so a refund is refused too.

After this card:
- staff can refund up to the policy amount, per period, to store credit or by a payment method;
- refunds follow the existing refund approval rules;
- the books lower the income that 3.31 kept at cancel.

- payment: `refund-payment.use-case.ts` and `refund-payment-helpers.ts` (`validateRefundRequests`, `isApprovalRequired` / `resolveRefundApproval`, `creditStoreCreditOnRefund`, `updateRefundSummaries`), `application/ports/request-reader.ts`, `receive-payment.use-case.ts`

- ADR-139, ADR-142 (3.31)

## Decisions
1. **Refunds go through the existing refund endpoint.** There is no new refund route. Staff refund the periods of a cancelled enrollment with the normal payment refund (`POST /payments`, direction REFUND, allocations to the period ids). The method is either a payment method or `STORE_CREDIT`. Approval works as for every other refund: the refund-without-approval permission, or an approval token.

   Refunding inside the cancel request was rejected. A method refund would need the refund use case inside the cancel transaction, and its own approval flow there.
2. **The amount each period may refund is fixed at cancel.** Add a per-period variant of `refundableAmount`, `refundableByPeriod(periods, today, policy)`, that returns `Money` per period id. Its rules are unchanged and still count only PAID periods.

   In the cancel transaction, before `capPeriodSummaries`, store each period's amount on the period as `refundableOnCancel: Money` (new optional field, set once). The cancel response keeps `refundableAmount` (the sum) and adds `refundableByPeriod: { enrollmentPeriodId, amount }[]`.
3. **Readers state whether a request accepts payments and how much may be refunded.** `RequestReader.read` results get two new fields:
   - `acceptsPayments: boolean`, required in every reader. Booking and order keep their behaviour and answer `true` wherever they answer today.
   - `refundLimit: Money | null`: `null` means no extra limit.

   The enrollment reader then:
   - for a period of a **cancelled** enrollment, returns the period with `acceptsPayments: false`. The limit is `refundableOnCancel` (zero when unset), minus what was refunded on that period since the cancel.
   - for every other period, returns `acceptsPayments: true` and `refundLimit: null`.
   - for `WAIVED` periods, keeps answering undefined.
4. **Payment enforces the two fields, request-neutrally.**
   - Receive refuses a request with `acceptsPayments: false`, with the same error a missing request gets today (no new message to staff).
   - The refund validation, inside the refund transaction, refuses an allocation above its `refundLimit` with `PAYMENT_REFUND_ABOVE_LIMIT` (new rule key in contracts, `422`, `details: { requestId, limit }`).
   - The read and the check use the active session, so two parallel refunds cannot both pass (guide §11 item 2). A unit test and an API race test prove it.
5. **What "refunded since cancel" means.** The payment summary is the only counter. No second counter is kept, because the asynchronous payment handler would update it late.
   - In the cancel transaction, store the summary's `refunded` amount on the period as `refundedAtCancel: Money`.
   - The reader computes the limit in the refund transaction: `refundableOnCancel − (summary.refunded − refundedAtCancel)`, never below zero.
6. **Books.** A refund of a cancelled period is posted by the existing payment posting with the allocation's revenue state. After 3.31 every cancelled period with money kept is recognised, so the reader returns `AFTER_REVENUE`, and `refund_after_revenue` debits `ACCOUNTS_RECEIVABLE`. The kept income must drop by the same amount:
   - On `payment.payment.refunded`, the enrollment posting handler (3.31's `accounting.postEnrollments`, following the payment's stream as booking accounting does, ADR-136) posts `enrollment_period_refund_revenue` for each allocation to a cancelled enrollment period: Dr the income account the period closed with, Cr `ACCOUNTS_RECEIVABLE`, for the allocated amount.
   - The account is `REVENUE_PLAN` when the period has an `enrollment_period_revenue` journal, else `CANCELLATION_FEE_INCOME` (3.31 decision 6). The posting-source port answers this from the period's `revenueRecognizedOn` and the cancel date (recognised before the cancel date → `REVENUE_PLAN`), not by reading journals.
   - Idempotent per (payment, period): source key `sourceType ENROLLMENT`, `sourceId` = the period id, `postingKey` = `enrollment_period_refund_revenue:<paymentId>`. If the posting key type does not allow a suffix, stop and ask.
   - A refund of a non-cancelled period posts nothing new: the amount is owed again and shows in dues, as today.
7. **Store credit refunds** use the endpoint's `STORE_CREDIT` method, which `creditStoreCreditOnRefund` already handles, with entry kind `REFUND`. No new store credit kind.

### Part B
8. **Screens.**
   - The enrollment cancel dialog (3.7 B) shows the refundable amount per period after cancel.
   - A cancelled enrollment's detail page shows a "Refund" button on each period whose remaining limit is above zero. It opens the existing refund sheet (`apps/admin/src/payments/…`, the one 3.30 added) with the period's request and its limit as the maximum, and offers store credit and the payment methods.
   - An approval-required answer shows the existing approval prompt.
   - i18n BN and EN, mobile, budget 180 KiB.
   - Tests: a unit test of the per-period limits on screen; one browser test that cancels a paid GYM enrollment under `UNUSED_PERIODS` and refunds the future period to store credit.

- U1 `refundableByPeriod splits UNUSED_PERIODS and PRORATED per period and ignores unpaid periods`
- U2 `the limit is the stored amount minus what was refunded since cancel`
- A1 `cancel stores each period's refundable amount and returns it per period`
- A2 `a payment on a cancelled enrollment period is refused`

- A6 `refunding a period kept as a cancellation fee lowers CANCELLATION_FEE_INCOME; refunding a recognised period lowers REVENUE_PLAN`. Assert that AR and `CUSTOMER_ADVANCES` net to zero for the period.
- A7 `the refund revenue entry posts once on event replay`
- A8 `booking and order refunds and payments behave as before` (their suites green, plus one test each that the readers answer `acceptsPayments: true`)
- A9 `policy NONE stores zero and refuses every refund of the cancelled periods`
- Cross-org: another organization's period id → 404 as today.

## Out of scope
- Refunds inside the cancel request (decision 1).
- Partial-period refunds of PARTIAL periods: the policy rules stay as they are.
- Security deposits.
- Changing the refund approval rules.

## Risks & checks
- Decision 4 is the T1 heart: the limit must be read and checked in the refund transaction.
- Decision 3 changes a shared port. Every reader must set `acceptsPayments` explicitly; no default value.
