## Goal

A staff member can take a storefront product order through courier or own-rider delivery, record the customer's COD payment once, receive money from courier/rider, handle failed attempts and returned goods, and see correct stock, due, commission, reports and balanced accounts.

## Decisions

1. Fulfillment is an Order concern, carrier operations live in courier/delivery, payment owns collection, accounting owns posting. No website balance or stock ledger. Existing FULFILLMENT_METHOD COURIER/OWN_RIDER and shipping statuses become implemented; do not create a competing fulfillment status for the order.
2. Shipping requires a confirmed or packed order, validated destination, an associated manual consignment/assignment, all required advances satisfied, and location permission. Lines and totals freeze at first shipment. First ship commits reserved stock and emits the original order revenue/COGS event once. Failed delivery does not release stock or reverse revenue.
3. Redelivery is the **same goods still in transit**: create a new attempt/consignment reference and set SHIPPED again; never commit stock or recognize revenue again. RTS is terminal. To sell returned goods again, create a new order; never reship a terminal RTS order.
4. Entire-order delivery only in this phase. No partial shipment or partial delivery. RTS accepts RESTOCK/DAMAGED only when all shipped units have physically returned. Owner approved loss reconciliation on 2026-10-28: a failed shipment with missing goods closes through a separate manager-approved DELIVERY_LOSS_CLOSED transition with RESTOCK/DAMAGED/LOST quantities summing to every shipped line. It is never mislabeled as successful RTS. S3 and the loss/recovery accounting/tests below are required Phase 4 scope.
5. Collection occurs only on DELIVERED. Amount due is server-read order grandTotal minus net allocated payments; currency must match. Zero-due order records delivery without a zero Payment. Positive amount produces one IN payment COD_COURIER or RIDER_CASH, allocated to the order, in the **same transaction** as DELIVERED. Customer payment status becomes paid even while the courier still owes the business.
6. Courier settlement clears identified collection Payment IDs, not arbitrary order totals. Validate one organization, courierKey, currency and authorized location set; each payment is eligible once. Batch <=100, exact gross=sum selected payment amounts, courierCharges>=0 and <=gross, netReceived=gross-charges. receivedVia is CASH/BANK/BKASH/NAGAD. Underpayment/overpayment is a validation error and stays unsettled for explicit correction; no hidden balancing journal.
7. Rider handover identifies rider and unpaid-over collection IDs, with gross calculated by server. Staff records actual receiving account with permission delivery.cash.handover; the rider cannot approve its own handover. No implication that a POS register received cash unless a real open posSessionId is explicitly validated and existing register port participates transactionally.
8. Financial settlement/handover records are append-only; mistakes create a reversal with reason, manager approval and linked reversal ID. A unique reversal reference stops double reversal. Reversal mirrors journals and reopens eligible collection claims only when the original has no dependent correction; otherwise refuse with explicit conflict. Refunds of delivered orders use existing SalesReturn/payment policy, never a fake RTS.
9. Return-to-sender: restore original shipped units at original cost into chosen state, reverse the original order revenue/tax/delivery-income and stock COGS posting, settle actual advances through existing order termination/store-credit logic. Carrier fees actually incurred remain expenses. Financial entries from a customer payment must not be reversed as if money never arrived. A delivered/collected order cannot use RTS. Delivered-order SalesReturn eligibility uses deliveredAt as its return-window anchor (COMPLETED orders retain completedAt); delivery must not rewrite completedAt to hide the distinction. Refunds after a carrier collection reverse customer receivable/refund liability through existing payment policy while keeping the carrier settlement reconciliation correct.
10. Carrier fees for a failed/RTS shipment are recorded via existing expense API with the consignment reference, not a negative settlement of an uncollected payment. Warn against double recording: a settlement's fee and a separately recorded expense cannot share the same external fee reference. This check is server-side, transactionally claimed.
11. Delivery charges shown to customers are independent of actual courier costs. Add versioned organization-owned DeliveryZone rules in sales: zoneKey, localized name, served administrative area codes, fee Money, active flag. Checkout quotes fee by destination/zone and freezes it on order; caller cannot send amount, currency or arbitrary zone belonging to another organization. Existing geography data may be reused; no new industry-specific address fields.
12. Without a matching active zone, delivery is unavailable; pickup remains offered. Empty or ambiguous overlapping zone rules are rejected at save. Each organization has an explicit server currency; sums use integer minor units. A change after quote forces 4.3 quote refresh.
13. Courier module uses manual courier records with stable courierKey (configured data) and external tracking reference; this is not a provider adapter pretending success. Future 5.2 adapters invoke the same shipping/collection ports via queue. Own-rider assignments validate active membership at order.locationId. No automatic SMS/provider requests in the command transaction.
14. Surface permissions: sales.order.update for fail/reship/RTS; courier.consignment.create for manual courier dispatch; delivery.assignment.assign/complete for rider operations; courier.settlement.record and delivery.cash.handover for funds. Add explicit *.reverse permissions and manager approval for settlement/handover reversals. API guards use keys, not role strings. Customer has none of these permissions.
15. courier/delivery manifests declare actual routes, settings, events, menu and entitlements per catalog; no empty registration. System accounts are seeded once through accounting's existing seed mechanism (COURIER_RECEIVABLE, RIDER_CASH, COURIER_FEES if absent). Do not duplicate an existing account under a new code.
16. All commands require Idempotency-Key, expectedVersion on mutable aggregates, append-only unique financial claim indexes and transaction retries. Audit and outbox commit together. Replay with changed input is refused using existing idempotency semantics.
17. Reports and commission must recognize delivery-channel revenue at shipment per 11, with RTS reversing it. DELIVERED is not another sale. POS sessions are unaffected unless an explicit cash handover targets a register. Backfill old records is unnecessary before the new lifecycle exists; migration seeds new account/permission definitions idempotently.

## Transition and posting matrix

| Command | From → to | Stock | Money/accounting |
|---|---|---|---|
| ship first | CONFIRMED/PACKED → SHIPPED | release reservation + SALE once | order revenue/tax/delivery income; COGS; settle paid advance |
| fail | SHIPPED → DELIVERY_FAILED | none | none |
| reship | DELIVERY_FAILED → SHIPPED | none | none; another delivery attempt |
| delivered | SHIPPED → DELIVERED | none | remaining due → COD collection (or no payment at zero due) |
| receive RTS | DELIVERY_FAILED → RETURNED_TO_SENDER | original-cost RETURN to available/damaged | reverse first shipment postings; actual fee remains expense; paid advance per existing termination rules |
| reconcile loss | DELIVERY_FAILED → DELIVERY_LOSS_CLOSED | RETURN only actually received units at original cost; lost units remain out | reverse customer revenue/tax/fees; reverse COGS for received units and reclass lost COGS to delivery loss; settle advances |
| recover lost goods | closed loss record → append recovery | RETURN actually recovered units, bounded by outstanding lost quantity | debit available/damaged inventory; credit original delivery loss, no sale |
| courier settlement | collections pending → claimed | none | debit receiving account net + COURIER_FEES; credit COURIER_RECEIVABLE gross |
| rider handover | collections pending → claimed | none | debit receiving account; credit RIDER_CASH |
| settlement/handover reversal | original → reversed by new record | none | mirror exact original entries, reopen collection claims atomically |
| return after delivery | existing SalesReturn | existing return rules | existing refund/credit/dues logic, no duplicate revenue reversal |

Collection postings: COD_COURIER debit COURIER_RECEIVABLE / credit ACCOUNTS_RECEIVABLE; RIDER_CASH debit RIDER_CASH / credit ACCOUNTS_RECEIVABLE. Existing advance/posting engine determines before/after-revenue state; delivered collections are after revenue. Accounting remains asynchronous, idempotent, ordered through outbox; business records and stock/payment are transactionally synchronous. UI must distinguish recorded event from accounting failure in operations.

## Audit correction: settlement fences and immutable posting facts (2026-10-28)

P adds a unique natural collection origin {organizationId, orderId, deliveryCompletionId}; the trusted delivery completion ID and immutable input hash commit with DELIVERED/payment/claim. A second key cannot collect twice. COD method/owner is a discriminated union: COURIER requires consignmentId; OWN_RIDER requires deliveryAssignmentId. Remove the optional-field combination escape hatch from the concrete CodCollectionPort schema. Zero due creates no Payment/CollectionClaim.

Payment exposes claimCollections/releaseCollections through index.ts; each locks the SAME CollectionClaim documents that ReversePayment checks. A generic payment reversal cannot bypass an active settlement/handover: reverse the dependent financial record first, then the collection using its explicit correction command, all with approval. Settlement reversal releases only claims still owned by that exact settlement and generation; it cannot release a newer re-settlement. Refuse dependent refunds/corrections that cannot be reversed in the existing owner policy. Selected payment IDs are distinct, <=100, fully allocated to the source order, same carrier/rider/currency and authorized locations. Fees and sums are safe integers; charges <=gross. No ad hoc partial collection allocation.

Generic reverse-payment refuses COD origins even after claim release; only the trusted P correction orchestration may reverse them. For a wrong carrier/method, reverse and replace the collection for the same server-calculated amount in one transaction, with a new completion/correction ID linked to the original and no change to DELIVERED/revenue/stock. A wrongly recorded delivery may be undone only with approval, no dependent return/refund/settlement, and atomic payment reversal plus order transition back to SHIPPED; stock and first-shipment revenue remain unchanged. A later real delivery receives a new completion ID. These are explicit S2/P command seams with distinct approval/event constants and immutable correction receipts; they are not exposed as a caller-supplied bypass flag.

Every settlement, handover, loss and correction has a durable command receipt plus immutable input hash and result IDs in the same transaction. A partial unique reversal index allows one reversal per original. Approval tokens bind action, subject, server-calculated amount, actor/location and operation hash using the existing approval service; no role-name checks or new token issuer. Explicit constants: courier.settlement.reverse, delivery.cash.reverse, sales.deliveryLoss.record/reverse/recover; corresponding approval/audit/event keys are registered in contracts before use.

S1 snapshots first-shipment line quantities/cost allocations, net revenue/tax/delivery income, advance settlement and source business date in immutable posting facts. J1 reads these through sales/index.ts. Re-delivery does not change the first shipment source key. Source events for shipment/closure/recovery use the same order stream; payments use existing paymentAccount streams and settlement/handover their own source streams. Those streams have NO global ordering guarantee. J2 verifies prerequisite collection journals exist before clearing receivable; a reversal waits for its original posting. Missing prerequisite retries with bounded backoff and visible failure/DLQ, never posts a guessed counter-entry. Idempotent source/posting keys prevent duplicate effects on retry. Reports/commission consume the same immutable business facts, not current mutable order totals.

I adds bounded source-to-posting/claim reconciliation with persisted cursor; V injects crashes after each transaction boundary and processes delayed/shuffled events through the real worker. Operations distinguish business recorded, posting pending and posting failed. Accounting remains observable eventual consistency; no fabricated zero balance. P4-02/P4-13 through P4-16/P4-19/P4-20/P4-22 in [assurance](phase-4-assurance.md) apply.

## Owner-approved loss reconciliation and corrections

S3 owns DeliveryLossClosure and DeliveryLossRecovery append-only facts (UUID v7, tenant plugin, full audit), with versioned lifecycle metadata. Closure records orderId, firstShipmentEventId, per-line RESTOCK/DAMAGED/LOST quantities, original stock movement/cost references, total lost cost, reason/evidence file references and consumed approval snapshot. Evidence files stay private under existing file permissions. Unique active closure claim {organizationId,orderId}; history indexes start organizationId/orderId/createdAt/record ID. Recovery links closure ID and original line IDs; sum recovered minus reversed recovery never exceeds lost units. A shared versioned loss-balance fence serializes recovery/reversal; do not derive eligibility from an unlocked sum.

```ts
interface ReconcileDeliveryLossRequest {
  expectedVersion: number; reasonKey: string; approvalToken: string;
  evidenceFileIds: readonly string[];
  lines: readonly { orderLineId: string; restockQuantity: number;
    damagedQuantity: number; lostQuantity: number }[];
}
interface RecoverDeliveryLossRequest {
  expectedVersion: number; approvalToken: string;
  lines: readonly { orderLineId: string; restockQuantity: number;
    damagedQuantity: number }[];
}
interface DeliveryLossCommands {
  close(orderId: string, input: ReconcileDeliveryLossRequest): Promise<OrderResponse>;
  recover(deliveryLossClosureId: string, input: RecoverDeliveryLossRequest): Promise<{
    deliveryLossRecoveryId: string }>;
}
```

Close requires DELIVERY_FAILED, no delivered collection, manager approval for total lost cost, at least one lost unit, and complete nonduplicated line reconciliation. It atomically closes fulfillment/payment eligibility, returns only received goods, settles actual advances using existing termination policy, reverses recognized customer revenue and emits immutable loss facts. It never creates another SALE/write-off movement for goods already removed at first shipment. Original COGS is cleared by received-stock reversal plus Dr DELIVERY_LOSS / Cr COGS for the lost portion. Reuse the existing loss expense account if equivalent; seed a new system account only if none fits. Carrier fees remain expenses. No assumed courier compensation receivable: a later real recovery of money uses the existing authorized income/adjustment workflow with reference to the loss, not a fictional settlement of nonexistent COD collection.

Late physical recovery returns only actual units at their original cost and credits the original loss expense; it never restores customer dues or sales revenue. Recovery reversal removes those units at original cost only if the relevant bucket has sufficient stock, then mirrors its journal. Closure reversal requires all dependent recoveries reversed, unchanged closure generation, sufficient returned stock to reverse its movements, and approval. It restores DELIVERY_FAILED through an explicit correction, mirrors closure journals and adjusts advance settlement only through the payment policy; spent credit/refund dependencies block reversal until corrected. No silent history rewrite or automatic reship. Exact reverse request signatures and payment dependency links must be frozen in the S3 refresh before code, along with <=15-file parts if splitting is needed.

Add S3 exact file families on planner refresh: sales contracts/validation, application delivery-loss close/recover/reverse use cases, loss repository port/schema, loss-balance fence, router and public exports; stock movements only through the inventory public port. J1 owns posting handlers, I report/commission adapters, B1 staff reconciliation/recovery forms, V real day scenarios. No application code may start from these families alone.

Required tests: full/partial/all-goods loss, incorrect/missing/duplicate line quantities, zero loss directs to ordinary RTS, unauthorized/self approval and foreign evidence denial, concurrent closure vs redelivery, recovery twice/over outstanding quantity, recovery vs reversal, insufficient available/damaged stock on correction, already spent advance credit blocks reversal, and one balanced day with advance + failure + partial return + loss + carrier fee + later recovery. Assert ending inventory, COGS/loss, customer due, commission, reports and trial balance after real workers. Lost goods are never counted as available stock.
