## Binding decisions

- **D1 · Ownership.** Sales owns order state, zones, shipping transitions and stock commit. Courier (C) and delivery (R) own consignments/assignments, their permissions and the ship HTTP surface; they call `ShipOrderUseCase`/`ReshipOrderUseCase` exported from `apps/api/src/modules/commerce/sales/index.ts`. `fail`/`reship` are sales HTTP commands under `sales.order.update` (parent decision 14, `docs/11:106-107`).
- **D2 · Address.** Captured at quote, stored on the draft (`deliveryAddress` may be `null` on a DRAFT: the admin counter can start a delivery cart before the customer gives the address), **required at `place`** for COURIER/OWN_RIDER (`docs/11:100`), replaceable while `Order.assertEditable` accepts, i.e. `ORDER_EDITABLE_STATUSES` = DRAFT, PLACED, CONFIRMED (`packages/contracts/src/sales/sales-contracts.ts:34-38`; PACKED is not editable). The storefront checkout schema already requires the address at quote for delivery, so its drafts always have one. **The one address rule (S1c implements it in `UpdateOrderUseCase` and `Order.place`, nowhere else).** Create accepts a delivery draft with no address. `Order.place` always requires it for COURIER/OWN_RIDER (`422 DELIVERY_ADDRESS_REQUIRED`, a domain invariant, not the fee resolver — D3). After a place, the address is a standing fact of the order, so a PATCH is judged by the order's current status: on a **DRAFT** the method may be switched to COURIER/OWN_RIDER with no address and the address may be left absent; on a **PLACED or CONFIRMED** order a PATCH that sets `fulfillmentMethod` to COURIER/OWN_RIDER, or clears `deliveryAddress`, must carry a non-null address in the same body, or it is the same `422 DELIVERY_ADDRESS_REQUIRED`. A delivery draft without an address prices as fee 0 until an address arrives (D3). PICKUP/INSTANT may not carry one: create/edit refuses that combination (`422 ADDRESS_NOT_ALLOWED_FOR_METHOD`). `DeliveryAddress.phoneE164` is E.164 at every boundary: `checkoutDeliveryAddressSchema.phone` becomes `phoneE164Schema` (`packages/validation/src/phone.ts`, already transforms `01…`/`8801…`/`+…`), the storefront keeps the "phone" label and accepts the local form, and the admin form exposes the same transform. No free-text phone reaches the order.
- **D3 · Fee authority (one add point).** `DeliveryZone` (parent decision 11) replaces `website.deliveryCharge`. One exported resolver, `resolveDeliveryFee`, is the only fee algorithm: for COURIER/OWN_RIDER with a non-null `address` it reads the active zone claiming `address.areaCode` and returns `{deliveryZoneId, fee}`; no zone → 422 `DELIVERY_ZONE_UNAVAILABLE`; a **null** address returns `{deliveryZoneId:null, fee:0}` without a zone read (an addressless delivery draft, D2 — `place` refuses it before any fee matters); PICKUP/INSTANT → `{deliveryZoneId:null, fee:0}` without a zone read and ignores `address` (callers refuse a pickup with an address first). The pricing quote never carries delivery; **the fee is added exactly once, in one exported helper**: `withDeliveryFee(totals: OrderTotals, fee: Money): OrderTotals` in `sales-line-preparation.ts` sets `totals.deliveryCharge = fee` and `totals.grandTotal = { amount: totals.grandTotal.amount + fee.amount, currency }` (integer minor units), and it is the only place a fee enters an order — both `quoteAndPrepare` and the totals-only re-price (S1d rule below) call it. `prepareOrderLines`/`toTotals` stop forcing `deliveryCharge:0` as a silent constant: the fee-free quote is the input, and the overwrite happens in the fee-add point. **Currency is never assumed (ADR-013).** `resolveDeliveryFee` refuses a zone whose `fee.currency` differs from the `currency` it is handed, with `422 DELIVERY_ZONE_CURRENCY_MISMATCH`; it does not re-stamp the stored Money, because a silently re-labelled fee hides a zone written under an old organization currency. The refusal matches the module's own convention for cross-currency reads (`readSettlementBase`, `apps/api/src/modules/commerce/sales/application/ports/sales-ports.ts:204-210`: "Refuses when the payment summary is in another currency than the order (never assumed)"), and S1d tests it by writing a zone row with another currency through the repository. The storefront price adapter calls the same `resolveDeliveryFee` and adds it once to its preview total. `buildDeliveryZoneRepository()` is exported from the sales `index.ts` (S1b's shared change) and `resolveDeliveryFee` from the same `index.ts` (S1d's shared change), so the adapter builds both from the module's exports. The client never sends a fee, currency or zone id. `PublicOrderCommands.place` receives `expectedDeliveryChargeMinor` computed by `submit-checkout-helpers.ts` from the persisted quote (`quote.pricedSnapshot.deliveryCharge.amount`, already saved by `QuoteCheckoutUseCase`), never from the browser. The storefront command `handlePlaceStorefrontOrder` (`storefront-order-commands.ts`) re-quotes via `quoteAndPrepare`, compares the recomputed `totals.deliveryCharge.amount` with the expectation and throws the existing `409 CHECKOUT_PRICE_CHANGED` **before** `executePlaceTransaction` and stock reservation. The counter's `PlaceOrderUseCase` is a different path: it never receives an expectation and simply freezes the recomputed fee. **Storefront preview amount (owner decision 2026-10-31, binding).** The quote preview reports `amountRequiredBeforeConfirmation = 0` on every line (`storefront-price-adapter.ts:148` today) while `deliveryCharge` and the total show the zone fee; the real payable is only known at submit. S1d keeps that rule in the rewritten adapter and asserts it in `storefront-commerce-commands.api.test.ts` next to the zone fee. `docs/11:63,122` wording is updated in S1d's handoff because owner-approved parent decision 11 supersedes the flat-charge text.
- **D4 · Zone uniqueness.** One active zone per organization and area code via partial multikey unique index `{organizationId:1, areaCodes:1}` with `partialFilterExpression: {status:"ACTIVE"}` (buildable; partial-key precedent `apps/api/src/modules/commerce/catalog/infrastructure/offering.schema.ts:146`), plus duplicate codes inside one zone refused. `zoneKey` is client-chosen, unique per organization, immutable after create.

## Data model

`Order` gains `deliveryAddress` (null for pickup/instant), `deliveryZoneId`, `shippedAt`, `firstShipment` (immutable snapshot, null until first ship), `currentDeliveryAttemptId`, `deliveryAttemptCount`. `deliveredAt` is deliberately absent: it arrives with the DELIVERED transition in COD part P, so S1 never stores a field nothing writes. Existing documents lack these fields; `apps/api/src/modules/commerce/sales/infrastructure/mongo-order.mapper.ts` defaults them (five `null`s for address/zone/shippedAt/firstShipment/currentAttemptId, `0` for the count) and a test reads a legacy document. Pre-S1 COURIER/OWN_RIDER orders stay valid: completed ones are untouched; open ones in PLACED/CONFIRMED can receive an address and then ship, or be cancelled. A legacy PACKED delivery order cannot be edited (D5): ship refuses without an address and cancel remains the exit. No destructive backfill.

`delivery_zones`: `deliveryZoneId`, `organizationId`, `zoneKey`, `name` (LocalizedText), `areaCodes[]`, `fee` (integer minor units + the organization currency read at create time, `SalesCurrencyReader`), `status`, `version`, audit. Unique `{organizationId, zoneKey}`; partial unique `{organizationId, areaCodes}` where ACTIVE; `{organizationId, createdAt:-1, deliveryZoneId}` for listing. The organization currency is not assumed to stay the same after a zone exists, so pricing is the point that catches a stale zone currency (D3: `DELIVERY_ZONE_CURRENCY_MISMATCH`).

`delivery_attempts`: `deliveryAttemptId`, `organizationId`, `orderId`, `ordinal`, `method`, `consignmentId`, `deliveryAssignmentId`, `startedAt`, `failedAt`, `reasonKey`, `note`, `version`, audit. Unique indexes: see **Unique-index spec** below. There is no `attemptNo` and no `fulfillmentCode`.

### Unique-index spec (plan-check gap 4 · `fulfillmentCode`)

**`fulfillmentCode` does not exist on `origin/main`.** Grep over `apps/` + `packages/` is empty; `SEQUENCE_KEY` has no FULFILLMENT/SHIPMENT value; sales `sequenceKeys` are ORDER, INVOICE, RETURN only. S1 does **not** add `fulfillmentCode` (that would be a new customer-facing number and a new `SEQUENCE_KEY` — OQ-4). The uniqueness a manoxen `fulfillmentCode` would have provided is these schema indexes. The tenant plugin (`apps/api/src/kernel/tenancy/apply-tenancy-plugins.ts`) **stamps and filters `organizationId`**; it does **not** create unique indexes. Unique keys must therefore start with `organizationId` so two organizations may share the same `zoneKey` / `ordinal`. `embedded` docs stay `_id: false`.

**Collection `delivery_zones`** (`DELIVERY_ZONE_COLLECTION_NAME = "delivery_zones"`). `registerModel` tenancy `MODEL_TENANCY.ORGANIZATION` (no `locationId`; zone is an organization record). Plugin: `tenantPlugin` only.

| Keys | Unique | Partial | Purpose |
|---|---|---|---|
| `{ organizationId: 1, deliveryZoneId: 1 }` | yes | none | domain id |
| `{ organizationId: 1, zoneKey: 1 }` | yes | none | client-chosen key, immutable after create |
| `{ organizationId: 1, areaCodes: 1 }` | yes | `{ status: "ACTIVE" }` | one ACTIVE zone per org+area code (multikey; same pattern as `offering.schema.ts:144-147`) |
| `{ organizationId: 1, createdAt: -1, deliveryZoneId: 1 }` | no | none | list |

**Collection `delivery_attempts`** (`DELIVERY_ATTEMPT_COLLECTION_NAME = "delivery_attempts"`). Tenancy `MODEL_TENANCY.ORGANIZATION` (attempt has no `locationId`; location writes are enforced by loading the **order**, which is `ORGANIZATION_AND_LOCATION`, inside S1f). Plugin: `tenantPlugin` only.

| Keys | Unique | Partial | Purpose |
|---|---|---|---|
| `{ organizationId: 1, deliveryAttemptId: 1 }` | yes | none | domain id (the identifier that replaces `fulfillmentCode`) |
| `{ organizationId: 1, orderId: 1, ordinal: 1 }` | yes | none | one ordinal per order; concurrent ship/reship → 409 |
| `{ organizationId: 1, orderId: 1, startedAt: -1 }` | no | none | list by order |

S1a registers both models in `register-sales-models.ts` (add-only). A test in S1a proves `syncIndexes` accepts these definitions (follow `offering.schema.ts` / `sales.schema.ts` unique+partial shape; do not put `unique: true` on `areaCodes` without the ACTIVE partial, or INACTIVE rows could not reuse a code).

Totals: `totals.deliveryCharge = zone fee`; `grandTotal = fee-free quote grandTotal + fee`, applied once by `withDeliveryFee` (D3) on both the quote path and the totals-only re-price; the payment summary is initialised/updated from that grandTotal at create/place/edit. Integer minor units only.

**Response projection (interfaces: S1a contracts file; field and projection: S1c).** `OrderResponse` gains one nullable `delivery` object: `null` only for PICKUP/INSTANT; every COURIER/OWN_RIDER order (including legacy ones) returns the object, with `address: null` until one is stored. Old API clients keep working because the change is additive:

```ts
export interface OrderDeliveryResponse {
  readonly address: DeliveryAddress | null;
  readonly deliveryZoneId: string | null;
  readonly shippedAt: string | null; // ISO timestamp
  readonly currentDeliveryAttemptId: string | null;
  readonly deliveryAttemptCount: number;
  /** Immutable first-ship snapshot, read-only; null until the first ship. */
  readonly firstShipment: FirstShipmentResponse | null;
}
export interface FirstShipmentResponse {
  readonly shipmentEventId: string;
  readonly deliveryAttemptId: string;
  readonly shippedAt: string; // ISO timestamp
  readonly businessDate: string;
  readonly netRevenue: Money;
  readonly taxTotal: Money;
  readonly deliveryIncome: Money;

```

Both interfaces live in the S1a contracts file, so S1c only adds the field. S1c's `toOrderResponse` (`sales-views.ts`) builds the object for **every** state — unknown facts are `null`/`0`, never `undefined` — which is what makes the S1c legacy-COURIER test pass before any ship code exists. S1f then only moves state and writes `shippedAt`/`firstShipment`/attempt fields; it changes no response shape. The attempt row itself is not embedded (no N+1 on every read). S1f adds `GET /orgs/:organizationId/orders/:orderId/delivery-attempts` (`sales.order.read`, `sendData(items, { meta: { page, limit, hasNext } })` like `order.controller.ts:184-190`, ≤100) backed by `DeliveryAttemptRepository` through the owned `ListDeliveryAttemptsUseCase`, and a test that reship produces ordinals 1 and 2.

**Zone matching (S1a rule, read by `resolveDeliveryFee` in S1d).** `areaCode` keeps the bounds the checkout address already enforces (`checkoutDeliveryAddressSchema`, `packages/validation/src/website/checkout-command-schemas.ts:72-81`: trimmed, 1–50), and the zone form enforces the same bounds per code.
