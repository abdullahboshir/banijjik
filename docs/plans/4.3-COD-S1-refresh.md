## Binding decisions

- **D1 · Ownership.** Sales owns order state, zones, shipping transitions and stock commit. Courier (C) and delivery (R) own consignments/assignments, their permissions and the ship HTTP surface; they call `ShipOrderUseCase`/`ReshipOrderUseCase` exported from `apps/api/src/modules/commerce/sales/index.ts`. `fail`/`reship` are sales HTTP commands under `sales.order.update` (parent decision 14, `docs/11:106-107`).
- **D2 · Address.** Captured at quote, stored on the draft (`deliveryAddress` may be `null` on a DRAFT: the admin counter can start a delivery cart before the customer gives the address), **required at `place`** for COURIER/OWN_RIDER (`docs/11:100`), replaceable only while `PLACED`/`CONFIRMED` (`ORDER_EDITABLE_STATUSES`; PACKED is not editable). The storefront checkout schema already requires the address at quote for delivery, so its drafts always have one. Create and edit accept a delivery draft without an address; only `place` requires it, and `Order.place` enforces it as a domain invariant (`422 DELIVERY_ADDRESS_REQUIRED`) — not the fee resolver (D3). A delivery draft without an address prices as fee 0 until an address arrives. PICKUP/INSTANT may not carry one: create/edit refuses that combination (`422 ADDRESS_NOT_ALLOWED_FOR_METHOD`). `DeliveryAddress.phoneE164` is E.164 at every boundary: `checkoutDeliveryAddressSchema.phone` becomes `phoneE164Schema` (`packages/validation/src/phone.ts`, already transforms `01…`/`8801…`/`+…`), the storefront keeps the "phone" label and accepts the local form, and the admin form exposes the same transform. No free-text phone reaches the order.
- **D3 · Fee authority (one add point).** `DeliveryZone` (parent decision 11) replaces `website.deliveryCharge`. One exported resolver, `resolveDeliveryFee`, is the only fee algorithm: for COURIER/OWN_RIDER with a non-null `address` it reads the active zone claiming `address.areaCode` and returns `{deliveryZoneId, fee}`; no zone → 422 `DELIVERY_ZONE_UNAVAILABLE`; a **null** address returns `{deliveryZoneId:null, fee:0}` without a zone read (an addressless delivery draft, D2 — `place` refuses it before any fee matters); PICKUP/INSTANT → `{deliveryZoneId:null, fee:0}` without a zone read and ignores `address` (callers refuse a pickup with an address first). The pricing quote never carries delivery; **the fee is added exactly once in `quoteAndPrepare`** (after `prepareOrderLines`): `totals.deliveryCharge = fee` and `totals.grandTotal = quoteGrandTotal + fee` (integer minor units). `prepareOrderLines`/`toTotals` stop forcing `deliveryCharge:0` as a silent constant: the fee-free quote is the input, and the overwrite happens in the fee-add point. The storefront price adapter calls the same `resolveDeliveryFee` and adds it once to its preview total. `buildDeliveryZoneRepository()` is exported from the sales `index.ts` (S1b's shared change) and `resolveDeliveryFee` from the same `index.ts` (S1d's shared change), so the adapter builds both from the module's exports. The client never sends a fee, currency or zone id. `PublicOrderCommands.place` receives `expectedDeliveryChargeMinor` computed by `submit-checkout-helpers.ts` from the persisted quote (`quote.pricedSnapshot.deliveryCharge.amount`, already saved by `QuoteCheckoutUseCase`), never from the browser. The storefront command `handlePlaceStorefrontOrder` (`storefront-order-commands.ts`) re-quotes via `quoteAndPrepare`, compares the recomputed `totals.deliveryCharge.amount` with the expectation and throws the existing `409 CHECKOUT_PRICE_CHANGED` **before** `executePlaceTransaction` and stock reservation. The counter's `PlaceOrderUseCase` is a different path: it never receives an expectation and simply freezes the recomputed fee. **Storefront preview amount (owner decision 2026-10-31, binding).** The quote preview reports `amountRequiredBeforeConfirmation = 0` on every line (`storefront-price-adapter.ts:148` today) while `deliveryCharge` and the total show the zone fee; the real payable is only known at submit. S1d keeps that rule in the rewritten adapter and asserts it in `storefront-commerce-commands.api.test.ts` next to the zone fee. `docs/11:63,122` wording is updated in S1d's handoff because owner-approved parent decision 11 supersedes the flat-charge text.
- **D4 · Zone uniqueness.** One active zone per organization and area code via partial multikey unique index `{organizationId:1, areaCodes:1}` with `partialFilterExpression: {status:"ACTIVE"}` (buildable; partial-key precedent `apps/api/src/modules/commerce/catalog/infrastructure/offering.schema.ts:146`), plus duplicate codes inside one zone refused. `zoneKey` is client-chosen, unique per organization, immutable after create.
- **D5 · State machine.** `SHIPPED` only from `CONFIRMED`/`PACKED` for COURIER/OWN_RIDER; `DELIVERY_FAILED` only from `SHIPPED`; reship `DELIVERY_FAILED → SHIPPED` with a distinct use case. `CompleteOrder`/`Order.complete` refuse COURIER/OWN_RIDER (DELIVERED is their terminal, `docs/11:109`); admin create refuses INSTANT. **Legacy PACKED delivery orders** (created before S1, never had an address) get exactly two transitions: `cancel` (existing, `ORDER_CANCELLABLE_STATUSES` keeps PACKED) and `ship` only after an address exists. Because PACKED is not editable, such an order cannot gain an address; ship refuses it with `DELIVERY_ADDRESS_REQUIRED` and the owner cancels or re-creates. No backfill and no reopened edit window.
- **D6 · Stock.** First ship calls `commitSale` once; the ledger itself refuses when the reservation is missing (`apps/api/src/modules/commerce/inventory/application/stock-ledger.port.ts:138-145`) and requires a non-null actor (`:35-36`). S1's ship actor is a `UserId` by type (authenticated C/R staff), so there is no nullable actor path. Skip the call when `hasStockLines=false`. Reship/fail never touch stock.
- **D7 · Facts and costs.** First ship freezes `unitCostSnapshot` per line, then stores an immutable `firstShipment` snapshot: `shipmentEventId` generated with `newId()` (UUID v7 string, matching `apps/api/src/modules/commerce/sales/application/sales-line-preparation.ts:100`), attempt id, shippedAt, businessDate, per-line quantity/cost/lineNetTotal, netRevenue, taxTotal, deliveryIncome, netPaidAtShipment (`readNetPaid`, `sales-ports.ts:204`). Event payload stays `{orderId}`; J1 reads the order snapshot and uses `orderId` as the stable posting key.
- **D8 · Events/audit.** `sales.order.shipped` (ship and reship) and `sales.order.deliveryFailed`; audit `ORDER_SHIPPED`, `ORDER_DELIVERY_FAILED`. `SHIPPED`/`DELIVERY_FAILED` join `ORDER_IMPLEMENTED_STATUSES` in S1f only.
- **D9 · Permissions.** `sales.deliveryZone.manage` declared by the sales manifest (OWNER/MANAGER via `"ALL"`; not CASHIER/STAFF). Ship keys belong to C/R; S1 adds none.
- **D10 · Attempts.** `delivery_attempts` row per attempt, unique `{organizationId, orderId, ordinal}`, exactly one link, `version`. Order keeps `currentDeliveryAttemptId` and `deliveryAttemptCount`.
- **D11 · Idempotency/version.** All new commands require `Idempotency-Key` (parent decision 16); `version` rides in the body, matching `orderTransitionRequestSchema`.
- **D12 · Counts.** The parent's ≤15 cap counts part-owned production files; shared append-only files are listed separately (parent Files row `all | add-only shared` covers indexes, grants, i18n, READMEs, handoffs, STATUS; other append-only shared files are flagged as shared too). A file touched by two parts is listed in both and counted once per part.

## Data model

`Order` gains `deliveryAddress` (null for pickup/instant), `deliveryZoneId`, `shippedAt`, `firstShipment` (immutable snapshot, null until first ship), `currentDeliveryAttemptId`, `deliveryAttemptCount`. `deliveredAt` is deliberately absent: it arrives with the DELIVERED transition in COD part P, so S1 never stores a field nothing writes. Existing documents lack these fields; `apps/api/src/modules/commerce/sales/infrastructure/mongo-order.mapper.ts` defaults them (five `null`s for address/zone/shippedAt/firstShipment/currentAttemptId, `0` for the count) and a test reads a legacy document. Pre-S1 COURIER/OWN_RIDER orders stay valid: completed ones are untouched; open ones in PLACED/CONFIRMED can receive an address and then ship, or be cancelled. A legacy PACKED delivery order cannot be edited (D5): ship refuses without an address and cancel remains the exit. No destructive backfill.

`delivery_zones`: `deliveryZoneId`, `organizationId`, `zoneKey`, `name` (LocalizedText), `areaCodes[]`, `fee` (integer minor units + organization currency), `status`, `version`, audit. Unique `{organizationId, zoneKey}`; partial unique `{organizationId, areaCodes}` where ACTIVE; `{organizationId, createdAt:-1, deliveryZoneId}` for listing.

`delivery_attempts`: `deliveryAttemptId`, `organizationId`, `orderId`, `ordinal`, `method`, `consignmentId`, `deliveryAssignmentId`, `startedAt`, `failedAt`, `reasonKey`, `note`, `version`, audit. Unique `{organizationId, orderId, ordinal}`; `{organizationId, orderId, startedAt:-1}`.

Totals: `totals.deliveryCharge = zone fee`; `grandTotal = fee-free quote grandTotal + fee`, applied once in `quoteAndPrepare` (D3); the payment summary is initialised/updated from that grandTotal at create/place/edit. Integer minor units only.

**Response projection (interfaces: S1a contracts file; field and projection: S1c).** `OrderResponse` gains one nullable `delivery` object: `null` only for PICKUP/INSTANT; every COURIER/OWN_RIDER order (including legacy ones) returns the object, with `address: null` until one is stored. Old API clients keep working because the change is additive:
