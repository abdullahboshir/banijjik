## Goal
Today a `SUPPORT` or `BILLING` operator can only be created, changed or disabled by editing the database. After this card a SUPER_ADMIN can do all of it through `/api/v1/platform/operators`:
- list and read operators
- grant operator access to an existing user
- change an operator's roles
- disable and enable an operator

Every write is audited and takes effect on the operator's next request. The panel can never be left without an active SUPER_ADMIN, not even under concurrent requests.

## Decisions
**Where the code lives**
1. **`core/iam` owns operator management**, because it owns `PlatformOperator` (09 section 4.1).
   - One use case per file under `core/iam/application/use-cases/`.
   - A controller and a router under `core/iam/presentation/`.
   - The builder `buildIamPlatformOperatorRouter(input)` is exported from `core/iam/index.ts`.
   - `routes/platform.ts` mounts it at `/operators` inside `buildPlatformRouter`, guarded by `platformPermission`, like the package router. Add lines only.

**Permissions**
2. Two new keys in `PLATFORM_PERMISSION_KEY`:
   - `OPERATOR_READ: "platform.operator.read"`
   - `OPERATOR_WRITE: "platform.operator.write"`
   
   SUPER_ADMIN gets both automatically through `ALL_PLATFORM_PERMISSIONS`. SUPPORT and BILLING get neither. Managing who may operate the platform is a SUPER_ADMIN duty (ADR-093, least privilege).
   - Update the role-table test in contracts.
   - Update ADR-093's permission list.
   - A non-SUPER_ADMIN gets `403 FORBIDDEN` on every operator route.

**Endpoints** (all under `/api/v1/platform/operators`; every write takes a mandatory `reason`, like suspend and extend-trial)

3. **`GET /`**: the list, permission `OPERATOR_READ`.
   - Query: `paginationQuerySchema` plus an optional `status` (`ACTIVE` | `DISABLED`).
   - Order: `createdAt` descending, then `platformOperatorId` descending.
   - Page meta exactly as `GET /platform/packages`.
   - Each row is a `PlatformOperatorSummary` (see Interfaces).
   - The user's `name` and `identifierHint` come from **one** batched user read for the whole page (`UserRepository.findByIds`, a single `$in` query with lean and projection). No N+1.

4. **`GET /{platformOperatorId}`**: one operator, permission `OPERATOR_READ`. Same shape as a row. An unknown id answers `404 NOT_FOUND`.

5. **`POST /`**: grant operator access, permission `OPERATOR_WRITE`.
   - Body: `{ identifier, platformRoles, reason }`. `identifier` uses the existing `loginIdentifierSchema`, so an email or a phone number becomes E.164. `platformRoles` has 1 to 3 roles, no duplicates.
   - The user must already exist. People sign up through the normal admin sign-up first; the platform never sets another person's password.
   - Errors:

     | Case | Answer |
     |---|---|
     | No user has that identifier | `422 BUSINESS_RULE`, ruleKey `OPERATOR_USER_NOT_FOUND` |
     | The user is not `ACTIVE` | `422 BUSINESS_RULE`, ruleKey `OPERATOR_USER_NOT_ACTIVE` |
     | The user already has an operator record (any status) | `409 CONFLICT`, messageKey `errors.operator_exists` |

     For the conflict case, check first. Also map the driver duplicate-key error on the unique `userId` index to the same 409 (`isDuplicateKeyError(error, "userId")`), so two simultaneous grants also end in one 201 and one 409.
   - Revealing whether an identifier exists is acceptable here: only a SUPER_ADMIN can ask, and the per-operator rate limit applies.
   - Creates the operator `ACTIVE` with version 1, `createdByUserId` = the actor. Answers `201` with the summary.

6. **`PATCH /{platformOperatorId}`**: replace the roles, permission `OPERATOR_WRITE`.
   - Body: `{ platformRoles, version, reason }`.
   - A stale `version` answers `409 CONFLICT`, as package PATCH does.
   - The same set of roles as stored answers `200` with the unchanged summary: no write, no audit entry, no version bump.
   - Otherwise save, `version + 1`, `updatedByUserId` = the actor.

7. **`POST /{platformOperatorId}/disable`** and **`POST /{platformOperatorId}/enable`**, permission `OPERATOR_WRITE`.
   - Body: `{ version, reason }`. A stale version answers 409.
   - Already in the target status: `200` unchanged, no write, no audit entry.
   - **Disable** sets `DISABLED` and, in the same transaction, revokes every **PLATFORM** refresh session of that user (`revokeAllForUser(userId, TOKEN_AUDIENCE.PLATFORM, now)`). ADMIN sessions stay, because the person may also work in a business. The existing access token stops working at once, because `authenticatePlatform` reads the operator row on every request.
   - **Enable** sets `ACTIVE` and restores no session.
   - Operator status uses only `ACTIVE` and `DISABLED` of `USER_STATUS`; `LOCKED` is never set on an operator.

8. **No DELETE.** An operator record stays forever, because audit entries name it (`actorPlatformOperatorId`). "Remove" means disable. `14 §7` changes from "CRUD" to the exact list above.

**Safety rules**
9. **Own access is protected.** A SUPER_ADMIN cannot PATCH, disable or enable their own operator record: `422 BUSINESS_RULE`, ruleKey `OWN_OPERATOR_ACCESS`. Another SUPER_ADMIN must do it. This is the same rule as a member's own access (ADR-092), and it means a request can never take away the access of the person making it.

10. **There is always an active SUPER_ADMIN, even under concurrency.** The case to guard: A disables B while B disables A at the same moment. Each request sees the other as active, so both would commit and leave none.
    - Every operator write (create, PATCH, disable, enable) runs in **one transaction** (`MongoUnitOfWork`). Inside it:
      1. **Re-read the actor's own operator row and touch it**, with `$inc: { referenceVersion: 1 }` via `findOneAndUpdate` (returns the updated document).
      2. If the actor is not `ACTIVE` with `SUPER_ADMIN` any more, answer `403 FORBIDDEN`.
      3. **Touch the target the same way.**
    - Two such transactions always write overlapping documents, so MongoDB aborts one with a write conflict. `withTransaction` retries it, and the retry finds its actor disabled → 403.
    - Together with decision 9, the actor of every committed write is an active SUPER_ADMIN other than the target, so at least one active SUPER_ADMIN always remains.
    - `referenceVersion` is a guard counter: it leaves `version` and `updatedAt` alone. This is the ADR-092 mechanism, as on `Package` and `Location`. Schema field `referenceVersion: { type: Number, default: 0 }`; older rows get it with the first `$inc`.
    - Do **not** add a separate "count the super admins" check. With decisions 9 and 10 it could never fire, and untestable code is not wanted.

**Audit**
11. Every committed write writes exactly one `PlatformAuditLog` entry through the existing `PlatformAuditRecorder`, inside the transaction, with targetType `platform_operator`, targetId = `platformOperatorId`, and the request's `reason`.

    | Action | `changes` |
    |---|---|
    | `OPERATOR_CREATED: "platform.operator.created"` | `{ platformRoles: { to }, userId: { to } }` |
    | `OPERATOR_ROLES_CHANGED: "platform.operator.rolesChanged"` | `{ platformRoles: { from, to } }` |
    | `OPERATOR_DISABLED: "platform.operator.disabled"` | `{ status: { from, to } }` |
    | `OPERATOR_ENABLED: "platform.operator.enabled"` | `{ status: { from, to } }` |

    No-op answers (decisions 6 and 7) write none. Reads write none, as for the other platform reads.

**Identifier hint**
12. The summary carries `identifierHint`, masked exactly like the tenant owner contact: the email first, otherwise the phone with only its last 4 digits visible.
    - Move `maskIdentifier` and its test unchanged from `platform/tenant-admin/domain/mask-identifier.ts` to `packages/validation/src/text/mask-identifier.ts`, and export it from the package index.
    - `get-tenant.use-case.ts` imports it from there. Its tests stay as they are; moved imports only.
    - `core/iam` uses the same function. This is a move, not a third copy; the invitation hint keeps its own helper by design (1.9e).

**Records**
13. M14 closes with this card and 1.10b.
    - Operator sign-in stays unaudited in the platform audit log. It is logged by the access log, and an audit of sign-ins belongs to a later security card. Record this in ADR-093.
    - The seed already writes `OPERATOR_SEEDED`; no change.

## Interfaces & types
```ts
// packages/contracts
export interface PlatformOperatorSummary {
  platformOperatorId: string;
  userId: string;
  name: string;
  identifierHint: string;
  platformRoles: PlatformRole[];
  status: "ACTIVE" | "DISABLED";
  version: number;
  createdAt: string;   // ISO
  updatedAt: string;   // ISO
}
// PLATFORM_RULE_KEY additions
OPERATOR_USER_NOT_FOUND: "OPERATOR_USER_NOT_FOUND",
OPERATOR_USER_NOT_ACTIVE: "OPERATOR_USER_NOT_ACTIVE",
OWN_OPERATOR_ACCESS: "OWN_OPERATOR_ACCESS",

// packages/validation. `reasonSchema` is private to platform-schemas.ts today: export it there
// unchanged (an added `export` keyword only) and import it here, so every platform reason has one rule.
platformOperatorParamsSchema       = z.object({ platformOperatorId: uuidV7Schema })
platformOperatorListQuerySchema    = paginationQuerySchema.extend({ status: z.enum(["ACTIVE", "DISABLED"]).optional() })
platformRolesSchema                = z.array(z.enum(PLATFORM_ROLE values)).min(1).max(3), refined to unique
platformOperatorCreateRequestSchema = z.strictObject({ identifier: loginIdentifierSchema, platformRoles: platformRolesSchema, reason: reasonSchema })
platformOperatorUpdateRequestSchema = z.strictObject({ platformRoles: platformRolesSchema, version: positive int, reason: reasonSchema })
platformOperatorStatusRequestSchema = z.strictObject({ version: positive int, reason: reasonSchema })

// core/iam/application/ports/platform-operator-repository.ts (existing methods stay)
findById(platformOperatorId: string): Promise<PlatformOperator | undefined>;
list(query: { status?: UserStatus; page: number; limit: number }): Promise<{ items: readonly PlatformOperator[]; hasNext: boolean }>;
/** `$inc referenceVersion` on one row inside the active transaction; the updated row, or undefined. */
touch(platformOperatorId: string): Promise<PlatformOperator | undefined>;
/** Saves roles or status if `expectedVersion` is current (version + 1), else a 409 CONFLICT. */
save(operator: PlatformOperator, expectedVersion: number, actorUserId: UserId): Promise<PlatformOperator>;

// core/iam/application/ports/user-repository.ts
findByIds(userIds: readonly UserId[]): Promise<User[]>;
```
Use the same paging result type and meta that `GET /platform/packages` uses; do not invent a new one.

## Data
- `platform_operators` gets:
  - the field `referenceVersion` (Number, default 0)
  - the index `{ status: 1, createdAt: -1, platformOperatorId: -1 }`, which backs the list. The collection has no `organizationId`; it is platform-wide.
- `npm run db:sync-indexes` picks the new index up; no migration.
- `findByIds` uses the existing unique index on `userId`.

## Tests (must exist and pass)
API tests (`core/iam/presentation/platform-operators-api.test.ts`, with the existing platform test helpers and fixture operators):
- [ ] **Happy path:**
  - The SUPER_ADMIN lists operators (paged, `status` filter), reads one, grants SUPPORT to a registered user (201, the row shows name and masked hint), changes the roles to BILLING (version moves), disables, then enables.
  - Each write leaves exactly one platform audit entry with the right action, changes and reason.
  - The no-op PATCH and status calls write nothing.
- [ ] **Effect is immediate:**
  - After PATCH SUPPORT → BILLING, that operator's next `POST …/suspend` answers 403 and the next `POST …/extend-trial` passes the permission check.
  - After disable, their next request with the old access token answers 401 and their platform refresh answers 401.
  - Their ADMIN refresh still works.
  - After enable, they can sign in to the platform again.
- [ ] **Validation errors:** unknown body keys, 0 roles, an unknown role, a duplicate role, a missing reason, a bad identifier, a non-UUID id → 400 at the right path.
- [ ] **Permission denied:** a SUPPORT and a BILLING operator get 403 on all six routes. No platform session → 401. An admin-audience cookie → 401.
- [ ] **Business rules:**
  - an unknown identifier → `OPERATOR_USER_NOT_FOUND`
  - a LOCKED or DISABLED user → `OPERATOR_USER_NOT_ACTIVE`
  - an existing operator → 409 `errors.operator_exists`
  - stale version → 409
  - unknown id → 404
  - own record (PATCH, disable, enable) → `OWN_OPERATOR_ACCESS`
- [ ] **Concurrency** (in the style of `organization-status-atomicity.test.ts`):
  - two SUPER_ADMINs disable each other at the same time: exactly one succeeds, the other answers 403, one ACTIVE SUPER_ADMIN remains, and only one audit entry exists
  - two simultaneous grants for one user: one 201, one 409
- [ ] **Unit tests:** the entity methods, the write guard (actor not active, actor without SUPER_ADMIN, target touched), the schemas, `findByIds` (one query for a page), the moved `maskIdentifier` test.
- [ ] **Cross-org denied:** not applicable. Operators are platform-wide, and a tenant session never reaches `/platform` (covered by the 401 test above).
- [ ] Every existing suite stays green with assertions unchanged. The only allowed changes are moved imports (the mask) and the contracts role-table test gaining the two keys; list each.
- [ ] Full "Done means" list of `docs/ops/implement-with-cursor.md`, including the **platform browser suite** (the platform app is untouched, but it reads `/platform/me` permissions).

## Out of scope
- Any platform panel screen or menu entry (card 1.10b).
- Creating users or setting passwords for others, invitations by email or SMS, operator sign-in audit, impersonation.
- Changing the seed, the login flow or `authenticatePlatform`.

## Risks & checks
- **The guard must really serialize.** The concurrency test must fail if the actor touch is removed. Prove it once: remove the touch locally, run the test, paste the failing output into the handoff, then restore it.
- **Do not trust the token for roles.** Roles are read from the operator row on every request today; do not cache them anywhere new.
- **The no-op paths** must not bump `version` or write audit entries; assert both.
- **Memory, disk, services:** `--concurrency=1`, `VITEST_MAX_WORKERS=2` (browser suite `=1`), the system MongoDB binary, `TEST_REDIS_URL=redis://127.0.0.1:6380`. No downloads.
- Stop and ask if any decision above conflicts with the code you find.

## Done when
- A SUPER_ADMIN can list, read, grant, re-role, disable and enable operators through the API, each audited and effective on the next request.
- No API path removes the last active SUPER_ADMIN, even under concurrency.
- SUPPORT and BILLING cannot reach these routes.
- The docs say what the code does.
- The Opus review of this card passes.
