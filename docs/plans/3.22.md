# Plan: card 3.22 · Ordered handlers follow whole streams

Tier: **T1** (kernel events; every ledger posting depends on it) · Planned by: Opus 5.5 (Claude) · Date: 2026-10-23 · Based on commit: `main 8f09c23`

Reserved ADR number: **ADR-136** (amends ADR-115). Found by the 3.11 A1 session (plan 3.11 Amendment 1).

## Session parts
One part, API and kernel only. Branch `s/3.22-ordered-stream-follow`. T1 review by the lead. **Merge before 3.11 A2** if A2 has not started its accounting handler yet; otherwise A2 rebases and adds `streamPrefixes` to `accounting.postCommission` (see decision 6).

## Goal
Today an ORDERED handler waits forever when its stream also carries event types it does not handle:
- A stream sequence is counted per `(organizationId, orderingKey)` over **all** event types (`publish-event.ts` `nextStreamSequence`).
- The dispatcher enqueues an event only for the handlers of its type (`outbox-dispatcher.ts` → `registry.handlersFor(event.type)`).
- The runner moves a handler's position only on events it receives (`handler-runner.ts` `runOrdered`).

So `accounting.postBookings` never sees `booking.booking.created` (sequence 1) on `booking:<bookingId>`, its position stays 0, and `booking.booking.completed` (sequence 2 or later) is AHEAD forever. **Booking revenue is never posted.** `accounting.postPayments` and `accounting.postExpenses` work only because they happen to handle every type on their streams today.

After this card, an ORDERED handler declares the streams it follows. It receives every event of those streams, handles its own types, and steps over the others, so its position always moves.

  - Scan the outbox for the gap: dispatched events are deleted after 30 days (TTL on `dispatchedAt`), so a long-lived stream would have holes and wait again.
  - Let ORDERED handlers listen to every type by hand: fragile, because a new event type on the stream silently stops the ledger again.

## Decisions
1. **Handler contract** (`event-handler-registry.ts`): `EventHandler` becomes a union on `ordering`:
   - `ordering: "UNORDERED"` stays as it is today. A `streamPrefixes` field is a type error.
   - `ordering: "ORDERED"` requires `streamPrefixes: readonly [string, ...string[]]`. Each prefix matches `/^[a-z][a-zA-Z]*:$/` (e.g. `"booking:"`).
   - `register()` refuses an ORDERED handler with an invalid prefix (`registryError("errors.event_handler_invalid_stream", ...)`, the existing pattern). It also refuses two prefixes where one starts with the other.
   - Doc comments state: "an ORDERED handler receives every event whose `orderingKey` starts with one of its prefixes; it handles `eventType` and `alsoHandles` and steps over the rest".
2. **Fan-out** (`outbox-dispatcher.ts`): `registry.handlersFor(event.type)` becomes `registry.handlersFor({ type, orderingKey })`. It returns:
   - every handler of that type, as today
   - **plus** every ORDERED handler with a prefix that matches `orderingKey`, even when it does not handle the type
   - each handler once
   - Keyless events (`orderingKey: null`) fan out exactly as today.
3. **Step over** (`handler-runner.ts`, inside `runOrdered`, after the sequence check returns NEXT): if the handler does not handle `event.type`, advance the position and return a new result `"SKIPPED_NOT_HANDLED"`. This works the same way as the module-off path: no processed marker, no `handle()` call, and the same transaction. ALREADY_HANDLED and AHEAD behave as today. Add `"SKIPPED_NOT_HANDLED"` to `HandlerRunResult`. `event-worker.ts` acts only on `WAITING_FOR_EARLIER_EVENT`, so it needs no change.
4. **Wrong stream is loud, not silent.** Suppose an ORDERED handler receives an event of a type it handles whose `orderingKey` matches none of its prefixes, for example because a module changed its key. Then the runner throws an `AppError` (`ERROR_CODE.INTERNAL`, `errors.event_handler_stream_mismatch`, details `{ handlerKey, orderingKey }`) before calling `handle`. The kernel has no non-retryable path, and none is added: the job fails through its normal attempts, then dead-letters on the last one (the existing flow) and shows on the Failed events screen. The retries are harmless because `handle` never runs. It can be replayed after the fix.
   - A keyed event for an ORDERED handler is checked; a keyless event runs as today.
5. **Declare the streams of the three existing handlers:**
   - `accounting.postBookings` → `["booking:"]`
   - `accounting.postPayments` → `["paymentAccount:"]`
   - `accounting.postExpenses` → `["expenseAccount:"]`
   - No other code change in them. The 3.8c comment in the registry that names `bookingAccount` is out of date; fix the comment.
6. **3.11 A2:** `accounting.postCommission` declares `["commission:"]`. If A2 merges first, this card adds the line; if this card merges first, A2 must add it. The lead checks it at whichever merge is second.
7. **Records:**
   - ADR-136 ("Accepted (proposed)"), one row: the declared prefixes, fan-out to followers, step-over in the ordered transaction, loud wrong-stream failure, and why gap scanning was rejected (30-day TTL)
   - a one-line note on ADR-115 ("amended by ADR-136")
   - STATUS row 3.22, and the 3.8a and 3.8c gaps the fix closes
   - handoff `docs/handoffs/3.22-api.md`
8. **Existing data:** there is no production data. Local and CI databases that already hold a stuck position need no migration: the waiting job for the later sequence still waits, because the earlier events were never enqueued for the handler. The handoff tells the owner to recreate local test databases (`infra/docker-compose.yml` volumes) after the merge. No repair job.

## Interfaces & types
```ts
interface EventHandlerBase<Type extends EventType> {
  readonly handlerKey: string;
  readonly moduleKey: ModuleKey;
  readonly eventType: Type;
  readonly alsoHandles?: readonly EventType[];
  handle(envelope: EventEnvelope<EventPayloadMap[Type]>): Promise<void>;
}
export type EventHandler<Type extends EventType = EventType> =
  | (EventHandlerBase<Type> & { readonly ordering: "UNORDERED" })
  | (EventHandlerBase<Type> & {
      readonly ordering: "ORDERED";
      /** Every event whose orderingKey starts with one of these reaches the handler (ADR-136). */
      readonly streamPrefixes: readonly [string, ...string[]];
    });

export function handlesType(handler: EventHandler, eventType: string): boolean;
export function followsStream(handler: EventHandler, orderingKey: string | null): boolean;

class EventHandlerRegistry {
  handlersFor(event: { readonly type: string; readonly orderingKey: string | null }): readonly EventHandler[];
}

export type HandlerRunResult =
  | "HANDLED" | "ALREADY_PROCESSED" | "SKIPPED_MODULE_OFF" | "SKIPPED_NOT_HANDLED" | "WAITING_FOR_EARLIER_EVENT";
```
`handlesType` replaces the inline `eventType === … || alsoHandles.includes(…)` check, without an `as EventType` cast (compare as strings).

## Tests (must exist and pass)
- [ ] **The bug, end to end** (`ordered-event-worker.test.ts` style, real outbox, dispatcher and worker): publish `booking.booking.created`, `booking.booking.confirmed`, `booking.booking.completed` on `booking:<id>` with an ORDERED test handler that handles only `completed` and follows `booking:`. Expect: `completed` is handled once, the position ends at 3, and nothing waits.
- [ ] Out-of-order delivery: the `completed` job runs before the two earlier jobs. It waits, the others step over, then it runs. The position ends at 3.
- [ ] Step over: a NEXT event of an unhandled type advances the position, writes no processed marker and does not call `handle`. Running it again → ALREADY_PROCESSED.
- [ ] Fan-out: `handlersFor` returns a following ORDERED handler for an unhandled type on its stream; it does not return it for another stream or for a keyless event. UNORDERED handlers are unchanged. No handler appears twice.
- [ ] Registration: an ORDERED handler without prefixes fails to compile (type test with `// @ts-expect-error`); an invalid prefix (`"Booking"`, `"booking"`, `""`) and overlapping prefixes are refused at `register()`.
- [ ] Wrong stream: a handled type on a stream outside the prefixes dead-letters with `errors.event_handler_stream_mismatch`, and `handle` is not called.
- [ ] Module off still advances through both handled and unhandled types (the existing test stays green).
- [ ] **Accounting regression:** a booking created, confirmed, checked in and completed through the real use cases ends with the `booking_completed` journal posted (extend `payment-accounting-handlers.test.ts` or the accounting handler tests; drive the worker as the existing test does).

## Risks & checks
- **More jobs:** every booking event now also creates a `accounting.postBookings` job that steps over. They are cheap (one position read and one update), and stream order needs them.
- **A stuck stream after merge** means a handler forgot a prefix. Decision 4 makes that a dead letter, not a silent wait.
- Run the whole `kernel/events` suite and the accounting and payment suites locally, then `npm run card:check`.
