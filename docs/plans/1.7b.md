# Plan: card 1.7b · Organization tenant API: profile, locations, members, invitations

Tier: **T1** (member management is an access-control surface) · Planned by: Opus 5.5 · Date: 2026-10-10 · Based on commit: `main 25e31cd`

API half of roadmap card 1.7 (the screens are 1.7c). Runs in parallel with **1.6b** (scripts and generated tests). Shared files: `routes/v1.ts`, contracts/validation/i18n index files and catalogs (add-only).

## Goal
The owner and managers of a business can, through the API:
- edit the business profile
- manage locations
- see and manage staff (assignments, suspend, remove)
- invite people by phone or email

An invited person accepts with a secret link after signing in. Every route is permission-checked, entitlement-gated, tenant-isolated, audited, and emits its event. Package limits on locations and members are enforced.

## Decisions
**Common rules**
1. All tenant routes live in a new organization tenant router, mounted through `tenantRouters`. The manifest gains the route prefixes `/orgs/:organizationId/{profile,locations,members,invitations}` and `/invitations`.
   - Each write runs in `withTransaction` with its audit entry (`AuditRecorder`) and its event (`EventPublisher`).
   - Lists are paginated (limit ≤ 100) on indexes starting with `organizationId`.
   - PATCH bodies carry `version` (409 on mismatch).
2. **Limits** (`10 §9`): kernel port `LimitGuard { assertBelow(limitKey, currentCount): Promise<void> }`, implemented by entitlement from the resolved config.
   - Over the limit → `422 LIMIT_REACHED` with `details { limitKey, limit }`. `null` = unlimited.
   - `locations` counts ACTIVE locations. `members` counts ACTIVE members **plus** PENDING invitations, so invitations cannot overshoot.

**Profile**
3. `GET /profile` (any active member; no permission key, as decided in 1.4) and `PATCH /profile` (`organization.profile.update`): `name` and the `profile` object of `09 §4.2` (`legalName, legalType, phoneE164, email, address, tradeLicenseNumber`), plus `defaultLocale`.
   - `slug`, `currencyCode`, `timezone`, `countryCode` and the industry template are **not** editable here (their own use cases later).
   - `logoFileId` waits for the file module (3.2).
   - Audit `organization.organization.updated`; event `organization.organization.renamed` when the name changed.

**Locations**
4. Endpoints:
   - `GET /locations` (`organization.location.read`; `?status=`)
   - `POST /locations` (`.create`, **I**): name, `locationType`, address, phone, timezone
   - `PATCH /locations/{locationId}` (`.update`)
   - `POST /locations/{locationId}/archive` (`.archive`)

   Rules (`09 §4.3`):
   - the name is unique per org among ACTIVE locations
   - the default location cannot be archived
   - archive is refused while any ACTIVE member has an assignment to that location (`422 BUSINESS_RULE`, `LOCATION_IN_USE`) and while pending invitations name it. The stock/open-request checks of D3 are added by the inventory and sales cards.
   - `openingHours` is not in this card (booking defaults, 3.6).
   - the limit `locations` applies on create.
   - Events: `organization.location.created/updated/archived`.
5. **Location visibility:** the `Location` model stays tenancy `ORGANIZATION` (not location-scoped): every member may read the list of locations they are assigned to. A caller with a limited `allowedLocationIds` sees only those locations in `GET /locations`; ALL sees every one. Writes need the permission at ALL (a location manager cannot create or archive locations): the router checks that the narrowed set is `"ALL"`, else 403.

**Members**
6. Endpoints:
   - `GET /members` (`organization.member.read`; `?status=&q=` on `displayName`)
   - `GET /members/{memberId}`
   - `PATCH /members/{memberId}` (`.update`: `displayName`, `jobTitle`, `assignments`)
   - `POST /members/{memberId}/suspend`, `/reactivate`, `/remove` (`.remove` for remove; `.update` for suspend/reactivate)

   Custom fields and `readSensitive` arrive with custom fields (2.3).
7. **Assignment rules** (`09 §4.4`, plus anti-escalation, recorded in **ADR-092**):
   - each `locationId` is an ACTIVE location of the org or `"ALL"`; no duplicates; `"ALL"` is not combined with specific locations for the same role set (as in 1.2)
   - each `roleId` is an ACTIVE role of the org (closes the 1.4 note)
   - **the OWNER role is never assignable or removable here** (ownership transfer only)
   - a caller **cannot change their own** assignments, or suspend or remove themselves
   - **no privilege escalation:** every permission key of every role being granted must already be held by the caller (at ALL, or at that location). The check uses the iam grant map through a port.
   - the owner member cannot be suspended, removed or have assignments edited (ADR-046)
   - an ACTIVE member keeps ≥ 1 assignment
   - every change saves through `updateVersioned`, so `Member.version` moves and the permission cache key changes (ADR-088)
   - Events: `organization.member.assignmentsChanged/suspended/removed`.
8. A suspended or removed member loses access on the next request: `tenantContext` already requires `ACTIVE`. Test it end to end.

**Invitations** (`09 §4.4`)
9. Endpoints:
   - `POST /invitations` (`organization.member.invite`, **I**): `{ email? | phone?, displayName?, assignments }`
   - `GET /invitations` (`?status=`)
   - `POST /invitations/{invitationId}/revoke`

   Rules:
   - the same assignment and anti-escalation rules as decision 7
   - an identifier that already belongs to an ACTIVE or INVITED member of this org → `409 DUPLICATE`
   - the token is 32 random bytes (base64url); only its SHA-256 is stored; it expires after 7 days
   - **Delivery:** SMS and email sending do not exist yet (5.13). The create response returns `inviteUrlPath` (`/invitations/<token>`) **once**, so the inviter can share the link by hand. The event `organization.member.invited` (ids only, no token) is emitted for the future notification handler. Write this in STATUS.
   - the limit `members` applies.
10. **Accepting** (user-level routes, outside the tenant pipeline):
    - `GET /invitations/{token}` (public, rate-limited per IP) → `{ organizationName, invitedByDisplayName, identifierHint (masked), status }`. An unknown, expired or revoked token → 404.
    - `POST /invitations/{token}/accept` (authenticated, **I** not needed: the token is single-use). The signed-in user's email or phone must equal the invitation's identifier, else `403 FORBIDDEN` (`errors.invitation_identifier_mismatch`). It is the only binding until verification exists (STATUS gap, same as 1.2).
    - In one transaction, inside `runInOrganizationContext` (wired in `routes/v1.ts`): create the Member (ACTIVE, the invitation's assignments, `employeeNumber` from the MEMBER sequence) or reactivate a REMOVED one, mark the invitation ACCEPTED, audit, event `organization.member.joined`.
    - It answers `MyOrganizationSummary`.
    - A second accept → 404.
11. **Contracts, validation, messages:** request/response types and Zod schemas per `14 §2` naming, `INVITATION_STATUS`, rule keys (`LOCATION_IN_USE`, `LOCATION_IS_DEFAULT`, `OWNER_IS_PROTECTED`, `CANNOT_CHANGE_SELF`, `ROLE_NOT_GRANTABLE`), audit actions, event types and payloads, message keys in both catalogs.
12. The manifest gets menu entries for `settings › Business profile`, `Locations`, `Staff & roles` (`10 §6`), with their permission keys and `labelTermKey`s. The Locations entry carries a flag the resolver cannot evaluate yet ("hidden while 1 location"): the admin hides it from the location count (1.7c).

## Tests (must exist and pass)
For **each** endpoint group (profile, locations, members, invitations): happy path, validation error, permission denied (a STAFF member), cross-org denied (org B's ids in org A's path → 404, and B's data untouched), and a stale `version` → 409.

Specific:
- [ ] locations: default cannot be archived; archive refused while assigned; limit reached on the 3rd location of a BUNDLE trial (limit 2) → 422; a limited member lists only their locations and cannot create one
- [ ] members: cannot edit own assignments; cannot touch the owner; cannot assign OWNER; **escalation:** a MANAGER cannot grant a custom role holding a key they lack; assigning an ARCHIVED role → 422; a suspended member's next request is 404, and after reactivation it works; removal keeps the document (REMOVED)
- [ ] permission cache: after an assignment change the member's very next request reflects the new permissions
- [ ] invitations: the token is returned once and not stored in clear (grep the DB document and the logs); duplicate identifier → 409; revoke; expiry (fake clock); the member limit counts pending invitations
- [ ] accept: happy path creates an ACTIVE member with the invited assignments and shows the org in `GET /me/orgs`; identifier mismatch → 403; second accept → 404; unauthenticated → 401; the public GET masks the identifier and is rate-limited
- [ ] every write has one audit entry and its outbox event in the same transaction (one atomicity test per group with an injected failure)
- [ ] the entitlement gate owns every new route (no `route_without_module` warning in the suite) and READ_ONLY blocks the writes
- [ ] earlier suites stay green

All with `--force`: lint, format:check, typecheck, test, build; `npm run test:tools`.

## Risks & checks
- **Escalation logic** is the critical part: table-driven tests over caller grants × target role keys × location.
- **Token leakage:** the invitation token must never be logged (the access log already strips query strings; the token is in the path, so check the access log line stores the route pattern or masks the last segment. If it logs the raw path, mask `/invitations/<token>` in the access-log serializer and test it).
- **Disk and services:** system MongoDB binary, `TEST_REDIS_URL=redis://127.0.0.1:6380`, `--concurrency=2`. No downloads.
