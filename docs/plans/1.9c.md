**Platform roles (ADR-093 becomes "Accepted: decided by the lead under owner delegation, 2026-10-11")**
2. Least privilege and separation of duties:
   - `SUPER_ADMIN`: every platform permission
   - `SUPPORT`: `tenant.read`, `tenant.suspend`, `package.read`, `entitlement.read`, `subscription.read`
   - `BILLING`: `tenant.read`, `package.read`, `entitlement.read/write`, `subscription.read/write`
   - **Change from the code today:** `platform.package.write` moves from BILLING to SUPER_ADMIN only. A package definition changes every tenant on it, which is a product decision, not billing operations.
   - `platform.audit.read` stays SUPER_ADMIN only.
   - Update the mapping, its table test, the 1.8a permission tests that assumed BILLING can write packages (assertions that encoded the old mapping: list them), and ADR-093's text. The platform app needs no change: it reads permissions from `GET /platform/me`. Re-run its unit tests.

**Location-aware staff management (review M3; new ADR-095, same status wording as decision 2)**
3. **Organization-level records need the permission at ALL locations.** Use `requireAllLocations()` (1.9a) on `PATCH /profile` (`organization.profile.update`) and on `GET /audit-logs` (`audit.log.read`). Reading the profile stays open to every member.
4. **Members are visible and manageable within the caller's reach.** "Reach" for a permission key = the locations where the caller holds that key (the narrowed `allowedLocationIds` after `permission(key)`).
   - A member is **in reach** when every one of their assignments names a location inside the caller's reach. A member with any `"ALL"` assignment is in reach only for a caller whose reach is `"ALL"`.
   - `GET /members` returns only members in reach for `organization.member.read`. The filter runs in the query (index-backed on `{ organizationId, status }`, with the assignment condition), and paging stays correct.
   - `GET /members/{memberId}`, `PATCH`, `suspend`, `reactivate`, `remove`: a member out of reach → `404 NOT_FOUND` (existence is not revealed, ADR-080).
   - `PATCH` assignments: the **new** assignments must also be inside the caller's reach for `organization.member.update`. A limited manager cannot hand out `"ALL"`, or a location they do not manage. The existing ADR-092 key rule still applies on top.
5. **Invitations** already follow reach after 1.9a (M2). Verify, and align the wording and helper so members and invitations use **one** reach function (`organization/domain/reach.ts`), not two implementations.
6. The admin staff screens need no new code for correctness, because the API filters. Check the staff list and detail in the browser flow with a one-location manager: they see only their location's staff and no audit or profile-edit entry (the menu already follows `/me/config`; make sure `/me/config` reports those two permissions only when held at ALL, so the menu does not offer what the API refuses).

**Clearable fields (1.7d gap)**
7. `PATCH /profile` and `PATCH /locations/{locationId}`: for optional fields, **`null` clears the field** and an absent key leaves it unchanged. Required fields reject `null` (400).
   - Update the Zod schemas (`.nullable()` on the optional ones), the use cases (unset on null), the audit diff (`to: null`), and `14 §5.1` in one line.
   - The admin forms send `null` when a previously filled optional field is emptied.
   - Tests: API (set → clear → read back absent; null on a required field → 400; audit entry shows the clearing) and admin form unit tests.
