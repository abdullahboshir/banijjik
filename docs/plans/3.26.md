## Decisions
1. **Find the cause first, per test, and write it in the handoff** (one or two sentences each). Likely causes to check, not conclusions:
   - Test 1 uses `sleep(200)` and hopes the held request has taken the lock before the next call. Replace sleeps with an explicit signal: the probe handler resolves a promise when it starts (`mode: "hold"` already parks the request; add a "started" notifier), and the test awaits that signal.
   - Test 2 shares a module-level `MutableClock` and limiter with the test above it, and the bucket key may depend on the client address. Check whether the window can roll over between requests or whether counts leak between tests; give the middleware test its own bucket name, its own fixed clock, and a clean counter collection.
   - Test 3: find what the 30 s `waitFor` waits on (attempt back-off, worker poll interval, the skip's transaction visibility). Use the worker's own hooks or a shorter configured back-off for the test; never a longer timeout.
2. **No production change** unless the cause is a real bug. If it is, stop and tell the lead: that becomes a T1 kernel fix, not part of this card.
3. **No `retry` option, no skip, no longer timeouts.** A fix that only raises a timeout is rejected.
4. **Proof:** run each fixed file 30 times in a loop locally (`for i in $(seq 30); do npx vitest run --config src/test-support/vitest.config.ts <file> || break; done` in `apps/api`) and paste the last lines into the handoff, plus one green CI run.
5. Add a short "writing time-dependent tests" note to `docs/05-CONVENTIONS.md` testing section: inject the clock, await signals not sleeps, isolate shared counters per test.
