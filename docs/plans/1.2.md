# Plan: card 1.2 · Organization, Location, Membership

Tier: **T1** · Planned by: Opus 5.5 · Date: 2026-10-10 · Based on commit: `main 4cb5ebb`

Runs **alone**. The roadmap pairs 1.2 with 1.4, but 1.4 needs Redis for its permission cache, and Docker (Redis) is not available on the owner's machine right now. 1.4 starts after 1.2 merges, and it builds on the Role model this card adds.

## Goal
A logged-in user creates a business: `POST /me/orgs` creates, in one transaction:
- exactly **1 Organization**
- **1 default Location**
- the **6 system Roles**
- **1 owner Member** (ACTIVE, OWNER role at ALL)

`GET /me/orgs` lists every organization the user belongs to with one login (ADR-022). This is the second real module (`core/organization`), built on the pattern 1.1 set.

## Decisions
**Ownership of models**
1. **`core/organization`** owns Organization, Location and Member. **`core/iam`** owns Role (`09 §4.5`). All four are **PLATFORM** models (`09 §4`, "Platform DB entities"). Location, Member and Role carry STF with `organizationId`. The tenant plugin that enforces it is card 1.3. Until then repositories always filter by `organizationId` explicitly.
2. **Role model in this card, permissions in 1.4.** iam gets the `Role` entity/schema/repository and the use case `ProvisionSystemRolesUseCase`.
   - It creates the six system roles `OWNER, MANAGER, CASHIER, STAFF, RIDER, VIEWER` (contracts `SYSTEM_ROLE_KEY`) for an organization with `isSystem: true`, `nameKey: "role.<key lowercased>"` and `permissionKeys: []`.
   - Why empty: `09 §4.5` says system role permissions come from code templates and change with releases. 1.4 adds the templates and the resolution (OWNER = every permission), so nothing stored here has to be migrated.
   - iam's `index.ts` exports `buildProvisionSystemRolesUseCase()` and a read port `findRoleKeysByIds(organizationId, roleIds)` for `GET /me/orgs`.
3. **Cross-module call:** organization imports iam only through `modules/core/iam/index.ts` (R19). Its application layer defines a port `SystemRoleProvisioner { provision(organizationId, actorUserId): Promise<{ ownerRoleId: RoleId }> }`. Its `index.ts` (the composition root) adapts iam's use case to it. organization's domain never sees iam.

**Organization creation**
4. **Request** `OrganizationCreateRequest` (contracts + `organizationCreateRequestSchema` in validation): `{ name, slug, industryTemplateKey, district? }`.
   - `packageKey`/trial from `14 §4` is card 1.6. The schema rejects unknown keys, so 1.6 adds the field explicitly.
   - Defaults from the request context, not from the client:
     - `countryCode` `BD`
     - `currencyCode` `BDT`
     - `timezone` `Asia/Dhaka`
     - `defaultLocale` = the user's `preferredLocale`
     - `deployment` `SHARED`, `status` `ACTIVE`, `configVersion` 1
     - `ownerUserId` and `createdByUserId` = the caller
   - Contracts enums: `ORGANIZATION_STATUS`, `ORGANIZATION_DEPLOYMENT` (`SHARED | DEDICATED`; `models.ts`'s local union switches to it, closing review M11's open part), `LOCATION_TYPE`, `LOCATION_STATUS`, `MEMBER_STATUS`, `COUNTRY_CODE` (`BD`), `CURRENCY_CODE` (`BDT`), `INDUSTRY_TEMPLATE_KEY` (the 8 keys of `12`).
5. **Template key:** validated against `INDUSTRY_TEMPLATE_KEY` only.
   - Whether a template is PUBLISHED or DRAFT (ADR-075) is registry data owned by `platform/industry` (1.6). 1.6 adds that check (and the trial subscription) to this endpoint. Until then any of the 8 keys is accepted; write this in STATUS.
   - The organization module stores the key and never branches on it (ADR-033).
6. **Lint R16 adjustment** (ADR-082 note): R16 bans the identifier `industryTemplateKey` outside the reader files, but `core/organization` owns that field (`09 §4.2`) and must carry it through presentation → application → domain.
   - New config block for `**/modules/core/organization/**`: only R16's comparison/switch/includes/computed-member selectors apply there; the bare-identifier selector does not.
   - Fixtures: storing the key in `core/organization/domain` passes; comparing it there fails; the identifier in `commerce/sales` still fails.
   - Append one sentence to ADR-082's row.
7. **Slug rules** (`packages/validation/src/slug.ts`, `organizationSlugSchema`):
   - lower-case `a-z`, `0-9` and single hyphens, 3–40 chars, no leading or trailing hyphen
   - not in contracts `RESERVED_ORGANIZATION_SLUGS`: `api, admin, app, www, platform, storefront, shop, static, assets, cdn, help, support, docs, status, mail, email, login, logout, signup, register, auth, me, orgs, settings, billing, account, dashboard, new, test, demo, banijjik`
   - The input is trimmed and lower-cased before checking. A taken slug → `409 DUPLICATE` with `details.field = "slug"`.
   - Slug history and slug changes are **out of scope**: they arrive with the slug-change use case, which must also make creation check the history.
8. **Default location:** `name` = the organization name, `locationType` `STORE`, `isDefault` true, `status` `ACTIVE`, `address` = `{ district }` when given, `timezone` unset (falls back to the org).
   - Contracts type `PostalAddress { line1?, area?, thana?, district?, postalCode? }` (same field names as Contact addresses, `09 §5`).
9. **Owner member:** `status` ACTIVE, `assignments: [{ locationId: "ALL", roleId: ownerRoleId }]` (contracts constant `ALL_LOCATIONS = "ALL"`), `displayName` = the user's name, `joinedAt` = now, `employeeNumber` = `nextSequenceValue({ organizationId, sequenceKey: MEMBER })` (FAST mode, ADR-085: taken outside the transaction, a gap on abort is fine).
10. **One transaction** (`withTransaction`, PLATFORM connection): insert organization → provision roles → insert location → insert member. Any failure rolls all of it back.
    - The use case `CreateOrganizationUseCase` takes a `UnitOfWork` port (same as 1.1).
    - Retrying a request with the same slug answers `409 DUPLICATE` and never makes a second org. That is why the endpoint is safe before card 1.5 makes `Idempotency-Key` mandatory on it (`14 §4` marks it **I**; 1.5 adds the middleware).
11. **Who may create:** any authenticated user (`authenticate`, audience ADMIN). `14 §4` says "verified identifier", but verification does not exist yet (OTP was deferred by the owner in 1.1).
    - Interim guard: rate limit `ORGANIZATION_CREATE_PER_USER` = 5 per 24 h (kernel rate limiter, key = `userId`).
    - STATUS gap: "verified identifier required before public signup (6.1)".
12. **Invariants in the domain:**
    - Organization: `ownerUserId` set; name 2–80 chars after trim
    - Location: name 1–80 chars
    - Member: ACTIVE needs ≥ 1 assignment; no two assignments for the same location; `"ALL"` cannot be combined with a specific location
    - The cross-entity check (assignment locations belong to the org and are ACTIVE) happens in the use case.

**Listing**
13. `GET /me/orgs` → `MyOrganizationSummary[] { organizationId, slug, name, status, roleKeys }`, sorted by name.
    - Three queries, no N+1: members by `{ userId, status: ACTIVE }`, organizations `$in` (status ≠ CLOSED), role keys `$in` via iam's read port.
    - SUSPENDED orgs are listed with their status (card 1.8 blocks entering them).
14. **Note for 1.3** (write in the handoff and STATUS): once the tenant plugin exists, "members of this user across orgs" and "is this user a member of org X" are lookups without a tenant context. 1.3 must decide where they run with `runAsSystem(AUTH_LOOKUP)`: R26 forbids it inside `core/organization`, so a kernel-level membership lookup port is the likely shape. 1.2 does not pre-empt it.

**Indexes** (`09 §4.2–4.5`)
15. **Organization:** `{ organizationId }` unique, `{ slug }` unique, `{ ownerUserId }`, `{ status }`.
    **Location:** `{ organizationId, locationId }` unique, `{ organizationId, name }` unique, plus a partial unique `{ organizationId }` where `isDefault: true` (enforces exactly one default).
    **Member:** `{ organizationId, memberId }` unique, `{ organizationId, userId }` unique, `{ userId, status }`.
    **Role:** `{ organizationId, roleId }` unique, `{ organizationId, roleKey }` unique.

**Manifest and events**
16. `organizationManifest`: `key: "organization"`, `path: "core/organization"`, `moduleClass: "SYSTEM"`, `tenantCanDisable: false`, `dependsOn: ["iam"]`, `routes.admin: ["/me/orgs"]`, `events.emits`: `organization.organization.created`, `organization.location.created`, `organization.member.joined`.
    - Declared but **not emitted** until the event bus (1.5), same as 1.1.
17. **Message keys:** contracts `ORGANIZATION_MESSAGE_KEYS` (`validation.slug_invalid`, `validation.slug_reserved`, `validation.name_length`: only keys the code actually emits) plus the role name keys `role.owner … role.viewer`. Add them to both catalogs and to the i18n key test.

## Tests (must exist and pass)
Domain/unit (in-memory fakes):
- [ ] the entity invariants of decision 12; slug schema table (valid, too short, upper case → normalized, double hyphen, leading hyphen, reserved word, Bangla text → invalid)

API (supertest + in-memory replica set, the 1.1 harness):
- [ ] **happy path:** register → `POST /me/orgs` → `201` with `{ organizationId, slug, name, status, roleKeys: ["OWNER"] }`. In the DB: exactly 1 org, 1 location (`isDefault`), 6 roles, 1 member (ACTIVE, assignment ALL → OWNER role), member `employeeNumber` 1.
- [ ] **atomicity:** a failure injected after the member insert (a test-only failing repository wired through the module's builder) → 0 orgs, 0 locations, 0 roles, 0 members
- [ ] **validation error:** bad slug, reserved slug, unknown template key, unknown extra field → `400` with field paths
- [ ] **duplicate slug** → `409 DUPLICATE` `details.field = "slug"`; two concurrent creates with the same slug → exactly one `201`
- [ ] **unauthenticated** → `401`
- [ ] the 6th create within 24 h → `429`
- [ ] **one login, many orgs:** a user creates two orgs and is added as a member of a third created by someone else (through the use case, since invites are not in this card) → `GET /me/orgs` lists all three with the right role keys. A CLOSED org (set directly in the test DB) is not listed. A second user sees only their own orgs (**cross-user denied** stands in for cross-org here: there is no tenant route yet).
- [ ] `GET /me/orgs` runs a fixed number of queries regardless of the org count (count through a Mongoose debug hook or a repository spy)
- [ ] no org name or slug passes through any log line at a level above debug; no email or phone in logs (reuse the 1.1 log grep)

Lint:
- [ ] R16 fixtures of decision 6; all existing fixtures pass

All with `--force`: lint, format:check, typecheck, test, build; `npm run test:tools`.

## Risks & checks
- **One transaction across iam and organization models on the PLATFORM connection:** prove it with the atomicity test.
- **`isDefault` partial unique index:** confirm Mongoose creates it (`listIndexes` in a test).
- **Sequence across DBs:** `MEMBER` lives in the TENANT DB (FAST). Check the number is taken before the transaction and that a rolled-back creation leaves a gap, not a duplicate.
- **Disk:** use the installed MongoDB binary as in 1.1 (`MONGOMS_SYSTEM_BINARY`, `MONGOMS_VERSION_CHECK=false`, `--env-mode=loose`). No downloads.
