## Goal
One Contact per real party per organization (ADR-039), named by the business's terms: a gym's "মেম্বার", a coaching centre's "ছাত্র-ছাত্রী", a clinic's "রোগী". It carries:
- the API for create, read, update, archive and anonymize
- search by name, phone and custom-field values
- phone-first duplicate protection
- addresses, relations and tags
- custom fields with sensitive protection (the 2.7a pattern)
- **the contact-link field (ADR-073)**: a COACHING student's required guardian is created or linked by phone, which unblocks 2.5's last pending input

The screens are card 3.1b.

## Decisions
**Module and model**
1. **New module `commerce/contact`** (CORE; the key exists). The manifest declares:
   - `customFieldEntities: ["contact"]`
   - menu entry `contact.contacts` in group `contacts`, path `contacts`, `termKey: "contact"`, permission `contact.contact.read`
   - setting `contact.dedupeOn`: ENUM `PHONE | PHONE_OR_EMAIL`, default `PHONE`, client-visible
   - events `contact.contact.{created, updated, archived, anonymized}` (merge is a later card)

2. **`Contact`**, as in `09 §5.1`: tenant DB, tenancy `ORGANIZATION`, versioned, audit fields, soft archive (`status ACTIVE | ARCHIVED`).
   - The fields: `contactType`, `name`, `phoneE164?`, `additionalPhonesE164[]`, `email?`, `contactRoles[]` (`CONTACT_ROLE`, at least one), `addresses[]`, `relations[]`, `tagKeys[]`, `homeLocationId?`, `customFields`, `customFieldSearch`, `source`.
   - `summary` exists with zero values (projections arrive with requests); it is never written by these use cases.
   - **Indexes:**
     - `{ organizationId, contactId }` unique
     - `{ organizationId, phoneE164 }` unique partial (ACTIVE and phone present)
     - `{ organizationId, email }` partial
     - `{ organizationId, status, contactRoles, updatedAt }`
     - `{ organizationId, nameSearch }`: `nameSearch` is a lower-cased, Bangla-folded, prefix-searchable copy of the name
     - the 2.7a-style custom-field search index
   - A contact needs a `name` or a `phoneE164`.

**Duplicates (manoxen rule 11, ported)**
3. **One party, one contact.**
   - A create whose phone (or email, when `contact.dedupeOn = PHONE_OR_EMAIL`) matches an ACTIVE contact → `409 CONFLICT`, messageKey `errors.contact_duplicate`, `details.contactId` of the existing one. The screen offers "open existing".
   - An update that would collide answers the same.
   - Concurrent creates are caught by the unique partial index and mapped to the same 409.
   - Phones are E.164 through the shared phone schema.

**Contact-link field (ADR-073)**
4. When a `contact` custom field is a REFERENCE with `referenceEntity: "contact"` and a `link`, the request may send either an existing `contactId` of this organization, or `{ "create": { "name", "phone" } }`.
   - On save, in the same transaction, the server resolves or creates the linked contact by phone (dedupe rule 3; an existing ACTIVE match is linked, never duplicated).
   - It stores the `contactId` in `customFields.<key>`, and adds `relations[{ relatedContactId: <linked>, relationKey: link.relationKey }]` on the **linked** contact: the guardian is `GUARDIAN_OF` the student.
   - `link.defaultBillTo` is stored for enrollments (3.7) to read; nothing bills here.
   - A linked id from another organization, or an archived one → 400 at `customFields.<key>`.
   - Add the `{ create }` shape to 2.3's value builder as an allowed input **only for contact-link fields**. The builder still outputs a `contactId` after the use case resolves it, so other entities keep the UUID rule. Coordinate the builder change in this card.

**Endpoints** (`/api/v1/orgs/{organizationId}/contacts`, the tenant pipeline)

5. The endpoints:

   | Endpoint | Permission | Notes |
   |---|---|---|
   | `GET /contacts` | `contact.contact.read` | `?q=&role=&tag=&status=&page=&limit=`. `q` matches a name prefix, a phone (any typed form normalized; prefix on the national digits) and custom-field search entries. Lean, projected rows: `{ contactId, name, phoneE164, contactRoles, tagKeys, status, updatedAt }`, no custom fields. Paged, limit ≤ 100 |
   | `GET /contacts/{contactId}` | `contact.contact.read` | the contact with its addresses, relations (each with the related contact's name) and readable custom fields: sensitive ones only with **`contact.contact.readSensitive`** (new key, at ALL), redacted otherwise |
   | `POST /contacts` | `contact.contact.create` | `201` |
   | `PATCH /contacts/{contactId}` | `contact.contact.update` | with `version`; `customFields` merge as in 2.7a; **writing a sensitive key without `readSensitive` → 403** (the 2.7a R1-1 rule) |
   | `POST /contacts/{contactId}/archive` | `contact.contact.archive` | with `version`; an archived contact frees its phone for a new contact |
   | `POST /contacts/{contactId}/anonymize` | `contact.contact.anonymize` | with `version` and a `reason`: clears name, phones, email, addresses and every custom field; keeps the id for ledgers; irreversible; audited without the old values |

   - Every write records one audit entry, with sensitive values masked as in 2.7a, and emits its event. Writes need no `Idempotency-Key` (no money or stock), but `POST /contacts` accepts one, so a retry after a timeout does not hit the duplicate rule as an error.
   - **Locations:** contacts are organization-wide (`09`). `homeLocationId`, when given, must be a location in the caller's reach (2.4's `buildLocationLookup` pattern).

6. **Role grants** (add-only): OWNER and MANAGER ALL; CASHIER and STAFF read, create and update; VIEWER read; RIDER read. A rider sees the delivery contact; this is revisited in 5.3. `readSensitive`, `archive` and `anonymize` go to OWNER and MANAGER only.

7. **Records:**
   - ADR-110 ("Accepted (proposed)"). It records:
     - the dedupe as a 409 with the existing id
     - the contact-link input shape and transaction
     - `readSensitive` for contacts
     - `nameSearch` folding
     - anonymize semantics
   - `14` rows, `09 §5.1` field notes if any change, the module README, the 3.1a STATUS row.

## Tests (must exist and pass)
- [ ] **Happy path:** create, read, list with `q` by a name prefix (Bangla and Latin), by phone in national form `017…` and by a custom-field value; update with version; archive; anonymize. Each with one audit entry and its event.
- [ ] **Dedupe:**
  - the same phone → 409 with `details.contactId`
  - `PHONE_OR_EMAIL` catches an email
  - an archived contact's phone is reusable
  - two concurrent creates with one phone → one 201, one 409
- [ ] **Contact-link** (an organization moved onto COACHING with 2.1b's change-template, or a fixture template):
  - a student with `guardian: { create: { name, phone } }` creates the guardian and stores its id
  - the guardian gets `GUARDIAN_OF` toward the student
  - a second student with the same guardian phone links the same guardian (one guardian contact)
  - another organization's id → 400
  - all in one transaction: a failure leaves no orphan guardian (assert)
- [ ] **Validation:** no name and no phone → 400; a bad phone; an unknown role; a sensitive write without permission → 403.
- [ ] **Permission denied:** RIDER cannot create; STAFF cannot archive or anonymize.
- [ ] **Cross-org:** another organization's contact → 404 by id and absent from lists.
- [ ] **Cross-location:** a `homeLocationId` outside reach → 403.
- [ ] **Module off:** the generated module-off tests include `contact` (routes 403 `MODULE_DISABLED`, menu absent). The first real CORE module in this list closes Phase 1 review M13.
- [ ] **Performance:** the list uses the compound index (explain in a test, or document the index use); no N+1 when listing relations' names (one batched read).
- [ ] Every existing suite green; full "Done means" list.
