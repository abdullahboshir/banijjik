## Goal
One price calculator for the whole platform (`11 §3`). Sales, bookings, enrollments, POS, the storefront and the bot all ask it for a **quote** and get the same numbers:
- unit price
- gross
- discounts
- tax
- net, per line and in total

The card also adds the business's **tax classes** and **promotions as data rules**. Manual discounts above a threshold are flagged as needing a manager approval; the approval itself is card 3.4b.

## Decisions
**Module and data** (`commerce/pricing`, CORE, depends on `catalog`)

1. **TaxClass:** `taxClassId`, `taxClassKey` (kebab, unique per organization), `name`, `rateBasisPoints` (integer: 750 = 7.5%; 0 allowed), `status` (`ACTIVE | ARCHIVED`), version, audit fields.
   - Catalog stores `taxClassKey` on offerings without checking it. A quote with an unknown or archived class is `422 TAX_CLASS_UNKNOWN` naming the offering, so bad data is fixed, never priced silently.
   - `pricing.defaultTaxClassKey` (TEXT, optional) applies to offerings with no class; empty means 0%.

2. **Promotion** (rules as data): `promotionId`, `name`, `status` (`DRAFT | ACTIVE | ARCHIVED`), `priority` (integer, higher first), `startsAt?`, `endsAt?`, `locationIds` (empty = all), `target`, `benefit`, `minQuantity?` (in unit precision), `isStackable` (default false), `maxDiscountPerLine?: Money`.
   - `target`: `{ scope: ALL | KIND | CATEGORY | OFFERING | VARIANT, ids[] }`.
   - `benefit`: `{ type: PERCENT | AMOUNT_OFF | FIXED_PRICE, value }`, where PERCENT is basis points and the other two are Money per sales unit.
   - "Buy X get Y" and coupon codes are later cards; the shape leaves room (`benefit.type` is an enum).

3. **Settings** on the manifest:

   | Setting | Spec | Default |
   |---|---|---|
   | `pricing.taxInclusive` | BOOLEAN | true: prices in Bangladesh are usually shown with VAT |
   | `pricing.rounding` | ENUM `NONE \| NEAREST_1 \| NEAREST_5 \| NEAREST_10` (taka) | NONE: applies to the grand total of cash payments only, and the difference is returned as `roundingAdjustment` for the ROUNDING account (3.8c) |
   | `pricing.approval.discountPercentAbove` | INTEGER basis points | 1000 |
   | `pricing.approval.discountAmountAbove` | MONEY | none |
   | `pricing.defaultTaxClassKey` | | |

**The quote** (one implementation)

4. **`PriceQuoter.quote(input)`**, exported from `pricing/index.ts` for other modules, adapted to each module's own port in routes.
   - **Input:** `{ locationId, at: Date, lines[{ offeringId, variantId, quantity, modifierOptionIds[], manualDiscount? }], orderDiscount?, paymentIsCash? }`. A manual discount is `{ type: PERCENT | AMOUNT, value }`.
   - **Steps, exactly `11 §3`:**
     1. **Unit price:** `OfferingLocation.priceOverride ?? variant.price`, plus the modifier deltas.
     2. **Gross:** `unitPrice × quantity / 10^precision`, rounded half up to minor units. Integer and BigInt-safe math only; never floats.
     3. **Promotions:** the best ACTIVE, in-time, in-location promotion per line by largest discount, ties by priority. Stackable ones add, each capped by `maxDiscountPerLine`. The line never drops below 0, and FIXED_PRICE never raises a price.
     4. **Manual line discount**, then the **order discount**, allocated by line gross with the largest-remainder method.
     5. **Tax** per line on `gross − discount`. Inclusive prices split the tax out as `round(net × rate / (10000 + rate))`; exclusive prices add it.
     6. **Totals** and the optional cash rounding.
   - **Output:** per line `{ unitPrice, lineGross, promotionDiscount, manualDiscount, lineDiscount, lineTax, lineNetTotal, promotionIds[], taxClassKey, taxRateBasisPoints }`; totals `{ subtotal, discountTotal, taxTotal, grandTotal, roundingAdjustment }`; plus `approvalsRequired[]`, which lists a manual discount above either threshold as `{ action: "DISCOUNT", lineIndex? }`.
   - **Checks:** offering ACTIVE, variant ACTIVE, the location row not `isAvailable: false` (`422 OFFERING_NOT_AVAILABLE`), modifier options belong to the offering's groups and satisfy each group's required, min and max rules (400 at the line path), quantity follows the variant's `quantityRule`, and the currency is the organization's.
   - **Delivery charges** are not here (sales, later); the quote leaves a `deliveryCharge` input for 3.5.
5. **`POST /api/v1/orgs/{organizationId}/quotes`** (permission `catalog.offering.read`; read-only, no writes) returns the quote. Used by admin and POS previews; the storefront gets its own route later. It is rate-limited like other reads.

**Screens** (`apps/admin`)

6. Two screens:
   - **Promotions** (menu `catalog › Promotions`, `pricing.promotion.read`): list, editor (target picker for kind, category, offering or variant; benefit; dates; branches; stackable; preview against an example offering through the quote endpoint), activate, archive.
   - **Tax classes** (settings topic SALES, `pricing.taxClass.update`): list and editor.

   The catalog editor (3.2b) gets a tax class select from the list, a small change in `apps/admin/src/catalog`. Pricing settings appear automatically on the general settings page.

## Tests (must exist and pass)
- [ ] **Quote math, one test per rule:**
  - loose rice 1.25 kg at ৳80/kg → 10000 minor units
  - half-up rounding
  - branch override
  - modifier deltas
  - inclusive 7.5% split (৳107.50 → tax ৳7.50)
  - exclusive tax added
  - order discount allocation with largest remainder (three lines, uneven)
  - a line never below zero
  - FIXED_PRICE never raises
  - cash rounding to 5 taka with the adjustment
- [ ] **Promotions:** the best one wins; ties by priority; stackable ones add; caps; out of time, wrong branch or DRAFT are ignored; `minQuantity`.
- [ ] **Refusals:** an archived variant or offering; an unavailable branch (422); bad modifiers (missing required, over max, foreign option); an unknown tax class (422); a wrong currency; a quantity breaking the rule.
- [ ] **Approvals flag:** 11% manual discount with a 10% threshold → `approvalsRequired`; the amount threshold.
- [ ] **API:** quote happy path; permission denied; cross-org offering 404; promotions and tax classes CRUD with version, audit and event; module-off suite includes `pricing`.
- [ ] **Ported manoxen pricing tests** adapted (listed in the handoff).

## Out of scope

## Risks & checks
- **Integer math everywhere:** add a test that fails if a float sneaks in (for example an odd quantity and price whose float product rounds differently).
- Stop and ask if a `11 §3` step is ambiguous; do not invent a pricing rule.

## Done when

- Businesses can manage tax classes and promotions.
