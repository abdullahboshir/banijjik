# Plan: card 3.27 · Enrollment periods as payment requests

Tier: **T1** (money: what a member owes, payment-driven activation) · Planned by: Opus 5.5 (lead) · Date: 2026-10-24 · Based on commit: `main 358d703`

Reserved ADR number: **ADR-139**. Found in the 3.7 Part A handoff ("Known gaps"). Today `enrollment.requirePaymentToActivate` defaults to true, but no payment can reach an enrollment, so **no enrollment can be activated** and every unpaid ACTIVE one turns OVERDUE. This card follows the pattern of card 3.23 (orders as payment requests). Runs in parallel with 3.24 (no shared files except the add-only ones listed).

## Session parts
One part, API only. Branch `s/3.27-api-enrollment-payments`. T1 review by the lead. Screens come in 3.7 Part B, refreshed after this card.

## Goal
After this card:
- staff record a payment against an **enrollment period** (`POST /payments` with `requestType: ENROLLMENT`, `requestId: <enrollmentPeriodId>`), and refunds against it;
- each period's status (`OPEN | PARTIAL | PAID`; `WAIVED` untouched) follows its payment summary;
- a PENDING enrollment whose first period is paid becomes ACTIVE (now, or by the job on its start date); an OVERDUE enrollment whose current period is paid returns to ACTIVE;
- unpaid periods appear in dues from the moment they are created; cancelling an enrollment drops what was never paid from dues.

## Decisions
1. **The request is the period.** `requestType: ENROLLMENT`, `requestId: enrollmentPeriodId`. One payment summary per period, `total` = the period's `fee` (period 1 includes the admission fee). The allocation's separate `enrollmentPeriodId` field (doc 11 §7) is not used: payment keeps storing whatever is sent, enrollment never reads it. ADR-139 records this and `docs/11 §7` gets a note.
2. **ENROLLMENT request reader** `routes/enrollment-request-reader.ts`, registered in `buildPaymentRequestReaders()` (add one line), built from a function exported by `enrollment/index.ts` (for example `buildEnrollmentPeriodSnapshotReader()`; no Mongo class in the index). It returns `undefined` for a missing period, another organization's period, a `WAIVED` period and a period of a `CANCELLED` enrollment. Otherwise:
   - `total` = `period.fee`; `contactId` = the enrollment's `billToContactId` (the payer); `locationId` = the period's `locationId`;
   - `revenueState`: always `BEFORE_REVENUE`. No enrollment revenue is posted yet (doc 11 §10 row "enrollment period started" has no handler), so every payment is held in `CUSTOMER_ADVANCES`. Card 3.31 (period revenue posting) changes this rule and settles the held advances. Say so in ADR-139 and the README.
   - Payments for an EXPIRED or COMPLETED enrollment's unpaid period are allowed (collecting a debt).
3. **Enrollment payment port** in `enrollment/application/ports.ts`, required in `EnrollmentDependencies` (no optional dependency), adapter `routes/enrollment-payment-adapter.ts` built like `order-payment-adapter.ts` (joins the caller's session):
   ```ts
   export interface EnrollmentPaymentPort {
     /** Inside the create / renew transaction. Idempotent (payment's ensureSummary). */
     initializeSummary(input: { organizationId: string; enrollmentPeriodId: string; contactId: string; locationId: string; fee: Money; now: Date }): Promise<void>;
     /** Net paid (allocated − refunded) in minor units, read with the active session. Zero when no summary exists. */
     readNetPaid(input: { organizationId: string; enrollmentPeriodId: string }): Promise<Money>;
     /** Lowers the summary total to the net paid amount (cancel). Never raises it. */
     capTotalAtNetPaid(input: { organizationId: string; enrollmentPeriodId: string; now: Date }): Promise<void>;
     /** The ENROLLMENT period ids a payment allocates to (payment event handler). */
     listPeriodIdsOfPayment(paymentId: string): Promise<readonly string[]>;
   }
   ```
4. **Summary lifecycle:** create-enrollment calls `initializeSummary` for period 1, renewal (manual advance period and the renew job) for the new period, in their transactions. A period created before this card has no summary; payment's `applyAllocation()` creates it on the first payment with the reader's `total` (as 3.23 Amendment 1). Cancel calls `capTotalAtNetPaid` for every period of the enrollment that is not WAIVED, in the cancel transaction: unpaid amounts leave dues, paid ones stay as they are (refunds on cancel are card 3.32).
5. **Period status is derived, never counted.** One application function `syncPeriodPaymentStatus(dependencies, period)`: net paid ≥ fee → `PAID`; 0 < net paid < fee → `PARTIAL`; 0 → `OPEN`; a `WAIVED` period is never changed. It saves the period with its `version` only when the status changes. Currency of the net paid and the fee is compared; a mismatch throws (§11 item 3).
6. **Who calls it:**
   - **Payment event handler** `enrollment.syncPayments` on `payment.payment.received`, `.refunded`, `.reversed`: UNORDERED, idempotent because the status is recomputed from the summary every time. For each period id from `listPeriodIdsOfPayment`, in one transaction: sync the period, then decision 7. A 409 on the period (staff changed it) is retried by the event runner. Registered for the worker next to the enrollment jobs (`routes/enrollment-worker-jobs.ts` or a sibling, following the commission handler); the runner skips an organization whose enrollment module is off.
   - **Activate (manual) and the jobs** call `syncPeriodPaymentStatus` on the period they check, inside their transaction, before reading its status. So a staff "activate" right after a payment works even when the worker has not run yet, and `markOverdue` never marks a period that was just paid.
7. **Payment-driven transitions:**
   - PENDING, period 1 now `PAID`/`WAIVED`, `today >= startsOn` → `activate` (the existing transition, event `ENROLLMENT_ACTIVATED`, audit by the system actor).
   - PENDING with a future start: the renew/activate job activates it on `startsOn` when payment is required **and** period 1 is `PAID`/`WAIVED` (today it activates only when payment is not required).
   - OVERDUE and the **current** period now `PAID`/`WAIVED` → back to ACTIVE. `assertTransition` allows `activate` from `OVERDUE`; `activateEnrollment` from OVERDUE requires the current period `PAID`/`WAIVED` regardless of `requirePaymentToActivate` (being overdue means unpaid). Same event `ENROLLMENT_ACTIVATED`.
   - A refund never moves an enrollment back (ACTIVE stays ACTIVE); the overdue job decides later from the period status. Write this in the README.
8. **Records:** ADR-139 ("Accepted (proposed)"): period as the request, `BEFORE_REVENUE` until 3.31, derived period status, the handler plus the synchronous sync in activate and jobs, OVERDUE → ACTIVE, cancel caps unpaid summaries. `docs/11 §7` and `§8` notes. Enrollment and payment READMEs (remove the "follow-up" sentences). Handoff `docs/handoffs/3.27-api.md` with the §11 table. STATUS row 3.27.

## Tests (must exist and pass)
- [ ] **Pay a period:** create (payment required) → `POST /payments` ENROLLMENT for period 1 → after the handler runs, the period is `PAID` and the enrollment `ACTIVE` with an `ENROLLMENT_ACTIVATED` event; a partial payment leaves `PARTIAL` and PENDING.
- [ ] Manual `activate` right after a payment, before the handler ran, succeeds (synchronous sync).
- [ ] Future start: paid period 1 stays PENDING until the job runs on `startsOn` (fixed clock, 02:00 Dhaka), then ACTIVE; unpaid stays PENDING.
- [ ] **Overdue:** ACTIVE with an unpaid current period → OVERDUE by the job; paying it → ACTIVE; the overdue job does not mark a period paid moments before (sync inside the job).
- [ ] Refund of a paid period → `PARTIAL`/`OPEN`, enrollment stays ACTIVE.
- [ ] The handler run twice for the same payment changes nothing the second time.
- [ ] Payment refused for a missing period, a WAIVED period, a CANCELLED enrollment's period and another organization's period; allowed for an EXPIRED enrollment's unpaid period.
- [ ] `revenueState` of an enrollment payment is `BEFORE_REVENUE`.
- [ ] Dues: a new enrollment's period 1 and a renewed period show in dues with their fee and the bill-to contact; after cancel, an unpaid period leaves dues and a partly paid one shows nothing more due.
- [ ] A period created before this card (summary deleted in the test) is payable and gets a summary with its fee.
- [ ] Permission denied, validation error, cross-org and cross-location for the enrollment payment paths; module-off suites green (enrollment off: the handler skips).
- [ ] Existing enrollment, payment and 3.23 order-payment suites unchanged and green.
- [ ] T1 §11 items 1, 2, 3, 6, 7, 8, 10, 11, 13, 14, 17, 18, 19, 20, 21, 23, 24, each with a named test or file.

## Out of scope
- Enrollment revenue posting and advance settle (card 3.31). Refunds executed on cancel (`UNUSED_PERIODS`/`PRORATED`, card 3.32). Waiving a period. Screens (3.7 Part B). Auto-pay or reminders with a payment link.

## Risks & checks
- Activation must never run on a summary read outside the transaction that saves the enrollment.
- The handler and staff actions race on the same period: the period `version` decides; the event runner retries.
- Renewal writes a new period and its summary in one transaction; a crash between them must not leave a period without a summary that later shows wrong dues (the first payment recreates it anyway, decision 4).

## Done when
- Members can pay periods, enrollments activate and recover from OVERDUE through payment, dues are right; the Opus review passes; CI green; `npm run card:check` all PASS.
