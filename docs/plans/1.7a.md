# Plan: card 1.7a · Admin app: sign in, sign up, business list and switcher

Tier: T2 · Planned by: Opus 5.5 · Date: 2026-10-10 · Based on commit: `main fa23a98`

Roadmap card 1.7 is split, because half of it needs APIs that do not exist yet:
- **1.7a (this card):** sign up, sign in, sign out, session refresh, route protection, "your businesses" list, org switcher in the account menu. It uses only APIs that exist (`/auth/*`, `/me`, `/me/orgs`).
- **1.7b (API, after 1.6a):** organization tenant endpoints of `14 §5.1` (profile, locations, members, invitations), with package limits.
- **1.7c (after 1.6a + 1.7b):** menu from `/me/config`, package-aware home, staff and locations screens.

1.7a runs in parallel with **1.6a** (API). The only `apps/api` file this card touches is `modules/core/iam/presentation/auth-cookies.ts` (and its tests).

## Goal
A person opens the admin app, creates an account or signs in with phone or email + password, sees the businesses they belong to, and enters one. The shell (0.5b) shows the business name and an account menu with the business switcher, language and sign out.
- An expired access token is renewed silently.
- Without a session every page under `/{orgSlug}` leads to the sign-in page and back.
- Switching business is a full page load (ADR-022). Navigation inside a business never remounts the shell.

## Decisions
**Cookies and where auth is checked**
1. **The access cookie path becomes `/`** (it was `/api`). The refresh cookie stays on `/api/v1/auth`.
   - Why: the shell is server-rendered (ADR-010). Next server components can only read and forward the access cookie when the browser sends it on page requests. In production the API and the admin app share a parent domain (`COOKIE_DOMAIN`); in development both run on `localhost`, where cookies are shared across ports.
   - The cookie stays httpOnly, SameSite=Lax, and Secure in production.
   - Change `ACCESS_COOKIE_PATH` and the two cookie assertions in the iam tests that name the path. Update `apps/api/README.md` and the iam README in one line each.
2. **Server-side API calls:** `serverApiFetch` (`src/lib/api/server-api-fetch.ts`) reads the `access_token` cookie with `next/headers` and forwards it as a `Cookie` header to the API, `cache: "no-store"`. It is used only in server components and server-only modules (`import "server-only"`).
3. **Route protection** in the `[orgSlug]/(app)` layout (server):
   - No access cookie, or `/me/orgs` answers 401 → `redirect("/session?next=<current path>")`.
   - `/session` is a small **client** page. It calls `POST /auth/refresh` (the browser holds the refresh cookie for that path). On success it does `location.replace(next)`; on failure it goes to `/sign-in?next=…`.
   - `next` is validated: it must be a same-origin path starting with one `/` and not `//`, else `/`.
4. **Client-side renewal:** `apiFetch` gains one retry: on `401 UNAUTHENTICATED` it calls `POST /auth/refresh` once (a single shared in-flight promise, so parallel requests refresh once), then repeats the request. A second 401 redirects to `/sign-in?next=…`. Refresh and auth endpoints themselves are never retried.

**Pages** (all text through i18n keys; forms from the `@banijjik/ui` Form primitives; mobile-first; no new layout pattern)
5. Route group `app/(auth)/` with a minimal centered layout (brand name from env, language switch):
   - `/sign-in`: identifier (phone or email) + password. On submit, `POST /auth/login`. Errors: `errors.invalid_credentials` under the form, `429` → the rate-limit message with the wait in minutes from `Retry-After`, account locked/disabled messages. A link to `/sign-up`.
   - `/sign-up`: name, phone **or** email (one field that accepts either, like sign-in, plus the name), password. `POST /auth/register`. Field errors are mapped from `details.fields[].path` and `messageKey`; `409 DUPLICATE` is shown on the identifier field.
   - Both validate on blur and on submit with the same Zod schemas as the API (`@banijjik/validation`), then go to `next` or `/`.
   - Password field: a show/hide toggle with an accessible name, `autocomplete` values (`username`, `current-password` / `new-password`), 16 px inputs.
6. `/` (root, server): signed in → `GET /me/orgs`:
   - one business → `redirect("/{slug}")`
   - several → the list page (`DataList` cards: name, role names, a SUSPENDED badge through `StatusBadge`), each a full-page link (`<a>`, not the router link: ADR-022)
   - none → `EmptyState` with the text key `orgs.empty` and no action. **Creating a business in the UI is not in this card:** the form needs the industry template list, which is served by `platform/industry` (card 2.1) and designed in onboarding (6.1). Write this in STATUS so nobody thinks it was forgotten.
7. **Shell with real data** (`[orgSlug]/(app)/layout.tsx`, server): load `/me` and `/me/orgs` in parallel with `serverApiFetch`. Find the org by `orgSlug`; unknown → `notFound()`. Pass the business name to `TopBar`.
   - A SUSPENDED business renders a full-page `EmptyState` with `errors.org_suspended` instead of the shell content.
8. **Account menu** (new ui component `AccountMenu`, listed in `13 §9`): a button in the TopBar actions showing the user's initials. It opens the existing sheet/dialog primitive (bottom sheet on mobile) with:
   - the user's name
   - the business list (current one marked with `aria-current`; the others are plain `<a href="/{slug}">` for a full reload)
   - a language switch (বাংলা / English)
   - sign out

   Text and items come in through props (ui stays text-agnostic). It is lazy-loaded like the other sheets, so the initial JS budget holds.
9. **Language switch:** a server action sets the `locale` cookie (1 year, `SameSite=Lax`), then `PATCH /me { preferredLocale, version }` when signed in. A failed PATCH still keeps the cookie (the cookie is what the UI reads). Then `router.refresh()`.
10. **Sign out:** `POST /auth/logout`, clear the TanStack Query cache, `location.assign("/sign-in")`.
11. **API helpers** (`src/lib/api/auth-api.ts`, `me-api.ts`): typed with contracts (`LoginRequest`, `UserRegisterRequest`, `MeResponse`, `MyOrganizationSummary`). The org list on the client uses TanStack Query key `["me", "orgs"]`.
12. **Messages:** every `messageKey` the pages can show already exists in the catalogs (kernel + iam lists) except the new UI strings. Add keys under `auth.*`, `orgs.*`, `account.*`, bn + en, same key set. Unknown message keys fall back to `errors.internal`.
13. **Tests** stay vitest + jsdom for components and logic. The existing headless-Chrome `test:browser` gets one flow: with an API started by the test (the real `apps/api` against the in-memory replica set, using the test harness export) it signs up, lands on the empty list, and signs out. If starting the API from the admin test is not practical, **stop and report**; do not replace it with a mocked API silently.

## Risks & checks
- **Cookies across ports in development:** verify in the browser test that the Next server receives the access cookie on a page request after sign-in. If the browser does not send it (different host names), stop and report: do not work around it with client-only auth.
- **Open redirect:** `next` goes through `safeNextPath` in every place it is read (sign-in, sign-up, session).
- **Hydration and budgets:** forms are client components inside server pages; the account menu is lazy.
- **Disk:** very tight (E: ~3 GB). No browser or MongoDB downloads: use the installed Chrome (`CHROME_PATH`) and the system MongoDB binary (`MONGOMS_SYSTEM_BINARY`, `MONGOMS_VERSION_CHECK=false`).
