# Plan: card 2.1a · Industry templates: model, seeds, real reader, signup check

Tier: **T1** (foundation of the configuration engine) · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor · Date: 2026-10-13 · Based on commit: `main e2817c8`

Roadmap card 2.1 is split:
- **2.1a (this plan):** the model, the 8 seed templates, the real template reader behind the resolver, the PUBLISHED check at signup, and the read endpoints.
- **2.1b:** platform writes (create, edit, publish, retire, change an organization's template). Planned after 2.1a is merged.

Read `docs/ops/implement-with-cursor.md` first.

## Goal
Today every organization gets every module and every offering kind, because `InterimIndustryTemplateReader` allows everything. After this card:
- the 8 templates of `12-INDUSTRY-TEMPLATES.md` exist as data
- the resolver drops modules and kinds that an organization's template does not allow
- signup accepts only a PUBLISHED template
- a template key is data, not a code enum, so card 2.1b (and the Phase 2 goal: "a new industry from the Platform Panel alone, no deploy") can add templates without a release

## Decisions
**Template keys are data (new ADR-097)**
1. `INDUSTRY_TEMPLATE_KEY` as a closed enum contradicts ADR-034 ("an industry is template data") and the Phase 2 done-criterion. Change it:
   - **`IndustryTemplateKey` becomes a branded string type** in contracts, with a format: `^[A-Z][A-Z0-9_]{1,39}$`.
     - `packages/validation` exports `industryTemplateKeySchema`, which checks the format only.
     - Whether a key exists, and its status, is checked against the database by the use case that needs it.
   - **The eight seed keys stay in contracts** as `SEED_INDUSTRY_TEMPLATE_KEY`, used only by the seed data and by tests.
     - Rename the constant. No production code may branch on it; the existing `no-industry-branching` lint keeps that true.
     - `INDUSTRY_TEMPLATE_KEY` is removed, and every reference moves to the type or the seed constant.
   - **`organization.schema.ts`** drops the `enum` on `industryTemplateKey` and validates the same format with a `match`. Existing rows all hold seed keys, so no migration.
   - **`organizationCreateRequestSchema`** uses `industryTemplateKeySchema`.
   - **The one affected assertion:** in `organization-api.test.ts`, the 400 row "an industry template key that does not exist" (`"BAKERY"`) becomes "an industry template key in the wrong format" with `"bakery-shop"`. It is still a 400 at the same path. A well-formed unknown key is now a 422 (decision 7).
   - Write ADR-097 ("Industry template keys are data; the seed keys are only seed constants"), status "Accepted (proposed)".

**The module `platform/industry`**
2. **New module `apps/api/src/modules/platform/industry/`.** Follow the layout of `platform/package`: `domain/`, `application/{ports,use-cases}/`, `infrastructure/`, `presentation/`, `index.ts`, `module.manifest.ts` and `README.md`.
   - `industry` is already a SYSTEM module key in `MODULE_KEY`, and the lint scope `INDUSTRY_READER_FILES` already lists `modules/platform/industry/**`.
   - Register its manifest in the module registry the way `package` does.

3. **The `IndustryTemplate` aggregate stores the D4 schema** (`12 §1`), fully materialized (ADR-076):

   | Field | Notes |
   |---|---|
   | `industryTemplateId` | UUID v7 |
   | `industryTemplateKey` | unique, immutable |
   | `status` | `DRAFT \| PUBLISHED \| RETIRED`, new contracts enum `INDUSTRY_TEMPLATE_STATUS` |
   | `name`, `description` | `{ bn, en }`, each 1 to 80 / 1 to 160 characters, plain text |
   | `iconKey` | |
   | `enabledKinds` | non-empty, from `OFFERING_KIND` |
   | `allowedModuleKeys` | CORE/OPTIONAL keys from `MODULE_KEY`; SYSTEM modules are always on and are not listed |
   | `configuration` | see below |
   | `version`, audit fields | |

   `configuration` is a sub-document. It holds:
   - `contactRoleKeys`
   - `relationKeys`
   - `resourceTypes`
   - `terms`
   - `customFields`
   - `settingsDefaults`
   - `modifierGroupsSeed?`
   - `knowledgeSeed`
   - `websiteTemplateKeys`
   - `botDefaults { personaKey, handoffTopics }`

   Validate it with **`industryTemplateConfigurationSchema`** in `packages/validation`:
   - Enums where contracts own the list. Add three small enums to contracts now; they are used by these seeds and by cards 2.3 and 3.1:
     - `CONTACT_ROLE`: `CUSTOMER`, `SUPPLIER`, `LEAD`
     - `RELATION_KEY`: `GUARDIAN_OF`, `PARENT_OF`, `EMPLOYEE_OF`
     - `CUSTOM_FIELD_TYPE`: the 16 types of `01 §5`
   - Strict formats elsewhere:
     - term keys `^[a-z]+(\.[A-Z]+)?$`, for example `offering.SERVICE`
     - setting keys `^[a-z]+(\.[a-zA-Z]+)+$`
     - field keys `^[a-z][a-z0-9_]{1,39}$`
   - The setting values, and the meaning of terms and fields, are validated by the cards that own those registries:
     - 2.2 for terms in the resolver
     - 2.3 for the field engine
     - 2.4 for the settings registry
     
     Say so in the module README. Do not build those registries here.
   - **Money** in seeds is integer minor units, as `12` writes it (`7000` = ৳70).

4. **Seed data.** One JSON file per template, transcribed exactly from `12 §1.2` (the common seed), `§2` and `§3`. The common terms, knowledge starters, handoff topics and settings are merged into each file, because templates are materialized and do not inherit (ADR-076).
   - **Location:** `apps/api/src/modules/platform/industry/infrastructure/seeds/<key>.json`, not `packages/seed/…`.
   - The module owns its seed data, like `platform/package`. A new workspace package only for eight JSON files is not worth its build and config. Amend ADR-076's path in one dated line.
   - Every file must pass the domain factory and `industryTemplateConfigurationSchema`, and is checked by a test.
   - **Status:** FCOMMERCE and RETAIL are PUBLISHED; the other six are DRAFT (ADR-075).
   - **Stop and ask** if a module key, kind, role or field type written in `12` does not exist in contracts. Do not invent a key, and do not drop the row silently.

5. **Seeding is idempotent and runs at startup**, like the packages.
   - `EnsureSeedIndustryTemplatesUseCase` inserts only the templates whose key is missing. It never overwrites an existing one: after the first seed, the database is the source of truth (ADR-076), and 2.1b's edits must survive restarts.
   - `main.ts` calls it next to `seedPackages`.
   - Add `npm run seed:industry-templates -w @banijjik/api` like `seed:packages`.

**The real reader**
6. **`platform/industry` implements `IndustryTemplateReader`** (port in `platform/entitlement`). The adapter is built in `routes/v1.ts` and passed as `templates` to `buildOrgConfigService`, both there and in `routes/module-effectiveness.ts`. `InterimIndustryTemplateReader` and its file are deleted.
   - It returns `{ allowedModuleKeys, enabledKinds, templateVersion: template.version }`.
   - It answers for **any status**. An organization keeps working on a template that was later retired, and a pilot organization on a DRAFT template works (ADR-075).
   - **Hot path** (the port's comment): cache views in the kernel `InMemoryLruCache` for 30 seconds per key (named constant). 2.1b will bump `version`, and the config cache key reads `templateVersion`, so an edit reaches tenants within 30 seconds. Write that in the README.
   - **A key with no template row** (data corruption): throw `AppError` `INTERNAL` with messageKey `errors.industry_template_missing`, and log the key. Never fall back to "allow everything".

7. **Signup accepts only PUBLISHED templates.**
   - `CreateOrganizationUseCase` gets a port `IndustryTemplateAvailability { isSelectableAtSignup(templateKey): Promise<boolean> }`, adapted from `platform/industry` in `routes/v1.ts`.
   - An unknown key, a DRAFT key and a RETIRED key all answer `422 BUSINESS_RULE`, ruleKey `INDUSTRY_TEMPLATE_NOT_AVAILABLE`, messageKey `errors.industry_template_not_available`. Add the key to `ORGANIZATION_RULE_KEY` and both catalogs.
   - The check runs before the transaction, then again inside it, so a template retired at the same moment cannot slip through. Two reads are cheap.
   - The lint rule bans the identifier `industryTemplateKey` outside the reader files. `core/organization` may name it, as the key owner. In `routes/v1.ts`, pass it positionally, without the name.

**Read endpoints**
8. **For signup, `GET /api/v1/industry-templates`.**
   - Any signed-in admin-audience user. Mount it in `routes/v1.ts` with the user routes (`/me`, `/me/orgs`), not in the tenant pipeline.
   - Lists PUBLISHED templates only, ordered by key: `{ industryTemplateKey, name, description, iconKey }`, with both languages so the client picks its own.
   - Not paginated: the list is bounded by what operators publish. Add a hard cap of 100 (named constant) so it stays bounded.
   - New row in `14 §2` or `§5`, wherever `/me/orgs` lives.

9. **For the platform panel:**
   - **Endpoints:**
     - `GET /platform/industry-templates` (paged by `paginationQuerySchema`, optional `status`, ordered by key)
     - `GET /platform/industry-templates/{industryTemplateId}` (the full template including `configuration`; an unknown id answers 404)
   - **Permissions:** new keys `PLATFORM_PERMISSION_KEY.INDUSTRY_READ` (`platform.industry.read`) and `INDUSTRY_WRITE` (`platform.industry.write`; defined now, used by 2.1b).
   - **Role grants:**
     - SUPER_ADMIN: both, through ALL
     - SUPPORT: `INDUSTRY_READ`
     - BILLING: `INDUSTRY_READ`
     
     Templates are not sensitive, and support needs to see what a tenant runs on. Update ADR-093's list and the role-table test.

**Records**
10. **Docs:**
    - `09 §4.6`: the stored shape follows `12 §1`. `defaultModuleKeys` and `websiteTemplateIds` go: nothing reads them, and D4 is the approved, later source. Note it in one line.
    - `14 §7` industry rows: the reads now, the writes "card 2.1b".
    - `10` module catalogue entry of `industry` if it describes storage.
    - ADR-097 new, ADR-076 path amendment, ADR-093 permission list.
    - `STATUS.md`: the 1.6a gap "industry template reader is interim … until card 2.1" is closed.

## Interfaces & types
```ts
// contracts
export type IndustryTemplateKey = string & { readonly __brand: "IndustryTemplateKey" };
export const SEED_INDUSTRY_TEMPLATE_KEY = defineEnum(["FCOMMERCE", "RETAIL", "SALON", "CLINIC", "GYM", "COACHING", "RESTAURANT", "HOSTEL"]);
export const INDUSTRY_TEMPLATE_STATUS = defineEnum(["DRAFT", "PUBLISHED", "RETIRED"]);
export interface IndustryTemplateCard {              // GET /industry-templates
  industryTemplateKey: string; name: LocalizedText; description: LocalizedText; iconKey: string;
}
export interface PlatformIndustryTemplateSummary {   // platform list row
  industryTemplateId: string; industryTemplateKey: string; status: IndustryTemplateStatus;
  name: LocalizedText; iconKey: string; enabledKinds: OfferingKind[]; allowedModuleKeys: ModuleKey[];
  version: number; updatedAt: string;
}
export interface PlatformIndustryTemplateDetail extends PlatformIndustryTemplateSummary {
  description: LocalizedText; configuration: IndustryTemplateConfiguration; createdAt: string;
}
export interface LocalizedText { bn: string; en: string }
// IndustryTemplateConfiguration mirrors industryTemplateConfigurationSchema (z.output), exported from validation.

// core/organization/application/ports/industry-template-availability.ts
export interface IndustryTemplateAvailability {
  isSelectableAtSignup(templateKey: IndustryTemplateKey): Promise<boolean>;
}
```
If `LocalizedText` or a similar type already exists in contracts, reuse it.

## Data
- Collection `industry_templates` (platform DB, tenancy `NONE`), versioned, with audit fields.
- Indexes:
  - `{ industryTemplateId: 1 }` unique
  - `{ industryTemplateKey: 1 }` unique
  - `{ status: 1, industryTemplateKey: 1 }`, which backs both lists
- `db:sync-indexes` picks them up.
- Seeds are inserted at startup and by the seed script.

  - the common terms are present in every file
- [ ] **Seeding:**
  - a first run inserts 8
  - a second run inserts 0
  - an edited template (change a name in the DB) is not overwritten by a re-run
  - startup seeds an empty DB

## Out of scope
- Platform writes, publish/retire, changing an organization's template: card 2.1b.
- Terms, settings and fields in `resolveOrgConfig`: cards 2.2 to 2.4. The reader exposes modules, kinds and version only.
- Any admin or platform UI. Signup cards in the admin app come with onboarding (6.1); the panel builder comes with 2.6.
- A `packages/seed` workspace package.

## Risks & checks
- **Do not weaken the resolver.** The template filter is applied in the existing step of `org-config.service.ts`. A test must fail if the filter is skipped. Prove it once: remove it locally, show the failing test in the handoff, restore it.
- **No regression for existing organizations:** every existing test organization uses RETAIL. Check that its allowed modules cover what the admin browser suite uses: staff, locations, roles, invitations, settings, all SYSTEM modules.
- **Lint scope:** if a file outside `INDUSTRY_READER_FILES` must handle the key, stop and ask. Do not widen the lint scope on your own.
- **Seed transcription errors are the biggest risk.** Transcribe `12` table by table, and keep the spot-check tests.
- **Memory, disk, services:** as in the guide. No downloads.

## Done when
- The eight templates exist as data and are seeded idempotently.
- The resolver filters modules and kinds by each organization's template.
- Signup accepts only PUBLISHED templates.
- Template keys are data (ADR-097).
- The docs say what the code does.
- The Opus review passes.
