# Plan: card 3.8c · Accounting engine and expenses

Tier: **T1** (the books must balance) · Planned by: Opus 5.5 (Claude) · Implemented by: Cursor or a Claude Code session · Date: 2026-10-19 · Based on commit: `main 3c0165b`

Phase 3, wave 3. Runs beside 3.8; the two meet only through the event contract. Read `docs/plans/phase-3-lanes.md` (wave 3) and your rows in `docs/15-PORT-MAP.md` (`accounting`, `expense`). Reserved ADR number: **ADR-124**.

## Goal
Every money event becomes a balanced double-entry journal entry automatically (`11 §10`), so a business has correct books without knowing accounting. The postable events are the payments of 3.8, bookings completed (3.6) and expenses. Expenses (rent, salary, utilities) are recorded in the admin and post to their own accounts.

The engine is SYSTEM (always on, no menu). A bookkeeping UI over it is card 3.8b.

## Decisions
**Accounts** (`commerce/accounting`, SYSTEM)

1. **Account** (organization scope): `accountId`, `accountCode`, `name` (bn/en), `accountType`, `isSystem`, `status`.
   - The **system accounts** of `11 §10` are seeded per organization, with codes from contracts `SYSTEM_ACCOUNT_CODE`. Seeding happens on organization creation (a handler of `organization.organization.created`) and once for existing organizations through an idempotent job.
   - System accounts are never edited or deleted.
   - Account resolution is **by code only**.

**Journal** (append-only, number from sequence `JOURNAL`)

2. **JournalEntry:** `journalEntryId`, `entryNumber`, `businessDate`, `locationId?`, `lines[{ accountId, debit: Money, credit: Money }]` (each line one side only), `sourceType`, `sourceId`, `postingKey`, `reversesJournalEntryId?`, audit fields.
   - Σ debit = Σ credit is asserted before insert; a mismatch throws, and the event retries and then dead-letters for replay (3.8a). It never skips.
   - A unique index on `(organizationId, sourceType, sourceId, postingKey)` makes posting idempotent.
   - A correction is a mirrored reversing entry.

3. **Posting engine:** one ORDERED event handler per source module (`accounting.postPayments`, `accounting.postBookings`, `accounting.postExpenses`), reading the per-organization streams (3.8 uses `paymentAccount:<organizationId>`; bookings and expenses use their own keys). Each maps its event to a posting rule of `11 §10` and builds the lines from data it reads through the source module's index (amounts, method, allocations, deposit state).

   **Rows built in this card:**

   | Event | Lines |
   |---|---|
   | Payment IN before revenue (deposit or advance) | method account / CUSTOMER_ADVANCES |
   | Payment IN after revenue | method account / ACCOUNTS_RECEIVABLE |
   | Payment STORE_CREDIT | STORE_CREDIT_LIABILITY / AR or ADVANCES |
   | Overpayment to store credit | method account / STORE_CREDIT_LIABILITY |
   | Refund of advance | CUSTOMER_ADVANCES / method account or STORE_CREDIT_LIABILITY |
   | Refund after revenue | |
   | Reversal | mirror of the reversed entry |
   | Booking completed | AR / REVENUE_SERVICE + TAX_PAYABLE (tax from the booking's quote snapshot), plus moving held advances to settle AR |
   | Cancellation fee retained | CUSTOMER_ADVANCES / CANCELLATION_FEE_INCOME |
   | Store credit expiry | STORE_CREDIT_LIABILITY / OTHER_INCOME |
   | Expense posted and voided | category account / method account, and the reversal |
   | Rounding | ROUNDING |

   The order, stock, return, COD and inventory rows come with 3.3, 3.5 and Phase 5; their codes exist now.

4. **Read API** (`accounting.ledger.read`, OWNER and MANAGER; used by reports and 3.8b):
   - `GET /accounting/trial-balance?asOf=`: per account debits, credits and balance; totals must net to zero
   - `GET /accounting/journal?from&to&sourceType&page&limit`
   - `GET /accounting/accounts`

   There are no write endpoints; manual entries are 3.8b.

**Expenses** (`commerce/expense`, CORE, location scope)

5. **ExpenseCategory:** seeded per organization (rent, salary, utilities, delivery, marketing, other), each with its own EXPENSE account created in accounting. `expense.category.update` adds or renames; archive, never delete.

6. **Expense** (number from sequence `EXPENSE`): `expenseCategoryId`, `amount`, `paidVia` (`CASH | BKASH | NAGAD | BANK | CARD`), `businessDate`, `note?`, `attachmentFileIds[]` (purpose `ATTACHMENT`, ≤ 5), `status` (`POSTED | VOIDED`), custom fields (entity `expense`).
   - Creating posts it.
   - Void (`expense.expense.void`) needs a reason, keeps the record, and emits the event that accounting reverses.
   - An attachment is required above `expense.requireAttachmentAbove` (MONEY setting).
   - Create needs `Idempotency-Key`.

**Screens**

7. Screens:
   - **Expenses** (group `money`): list with filters (date, category, location), add sheet (amount, category, paid via, date, note, attachments through 3.0's `FileInput`), detail, void with confirm.
   - **Categories** page.
   - No accounting screens here (3.8b), except a small **Trial balance** check page under settings topic ADVANCED for owners, with a "books balance: yes or no" summary.

**Records**

8. ADR-124 ("Accepted (proposed)"):
   - accounts by code
   - seeding on creation plus the catch-up job
   - posting rules as ORDERED handlers
   - the idempotency key
   - the built rows vs later rows
   - expense posting and void

   Also `09` (Account, JournalEntry, Expense notes), `11 §10` row status, `14` rows, the module READMEs, STATUS row 3.8c.

## Tests (must exist and pass)
- [ ] **One test per built row of the matrix:** exact lines and accounts by code, debits = credits.
- [ ] **Idempotency:** the same event delivered twice → one entry; a reversal mirrors; an out-of-order delivery waits (ORDERED) and the final ledger is identical.
- [ ] **Unbalanced posting** (a forced bug in a test rule) throws, nothing is written, the event dead-letters and can be replayed after the fix.
- [ ] **Full-day scenario:** deposits, a completed booking, a refund, a reversal, store credit use and expiry, two expenses and a void. Then the trial balance nets to zero, and AR, ADVANCES and STORE_CREDIT_LIABILITY equal the payment module's projections.
- [ ] **Seeding:** a new organization gets the system accounts; the catch-up job run twice changes nothing.
- [ ] **Expenses:** create, attachment rule, void, cross-org, cross-location, permission denied; module-off suite includes `expense` (accounting is SYSTEM).
- [ ] **Ported manoxen accounting tests** adapted.
- [ ] **Admin:** unit tests for the expense sheet and the trial balance page; browser: add an expense with a photo attachment, void it, the trial balance still balances.
- [ ] Every existing suite green; full "Done means" list.

## Done when
- Every payment, completed booking and expense posts a balanced, idempotent journal entry.
- The trial balance of a full day nets to zero.
- Businesses record expenses.
- The Opus review passes.
