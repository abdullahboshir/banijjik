## Goal
When a business renames a term, the app shows the new word where that term is used. For example "শাখা" becomes "আউটলেট" in the menu and on the locations page. Phase 3 entity screens follow the same rule from their first card.

## Decisions
1. **`MenuEntry.termKey?: string`** (contracts, optional, add-only).
   - When it is set, the label is `terms[termKey][locale]`; otherwise, or when the term is missing, it falls back to the message key `labelTermKey`.
   - Keep `labelTermKey` required: it is the fallback and the label in catalogs.
   - The registry validates `termKey` against the term-key format of 2.1a (`^[a-z]+(\.[A-Z]+)?$`).
   - The admin menu (`menu-groups.ts`) applies it. The generated module-off tests stay green.

2. **`termLabel(terms, termKey, locale, fallback)`** in `@banijjik/web-client`: one helper for menus and page titles, unit-tested.

3. **Locations:**
   - the organization manifest's `organization.locations` entry gets `termKey: "location"`
   - the locations page title, empty state and "add" button read the term through `termLabel`, with their current message keys as the fallback
   - a sentence such as "Add a branch" becomes `t("locations.add", { term })`, with the term in the user's language

   Only the locations screens change in this card; other screens have no matching term today.

4. **Convention for Phase 3:** add to `05-CONVENTIONS.md`:
   > A module's menu entry and page titles for an entity name its term key (`contact`, `offering`, `order`, `booking`, `enrollment`, `resource`, `location`); labels never hard-code "Customer" or "Product".

   Add one line to ADR-104 as well.
