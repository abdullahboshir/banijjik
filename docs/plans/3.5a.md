## Goal
A shop sells products across the counter-less paths of `11 §4`:
- draft an order
- place it (number assigned, stock reserved, totals frozen)
- confirm it
- edit it while editable
- hand it over (pickup) or complete it directly (instant)
- cancel it

Every number comes from the 3.4 quoter and every stock effect from the 3.3 `StockLedger`. The order is the first real caller of both ports.

## Decisions
**Module** (`commerce/sales`, CORE; the key exists; depends on `catalog`, `contact`, `pricing`, `inventory`)

1. **Order** (location scope, versioned, audit fields) as `09 §5.5`:
   - `orderId`
   - `orderNumber` (sequence `ORDER`, assigned at PLACED, never for DRAFT)
   - `locationId`, `contactId?` (null only for an anonymous instant sale)
   - `status` (this card: `DRAFT | PLACED | CONFIRMED | PACKED | COMPLETED | CANCELLED`; the shipping states are declared in contracts and refused until Phase 5)
   - `lines[]`, `totals`, `fulfillment { method: INSTANT | PICKUP }` (COURIER and OWN_RIDER declared, refused)
   - `paymentStatus` (decision 8), `businessDate`, `source` (`ADMIN` now), `approval?`, `customFields` (entity `order`)
   - Indexes start with `organizationId`: `{ organizationId, orderId }` unique, `{ organizationId, orderNumber }` unique partial, `{ organizationId, locationId, status, createdAt }`, `{ organizationId, contactId, createdAt }`.

2. **Lines:**
   - A line is `{ orderLineId, offeringId, variantId, kind, nameSnapshot, quantity, unitPrice, lineGross, lineDiscount, lineTax, lineNetTotal, unitCostSnapshot?, modifiers?, returnedQuantity: 0, promotionIds, taxClassKey }`.
   - **Only PRODUCT-kind** offerings are accepted. A SERVICE, PLAN, RENTAL or EVENT line is `422 KIND_NEEDS_BOOKING` (`11 §5.5`: those go to bookings and enrollments). A walk-in service line comes with POS (3.9).
   - Name, prices and tax are **snapshots**: later catalog or price changes never touch an order.
   - `unitCostSnapshot` is the inventory average cost at commit (decision 5), for margin reports.

3. **Totals come only from the quoter.** The client sends `{ offeringId, variantId, quantity, modifierOptionIds, manualDiscount? }` per line and an optional order discount; the server calls `PriceQuoter.quote` and stores its result. Never trust client money.
   - A **manual discount** above the thresholds returns `approvalsRequired`; the request must then carry an approval token (action `DISCOUNT`, subject `order:<orderId>`) that the use case consumes in the same transaction, or the caller must be OWNER (setting `sales.discountOwnerWithoutApproval`, default true).
   - The delivery charge input stays 0 until fulfillment methods arrive.

4. **Draft:** `POST /orders` creates a DRAFT (no number, no stock effect). `PATCH /orders/{orderId}` (with `version`) edits a DRAFT freely and re-quotes. `DELETE /orders/{orderId}` discards a DRAFT (the only delete in the module, allowed because a draft never had a number). A job `sales.expireDrafts` (hourly, `kernel/jobs`) deletes DRAFTs older than `sales.draftExpiryHours` (default 48).

5. **Transitions** exactly `11 §4.2` for this card's states. Every transition has `version`, one audit entry and an event with `orderingKey: order:<orderId>`. Events (ids only): `sales.order.{drafted, placed, confirmed, updated, packed, completed, cancelled}`.

   | Transition | Endpoint | Rules |
   |---|---|---|
   | place | `POST /orders/{orderId}/place` | `Idempotency-Key`; ≥ 1 line; contact with a phone for PICKUP; **order limit** (decision 7); number from the sequence; **`StockLedger.reserve`** for tracked lines with `allowNegativeStock` read before the transaction; totals frozen to a fresh quote |
   | confirm | `POST …/confirm` | PLACED only; auto-confirm when `sales.autoConfirm` (default false) and the advance rule allows (`sales.advance.required` is declared; its enforcement waits for 3.8, so with any value but NONE confirm answers `422 ADVANCE_NEEDS_PAYMENTS` until 3.8 is merged) |
   | edit | `PATCH …` on PLACED or CONFIRMED | re-quote, **release and re-reserve** the difference in one transaction, `version`+1, event `updated` |
   | pack | `POST …/pack` | only when `sales.usePacking` is on |
   | complete (pickup) | `POST …/complete` | CONFIRMED or PACKED with PICKUP: **`StockLedger.commitSale`** (SALE movements, reservation consumed, `unitCostSnapshot` filled) |
   | instant | `POST /orders/instant` | `Idempotency-Key`; creates and completes in one transaction (reserve and commit together); this is the building block POS (3.9) will call |
   | cancel | `POST …/cancel` | DRAFT, PLACED, CONFIRMED, PACKED; reason; **`StockLedger.release`**; advance refund waits for 3.8 (nothing to refund before it) |

   - The reservation is keyed `(sourceType ORDER, sourceId orderId)`, so a retry never reserves twice. Every stock call runs inside the order's transaction, and `StockLedger` must not open its own.
   - A job `sales.autoCancelPlaced` (hourly) cancels PLACED orders older than `sales.placedAutoCancelHours` (default off).

6. **Invoice number:** at COMPLETED the order gets `invoiceNumber` from sequence `INVOICE` (instant and pickup sales), so receipts have a number. Printing is card 3.9.

7. **Limit:** `LIMIT_KEY.ordersPerMonth` counts PLACED and instant orders per organization per calendar month in the organization's timezone, with a counter document and a conditional `$inc` in the place transaction (the 3.2a offering-limit pattern). Over the limit is `422 LIMIT_REACHED`. Cancelling does not give the count back (it is a monthly usage count).

8. **Payment status:** declared as `UNPAID | PARTIAL | PAID | REFUNDED | PARTIALLY_REFUNDED`, computed by a pure function from `Σ allocations` (given by a `PaymentSummaryReader` port). In this card the port is satisfied by a stub reader returning zero in `routes/`, with a STATUS note; card 3.8 replaces it with the real reader (payment already plans a `PaymentSummary` projection). No payment is created here.

9. **Reads:**
   - `GET /orders?locationId&status&q&from&to&contactId&page&limit` (≤ 100, index above): lean rows `{ orderId, orderNumber, status, contactName, grandTotal, paymentStatus, createdAt }`. `q` matches an exact order number or the contact's name/phone prefix through contact's index (batched, no N+1).
   - `GET /orders/{orderId}`: the full order with line snapshots.
   - Location-scoped: only locations the caller reaches (2.4 pattern); a write needs the location in the caller's assignments.

10. **Grants** (add-only): OWNER, MANAGER all; CASHIER and STAFF read, create, update, confirm, cancel own location; VIEWER read; RIDER read (their deliveries come in Phase 5).

**Screens** (`apps/admin`, group `sales`, words from the term `order`)

    - **Order detail:** status, lines, totals, actions by status and permission, history.
    - Budget ≤ 170 KiB per route (the product picker and quote panel lazy); no sideways scroll at 375 px; numeric keypad on quantity.

12. **Records:**

    - `09 §5.5`, `11 §4` notes, `14` rows, the module README, STATUS row 3.5a

## Tests (must exist and pass)
- [ ] **Happy path:**
  - draft → place → confirm → complete with the right numbers, a stock reservation at place and a SALE movement at complete (one per component of a pack variant)
  - totals equal the quoter's output
  - the order number and invoice number come from their sequences
- [ ] **Quote integrity:** a client-sent price is ignored; a later price change does not alter the order; a promotion and tax class are reflected; an over-threshold manual discount without approval → 422 `APPROVAL_REQUIRED`, with a token → ok and the token is single-use; OWNER exempt by default.
- [ ] **Stock:**
  - place with insufficient stock → 422 with the item (and allowed with `allowNegativeStock`)
  - two parallel places for the last unit → exactly one succeeds
  - edit re-reserves the difference
  - cancel releases
  - a retried place never double-reserves
  - loose rice and a 1 kg pack drawing from one item
- [ ] **Refusals:** SERVICE or PLAN line → 422 `KIND_NEEDS_BOOKING`; COURIER fulfillment → 422; editing a COMPLETED order; confirming a DRAFT; every refused transition of the table.
- [ ] **Instant sale:** one transaction; a failure (stock) leaves no order number consumed beyond the sequence rules and no reservation.
- [ ] **Jobs** (each run twice): draft expiry deletes only old DRAFTs; auto-cancel respects its setting and releases stock.
- [ ] **Limit:** at `ordersPerMonth` → 422; two parallel places at the edge → one wins.
- [ ] **Permission denied** (VIEWER cannot create), **cross-org** 404, **cross-location** 403; module-off suite includes `sales`.
- [ ] **Events** carry the ordering key and ids only.
- [ ] **Ported manoxen sales tests** (transitions, totals recalc invariants, edit after confirm, reservation then commit) adapted and listed in the handoff.
- [ ] **Admin:** unit tests for the quote panel, line editor (loose quantity), approval dialog flow and status actions; browser: on RETAIL, receive stock (3.3), create an order with two products, place, confirm, complete, see stock reduced and the numbers right, then cancel a second order and see stock released.
- [ ] Every existing suite green; full "Done means" list.
