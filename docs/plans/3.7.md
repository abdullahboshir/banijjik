## Goal
Gyms, coaching centres and hostels sell **plans**:
- monthly membership
- a course of a fixed number of months
- a hostel bed per month

A person is **enrolled**, each billing **period** carries its fee, the enrollment **renews** automatically or expires, and members **check in**.

The enrollment module **provides the PLAN kind**, so GYM and COACHING businesses can add plans in the catalog (3.2b's gap). For coaching, the guardian (3.1c) is the default payer.

## Decisions
1. **Module `commerce/enrollment`** (CORE; manifest provides kind `PLAN`). Probe modules in test-support that squat `MODULE_KEY.ENROLLMENT` move as before.

2. **Enrollment** as `09 §5.5` (location scope, versioned, number from sequence `ENROLLMENT`).
   - `contactId` is the enrolled person.
   - `billToContactId` defaults to the contact's linked guardian when the template field has `link.defaultBillTo` (ADR-073); it can be changed.
   - `resourceIds` (a hostel bed) are capacity-checked through booking's resource port (whole periods: the bed is taken from `startsOn` while the enrollment is not terminal).
   - `securityDepositHeld` is recorded (its payment is a 3.8 allocation).
   - Custom fields (entity `enrollment`).

3. **States** exactly `11 §8.1`; each transition is audited and emits an event with `orderingKey: enrollment:<enrollmentId>`.

   | Transition | Endpoint | Rule |
   |---|---|---|
   | create | `POST /enrollments` | `Idempotency-Key`; PENDING, or ACTIVE when payment is not required to activate and the start is due |
   | activate | `…/activate` | |
   | freeze | `…/freeze` | ≤ `maxFreezeDaysPerYear`; extends the period end |
   | unfreeze | `…/unfreeze` | |
   | cancel | `…/cancel` | refund policy (decision 7) |
   | renew | `…/renew` | manual, when not auto-renewing |

   **Plan capacity** (`kindDetails.capacity`): PENDING + ACTIVE + FROZEN + OVERDUE ≤ capacity. Use a per-variant counter with a conditional increment in the create transaction (the 3.2a limit pattern); terminal states release.

4. **Periods** (`EnrollmentPeriod`, `11 §8.2`), created in order, never edited after creation except `sessionsUsed` and `status`.
   - Period 1's fee = the quote of the variant (3.4), plus the admission fee.
   - A renewal's fee = the current quote, or the locked first fee with `enrollment.lockPriceOnRenewal`.
   - Business dates are in the organization's timezone; `billingPeriod { unit, count }` arithmetic handles month ends (31 January + 1 month = 28 or 29 February; test it).
   - Fixed-term plans stop after `fixedTermPeriods` (COMPLETED).

5. **Jobs** (`kernel/jobs`, daily at the organization's local midnight, idempotent):

   | Job | Does |
   |---|---|
   | `enrollment.renew` | creates the next period for auto-renewing enrollments at `periodEndsOn` + 1; others become EXPIRED |
   | `enrollment.markOverdue` | an unpaid period past `graceDays` → OVERDUE |
   | `enrollment.remind` | emits `enrollment.renewal.due` `renewalReminderDays` before the end (SMS sending comes with the notification card) |

6. **Payment link:** if 3.8 is merged, register `ENROLLMENT` as a request type in payment's request readers. Allocations go to a period (`enrollmentPeriodId`); paid periods become PAID or PARTIAL; paying an OVERDUE enrollment's period returns it to ACTIVE; `requirePaymentToActivate` activates on the first full payment of period 1.
   - If 3.8 is not merged yet, leave this part to 3.8 and record it in STATUS.

7. **Cancellation and refunds** (`11 §8.4`): `refundPolicy` decides the refundable amount (`NONE`, `UNUSED_PERIODS`, `PRORATED` by unused days, integer math). The refund itself is a 3.8 payment REFUND with an `ENROLLMENT_REFUND` approval; this card computes and returns the amount and records the cancellation.

8. **Check-in** (`CheckIn`, append-only): `POST /check-ins { contactId, enrollmentId? }` (`enrollment.checkIn.create`).
   - It needs an ACTIVE enrollment (or a CONFIRMED booking of the same contact today).
   - It increments `sessionsUsed`. At `sessionsAllowed` it is refused unless a `SESSION_LIMIT_OVERRIDE` approval token is given. With `blockCheckInWhenOverdue` an OVERDUE enrollment is refused.
   - **Method `STAFF` now**; QR and device later.
   - A fast **check-in screen** finds the member by name or phone.

9. **Screens** (`apps/admin`, group `enrollments`, words from the terms `enrollment` and `offering.PLAN`):
   - Enrollments list (filters: status, plan, due).
   - New enrollment sheet: person (contact-link input, guardian default payer), plan and variant, start date (fixed dates when the plan says so), bed for hostels.
   - Enrollment detail: periods with fees and status, actions, history.
   - Check-in page: search, one tap, today's list.
   - **Catalog:** the GYM plan browser scenario that 3.2b deferred.

10. **Records:**
    - ADR-126 ("Accepted (proposed)"): the capacity counter, period date arithmetic, jobs, the payment link split with 3.8, refund calculation here vs payment there, check-in rules
    - `09`, `11 §8` notes, `14` rows, the module README, STATUS row 3.7

## Tests (must exist and pass)
- [ ] **Lifecycle:** create → activate → freeze (period end moves) → unfreeze → renew → cancel; every refused transition.
- [ ] **Periods:** month-end arithmetic (31 Jan, leap year); admission fee in period 1; locked price on renewal; fixed term → COMPLETED; no overlap.
- [ ] **Jobs** run twice (idempotent): renew, expire, overdue, reminder event; a failing organization does not stop others.
- [ ] **Capacity:** parallel enrollments for the last seat → one succeeds; a hostel bed cannot be taken twice for overlapping periods.
- [ ] **Check-in:** session limit (refused, then allowed with an approval token); overdue block; a booking check-in.
- [ ] **Refund amounts** per policy with integer math.
- [ ] **Payments** (if 3.8 merged): an allocation to a period, PAID and PARTIAL, overdue back to ACTIVE, activation on the first payment.
- [ ] **COACHING:** the guardian becomes the default payer.
